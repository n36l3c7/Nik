REST API

Nik can be driven without the browser. The API is the same one the web app uses, so anything the UI does — create, edit and delete incidents, add notes, upload raw artifact files (parsed server-side) — is available programmatically under /api.

Interactive documentation

Open /api/docs on a running server (for example https://localhost:8443/api/docs) for the Swagger UI. It is public to view and always in sync with the server. Click Authorize, paste an API key, and every endpoint gains a Try it out button. The OpenAPI document is at /api/openapi.json; generate a typed client from it, e.g. openapi-generator generate -i https://HOST/api/openapi.json -g python.

Authentication

Write endpoints accept either a browser session or an API key, sent in the X-API-Key header:

curl -H "X-API-Key: nik_XXXXXXXX…" https://localhost:8443/api/incidents

Keys are created and revoked in the app under Settings → API keys (admin only). The plaintext key is shown once, at creation, and carries what it may do:

  • roles — one or more of the roles below, as an account. A read-only key is a key with the role viewer.
  • expiry — optional; an expired key is rejected.

Roles and permissions

An account or a key holds one or more roles. A role is a tag that grants permissions; what a caller may do is everything its roles grant together, and a route asks for a permission, never for a role. A caller without the permission gets 403.

Role Grants
viewer read: incidents, artifacts, indicators, analyses.
analyst read, write (change, upload, analyse) and automation.run.
rules rules.manage: the YARA, capa and FLIRT rule sets.
audit audit.read: the audit log.
admin Every permission, among them admin: accounts, API keys, webhooks, storage, backup, the provider keys and the settings that decide what leaves the server.
playbooks automation.run and automation.edit: build playbooks and scripts (4.1).
connectors connectors.manage: install connectors, make connections and hold their credentials (4.2).
dashboards Accepted and stored now; what it grants (dashboards.share) is used by a later 4.x release.

GET /api/auth/me answers with roles and with permissions, the list of what they grant. A role given or taken away takes effect at the account's next request.

Removed in 6.4. Before 4.0 an account had one role (admin or analyst) and a key a role plus scopes; both were still accepted and answered next to roles until 6.4. They are gone: an answer no longer carries role or scopes, and a request that sends either (to POST /api/users, PATCH /api/users/{id} or POST /api/keys) is refused with 400 and a sentence that says to send roles. It is refused, not read without them, because a client that asks for a key with scopes: ["read"] would otherwise get a key that writes. What the old values become: role: "admin" → roles: ["admin"], role: "analyst" → ["analyst"], a key with the read scope alone → ["viewer"]. Accounts and keys that exist keep the roles they have. A backup taken before 4.0, which holds the single role, is still restored with the matching roles. The audit log is read with audit.read: an analyst who should read it holds the role audit as well.

Every change is recorded in the audit log by the server, whoever makes it: a key appears as api:<label>, a session as its username.

A browser session is opened with POST /api/auth/login ({ username, password }, at most 10 attempts a minute per address) and closed with POST /api/auth/logout; GET /api/auth/me returns the signed-in user and GET /api/auth/bootstrap says whether any account exists. After ten wrong passwords in a row an account answers 429 for five minutes; a disabled account answers 403.

Endpoints

Method & path Purpose
GET /api/incidents List incidents. Query: q (the query language: status:open severity:>=high; plain words match name, host, user and ticket), limit / offset, view=summary (light rows without the document body; each carries tags, the tags of the incident). The older host, username, status and assignee parameters still work and add to q. Total in the X-Total-Count header. With view=summary, fields=a,b (names of fields of the registry, 30 at most) adds to each row fields, the values it holds for those names: what the columns of the incident list are read from.
GET /api/incidents/{id} One incident, with an ETag: its revision, which changes at every write, whoever makes it. Send If-None-Match to get 304 while your copy is current. {id} is the incident's uuid, here and in every route; the document says it twice, as id and as uuid, and carries number, the number people call the incident by (#00042). The number is given by the server when the incident is created and is never used twice; a number sent in a document is kept as importedNumber.
GET /api/incidents/{id}/quick What the quick view of the incident list shows of an incident, without its evidence: {id, number, type, fields, createdBy, suspiciousStart, suspiciousEnd, counts, timers, last}. counts is how much evidence it holds (browserEvents, commands, endpointArtifacts, flagged, bookmarks, notes), timers its SLA timers as GET …/timers gives them, last the last three entries of its War Room, oldest first.
GET /api/incidents/by-number/{number} The incident with that number: {id, uuid, number, name}. In a query it is number:42.
POST /api/incidents Create / upsert (id generated if omitted). The response carries the ETag.
PATCH /api/incidents/{id} The document an incident is read as carries two keys that are not stored in it: type (the id of its type; unclassified when it has none) and fields (its custom fields, and how it was closed). Sent back in a POST or a PATCH, they are checked as PATCH …/fields checks them. application/json: replace the given top-level fields. application/merge-patch+json: apply an RFC 7396 merge patch (nested merge, null deletes). Honors If-Match (412 on a stale version) and answers with the new ETag.
DELETE /api/incidents/{id} Delete an incident.
GET /api/incidents/{id}/fields The fields of the incident that have a value, by the names of the registry: {fields: {name: value}, rev, type}. System fields (name, status, severity, owner, ticket…) are read from where the incident always kept them.
GET /api/incidents/{id}/war-room · GET /api/incidents/{id}/war-room/{entry} The War Room of the incident, oldest first: {entries: [{id, at, author, kind, body, runId, stepId, tags, parentId}]}. kind is note, command, result, error, approval, system… Filters: show (all, notes, commands, automation, evidence), tag, author, limit, before · one entry, with step: what the step behind it was given, gave and sent, when a playbook or a command made it.
POST /api/incidents/{id}/war-room · PUT /api/incidents/{id}/war-room/{entry}/tags Write a note: {text, tags}. It is a note of the incident like those of POST …/notes, with a line here · tag an entry: {tags}; evidence puts it among the evidence of the incident.
POST /api/incidents/{id}/war-room/command What is typed in the War Room: {line, confirm?}. Plain text and /note write a note; /assign @user changes the owner; /close answers {action: "close"}; !name arg=value … runs a command as a run of one node (needs automation.run) and answers its entry with runId: the result is the entry whose parentId is this one. 400 with what is wrong in the line; 409 with needsConfirm for a command that changes something outside, until confirm: true is sent. GET /api/automation/catalog?prefix= lists the commands with their arguments (Automation → The command line).
GET /api/script-buttons/scripts · POST /api/incidents/{id}/script-buttons/plan The scripts a button of a page can run: those with a saved version, each {name, description, version, arguments}, and sandbox (needs incidents.configure or automation.run) · what pressing a button would run, without running anything (needs automation.run, and read): {script, args: {name: template}, values?: {name: typed}}. The templates are rendered here, on the incident as it is now: they read its fields by name ({{ sender_address }}, {{ incident.host }}, incident.number, incident.user, incident.url) and its context. Answers each argument of the script with its state: filled (with value, the source field, and count when it holds several values) or ask (with problem when a template gave nothing); runs, one for each value of the argument named by each; missing, the required arguments nobody filled. 400 for a script with no saved version, and when two arguments hold several values; 404 for a script that is not there.
POST /api/incidents/{id}/script-buttons/run · POST /api/incidents/{id}/script-buttons/status Needs automation.run, and read. Press a button: {script, label, args, values, expect?, only?}. The script runs in the sandbox, once, or once for each value of the argument that holds several; only keeps the runs at those places (the failed ones, to run again). Each run is a command in the War Room of the incident (as !Script name=value, its result under it) and a line of the audit log. Answers 201 with {script, total, runs: [{index, item, runId, entryId}]}. 400 while a required argument is missing; 409 when the press would not make expect runs any more (the incident changed since it was planned), or when automation is stopped · where runs are: {runs: [ids]} answers {runs: [{runId, status, durationMs?, error?}]} with status one of running, done, failed (Guide → Script buttons).
GET /api/incidents/{id}/linked · GET /api/incidents/{id}/chart?dashboard=&widget=&field= The incidents linked to this one, ten at most: {incidents: [{id, number, name, status, severity, type, related, shared, indicators}], total}. First those its field related_incidents names (by id or by number) and those that name it, then those that hold the most indicators it holds too (shared, with the first three); values on the allowlist link nothing · a widget of a dashboard with its query narrowed to what this incident holds for field, a field of the query language for what the widget counts (for incidents, any field of the registry, custom ones included): {widget, board, field, value, empty}, the widget to be asked of POST /api/query/aggregate like any other. empty is true, with no widget, when the incident holds nothing for the field. 404 for a dashboard the caller does not see or a widget that is gone; 400 for a widget that asks no query, or a field it does not have.
GET · DELETE /api/playground Needs automation.run. The caller's own Playground, oldest first: {entries: [{id, at, author, kind, body, runId, stepId, parentId, tags}]}, the shape of an entry of the War Room, with kind one of command, result, error, note. ?show= keeps the notes or the commands; ?limit= up to 500 · forget it (the runs stay).
POST /api/playground/command · GET /api/playground/{id} {line, confirm?}: !name arg=value … runs a command with no incident, as a run of one node, and answers its entry with runId; plain text and /note write a note. 400 with what is wrong in the line, and for /assign and /close; 409 with needsConfirm for a command that changes something outside · one entry with its step (what it got, gave and sent). 404 for an entry of somebody else (Automation → The Playground).
GET /api/incidents/{id}/context Needs automation.run. What a playbook reads of the incident: incident (its fields by the names of the registry), context (the entities of the common schema and ext), provenance (for each item, {source, at}: who set it last), schema (each entity's keys and the keys an item is told apart by) and version. Read only: the context is written by Nik's analysis and by what commands and scripts declare (Automation → The incident and its context).
PATCH /api/incidents/{id}/fields {changes: {name: value}, ifRev?}; null clears a field. Every value is checked against the registry and the incident's type, and stored as the field's type says (a date as UTC, a number as a number, a user as the account is written). One wrong value refuses the whole change: 400 with which and why; a name the registry does not know is refused the same way. 409 when ifRev is not the current rev. Answers the fields as they are now, with changed. Setting status to closed is refused while a field the incident's type wants filled before closing is empty, or when close_reason is not one of the type's. The tags of an incident are its field labels (a list): what is added is kept lower case and held to the rules of a tag (a letter or a digit, then letters, digits and . _ : -, 40 characters; 12 tags at most), what the incident already held is kept as it is.
GET /api/incident-types · GET /api/incident-types/{id} The types of incident: id, name, colour, fields (its own, each {name, required, requiredOnClose}), layout (the saved one, or one generated from its fields; customLayout says which), closeReasons, incidents (how many are of it). A type limited to some roles is listed only to accounts that hold one of them.
POST /api/incident-types · PUT /api/incident-types/{id} · DELETE /api/incident-types/{id}?moveTo= Needs incidents.configure. {name, description, colour, fields, layout, closeReasons, visibleToRoles}; on PUT a key left out keeps what the type has, and layout: null goes back to the generated one. A layout is {sections: [{id, title, key, columns, fields: [names]}], tabs: [ids], hidden: [ids], grid}: a section names fields the type has, a field is in one section, one section at most is the side panel (key). tabs and hidden name the tabs (summary, war_room, work_plan, context, iocs, timeline, evidence) and the kinds of evidence (mail, malware, network, urls, endpoint, eventlogs, browser, commands), which they order and hide inside the Evidence tab. grid, when there is one, is the Summary: [{id, kind, x, y, w, h, title?, section?, text?, buttons?, dashboard?, widget?, field?}] on twelve columns, thirty widgets at most, kind one of facts, section (with the id of a section that is not the side panel), stats, timeline, timers, evidence, war_room, work_plan, indicators, linked, buttons, chart and note (with its text); all but section, buttons, chart and note are on a page once. A widget of buttons holds up to eight {label, background, color, script, args: {name: template}}: the colours as #rrggbb, the name of a script, and for an argument a template in the {{ }} language (one left out is asked when the button is pressed). A chart names a dashboard, one of its widgets (widget) and the field it is narrowed by. A widget of the kind playbooks, which 5.3 had, is left out when a layout is read and when one is saved. A layout without a grid is drawn with one made from its sections. Since 6.2 a layout also keeps pages, the pages the type adds: [{id, name, grid}], ten at most, each grid like the Summary's; a page is the tab page:<id> in tabs and hidden. close is {sections: [ids]}, the sections the form of closing shows, in order. quick is the quick view of the incident list: [{kind, section?, text?}], twelve blocks at most, kind one of facts, section (a section that is not the side panel, once each), stats, timers, last, linked (each once) and note (with its text). 400 says what is wrong. Deleting a type moves its incidents to moveTo (unclassified when not said) with every value they hold; unclassified itself cannot be deleted.
GET /api/fields · GET /api/fields/{name} The registry: every field with name, label, type, options, system, writable, allTypes · one field, with usedBy (the types that list it, how many incidents hold a value).
POST /api/fields · PATCH /api/fields/{name} · DELETE /api/fields/{name} Needs incidents.configure. Make a custom field: {name, label, description, type, options, allTypes}. The name (a lower-case letter, then lower-case letters, digits or _) and the type are for ever. Types: text, long_text, number, bool, date, choice and multi_choice (options.choices), user, role, url, tags, indicator, list (options.columns), timer, json · change its label, description, choices or allTypes · delete one no type lists and no incident holds (409 otherwise, and for a system field).
POST /api/incidents/{id}/notes · PATCH / DELETE …/{noteId} Add / edit / remove notes.
POST /api/incidents/{id}/upload Upload a raw artifact file (multipart). ?async=true → 202 { jobId }.
GET /api/jobs/{id} Poll an async upload job.
GET /api/incidents/{id}/iocs The incident's indicators of compromise (type, value, sources, count, first/last seen, number of other incidents, allowlisted), indexed from every tab each time its data is saved.
GET /api/iocs/lookup?type=&value= Every incident an indicator appears in ("where seen"); per incident, sourceArtifacts maps a source to the artifact it comes from. artifacts lists the artifacts analysed on their own that hold the value.
GET /api/iocs/shared Indicators seen in two or more incidents, most widespread first.
GET /api/iocs The Indicators page: every indicator an incident holds, an analyst added or a list keeps, with its reputation, lists, tags, TLP and expiry. Query: q (the query language: verdict:>=suspicious -tag:test), and the older type, verdict (malicious, suspicious, harmless, flagged, none), origin, list, expired, sort, dir, offset, limit. Returns iocs, total, counts and the number of unseen alerts.
POST /api/iocs/parse · POST /api/iocs Read text without saving ({ text }: free text, CSV, STIX 2.1, MISP or Nik's JSON; returns the items and a summary), then add: { items | text, tags, note, tlp, expires, list: { id | name, watch }, check, origin }. Each indicator is saved on its own; list also groups them; check starts a bulk check. PATCH /api/iocs/item edits tags, note, TLP and expiry; POST /api/iocs/remove takes a scope out of the library. POST /api/iocs/tags takes a scope with add and remove (lists of tags) and changes the tags of every indicator in it, 5 000 at most: {changed, unchanged}, one line of the audit log.
GET/POST /api/iocs/lists · GET/PATCH/DELETE …/{id} Lists of indicators (name, description, tlp, watch; scope to fill a new one). POST …/{id}/items and POST …/{id}/items/remove add and take out. Removing a list takes its author or an admin.
GET /api/iocs/lists/{id}/history What the checks of the whole list found: {last: {checkedAt, total, changed, becameMalicious, becameSuspicious, cleared, text} | null, history: [{checkId, checkedAt, total, changed, byVerdict}], changes: [{type, value, old, new, at}]}. changes are those of the last check; a list keeps its last 200 checks. A line is written when a check started with scope: {list} (or by the action nik.recheck-list) ends.
GET /api/iocs/lists/{id}/feed The list as it is now, for machines: format (txt by default, csv, json, stix, misp), types, flagged. Signed with X-API-Key or HTTP Basic with the key as the password. Allowlisted and expired indicators are left out; a TLP:RED list answers 403.
POST /api/iocs/export Download a scope: { scope, format, fields, defang, flaggedOnly, allowlisted, expired }. Fields: type, value, verdict, score, tags, first_seen (the default), last_checked, sources_flagging, per_source, incidents, lists, note, tlp, origin, added_by, expires.
POST /api/iocs/check · GET /api/iocs/checks[/{id}] Bulk reputation check of a scope. dryRun returns the plan only (indicators to ask, answers reused, never sent, and per source the requests against today's quota); otherwise the check is queued and worked through in the background: poll its status (running, waiting for a quota, done, stopped), done and total. POST …/checks/{id}/stop ends it.
POST /api/iocs/analyse Have the isolated browser visit the URLs and domains of a scope that Nik has not analysed yet (the first 20, a domain as https://<domain>/). dryRun returns visit and skipped (with the reason) and visits nothing; otherwise started lists the new artifacts. Audited.
GET /api/iocs/alerts · POST /api/iocs/alerts/seen Incidents that came to hold an indicator of a watched list, newest first; mark them seen.
POST /api/incidents/{id}/report The incident report as a PDF (default) or HTML. Body, all optional: format, lang (en/it), tlp, sections, executiveSummary, detections (SOC rule hits with ATT&CK ids). Missing options come from the incident's saved report settings. scope: flagged (the default: only what the analysts flagged) or all (everything in the incident).
GET /api/query/schema · POST /api/query · POST /api/query/check · POST /api/query/aggregate The query language. schema (?entity= for one) lists the entities the caller may query and their fields. POST /api/query takes { entity, query, limit, offset } (incidents, artifacts, indicators, audit, runs, approvals, tasks) and returns { entity, total, items }; an incident carries under fields what it holds for the fields of the registry that are not in the row itself. check reads { entity, query } without running it and returns its tree. aggregate counts or measures what a query finds. Any signed-in caller; the permission of the entity is checked.
GET /api/search?q= Global search (2+ characters): incidents by name, host or user; indicators from every incident (3+ characters); samples by hash prefix (6+ hex characters) or file type.
GET /api/incidents/{id}/iocs/export ?format=csv|stix|misp: CSV, a STIX 2.1 bundle or a MISP event; types= narrows the types, allowlisted values are left out unless allowlisted=true.
POST /api/incidents/{id}/samples Upload a malware sample (multipart file): stored by SHA-256, analysed statically, attached to the incident. Re-uploading a known file reuses its analysis.
GET /api/samples/{sha256} · …/strings Metadata and full analysis (hashes, type, entropy blocks, indicators, first 5,000 strings); /strings?q=&minLength=&encoding= scans the stored file on demand.
GET /api/samples/{sha256}/download The sample inside an AES-256 zip. ?password= (default infected), ?name= for the file name inside the archive. Recorded in the audit log.
DELETE /api/incidents/{id}/samples/{sha256} Detach the sample from the incident; it stays as an artifact until the artifact is deleted.
POST /api/samples/{sha256}/reanalyse Run the current analysis engine and YARA rules again on the stored file.
POST /api/incidents/{id}/mails Analyse an e-mail (multipart file, .eml or Outlook .msg) and attach it to the incident: route, SPF/DKIM/DMARC through DNS and as reported by your servers, sender, links, body, attachments, score and verdict (phishing ≥ 70, suspicious 40–69, clean). 422 for a file that is not an e-mail.
GET /api/mails/{sha256} · POST …/reanalyse · GET …/source The full analysis and the incidents holding the message; analyse it again; the .eml as text.
GET /api/mails/{sha256}/attachments/{path}/bytes · …/download A slice of an attachment (≤ 64 KiB, base64; offset, length) for the hex view; the attachment in an AES-256 zip (password, default infected, audited). path is the index, 2.0 inside the attached message at index 2.
POST /api/incidents/{id}/mails/{sha256}/attachments/{path}/sample Send an attachment to Malware Analysis as a sample of the incident.
POST /api/mails/{sha256}/attachments/{path}/preview The attachment's first pages as PNG, rendered by the document viewer worker (LibreOffice with macros disabled, pdfium). GET /api/previews/status says which preview workers are configured.
POST /api/browser/sessions · …/{id}/action · DELETE …/{id} The isolated browser: open an HTML attachment or a link (network true or false, incident to keep the network log, width and height of the page, audited), replay clicks, typing, keys, scrolling and navigation, send or hold submissions (policy, audited), get a screenshot back; close the session. The answer lists the session's tabs ({ id, title, url, active }): the windows the page opened. The actions tab and closeTab (with the tab's id) show or close one, and resize (width, height, kept between 640×400 and 2560×1600) draws the pages at another size. GET …/{id}/network lists the session's requests.
POST/GET /api/incidents/{id}/captures · GET /api/captures/{id} Upload a pcap or pcapng (up to PCAP_MAX_MB, optional TLS key log), analysed in the background; list the incident's captures; the capture's state and summary (hosts, DNS, HTTP, TLS server names, submissions, beacons, objects, Expert Info).
POST /api/captures/{id}/rpc Read-only calls to Wireshark's engine: frames (display filter, paging, time format), frame (protocol tree and bytes), follow, tap (Export Objects, Expert Info), check, complete, status.
GET /api/captures/{id}/objects/download · …/file · …/har · …/requests An exported object in a protected zip, the capture file, an isolated browser session as HAR 1.2, its requests (one in full with …/requests/{entryId}). Downloads are audited.
PUT/DELETE /api/captures/{id}/keylog · POST …/reanalyse · DELETE /api/incidents/{id}/captures/{captureId} Add or remove a TLS key log (stored encrypted), analyse again, take the capture out of the incident (it stays as an artifact).
DELETE /api/incidents/{id}/mails/{sha256} Detach the message from the incident; it stays as an artifact until the artifact is deleted.
GET /api/artifacts · GET /api/artifacts/{id} The files, e-mails and captures analysed on their own or in incidents, newest first, each with the incidents that reference it. Query: kind (file, mail, pcap, url), q (the query language: verdict:phishing created:>=now-7d), tag, mine, linked, limit / offset. One artifact also lists its parents and children (the e-mail an attachment came from, the objects taken out of a capture). Ids are file-<sha256>, mail-<sha256>, pcap-<capture id>.
GET /api/artifacts/lookup?sha256= Is this file already known? The artifacts with that digest, to check before an upload.
POST /api/artifacts/files · …/mails · …/captures Analyse a file, an e-mail or a capture without an incident (multipart file; optional form field incident to link it at once; keylog for a capture). The analysis is then read from the samples, mails and captures endpoints.
POST /api/artifacts/urls Scan an address with the isolated browser ({"url", "incident"?}; defanged text accepted, private and internal hosts refused). Returns the scan and its artifactId (url-<id>); an address already scanned is returned as it is (known).
GET /api/urls/{id} · POST …/rescan · GET …/screenshot The scan's state (queued, running, done, error), verdict, score and result: final address, navigation chain, forms, findings with points, the capture of the visit, and scripts: per script its kind (external or inline), address, size, SHA-256, entropy, share of obfuscated text, recognised library, findings (id, severity, points, title, line, start, end, excerpt) and iocs. Visit it again; the screenshot as JPEG. GET …/scripts/{n} adds the script's code (text, never run); …/scripts/{n}/download is the script in a zip, password infected.
POST /api/artifacts/{id}/links · DELETE …/links/{incidentId} Link the artifact to an incident ({"incidentId"}) or take it out. A file or an e-mail can be in several incidents, a capture in one. Unlinking never deletes the artifact.
POST /api/artifacts/{id}/attachments/{path}/sample · POST /api/artifacts/{id}/objects/sample Analyse an e-mail's attachment, or an object exported from a capture, as a file artifact related to its source (optional ?incident=).
PUT /api/artifacts/{id}/tags · DELETE /api/artifacts/{id} Replace the tags ({"tags": []}, 12 at most). Delete the artifact: its file, its analyses and its reference in every incident.
PUT /api/artifacts/{id}/expiry (write) Give an artifact a day to be deleted on, {"expiresAt": "2027-01-31"}, or take it away (null). The day must be to come (400 otherwise). An artifact says expiresAt, expiresInDays and expiryNote. Nothing has a date unless it is set here. The worker deletes the artifact once the day has come, unless an incident that is not closed references it: then the date is put off by seven days and expiryNote says why. GET /api/storage lists the artifacts with a date in dated and counts the others in undated.
POST /api/artifacts/mailboxes · GET /api/mailboxes/{id} Upload a mailbox (multipart file: an mbox, a zip or tar archive of a Maildir, up to MAILBOX_MAX_MB; an Outlook PST up to PST_MAX_MB). It is indexed in the background: status is indexing, then ready or error; importing while messages are being imported, with progress. The detail has total, threads, from / to, attachments, topSenders, imported and verdicts. The artifact is mailbox-<id>.
GET /api/mailboxes/{id}/messages The messages, newest first, each with seq, the message it answers (parent), its conversation (thread), subject, sender, recipients, date, and when imported its artifactId, verdict and score. scope=imported (default) keeps the conversations with an imported message, whole; scope=all the whole file. Also q, flagged, thread, offset, limit.
POST /api/mailboxes/{id}/import · POST …/link Import messages by seqs or by a filter (dateFrom, dateTo in Unix milliseconds, sender, subject, attachments), with the rest of their conversations when threads is true: 500 at most, the others are counted in waiting, and { "next": true } goes on with them (the detail has them in pending). dryRun only counts. link puts imported messages in an incident: { incidentId, seqs }, all of them when seqs is omitted.
GET /api/workers Admins. The automation worker and the analysis workers, as the server last found them: workers, each with id, label, configured, state (up, failing from its first check without an answer, down once that lasted downAfterSeconds and the administrators were told; empty before its first check and when it is not configured), since and checkedAt.
GET /api/storage Admins. The disk of the file store: disk (total, used, free, in bytes), what Nik keeps on it by kind in groups (bytes, files), the rest of the used part in elsewhere, and the ten largest objects with their artifactId.

Automation: playbooks, runs, approvals, scripts

Everything the Automations area does is under /api/automation. Automation explains the playbook format, the nodes and the expressions. automation.run (analysts) reads, runs, stops and answers; automation.edit (the role playbooks) builds; the rows marked admin decide what leaves the server.

The query language

One language asks incidents, artifacts, indicators, the audit log, the runs of playbooks, their approvals and the tasks. It is what the q parameter of the list endpoints of the first four takes, and what POST /api/query runs on any of them: 

status:open severity:>=high owner:"" -host:srv-*
kind:mail verdict:phishing created:>=now-7d
verdict:>=suspicious (type:ip or type:domain) -tag:test
action:user.* at:[2026-11-01 TO today]
Write To ask for
word · "two words" The text, in any of the entity's text fields (incidents: name, host, user, ticket). An address or a path with a colon in it (http://…, C:\…, an IPv6 address) is text too.
field:value A text field contains the value; a keyword field (a status, a kind, a verdict) is the value. Neither minds upper and lower case. Quote a value with spaces: name:"lateral movement".
!field:value Not that value (a field that is empty counts). Until 5.0 this was written field:!value, which is read through 5.x and goes in 6.0.
field IN (a, b) · field NOT IN (a, b) One of the values, none of them: the same as field:a or field:b and !field:a !field:b. Values are separated by commas or spaces and quoted when they hold either.
:> :>= :< :<= Comparisons, for numbers, dates and ordered fields: score:>=70, severity:>=high (low < medium < high < critical), verdict:>=suspicious.
field:[a TO b] A range, both ends included; * leaves an end open: score:[40 TO *].
* · ? Wildcards in an unquoted value: any run of characters, one character. With a wildcard the value is matched whole: name:wks-*, action:incident.*. A backslash takes one literally (\*).
field:"" · field:* The field is empty · the field holds something. owner:"" is an unassigned incident.
and · or · not · - · ( ) Conditions side by side must all hold (and may be written); or binds less tightly; not or a leading - negates; parentheses group.
Dates 2026-11-10 (that day), 2026-11 (that month), 2026-11-10T14:30, today, yesterday, now, now-7d (m, h, d, w), "7 days ago". Times are UTC. created:2026-11-10 is the whole day, created:>2026-11-10 after it.

The fields of the registry

Every field of the registry that an incident can hold is a field of the language, under its name (GET /api/fields), the custom ones included. What a condition means follows the type of the field:

Type of the field In a query
text, long_text, url Text: contains the value, wildcards match it whole.
user, role, choice Keyword: is the value, as owner and status are. A choice takes its choices only; another value is refused with the list of them.
number, timer Number, with comparisons and ranges. A timer is the seconds it counted.
date Date, as created is: a day, a month, a relative date, comparisons and ranges.
bool true or false; a field that was never set is not true.
tags, multi_choice Holds the value, matched whole; grouped by, a row counts under each value it holds.
indicator Text: the value of the indicator.
list, json Searched as the text it is kept as: the value is found anywhere in it or not, empty or filled. It takes no comparison and cannot be grouped by. 
customer:acme !region:"North America" amount:[1000 TO *]
labels:vip due:<today sender_domain:""
  • Names. A name the language already uses wins: the fields above keep their names and their other names (number, user, source, updated…). A custom field is also written field.<name>, always, and that is how one whose name was taken is asked; the schema lists it under that name. System fields answer to the name the registry gives them as well (close_reason is closeReason, sla_breached is slaBreached, time_to_close is timeToClose). The tags of an incident, the field labels, are asked as tag: and tags: too, like the tags of an artifact or of an indicator; a custom field that was called tag or tags before 6.4 keeps that name, and the schema says which names labels answers to.
  • Counting. groupBy and measure of aggregate take them like any other field: "groupBy": ["region"], "measure": "sum:amount", due@week.
  • A field that is gone. The registry is read when a query is compiled. A query, a saved filter or a widget that names a field deleted since is answered 422 and the name of the field, like a misspelt one (unknown_field for a condition).
  • What it costs. The custom fields are kept in one JSON column of the incident, and a condition on one reads that column for every incident the other conditions leave: no index serves it. Put a condition on a column beside it (status, created) when the table is large. A value that is not of the type of its field, left by an older release, counts as no value.

GET /api/query/schema lists, for each entity the caller may query, its fields with their kind, the other names they answer to (owner / assignee) and the values a keyword can take; a field of the registry carries its label, and custom: true when it was made in Settings. A query that cannot be read is answered 422 with a fixed sentence in detail and, in query, the position of what is wrong, a code and, for a misspelt field or value, a suggestion: 

{ "detail": "\"stauts\" is not a field of incidents: did you mean \"status\"?",
  "query": { "code": "unknown_field", "position": 16, "suggestion": "status", "message": "…" } }

Limits: 2 000 characters, 20 levels of parentheses, 200 conditions, 8 wildcards in a value, pages of at most 500 from POST /api/query, and ten seconds for the database to answer. A query is compiled to bound parameters, never to SQL text; who may query an entity is checked when it is compiled (audit needs audit.read, runs and approvals need automation.run, the others read).

Counting and measuring

POST /api/query/aggregate answers with numbers instead of rows: it is what a widget of a dashboard asks. The query is compiled as above, so the answer never counts what the caller may not read. 

{ "entity": "incidents", "query": "status:open",
  "groupBy": ["created@day", "severity"], "measure": "count",
  "timeField": "created", "timeRange": "30d", "compare": "previous", "limit": 50 }

{ "entity": "incidents", "columns": [{ "name": "created", "kind": "date", "bucket": "day" }, …],
  "rows": [["2026-11-17", "high", 2], …], "total": 14, "previous": { "total": 9, "range": {…} },
  "more": 0, "truncated": false, "range": { "from": "…", "to": "…" } }
  • groupBy: two fields at most. A date is grouped by a stretch of time, field@hour|day|week|month|year (a week is named by its Monday, times are UTC); a field of tags counts a row under each of its tags. With no group the answer is its total alone.
  • measure: count (the default), or sum, avg, min, max, median, p90 of a number field (avg:score) or of the seconds between two dates, median:duration(created,closed); duration(asked,now) is an age. A row that lacks the number or one of the dates is not measured.
  • timeRange on timeField: a length of time back from now (24h, 7d, 12w, 6m, 1y) or {from, to}. compare: "previous" adds the total of the period of the same length before it. When the one group is the time field itself, the stretches with nothing in them are given as zeros.
  • Rows come by time when the first group is a date, in the order of the field when it has one (severity, the worst first), otherwise the largest first; limit (50, at most 500) keeps the first and more says how many groups were left out.
  • A plain count is grouped by the database. Anything else is worked out from the rows that match, 100 000 at most: past that, truncated is true.

For incidents the fields type, closed, closeReason, occurred, source, slaBreached and the seconds the SLA timers counted (timeToAssign, timeToContain, timeToClose) can be asked and measured too.

Uploading files

POST /api/incidents/{id}/upload takes a multipart file plus query parameters that route it to the right parser, mirroring the app's tabs. The server parses the raw file and merges the normalized result into the incident.

Evidence comes from hosts that may be compromised, so parsing is bounded: a file larger than ARTIFACT_MAX_MB (500 MB) is refused with 413; a browser database is opened read-only with its schema untrusted and a time budget, and one that exceeds it is refused with 400 and the reason. Downloads carry the file's own name in any script (filename*, RFC 5987), with path separators, control characters and text-direction marks replaced. 

# Browser history (Chromium History SQLite → data.browser.browsers.chrome)
curl -H "X-API-Key: $KEY" -F file=@History \
  "https://localhost:8443/api/incidents/$ID/upload?tab=browser&browser=chrome&source=history"

# Shell history (.bash_history → data.commands.shells.bash)
curl -H "X-API-Key: $KEY" -F file=@.bash_history \
  "https://localhost:8443/api/incidents/$ID/upload?tab=commands&shell=bash"

# Endpoint artifact (cron file or tool CSV → data.endpoint.categories.persistence)
curl -H "X-API-Key: $KEY" -F file=@crontab \
  "https://localhost:8443/api/incidents/$ID/upload?tab=endpoint&category=persistence&source=cron"

# Windows event log (.evtx → data.eventlogs.channels.Security), parsed in the background
curl -H "X-API-Key: $KEY" -F file=@Security.evtx \
  "https://localhost:8443/api/incidents/$ID/upload?tab=eventlogs&async=true"
  • tab=browser needs browser (chrome / firefox / edge / brave / opera / safari) and source (history / bookmarks / shortcuts / places; Safari: history / downloads / bookmarks), plus an optional profile: the profile name, matched case-insensitively and created if missing (default Default).
  • tab=commands needs shell (bash / zsh / fish / powershell).
  • tab=endpoint needs category (execution / persistence / fileaccess / usb) and source (the source key, e.g. cron).
  • tab=eventlogs needs nothing else: the channel comes from the .evtx file and the result lists it in channels. Only the curated event IDs are kept, records left after a log clear are recovered, and the channel's meta keeps the file's SHA-256 and the log's coverage.

Features for clients of the API

  • Pagination and filtering on GET /incidents and /audit; view=summary lists at scale, then fetch one incident's full document.
  • Optimistic concurrency: send the ETag back as If-Match on PATCH; a stale write gets 412. Read the incident again, apply your change to it and retry with the new ETag (each PATCH returns it). A whole-array value such as notes replaces what is stored, so an If-Match is what keeps two writers from dropping each other's items. Without the header the patch is applied to whatever is stored. Every write of an incident is serialised by a row lock.
  • Conditional GET: If-None-Match returns 304 Not Modified while nothing changed; the check reads only the version column.
  • Partial updates: application/merge-patch+json updates only the nested members you send, e.g. {"flags": {"<key>": null}} removes one flag.
  • Idempotency: an Idempotency-Key header on POST notes / upload makes retries safe.
  • Scopes of the Indicators page: the actions on many indicators take one of { items: [{ type, value }] }, { list: id }, { incident: id } or { filters: { q, type, verdict, origin, list, expired } }.
  • Async uploads: ?async=true → 202 { jobId }, then poll GET /api/jobs/{jobId}.
  • Webhooks: incident.created/updated/deleted, note.added, upload.completed, ioc.watch_hit (an incident holds an indicator of a watched list), mail.analysed, file.analysed, url.analysed, ioc.verdict_changed, storage.low, sla.breached (a timer of an incident passed its time), artifact.expiring and artifact.expired (an artifact with a date is a week from being deleted, or was); the last eight carry what a playbook's trigger reads for the same event (Automation → Trigger). Each delivery is HMAC-SHA256 signed (X-Nik-Signature). A webhook sends what the event holds to the address an admin gave, without the checks a playbook's nodes go through: subscribe an address you trust with senders, subjects and file names.
  • Operations: 600 requests a minute per client address (10 a minute for signing in), answered 429 beyond; Prometheus metrics at /api/metrics (not published by the bundled nginx); an X-Request-ID on every response.
  • Versioning: the current API is v1 under /api; breaking changes would ship under a new prefix.
