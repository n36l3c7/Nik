Security

Nik is where a team puts the worst files it has: live malware, phishing mail, captures of an attack, the addresses of the attacker's own servers. This page says how those are kept from doing harm, what leaves the server and when, what an administrator should check, and where the limits are.

What Nik defends against

The content is the adversary. Nik assumes that:

  • every evidence file may be built to attack whatever opens it: a sample, a document with an exploit, a database with a hostile schema, a capture that crashes a dissector, a file name that is a path or a header;
  • every string taken from evidence (a URL, a subject, a host name, a string of a binary) may be markup, a script, or a lure for a click;
  • every page the isolated browser visits is run by the attacker, and will try to reach the organisation's own network through the server;
  • the analysts are trusted colleagues with accounts, not administrators: what each of them does is recorded, and what decides where data goes is an admin's to set.

It does not defend against an attacker who already controls the server's host, nor against an administrator.

How hostile content is contained

Samples are never executed: there is no sandbox that detonates them. They are read, disassembled and matched against rules. Each kind of content is handled by the part with the least access that can do the job:

Container Handles Network Can read
analyzer (rizin) disassembly and decompilation of samples internal only, no route outside the sample store, read-only
capa capabilities of samples internal only the sample store, read-only
docview (LibreOffice, pdfium) previews of documents: macros disabled, links never updated; an Outlook PST made an mbox, on a volume of its own that holds nothing else internal only only the document it is sent
pcap (tshark, sharkd) packet captures internal only the sample store, read-only
browser (Chromium) HTML attachments and addresses its own network to the backend, and a route to the internet through a filtering proxy; no network shared with the other workers only the page it is sent
api everything else: e-mails, event logs, static analysis of samples, the report the database, the workers, the internet for threat-intelligence lookups the sample store, read-write

Every one of them runs as an unprivileged user on a read-only filesystem, with all capabilities dropped, no-new-privileges, and memory, CPU and process limits. A worker is reached with a token of its own, compared in constant time; none of them can reach the database. The database is on a network the workers are not on.

The isolated browser is the one part that runs attacker code on purpose. Without network (the default) only the attachment loads and every request is refused. With network, Chromium's only route is a proxy inside the worker that resolves each name itself, refuses unless every address is public, and connects to the address it checked: a redirect to 10.0.0.1, a name that changes its answer between the check and the connection, a cloud metadata address, all go nowhere. What a page submits is held until the analyst releases it. Downloads are refused, dialogs dismissed, permissions denied.

Limits on what a file can make the server do

  • Size: every upload has a limit, enforced while the file is read (SAMPLE_MAX_MB, ARTIFACT_MAX_MB, PCAP_MAX_MB).
  • Time: an analysis has a time limit that ends the work for real: a tool that stalls is killed with everything it started, and a preview is made in a process of its own.
  • SQLite files (browser databases) are opened read-only, with their schema untrusted, a time budget and a row limit: a view over an endless query in place of a table costs twenty seconds, not the server.
  • Names from evidence never become paths or commands: files are stored under their SHA-256 or an identifier, tools are given neutral names, and a download is offered under a name with separators, control characters and text-direction marks replaced.
  • E-mail: the HTML is sanitised on the server; only the first five DKIM signatures are verified; an image that declares a huge size is refused before it is decoded.
  • Reports: every value is escaped, and the PDF renderer fetches nothing, so a logo or a value that points at a URL or a local file is not followed.
  • Patterns: a script signature is a regular expression someone with rules.manage wrote, run on scripts an attacker wrote. One that takes too long on hostile texts is refused when it is saved, and a match is stopped after half a second.
  • Disk: a PST is converted only when the worker's volume has room for it and what it becomes, and an archive of artifacts holds a set amount of files at most, read and written in pieces on the disk of the store.
  • Mail. The Mail connector reads a mailbox and sends through an SMTP server, both written in an instance by who manages connectors and reached wherever they are. A message is parsed and never opened further: an attachment is described by name, type, size and SHA-256. A value put in an IMAP command is quoted, and refused when it holds a quote, a backslash or a line break. A recipient must be in a domain the playbook may reach, and what is said goes through the data guard. So does what forward and reply take from the message in the mailbox, which no node wrote: it is judged when it is read, the subject as an e-mail subject, the sender and recipients quoted as e-mail addresses, the text as an e-mail body, and a part that is held is not sent. Outside a playbook there is no guard, and neither command sends. The Message-ID a reply names is not judged: it goes back to those who had it. An attachment a playbook keeps (get-attachments) and a message the listener keeps go to the store as bytes, under the size limit of an upload, and are analysed as an upload is: never run, never opened by the program they are meant for. An attachment is carried by forward only when it is asked to and the data guard lets it: the file is judged by its class, its name, its size and its hash, and what cannot be judged is not sent. Like every connection, these are opened by the one module that opens connections.
  • Files a connector carries. A command of a connector may download a file (a sample, a capture, an archive) or submit one Nik holds. A file that comes in is bytes from the answer to the store: it is never decoded, unpacked or opened, an archive protected with a password stays that archive, and it is analysed as an upload is, under the size limit of an upload (a larger answer stops being read at the limit and nothing is kept). Its name is what the answer says, cut to a file name: never a path. A redirect on the way is followed only to a host the connector's file lists, and the key of the instance, whatever header it travels in, is not sent on to that host. A file that goes out is read from the store as bytes after the data guard judged it as it judges an attachment (its class, its name, its size and its hash; a sample is a sample); one that is not in the store, cannot be read or is over the limit is refused whatever was opened, the command that sends it must be declared as changing the outside (so it asks for approval), and both directions are written to the audit log (connector.file.keep, connector.file.send). The file is named by its artifact id or its SHA-256, which is checked to be one before it is used as a name in the store.
  • Logos of connectors come from outside, in a pack or an upload, and are shown to everyone. A logo is a PNG, by its signature, or an SVG that holds a drawing and nothing else: no script, no foreignObject, no event handler, no DOCTYPE, no reference outside the file. It is drawn with <img>, which runs nothing of an SVG, and served with a content security policy of its own.
  • Expiry deletes nothing by default: an artifact has a date only if someone who may change artifacts set one, and the deletion is in the audit log like one made by hand.

What reaches the analyst's browser

  • A picture, not the page: the isolated browser sends screenshots, documents are shown as page images.
  • Hostile HTML (an e-mail body, a captured page, the report preview) is drawn in a frame that runs no script and loads nothing, with its links, forms and redirects disarmed and remote references removed from its styles. Remote images of an e-mail load only when the analyst asks, and tracking pixels never.
  • Addresses from evidence are not links: opening one asks first, shows it defanged, and only http(s) can be opened.
  • Samples are downloaded only inside a password-protected zip (infected by default), so nothing on the way, nor the workstation's antivirus, runs or deletes them by accident.
  • An export of artifacts holds no file unless the analyst chooses so at that export; the files then sit in an AES-encrypted zip inside the archive (password infected). Treat such an archive as live malware. An import takes an admin, stores a file only when its SHA-256 is the one its artifact is named by, checks every id against the artifact id format, and runs nothing.
  • The app's pages carry a Content-Security-Policy that lets only its own scripts run and lets it talk to its own origin only, with X-Content-Type-Options, X-Frame-Options, Referrer-Policy and HSTS. The session cookie is HttpOnly, Secure and SameSite=Lax; nothing sensitive is kept in the browser's storage.

What leaves the server

Nothing, unless one of these is turned on or asked for:

What When What is sent
Threat-intelligence lookups when the connector of a source is installed and one of its instances is on, and someone asks (Check now, a bulk check, a playbook); automatic lookups only for the indicator types an admin switched on. Nik has no other way to a source: with no instance, nothing is sent the indicator (a hash, a domain, an address), to the hosts the connector of that source names, with the key of the instance, by the one command of its file marked for that kind of indicator: never a command that changes something at the vendor or that needs a paid plan. For a domain a registry is sent the registered domain only. Never a private or internal value, one on the allowlist, or one of an incident marked TLP:RED: no setting and no playbook opens that. A value that passes this rule is then read by the data guard, whoever asks: one that carries an e-mail address, a name under the organisation's own domains or a private address, or an allowlisted name is held, and no source is asked at all, until an admin opens that class (below)
The isolated browser, with network when an analyst opens a session with network, or scans an address ordinary web requests from the server's address; what the page submits only if released
Mail authentication checks when an e-mail is uploaded or re-analysed DNS queries for the sender's SPF, DKIM and DMARC records (the sender's DNS sees them)
Webhooks when an admin subscribed a URL through the API the event, signed: an incident created, an upload finished, an e-mail, a file or an address analysed (with its sender, subject, names and verdict), a verdict that changed, a disk nearly full
Playbooks: the nodes of connectors when a run reaches the node, after the approval if one is asked; when "Test" is pressed on an instance the command's request, with the instance's credentials, to the instance's host only, under the same rules as the HTTP node
Playbooks: the HTTP request and e-mail nodes when a run reaches the node, after the approval if one is asked what the node was given, to a host the playbook may reach, if the classes of data it holds may leave (below)

The app's own pages load nothing from outside: no CDN, no fonts, no telemetry.

What stops a look-up

  • The rule of the look-ups, first and for everyone: a private, loopback or reserved address, an internal name, a value on the IOC allowlist, a value of an incident marked TLP:RED and anything classified TLP:RED are refused before a source is chosen. No setting, no playbook and no role loosens it.
  • The data guard, on what passed the rule. A value is read as any text that leaves is read: an e-mail address in it, a name under the organisation's own domains (Settings → Mail analysis), a private address or a name of the allowlist inside a longer value each give it a class, and a class that is not open holds the look-up whole. Held, no source is asked: not some of them.
  • Which classes are open depends on who asks. A look-up a playbook makes is judged against the classes opened for that playbook, as before. Every other look-up (Check now, a check in bulk, the automatic look-ups of the worker, a list checked again) is judged against one setting of its own, Settings → Threat intelligence → What the look-ups may send: three classes an indicator can carry (e-mail addresses, internal names and addresses, allowlisted indicators), all closed on a new server and after an upgrade to 6.6. The two do not mix: what is opened there opens nothing in a playbook, and what a playbook has opened opens nothing there.
  • Opening a class is an admin's, behind the same double check as on a playbook (a box, and the name of the class typed as it is written); it cannot be done by saving the other settings, and the classes that are whole messages or files, and TLP:RED data, are not offered at all. Opening and closing are in the audit log, opening with the sources that are on, and so is each Check now that was held. An opened class goes to every source that is on, and to any turned on later.
  • Being held is not stored. The guard is asked again at each look-up, at each pass of the worker and as a check in bulk goes on, so closing a class stops what was queued, and a held value is asked about only once its class is open. The answers stored before a value was held stay, and are not refreshed while it is held.
  • What the guard cannot see. It reads addresses, names and e-mail addresses. A person's name, a token or a customer number written in the path of a link has no class and leaves with the link: do not turn on the automatic look-ups of URLs where such links must not reach a vendor.

Playbooks and scripts

A playbook is code that people of your team write and that runs by itself, so three things are kept apart: who may write it, where it may connect, and what it may send. The user's view is in Automation; this is what stands behind it.

  • Who. Building playbooks and scripts is the role Playbooks; running one and answering an approval is Analyst. Only an Admin chooses the hosts a playbook reaches, lets it reach any host, opens a class of data, or sets the SMTP server. A playbook brought in from a file arrives off, with nothing opened.
  • One way out. Playbooks run in the automation container, which publishes no port; the API container does not take their steps. A single module opens connections for them (backend/app/automation/egress.py; a test fails if another file of the package imports a socket or an HTTP client). It resolves the name, checks the address, connects to the address it checked, and checks every redirect again, three at most.
  • Where. By default a playbook reaches only the hosts listed for it and for every playbook. In either mode loopback, private, link-local and carrier-grade ranges, the containers of the stack and the cloud metadata address are refused, unless that host is listed by name: listing an internal system is the permission to reach it. Letting a playbook reach any host needs the double check and is in the audit log.
  • What. Values carry a class from where they are read (an incident's name, an e-mail address, a mail body) through filters, texts and scripts to where they would leave. A node sends only when every class in what it holds is one that always leaves, or one an admin opened for that playbook. E-mail bodies, attachments and samples are whole messages and whole files: the screen of a playbook lists them apart, under a warning of their own, and an admin opens one behind the same double check, for a playbook that must forward them. TLP:RED data is not offered to be opened. What leaves is also read as text for private addresses, internal names and allowlisted values typed by hand.
  • Files. The nodes that work on files (Automation) add no way of running or opening one. A file a playbook adds is stored as it came, under its SHA-256, within the size of an upload, and gets the analyses an upload gets; an analysis a playbook starts is one Nik already makes of an artifact. The automation container still reads the store read-only and reaches no analysis worker: a node writes what it wants as a row of the database, and the backend, which serves the same thing to an analyst, does it. A file is passed between nodes by its id: what an analysis found is given bounded, and no byte, string or body of a sample or a message enters what a run keeps. None of these nodes sends anything out; what they give carries its class (a file name, a subject, an e-mail address), and the artifact made from a content carries the classes of that content. No node deletes an artifact, downloads a sample or exports one: a playbook can take an artifact out of an incident, tag it and give it a day to expire on, each written to the audit log under nik-automation with the run.
  • The store and the worker. Everything a playbook keeps is written by the backend. The automation container mounts the store read-only and is on no network with the analysis workers, and nothing was added to either: the file a connector's command gives, the files of an archive, the attachments of a message, a message a fetch made an incident from and a file a node downloads are handed over through the database (artifact_jobs, the bytes in parts of 4 MB in artifact_job_parts, deleted once the file is in the store or the job is given up) and the step waits. The backend treats them as it treats an upload: the same size limit, the same analyses.
  • Archives. A connector's command (unpack) and the node Unpack an archive take the files out of a zip, plain or protected (ZipCrypto, WinZip AES; read with pyzipper, which Nik already used to write protected downloads). Unpacking happens in memory, in the process that has the archive, and does nothing else: no member is run, opened by a viewer or written to a disk; each is stored under its SHA-256 as an upload is. A member's name is never made a path: a name with .., an absolute path or a device name is kept as text and shown as text. Links are skipped, directories passed over, an archive inside the archive is stored and not unpacked. The limits are 200 members, a total no larger than an upload, and 200 times as the most a member may inflate; sizes written in the archive are not believed, reading stops at the limit. The password is given by an expression, never written to a record, an output or a dry run, replaced by a mark in the arguments a run keeps, and not sent to the backend: the worker unpacks, the files travel. A wrong password is said without repeating it. An archive that cannot be unpacked (the password, not a zip, more inside than an archive may hold) is kept all the same, as the file it is and nothing more: it is evidence, and the step fails naming the artifact.
  • Hosts downloads may come from. A connector reaches its instance and the hosts its file lists. One whose vendor serves files from storage hosts the file cannot name may ask the instance for them (download_hosts_from, Automation): who manages connectors writes host names, or *. and a name for the hosts under it, and nothing looser (no bare *, no address or range, no scheme, port or path, no internal name; checked when the instance is saved, each change in the audit log). It lets out one thing: a GET for a file, to one of those hosts, over https, when a command whose answer is a file is given a link there or is redirected there. No credential follows, and no header of the connector or of the request either: the egress client strips the request to its address before it leaves for such a host, because a signed link needs nothing else and a key sent to a storage host would be a key given away. No other request of the connector goes there, an address inside the network is still refused, and the size limit of a file and the redirect limit are those of every download. With the field empty, and for every connector that does not ask for it, nothing changed.
  • A file from an address. Download a file is the one node that brings a file in without a connector. It sends a GET with no credentials through the same guarded path as every request of a playbook: only to a listed host (or any, when an admin allowed that), a redirect only to such a host, an address inside the network only when that very host is listed, the address judged by the data guard, the size of an upload enforced while reading, a time limit. What comes back is stored as it came and never opened; the audit log names the host. The screens have no such action.
  • A file analysed as an e-mail or a capture. Analyse as an e-mail and Analyse as a capture (the page and the menu of a file, POST /api/artifacts/{id}/analyse-as, write permission; the node Analyse an artifact) run the analysis an upload of the same file would get, on bytes Nik already holds: the mail parser, or the packet capture worker under PCAP_MAX_MB. Nothing new reads a file.
  • Expressions. The {{ }} language compares, counts and chooses, and is still not code: it is read by a parser written for it, a name is a path into the data or one of four functions, and nothing in it reaches Python (no attribute of an object, no call that is not in its table of filters). Its work is bounded: the length of a text, 200 parts and 40 levels of nesting for one expression, numbers within 1015, a time limit on patterns, a most of items for the filters that compare two lists. The clock it reads is a value it is given. What it computes keeps the classes of data of everything it was computed from, so a condition or a sum cannot carry a held value past the data guard.
  • Approvals. A node that changes something outside asks a person first unless someone turned that off for the node or the playbook. An approval that nobody answers is never an approval.
  • Scripts are free Python, made safe by where they run. The sandbox container holds Python and nothing else (no pip, no compiler), on an internal network with no route outside, with a read-only filesystem, no capabilities, an unprivileged user and no volume. Each script runs in a new process with an empty environment and limits it cannot raise (time, 256 MB of memory, 16 open files, no other process, 1 MB of result). It receives the arguments of its node and nothing else: no secret, no instance, no file of Nik. An import hook refuses the modules that reach out; that is a second line, not the boundary.
  • What a script returns is not trusted more than what went in: it carries the classes of everything it was given, so a script cannot launder data past the guard.
  • Secrets. The SMTP password and the credentials of instances are stored encrypted with the vault key and never returned by the API: an instance says which secrets are set, not what they are. Run steps record what was sent, not credentials, and a value equal to a secret is blanked wherever it would be shown. Tokens obtained with OAuth2 and sessions opened by a connector live in memory, or encrypted in the state of a step that waits; never in a table in the clear.
  • Stored credentials. A secret can be kept once (Settings, Credentials) and named by the instances that use it. It is encrypted with the same key as the secrets of an instance, in a table of its own, and no route returns it; an instance stores the name, and the value is read at the moment a request is built. It is managed and used with connectors.manage, the permission that already lets a person type the same secret into an instance. Who may make an instance may make one that sends a credential to an address of their choosing, without ever seeing it: give that permission as you would give the secrets themselves. A credential never reaches a playbook: credentials is not a name an expression can read, in a node, a script, the War Room, the Playground or a connector file, so who writes a playbook cannot send one to a host of their choosing. A playbook only runs commands on an instance, whose host is the one the instance was made for. What is blanked for a secret of an instance (a step, a dry run, a debug session, an error) is blanked for a credential, and the audit log records that one was made, changed or deleted, never its value.
  • Connectors are data, not code. A connector is a YAML file read with a safe loader and checked against a fixed format, where an unknown key is an error; its templates are the playbooks' expression language, which has no code, no loop and no way to read a file or the environment. Installing one is the role Connectors. What a connector can do is send requests: every one of them goes to the host of the instance it runs on, and a path that names another host is refused, so a file cannot be written to carry a instance's credentials elsewhere. Its requests pass through the same egress module and the same data guard as every other node. A secret can be read only in what is sent, never in what a command returns. The shipped connectors were written from public documentation and are marked not verified until someone has run them against a real system.
  • The record. What a playbook changes in Nik is signed nik-automation, an account that cannot sign in, with the run and whoever approved the step. Versions of playbooks and scripts (with the difference in a script's code), openings of network and data, approvals and the general switch are all in the audit log.
  • One address that asks for no account. POST /api/automation/hooks/<token> starts a playbook whose trigger says From outside, and is the only route added by automation that answers without signing in. The token is 32 random bytes, made by the server, shown once to whoever builds the playbook and stored as its SHA-256: a copy of the database does not give the addresses. The route never reads a cookie or an API key, so a page open in an analyst's browser cannot use their session through it. A request carries at most 256 kB; each token has 60 requests a minute, and the playbook its runs an hour. Every reason a token starts nothing (it does not exist, the playbook is off, automation is stopped) gives the same 404, and a request that is taken is told only accepted. What arrives is data from outside: it has no class of its own, credentials and proxy headers are dropped before the playbook sees the rest, and what the playbook may send on is decided by the guard above. Treat the address as a password: it appears in the sender's configuration and may appear in the access log of a proxy in front of Nik. Replace it when in doubt; creating, replacing and removing one are in the audit log.
  • Commands typed in the War Room are runs of one node on the same engine, and get nothing a playbook does not get: the permission to run playbooks, the egress rules (the host of the command's instance and the hosts listed for every playbook), the data guard with no class opened, the audit log under the name of who typed. The line is read by a small grammar of its own, not by a shell: a name, pairs of name=value, and expressions that can only read the incident and its context. A command that changes something outside is not sent until it is confirmed.
  • Tasks and questions are completed by whom they are for, and by nobody else: the user a task names, whoever holds its role, the owner of its incident at that moment, and an admin. The fields a task asks for are written through the field registry under the name of who completed it, with the checks of any other write. The instructions of a task are written by whoever builds a playbook and read by someone else: they are drawn as text, with a small Markdown read into elements and never into HTML, and a link is kept only when it is http, https or mailto. The work plan of an incident shows a node by its name and its kind, never by what it is given.
  • Fetching and mirroring. A fetch reaches the host of its own instance and nothing else, and what it brings in is data, never instructions: an item is read through the mapper, a value is checked by the field it goes to, and the item as it came is shown as text. "The same incident" of a pre-processing rule is found by columns of the incident, never by a query built from what the other side sent. An instance that makes more than 500 incidents in an hour is paused. A mirror that sends is a standing permission, given by someone who may run playbooks and recorded with their name; what it sends passes the data guard with only the classes opened for that mirror, by someone who may open them. What a person set in Nik is not written over by the other side unless the mapper says the field is authoritative.
  • Dashboards. A dashboard holds questions, never answers: each widget is asked of the server as the person looking, through the same compiler as every query, so sharing a dashboard cannot show anyone what their roles do not let them read (a widget they may not ask says so). The same holds for a dashboard made into a report: it is written with what its reader may see. A dashboard that is not yours and not shared with you answers "not found". Sharing needs dashboards.share and is written to the audit log. What a chart shows of a value (a name of an incident, a tag) is drawn as text.
  • The catalogue of packs. The packs of vendors' products are read from outside (by default the release packs of Nik's repository), so nothing of the catalogue is trusted for where it comes from. Its index is read only when its Ed25519 signature is of the key Nik holds: the public half is in the code, the private half is a secret of the repository used only by the workflow that publishes the packs from main. A pack is taken only when its size and its SHA-256 are the ones the signed index gives, and the name of its file cannot leave the folder of the index. It is then read like an uploaded pack (below) and applied only after a person saw what it would do. Reading the catalogue goes out through the same guarded path as a playbook's request, to the host of the address and no other (for GitHub, the two hosts it answers a release from); only an administrator sets another address or another key, and that is written to the audit log. A pack from the folder NIK_PACKS_DIR is not checked against a signature: whoever can write that folder on the server installs content.
  • Content packs. A pack is a file from someone else and is read as one: at most 20 MB and 2 000 files, 100 MB unpacked, no path that leaves the pack, no links, only the folders Nik knows, YAML read without building objects. Reading it changes nothing; applying it needs content.manage, happens in one transaction and is written to the audit log. A pack cannot widen what Nik may do: it never carries an instance, a credential, an allowed host or an opened class of data; a playbook it brings arrives off, reaching only listed hosts and sending no class of data; it does not replace the items of the lists Nik's own settings read, nor a field of Nik's own. A script in a pack is code: it runs where every script runs, in the sandbox, and its difference is shown before it is imported.
  • The debugger. A debug run holds what goes outside, as a dry run does. Letting one node send for real needs the permission to run playbooks besides automation.debug, asks the approval the node normally needs, passes the data guard and the egress rules like any run, and is written to the audit log; it applies to that node and that step only. Arguments typed in the debugger are values, not templates: they are never evaluated. A debug run is shown to who started it and to an administrator.
  • Lists are read by whoever reads incidents and changed with lists.manage (the roles admin and playbooks). A playbook writes only to a list that says it may, which no list does until someone who manages lists turns it on: the IoC allowlist, your domains and the hosts every playbook may reach decide what Nik hides, trusts and reaches, so a playbook cannot widen them on its own. Choosing which list a feature reads is a change of the same weight and needs the same permission; both are in the audit log. A CSV export writes a cell a spreadsheet would run as a formula so that it does not.
  • Loops and floods. A playbook's changes can start other playbooks three deep; each playbook has a ceiling of runs an hour and, by default, one run at a time on the same object; the whole server has a ceiling of runs in progress. One switch stops everything.

Accounts, sessions and the audit log

  • Passwords are hashed with bcrypt; sessions are random tokens kept on the server. A session ends after eight hours without use (thirty minutes for an administrator) and twelve hours at most, unless an admin sets other times; what follows says how sign-in is protected beyond the password.
  • There is always one admin that can sign in. API keys are stored as digests, carry roles and an optional expiry, and are shown once.
  • Roles are tags that add up, and every route of the API asks for a permission, never for a role: read, write, rules.manage, audit.read, admin. An account or a key may do what its roles grant together, and nothing else: a test walks every route with a key of each role, and fails when a new route does not say who may call it. The roles are read from the database on every request, so one that is taken away stops working at once. Only an admin gives roles; nobody takes the admin role away from themselves or from the last admin; nobody, admin included, can write an audit entry by hand.
  • The audit log is written by the server for every change, whoever makes it and however: the app, a script with a key, a request sent by hand. It cannot be written from the browser. It is a chain, and it can be sent to a syslog receiver as it is written: see below.
  • Changes by two people to the same incident are merged or refused, never silently overwritten.

A second factor at sign-in

An account can have a second factor: a time-based code (TOTP, RFC 6238: SHA-1, six digits, thirty seconds, as every authenticator app makes them). An admin can make it a must for administrators (Settings → Sign-in and sessions); every other account decides for itself.

  • The first step gives nothing. The right password of an account with a second factor opens no session: the browser gets a ticket, in a cookie of its own (HttpOnly, SameSite=Strict, sent only to the sign-in routes), good for five minutes and for the second step only. The answer says that a code is needed and nothing else.
  • A code is accepted once. The server takes the code of the current half minute and of one either side, compares in constant time, and remembers the last time step it accepted: the same code, or an older one, is refused, also when two requests carry it at the same instant.
  • The secret is encrypted with SECRET_KEY where it is stored, is shown once at the set-up and is never sent again. The QR code is drawn in the browser.
  • Recovery codes: ten, single-use, stored hashed like passwords, shown once. Making new ones ends the old ones.
  • Required of administrators, when the switch is on: an account that holds the Admin role and has no second factor is let through to the routes of the set-up and to nothing else (the API answers 403 with the code second_factor_required), from the moment the rule is saved. There is no period of grace.
  • Asked again before the second factor is turned off, new recovery codes are made or the password is changed: the password and a current code. Setting a second factor up asks for the password first, so that a session somebody else got hold of cannot put its own factor on the account; only a session that signed in less than two minutes ago is spared the question. Wrong values there are counted like failed sign-ins.
  • What it covers: every interactive sign-in, the dialog of a session that ended included. There is no "remember this browser": on a platform like this one, a copied browser profile is the case a second factor is for. API keys are not asked: a key is a credential of its own, as strong as it is secret. Give keys the narrowest roles and an expiry, replace them regularly, and remember that a key with the Admin role can create accounts and set passwords. It cannot take somebody's second factor away: that needs a signed-in admin.
  • Passkeys (WebAuthn) and single sign-on are not part of this release.

Sessions

  • The session cookie is HttpOnly, SameSite=Lax and Secure (unless COOKIE_SECURE=false, for development over plain HTTP). Its value is a random 256-bit token that the lists of sessions never show.
  • A sign-in always makes a new session. The one the browser held before is ended on the server, and the id changes again when a second factor is turned on: an id planted in a browser beforehand is never the one that becomes signed in. Signing out deletes the session on the server.
  • Idle time and lifetime are checked by the server at every request. "Use" is a request the person caused: the page marks the ones it sends by itself (a list that refreshes, the count of notifications) and the server does not count them, so an open tab does not keep a session alive.
  • A new password, other roles, the account disabled, its second factor turned on, off or reset end the sessions of the account (the one the change is made from goes on). Everyone sees and ends their own sessions; an admin, anybody's.
  • Requests from another site: besides SameSite, the server refuses any request that changes something when the browser says it was sent by another site or by another host of the same site (Sec-Fetch-Site), whatever cookie it carries.

Failed sign-ins

  • Failures are counted in a row, per account and per client address, wrong codes apart from wrong passwords. After five (by default) the next attempt waits thirty seconds, then twice as long after each further failure, up to fifteen minutes; an attempt made during a wait is refused without being looked at. The count falls back with time, and to nothing with a good sign-in.
  • No lock that an attacker can hold. A wait never exceeds the maximum, and the addresses an account last signed in from are not made to wait by failures that came from elsewhere: guessing at somebody's password does not keep them out of their account.
  • Nothing says whether an account exists. A name that is no account is counted, answered and made to wait exactly like a wrong password, after the same work. What was typed as a name is written in the audit log only when it is an account.
  • The audit log has the first failure of a run and each one past the threshold; the admins get one notice when a run reaches ten.

Administrators' networks, and the client's address

An admin can list the networks administrators are accepted from. Accounts and API keys that hold the Admin role are then refused from anywhere else: at the sign-in, after the password and the code were right (so that nothing tells which accounts are administrators before that), and at every request of a session that moved. A list that would refuse the admin who saves it is refused unless they say they want it, and a command on the server empties it (deployment guide).

All of this, and the waits per address, rest on the server knowing where a request comes from. The web container writes the address it saw in X-Forwarded-For, and the backend believes that header only when the connection itself comes from the web container (TRUSTED_PROXIES); from anybody else it is ignored. Some container set-ups hide the addresses of clients from the web container itself (rootless podman, Docker Desktop): the server recognises that, says on the policy page that the restriction cannot work there, refuses the list, and counts failures per account only.

The audit log is a chain, and leaves the server

An audit log that sits in the database it describes can be changed by whoever can change that database: an administrator whose account was taken, an operator of the host. Nik does two things about it. Every entry is linked to the one before it by a hash, so a change shows when the log is walked; and every entry is sent to a syslog receiver as it is written, so a copy exists where that person cannot reach.

  • The chain. Each entry has a number, counted from 1 with no gap, the hash of the entry before it, and its own: the SHA-256 of a canonical form of its number, the previous hash and its eight fields, each written with its length (the exact bytes are specified at the top of backend/app/auditlog/verifier.py, a file that needs nothing of Nik and can be copied out). The numbers are given when the transaction that holds the entries commits, under one lock taken last and held for an instant, so writers that work at the same time never give the same number and none waits for long.
  • Nothing edits or removes an entry, with one exception that says so itself: a signed-in administrator (not an API key) can remove the oldest entries, and the chain then keeps an entry that says how many went, their numbers, by whom and the hash of the last one, so the log still verifies from where it now starts. While the log is forwarded, an entry that was not sent yet is never removed. Entries that come in a file of content from another server join the chain when they arrive, with the time and the author the file gives them: the entry of the import says how many, and the chain shows where they joined. Each of them is marked as imported (origin: import), on the screen, in the API and in the message sent to syslog, and the mark is hashed with the entry: nobody reading the receiver's copy can take an entry of another server, with a date of years ago, for something this server saw. Entries imported before 6.8 have no mark: nothing told them apart then.
  • Verification. The server walks the chain every five minutes (only what is new; every entry once a day), on demand from Settings → System → Audit log, and from the command line (python -m app.auditlog verify-audit). It names the first thing that does not hold: an entry whose content was edited, entries missing from the middle, entries reordered, an entry that does not follow the one before it, a log that starts late without saying why, a log whose end was cut. Every administrator is told once when a break is found.
  • What a chain cannot show alone. Removing the newest entries leaves a chain that still holds together, and so does computing the whole chain again from the point of a change. Only a head (a number and its hash) kept somewhere else tells. The server holds the end of the log against every head it can find: the head row, a file of heads it writes into the backup directory at each good walk (audit-heads.jsonl: outside the database, still on the server), the cursor of the forwarding, and a head typed by hand, such as the last checkpoint the syslog receiver got. Somebody who controls the database and the host can make all of those on the server agree. What they cannot change is what already left: that is what the forwarding is for.
  • The chain is signed with a key that is not in the database. Beside its hash every entry carries an HMAC-SHA-256 of that hash and the id of the key that made it. Whoever can write to the database can compute the hashes of a rewritten log again; without the key they cannot make its signatures, and the walk names the first entry that has none (unsigned) or one the key did not make (forged). The key is AUDIT_KEY, a secret of its own; when it is not set, a key derived from SECRET_KEY is used, so an upgraded server is protected without anybody doing anything. The hashes stay what anybody can check, the syslog receiver included; the signatures are checked by who holds the key (the standalone verifier takes it from a file or from its environment, never from its command line, and says "not checked: no key" without it). The signature and the id of the key travel in the syslog messages; the key never leaves the server.
  • The server signs as its own only what its own transactions wrote. An entry it finds in the table without a number (the one a restore leaves; one inserted by hand; one whose number was taken away so that it would be linked again) is linked and signed, and marked origin: outside, which is hashed and shown. Without that, emptying the numbers of a stretch of the log would be a way to have the server sign whatever was put there.
  • When the key changes, the new one signs from the next entry on and the entries before it keep the id of theirs. They stay verifiable while the server can still make their key: the earlier keys in AUDIT_KEY_PREVIOUS, and the keys derived from SECRET_KEY and from every SECRET_KEY_PREVIOUS. Setting AUDIT_KEY on a server that used the derived key therefore loses nothing. Changing SECRET_KEY starts a new derived key; the old entries verify while SECRET_KEY_PREVIOUS holds the old value, and after that only if the old derived key was put in AUDIT_KEY_PREVIOUS (python -m app.auditlog key --derived prints it, before the change). An entry whose key the server can no longer make is reported as one that cannot be checked, never as tampering, and its place in the chain of hashes is verified all the same.
  • What the key does not change. Somebody who holds the key as well as the database (the backend's container, its environment) can sign what they rewrite: the copy outside the server remains what shows it. And a signature says nothing of entries removed from the end of the log.
  • There is no database trigger that refuses an UPDATE or a DELETE on the table. A trigger is an object the backups refuse to carry, and the role the server connects with owns the table, so privileges could not hold it back either. The chain and the copy outside are the protection.
  • Entries written before 6.8 were linked once, at the upgrade, as they were found. The entry that follows them says so: the chain vouches for them from that day, not before.
  • After a restore the log on the server is the log of the backup. The restore writes the first new entry (audit.restore, naming the backup) and the chain goes on from the head the backup had. What the server wrote between the backup and the restore is not in its log any more: it exists only on the syslog receiver, which sees the same numbers arrive again with other content, the first of them being that entry.

Forwarding to syslog

  • What is sent. One RFC 5424 message for each entry, with the entry as a JSON object and, in the structured data, its number, its hash and the hash of the entry before: the receiver's copy can be verified on its own, and held against an export of the server, with verifier.py. Every few minutes a checkpoint carries the head of the chain and the number of entries, whether anything happened or not: silence is told from a cut line, and the receiver always holds a recent head. Nothing but the audit log is sent.
  • How. TCP with TLS (RFC 5425) is the one to use: the certificate of the receiver is always verified, against the authority or the certificate pasted in the settings (then only that is trusted) or the system's authorities, and a client certificate can be presented, its key pasted or taken from a stored credential. Plain TCP (RFC 6587, octet counting) and UDP exist for receivers that take nothing else; the screen says what they are: not encrypted, not authenticated, and for UDP lossy.
  • Who sends. The backend has no way out. The automation worker sends, in the order of the chain, at least once: a batch counts as arrived only when the connection is still up a moment later, and is sent again otherwise, so a receiver can see an entry twice and never out of order. Writing to the log never waits for the receiver. A receiver that is down makes a backlog, bounded only by the table, shown on the screen and on the health page, told to the administrators when it lasts and when it drained.
  • A log changed after it was sent. The sender remembers the hash of the last entries the receiver took. When the table no longer holds them as they were sent, it writes an entry that says so (audit.forward.diverged) and sends again from the last entry that is still the one the receiver got: the receiver then holds what the log said and what it says now, the same numbers with different content, which is what the verifier reports. The walk of the chain is held against the highest entry the receiver ever took, and that is never moved back.
  • The receiver is an exception of its own to the egress rules. A SIEM is usually on a private address, which the automation worker refuses for everything a playbook does unless the host is listed. The forwarding connects to the host and the port an administrator set, whatever range the address is in, and to nothing else; it sends syslog messages there and reads nothing back. It opens nothing for playbooks: their requests go through other code that does not read this setting, and the same host stays refused to them. A name is resolved once and the connection goes to that address. Link-local addresses (a cloud's metadata service), multicast and unspecified addresses are refused whatever is set.
  • The last word. Changing the forwarding needs a signed-in administrator and is itself an entry of the log. The sender keeps the settings it had until the receiver it had took that entry: turning the forwarding off, or pointing it elsewhere, is the last thing the old receiver hears. If that receiver does not take it within thirty seconds the change takes effect anyway, and an entry says it went unheard.

What is in the audit log, and what is not

Recorded: sign-ins, sign-outs and failed sign-ins (the first failure of a run, then each one from the number that starts the waits: the ones between are counted, not listed); an administrator refused for the network they come from; second factors turned on, turned off, reset, wrong codes, recovery codes used and made again; sessions ended by their owner or by an administrator; accounts created, changed (roles, password, disabled), deleted; API keys made and revoked; the sign-in policy; every change of settings, with the names of what changed; backups (settings, passphrase, each run, each restore test, each copy, each download and deletion), the export and the import of content; the data guard opened and closed, for playbooks and for look-ups; hosts a playbook is let reach; playbooks created, saved as a version, enabled, run by a person, stopped, deleted, imported; approvals answered; connectors, instances and credentials; packs; evidence uploaded, deleted, downloaded (samples, attachments, captures and what is exported from them), incident exports and reports; webhooks added and removed (from 6.8); the audit log itself (verified, old entries removed, forwarding changed and tested, a restore) and the health page (thresholds, the scrape token).

Not recorded, by design so far: what is only read (an incident opened, a list of accounts, the audit log itself, a query), the use of an API key, a session that ends by itself for lack of use. And, as things stand: the start of a second-factor enrolment (its confirmation is recorded); runs a playbook starts by schedule, trigger or inbound webhook (they are in the runs, not in the audit log); the draft of a playbook or a script saved without making a version; tests of an instance and of its keys; saved filters and dashboards created; tags and notes of an indicator in the library; a task given to somebody else; the export of a playbook, a script, a dashboard or a list as a file; reading the source of an e-mail or an attachment's bytes in the page. Old values are not kept: an entry says what changed, not what it was before.

The health page and the metrics

  • /api/health says that the process is up and nothing else, to anybody. The details are for administrators (/api/health/details).
  • /api/metrics answers to a scrape token and to nothing else: a bearer token made on the health page by a signed-in administrator, shown once and kept as a hash. A session cookie is not looked at, so no page a browser opens, of Nik or of another site, can read the metrics; an API key is not a scrape token and a scrape token opens no other route. No label of a metric carries an account, an incident, a host or anything a person typed.
  • The certificate of the web container is read by the backend as a browser gets it (a connection to the web container, nothing verified, nothing sent): the backend does not hold the certificate's key and does not mount its volume.

Secrets and backups

  • The stack does not start without DB_PASSWORD, SECRET_KEY and a token per worker, and refuses the example values. deploy/init-env.sh generates them. Keep a copy of .env somewhere that is neither the server nor the place its backups go.
  • SECRET_KEY encrypts the credentials of the instances of connectors (the keys of the threat-intelligence sources among them), the stored credentials they name, the secrets of the accounts' second factors and the TLS key logs stored in the database. Changing it with SECRET_KEY_PREVIOUS set re-encrypts all of them, the keys an instance holds beside its first included, and the backup passphrase with them. It lives in .env, which is not in a backup unless an administrator chose to put the key inside (below).

Backups

  • A backup is always encrypted. It holds live malware and every incident, so Nik writes none in clear, to its own disk or anywhere else: AES-256-GCM over chunks of one megabyte, each authenticated with its position in the file and with the header, under a key derived with scrypt from the backup passphrase and a salt of the file. A file that is changed, reordered or cut short is refused before anything is restored from it. The small .json beside a backup is in clear and holds nothing secret (name, sizes, version, how its test went).
  • The passphrase is not SECRET_KEY. A backup must be readable on a host that never had this server's .env, by someone who was given the passphrase and nothing else. It is kept in the database encrypted under SECRET_KEY, so that the scheduled backups can run; no route returns it and it is not in the audit log. Whoever can read both the database and .env can therefore read the backups too, as they can read everything else. When it is changed, earlier backups keep the passphrase they were made with.
  • The snapshot before an upgrade is encrypted the same way; while no passphrase is set (the first upgrade from 6.6) its key is derived from SECRET_KEY, so it is still never in clear, and is as protected as .env is.
  • Including SECRET_KEY in the backups (off by default) trades one risk for another, and the screen says so: without it, losing .env means entering every stored secret again after a restore; with it, a backup and its passphrase are enough to read every stored secret. The key is written only inside the encrypted file.
  • The backend still has no way out. The copy off the server is sent by the automation container, which already has one and mounts the backup directory read-only; nothing else gained a network, a port or a service. It goes over SFTP, with a key made for it, to a server whose host key was pinned by an administrator: a server that presents another key receives nothing, and there is no trust on first use. On that server, give the account SFTP only, chrooted, with no shell (the deployment guide has the lines). It receives encrypted files and the clear .json of each: it can delete or withhold a backup, not read one.
  • The restore test restores each backup into a scratch database owned by a role made for the test, which owns nothing of the database Nik runs on, and drops both. The code refuses any name but nik_scratch_… / nik_rehearsal_… and refuses the name of the live database. The rehearsal of an upgrade runs as Nik's own role, since it has to find out what the migrations will do as that role.
  • Restoring is not a route. No request to the API can put a backup back: it is done on the host, by someone who has a shell there, the file and its passphrase. An administrator of the application can take, test, download (the encrypted file) and delete backups; each of these is in the audit log, and deleting the last good backup is asked twice. An administrator's API key can read the state of the backups and ask for one or for a restore test, and nothing more: changing the settings or the passphrase, deleting a backup and downloading one need a signed-in administrator, with the second factor and the networks the sign-in policy asks of them.
  • A restored server starts with nobody signed in. A backup holds the sessions that were open when it was taken; a restore (and a rollback) ends them all, with the sign-ins that were half-way and the count of failed ones, so a cookie of that day opens nothing. Accounts, second factors, recovery codes and the sign-in policy are restored as they were.
  • The export of content as one file (the "Full backup" of earlier releases) no longer replaces anything when it is imported: it adds incidents, accounts and audit entries that are not there. An administrator who imports a file adds the accounts it holds, with their roles and passwords: read what the dialog lists before confirming.
  • What an anonymous request is told when an upgrade was stopped is one fixed sentence; the reason, which may quote the database, stays in the log of the container.

Hardening checklist

  1. Create the first account yourself, at once: whoever reaches a new install first becomes its admin.
  2. Publish the HTTPS port only where analysts are (a management network, a VPN), and replace the self-signed certificate with one your browsers trust; set TLS_HOSTNAME.
  3. Decide whether the server may reach the internet at all. Without it, threat-intelligence lookups, sessions with network and address scans do not work; everything else does.
  4. On the host firewall, keep the browser-egress network away from your internal ranges and the cloud metadata address. The worker already refuses them; a second lock costs nothing.
  5. Exclude the sample store volume from the host's antivirus, or it will quarantine the evidence; do not exclude anything else.
  6. Set the backup passphrase (Settings → System → Backup) and write it down away from the server; send the copies to a second host; keep .env elsewhere; and restore once on that second host, to know how long it takes.
  7. Send the audit log to a syslog receiver on another machine, over TLS (Settings → System → Audit log), and keep what it receives where the administrators of Nik cannot change it: it is the copy that shows a log that was altered here.
  8. Give each person an account; disable, do not delete, the account of someone who leaves.
  9. Under Settings → Sign-in and sessions, turn on Administrators must have a second factor, and ask everybody else to set one up under My account. Set up your own first, and keep its recovery codes.
  10. If administrators always work from the same networks, list them there. Check first what the page says of the address the server sees you at: where it cannot know it, fix the deployment before relying on this.
  11. Give an account and an API key the narrowest roles that work (Viewer for a key that only reads), and a key an expiry. Keep the Admin role for the few who manage the platform: an analyst who maintains the rule sets needs Rules, not Admin.
  12. Give the Playbooks role to the people who should write automation, and to nobody else: a playbook acts with Nik's own hands. Read the audit log for automation.egress.open and automation.data.open: they say which playbook was let reach further or send more, and by whom.
  13. Keep the automation-egress network away from what playbooks have no business reaching, on the host firewall, as for the browser's. The engine already refuses internal addresses that are not listed.
  14. Update: git pull and compose up -d --build rebuild the images with the current fixes of LibreOffice, Wireshark and Chromium, which is where the next vulnerability will be.

Known limits

  • Chromium runs with --no-sandbox: its own sandbox needs privileges the container does not give, so the container is the sandbox. A browser exploit gets an unprivileged process in a container with no capabilities, a read-only filesystem and no network but the backend's and the filtered way out.
  • The backend parses some formats itself (e-mails, event logs, PE headers, YARA, QR codes), in a hardened but not disposable container that holds the database password.
  • In a session without network every request is refused by the interception, not by the proxy; the proxy would still keep anything that slipped through away from private addresses.
  • A backup is as recent as the schedule: what was written since the last one is lost with the server. There is no continuous archiving of the database yet.
  • The database part of a backup is Nik's own (tables, constraints, indexes, sequences, rows), not a pg_dump: a database that holds anything Nik does not make (a view, a trigger of your own) is refused, loudly, rather than backed up without it.
  • Under rootless podman and Docker Desktop the web container does not see the addresses of its clients: the administrators' networks cannot be used there and failed sign-ins are counted per account only. The policy page says when that is the case.
  • A second factor does not protect an API key, nor the server itself: whoever can run commands in the backend container can reset any account's second factor.
  • The chain of the audit log shows a change to what is there. Without a copy off the server (the syslog receiver, its checkpoints) it cannot show that the newest entries were removed, nor that the whole log was computed again by somebody who controls the database and holds the key that signs it (the host). Anybody who can write to the database can also add entries: a chain says that nothing was changed, not that everything in it is true.
  • Over plain TCP and UDP the audit log crosses the network in clear and the receiver is not authenticated; over UDP messages can be lost in silence, and one that does not fit a datagram is shortened.
  • Analysts can read every incident: there is no per-incident access control.
  • A script can read what its own container holds, which includes the token the engine presents to the sandbox (in /proc). With it a script could ask the sandbox to run another script, which it already is: the token opens nothing else, and the container reaches nothing.
  • The data guard knows the class of what Nik gave a playbook. It cannot know what a person types into a field, beyond the patterns it scans for, nor what another system answers and a playbook forwards.
  • A playbook that may reach any host with a class of data opened can send that data anywhere a node says. That is what the double check is for; it does not make the choice safe.

Reporting a vulnerability

Please report it privately, through a GitHub security advisory, not in a public issue. Say what you did, what happened and what you expected; a sample that triggers it helps, shared the way you would share any malware. SECURITY.md in the repository has the details.
