Security

Nik is where a team puts the worst files it has: live malware, phishing mail, captures of an attack, the addresses of the attacker's own servers. This page says how those are kept from doing harm, what leaves the server and when, what an administrator should check, and where the limits are.

What Nik defends against

The content is the adversary. Nik assumes that:

  • every evidence file may be built to attack whatever opens it: a sample, a document with an exploit, a database with a hostile schema, a capture that crashes a dissector, a file name that is a path or a header;
  • every string taken from evidence (a URL, a subject, a host name, a string of a binary) may be markup, a script, or a lure for a click;
  • every page the isolated browser visits is run by the attacker, and will try to reach the organisation's own network through the server;
  • the analysts are trusted colleagues with accounts, not administrators: what each of them does is recorded, and what decides where data goes is an admin's to set.

It does not defend against an attacker who already controls the server's host, nor against an administrator.

How hostile content is contained

Samples are never executed: there is no sandbox that detonates them. They are read, disassembled and matched against rules. Each kind of content is handled by the part with the least access that can do the job:

Container Handles Network Can read
analyzer (rizin) disassembly and decompilation of samples internal only, no route outside the sample store, read-only
capa capabilities of samples internal only the sample store, read-only
docview (LibreOffice, pdfium) previews of documents: macros disabled, links never updated; an Outlook PST made an mbox, on a volume of its own that holds nothing else internal only only the document it is sent
pcap (tshark, sharkd) packet captures internal only the sample store, read-only
browser (Chromium) HTML attachments and addresses its own network to the backend, and a route to the internet through a filtering proxy; no network shared with the other workers only the page it is sent
api everything else: e-mails, event logs, static analysis of samples, the report the database, the workers, the internet for threat-intelligence lookups the sample store, read-write

Every one of them runs as an unprivileged user on a read-only filesystem, with all capabilities dropped, no-new-privileges, and memory, CPU and process limits. A worker is reached with a token of its own, compared in constant time; none of them can reach the database. The database is on a network the workers are not on.

The isolated browser is the one part that runs attacker code on purpose. Without network (the default) only the attachment loads and every request is refused. With network, Chromium's only route is a proxy inside the worker that resolves each name itself, refuses unless every address is public, and connects to the address it checked: a redirect to 10.0.0.1, a name that changes its answer between the check and the connection, a cloud metadata address, all go nowhere. What a page submits is held until the analyst releases it. Downloads are refused, dialogs dismissed, permissions denied.

Limits on what a file can make the server do

  • Size: every upload has a limit, enforced while the file is read (SAMPLE_MAX_MB, ARTIFACT_MAX_MB, PCAP_MAX_MB).
  • Time: an analysis has a time limit that ends the work for real: a tool that stalls is killed with everything it started, and a preview is made in a process of its own.
  • SQLite files (browser databases) are opened read-only, with their schema untrusted, a time budget and a row limit: a view over an endless query in place of a table costs twenty seconds, not the server.
  • Names from evidence never become paths or commands: files are stored under their SHA-256 or an identifier, tools are given neutral names, and a download is offered under a name with separators, control characters and text-direction marks replaced.
  • E-mail: the HTML is sanitised on the server; only the first five DKIM signatures are verified; an image that declares a huge size is refused before it is decoded.
  • Reports: every value is escaped, and the PDF renderer fetches nothing, so a logo or a value that points at a URL or a local file is not followed.
  • Patterns: a script signature is a regular expression someone with rules.manage wrote, run on scripts an attacker wrote. One that takes too long on hostile texts is refused when it is saved, and a match is stopped after half a second.
  • Disk: a PST is converted only when the worker's volume has room for it and what it becomes, and an archive of artifacts holds a set amount of files at most, read and written in pieces on the disk of the store.
  • Mail. The Mail connector reads a mailbox and sends through an SMTP server, both written in an instance by who manages connectors and reached wherever they are. A message is parsed and never opened further: an attachment is described by name, type, size and SHA-256. A value put in an IMAP command is quoted, and refused when it holds a quote, a backslash or a line break. A recipient must be in a domain the playbook may reach, and what is said goes through the data guard. An attachment a playbook keeps (get-attachments) and a message the listener keeps go to the store as bytes, under the size limit of an upload, and are analysed as an upload is: never run, never opened by the program they are meant for. An attachment is carried by forward only when it is asked to and the data guard lets it: the file is judged by its class, its name, its size and its hash, and what cannot be judged is not sent. Like every connection, these are opened by the one module that opens connections.
  • Logos of connectors come from outside, in a pack or an upload, and are shown to everyone. A logo is a PNG, by its signature, or an SVG that holds a drawing and nothing else: no script, no foreignObject, no event handler, no DOCTYPE, no reference outside the file. It is drawn with <img>, which runs nothing of an SVG, and served with a content security policy of its own.
  • Expiry deletes nothing by default: an artifact has a date only if someone who may change artifacts set one, and the deletion is in the audit log like one made by hand.

What reaches the analyst's browser

  • A picture, not the page: the isolated browser sends screenshots, documents are shown as page images.
  • Hostile HTML (an e-mail body, a captured page, the report preview) is drawn in a frame that runs no script and loads nothing, with its links, forms and redirects disarmed and remote references removed from its styles. Remote images of an e-mail load only when the analyst asks, and tracking pixels never.
  • Addresses from evidence are not links: opening one asks first, shows it defanged, and only http(s) can be opened.
  • Samples are downloaded only inside a password-protected zip (infected by default), so nothing on the way, nor the workstation's antivirus, runs or deletes them by accident.
  • An export of artifacts holds no file unless the analyst chooses so at that export; the files then sit in an AES-encrypted zip inside the archive (password infected). Treat such an archive as live malware. An import takes an admin, stores a file only when its SHA-256 is the one its artifact is named by, checks every id against the artifact id format, and runs nothing.
  • The app's pages carry a Content-Security-Policy that lets only its own scripts run and lets it talk to its own origin only, with X-Content-Type-Options, X-Frame-Options, Referrer-Policy and HSTS. The session cookie is HttpOnly, Secure and SameSite=Lax; nothing sensitive is kept in the browser's storage.

What leaves the server

Nothing, unless one of these is turned on or asked for:

What When What is sent
Threat-intelligence lookups when an admin has entered a provider's key; automatic lookups only for the indicator types an admin switched on the indicator (a hash, a domain, an address), to that provider. Never a private or internal value, one on the allowlist, or one of an incident marked TLP:RED
The isolated browser, with network when an analyst opens a session with network, or scans an address ordinary web requests from the server's address; what the page submits only if released
Mail authentication checks when an e-mail is uploaded or re-analysed DNS queries for the sender's SPF, DKIM and DMARC records (the sender's DNS sees them)
Webhooks when an admin subscribed a URL through the API the event, signed: an incident created, an upload finished, an e-mail, a file or an address analysed (with its sender, subject, names and verdict), a verdict that changed, a disk nearly full
Playbooks: the nodes of connectors when a run reaches the node, after the approval if one is asked; when "Test" is pressed on an instance the command's request, with the instance's credentials, to the instance's host only, under the same rules as the HTTP node
Playbooks: the HTTP request and e-mail nodes when a run reaches the node, after the approval if one is asked what the node was given, to a host the playbook may reach, if the classes of data it holds may leave (below)

The app's own pages load nothing from outside: no CDN, no fonts, no telemetry.

Playbooks and scripts

A playbook is code that people of your team write and that runs by itself, so three things are kept apart: who may write it, where it may connect, and what it may send. The user's view is in Automation; this is what stands behind it.

  • Who. Building playbooks and scripts is the role Playbooks; running one and answering an approval is Analyst. Only an Admin chooses the hosts a playbook reaches, lets it reach any host, opens a class of data, or sets the SMTP server. A playbook brought in from a file arrives off, with nothing opened.
  • One way out. Playbooks run in the automation container, which publishes no port; the API container does not take their steps. A single module opens connections for them (backend/app/automation/egress.py; a test fails if another file of the package imports a socket or an HTTP client). It resolves the name, checks the address, connects to the address it checked, and checks every redirect again, three at most.
  • Where. By default a playbook reaches only the hosts listed for it and for every playbook. In either mode loopback, private, link-local and carrier-grade ranges, the containers of the stack and the cloud metadata address are refused, unless that host is listed by name: listing an internal system is the permission to reach it. Letting a playbook reach any host needs the double check and is in the audit log.
  • What. Values carry a class from where they are read (an incident's name, an e-mail address, a mail body) through filters, texts and scripts to where they would leave. A node sends only when every class in what it holds is one that always leaves, or one an admin opened for that playbook. E-mail bodies, attachments, samples and TLP:RED data cannot be opened. What leaves is also read as text for private addresses, internal names and allowlisted values typed by hand.
  • Approvals. A node that changes something outside asks a person first unless someone turned that off for the node or the playbook. An approval that nobody answers is never an approval.
  • Scripts are free Python, made safe by where they run. The sandbox container holds Python and nothing else (no pip, no compiler), on an internal network with no route outside, with a read-only filesystem, no capabilities, an unprivileged user and no volume. Each script runs in a new process with an empty environment and limits it cannot raise (time, 256 MB of memory, 16 open files, no other process, 1 MB of result). It receives the arguments of its node and nothing else: no secret, no instance, no file of Nik. An import hook refuses the modules that reach out; that is a second line, not the boundary.
  • What a script returns is not trusted more than what went in: it carries the classes of everything it was given, so a script cannot launder data past the guard.
  • Secrets. The SMTP password and the credentials of instances are stored encrypted with the vault key and never returned by the API: an instance says which secrets are set, not what they are. Run steps record what was sent, not credentials, and a value equal to a secret is blanked wherever it would be shown. Tokens obtained with OAuth2 and sessions opened by a connector live in memory, or encrypted in the state of a step that waits; never in a table in the clear.
  • Connectors are data, not code. A connector is a YAML file read with a safe loader and checked against a fixed format, where an unknown key is an error; its templates are the playbooks' expression language, which has no code, no loop and no way to read a file or the environment. Installing one is the role Connectors. What a connector can do is send requests: every one of them goes to the host of the instance it runs on, and a path that names another host is refused, so a file cannot be written to carry a instance's credentials elsewhere. Its requests pass through the same egress module and the same data guard as every other node. A secret can be read only in what is sent, never in what a command returns. The shipped connectors were written from public documentation and are marked not verified until someone has run them against a real system.
  • The record. What a playbook changes in Nik is signed nik-automation, an account that cannot sign in, with the run and whoever approved the step. Versions of playbooks and scripts (with the difference in a script's code), openings of network and data, approvals and the general switch are all in the audit log.
  • One address that asks for no account. POST /api/automation/hooks/<token> starts a playbook whose trigger says From outside, and is the only route added by automation that answers without signing in. The token is 32 random bytes, made by the server, shown once to whoever builds the playbook and stored as its SHA-256: a copy of the database does not give the addresses. The route never reads a cookie or an API key, so a page open in an analyst's browser cannot use their session through it. A request carries at most 256 kB; each token has 60 requests a minute, and the playbook its runs an hour. Every reason a token starts nothing (it does not exist, the playbook is off, automation is stopped) gives the same 404, and a request that is taken is told only accepted. What arrives is data from outside: it has no class of its own, credentials and proxy headers are dropped before the playbook sees the rest, and what the playbook may send on is decided by the guard above. Treat the address as a password: it appears in the sender's configuration and may appear in the access log of a proxy in front of Nik. Replace it when in doubt; creating, replacing and removing one are in the audit log.
  • Commands typed in the War Room are runs of one node on the same engine, and get nothing a playbook does not get: the permission to run playbooks, the egress rules (the host of the command's instance and the hosts listed for every playbook), the data guard with no class opened, the audit log under the name of who typed. The line is read by a small grammar of its own, not by a shell: a name, pairs of name=value, and expressions that can only read the incident and its context. A command that changes something outside is not sent until it is confirmed.
  • Tasks and questions are completed by whom they are for, and by nobody else: the user a task names, whoever holds its role, the owner of its incident at that moment, and an admin. The fields a task asks for are written through the field registry under the name of who completed it, with the checks of any other write. The instructions of a task are written by whoever builds a playbook and read by someone else: they are drawn as text, with a small Markdown read into elements and never into HTML, and a link is kept only when it is http, https or mailto. The work plan of an incident shows a node by its name and its kind, never by what it is given.
  • Fetching and mirroring. A fetch reaches the host of its own instance and nothing else, and what it brings in is data, never instructions: an item is read through the mapper, a value is checked by the field it goes to, and the item as it came is shown as text. "The same incident" of a pre-processing rule is found by columns of the incident, never by a query built from what the other side sent. An instance that makes more than 500 incidents in an hour is paused. A mirror that sends is a standing permission, given by someone who may run playbooks and recorded with their name; what it sends passes the data guard with only the classes opened for that mirror, by someone who may open them. What a person set in Nik is not written over by the other side unless the mapper says the field is authoritative.
  • Dashboards. A dashboard holds questions, never answers: each widget is asked of the server as the person looking, through the same compiler as every query, so sharing a dashboard cannot show anyone what their roles do not let them read (a widget they may not ask says so). The same holds for a dashboard made into a report: it is written with what its reader may see. A dashboard that is not yours and not shared with you answers "not found". Sharing needs dashboards.share and is written to the audit log. What a chart shows of a value (a name of an incident, a tag) is drawn as text.
  • The catalogue of packs. The packs of vendors' products are read from outside (by default the release packs of Nik's repository), so nothing of the catalogue is trusted for where it comes from. Its index is read only when its Ed25519 signature is of the key Nik holds: the public half is in the code, the private half is a secret of the repository used only by the workflow that publishes the packs from main. A pack is taken only when its size and its SHA-256 are the ones the signed index gives, and the name of its file cannot leave the folder of the index. It is then read like an uploaded pack (below) and applied only after a person saw what it would do. Reading the catalogue goes out through the same guarded path as a playbook's request, to the host of the address and no other (for GitHub, the two hosts it answers a release from); only an administrator sets another address or another key, and that is written to the audit log. A pack from the folder NIK_PACKS_DIR is not checked against a signature: whoever can write that folder on the server installs content.
  • Content packs. A pack is a file from someone else and is read as one: at most 20 MB and 2 000 files, 100 MB unpacked, no path that leaves the pack, no links, only the folders Nik knows, YAML read without building objects. Reading it changes nothing; applying it needs content.manage, happens in one transaction and is written to the audit log. A pack cannot widen what Nik may do: it never carries an instance, a credential, an allowed host or an opened class of data; a playbook it brings arrives off, reaching only listed hosts and sending no class of data; it does not replace the items of the lists Nik's own settings read, nor a field of Nik's own. A script in a pack is code: it runs where every script runs, in the sandbox, and its difference is shown before it is imported.
  • The debugger. A debug run holds what goes outside, as a dry run does. Letting one node send for real needs the permission to run playbooks besides automation.debug, asks the approval the node normally needs, passes the data guard and the egress rules like any run, and is written to the audit log; it applies to that node and that step only. Arguments typed in the debugger are values, not templates: they are never evaluated. A debug run is shown to who started it and to an administrator.
  • Lists are read by whoever reads incidents and changed with lists.manage (the roles admin and playbooks). A playbook writes only to a list that says it may, which no list does until someone who manages lists turns it on: the IoC allowlist, your domains and the hosts every playbook may reach decide what Nik hides, trusts and reaches, so a playbook cannot widen them on its own. Choosing which list a feature reads is a change of the same weight and needs the same permission; both are in the audit log. A CSV export writes a cell a spreadsheet would run as a formula so that it does not.
  • Loops and floods. A playbook's changes can start other playbooks three deep; each playbook has a ceiling of runs an hour and, by default, one run at a time on the same object; the whole server has a ceiling of runs in progress. One switch stops everything.

Accounts, sessions and the audit log

  • Passwords are hashed with bcrypt; sessions are random tokens kept on the server, 12 hours by default.
  • Sign-in is limited per client address, and an account is locked for five minutes after ten wrong passwords in a row. A password change or disabling an account ends its sessions.
  • There is always one admin that can sign in. API keys are stored as digests, carry roles and an optional expiry, and are shown once.
  • Roles are tags that add up, and every route of the API asks for a permission, never for a role: read, write, rules.manage, audit.read, admin. An account or a key may do what its roles grant together, and nothing else: a test walks every route with a key of each role, and fails when a new route does not say who may call it. The roles are read from the database on every request, so one that is taken away stops working at once. Only an admin gives roles; nobody takes the admin role away from themselves or from the last admin; nobody, admin included, can write an audit entry by hand.
  • The audit log is written by the server for every change, whoever makes it and however: the app, a script with a key, a request sent by hand. It cannot be written from the browser, and clearing it leaves an entry naming who did.
  • Changes by two people to the same incident are merged or refused, never silently overwritten.

Secrets and backups

  • The stack does not start without DB_PASSWORD, SECRET_KEY and a token per worker, and refuses the example values. deploy/init-env.sh generates them.
  • SECRET_KEY encrypts the threat-intelligence API keys and the TLS key logs stored in the database. It lives in .env, which deploy/backup.sh copies with each backup: a backup directory holds the data, the samples and the key that decrypts the secrets.
  • Treat a backup as you treat the server: it contains live malware and password hashes. Keep a copy off the host, encrypted.

Hardening checklist

  1. Create the first account yourself, at once: whoever reaches a new install first becomes its admin.
  2. Publish the HTTPS port only where analysts are (a management network, a VPN), and replace the self-signed certificate with one your browsers trust; set TLS_HOSTNAME.
  3. Decide whether the server may reach the internet at all. Without it, threat-intelligence lookups, sessions with network and address scans do not work; everything else does.
  4. On the host firewall, keep the browser-egress network away from your internal ranges and the cloud metadata address. The worker already refuses them; a second lock costs nothing.
  5. Exclude the sample store volume from the host's antivirus, or it will quarantine the evidence; do not exclude anything else.
  6. Install the nightly backup (deploy/install-systemd.sh), copy the backups off the host, encrypted, and try a restore once.
  7. Give each person an account; disable, do not delete, the account of someone who leaves.
  8. Give an account and an API key the narrowest roles that work (Viewer for a key that only reads), and a key an expiry. Keep the Admin role for the few who manage the platform: an analyst who maintains the rule sets needs Rules, not Admin.
  9. Give the Playbooks role to the people who should write automation, and to nobody else: a playbook acts with Nik's own hands. Read the audit log for automation.egress.open and automation.data.open: they say which playbook was let reach further or send more, and by whom.
  10. Keep the automation-egress network away from what playbooks have no business reaching, on the host firewall, as for the browser's. The engine already refuses internal addresses that are not listed.
  11. Update: git pull and compose up -d --build rebuild the images with the current fixes of LibreOffice, Wireshark and Chromium, which is where the next vulnerability will be.

Known limits

  • Chromium runs with --no-sandbox: its own sandbox needs privileges the container does not give, so the container is the sandbox. A browser exploit gets an unprivileged process in a container with no capabilities, a read-only filesystem and no network but the backend's and the filtered way out.
  • The backend parses some formats itself (e-mails, event logs, PE headers, YARA, QR codes), in a hardened but not disposable container that holds the database password.
  • In a session without network every request is refused by the interception, not by the proxy; the proxy would still keep anything that slipped through away from private addresses.
  • The in-app full backup does not contain samples, e-mails, captures or rule sets: deploy/backup.sh is the backup. Backups are not encrypted by Nik.
  • Analysts can read every incident: there is no per-incident access control.
  • A script can read what its own container holds, which includes the token the engine presents to the sandbox (in /proc). With it a script could ask the sandbox to run another script, which it already is: the token opens nothing else, and the container reaches nothing.
  • The data guard knows the class of what Nik gave a playbook. It cannot know what a person types into a field, beyond the patterns it scans for, nor what another system answers and a playbook forwards.
  • A playbook that may reach any host with a class of data opened can send that data anywhere a node says. That is what the double check is for; it does not make the choice safe.

Reporting a vulnerability

Please report it privately, through a GitHub security advisory, not in a public issue. Say what you did, what happened and what you expected; a sample that triggers it helps, shared the way you would share any malware. SECURITY.md in the repository has the details.
