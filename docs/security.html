Security

Nik is where a team puts the worst files it has: live malware, phishing mail, captures of an attack, the addresses of the attacker's own servers. This page says how those are kept from doing harm, what leaves the server and when, what an administrator should check, and where the limits are.

What Nik defends against

The content is the adversary. Nik assumes that:

  • every evidence file may be built to attack whatever opens it: a sample, a document with an exploit, a database with a hostile schema, a capture that crashes a dissector, a file name that is a path or a header;
  • every string taken from evidence (a URL, a subject, a host name, a string of a binary) may be markup, a script, or a lure for a click;
  • every page the isolated browser visits is run by the attacker, and will try to reach the organisation's own network through the server;
  • the analysts are trusted colleagues with accounts, not administrators: what each of them does is recorded, and what decides where data goes is an admin's to set.

It does not defend against an attacker who already controls the server's host, nor against an administrator.

How hostile content is contained

Samples are never executed: there is no sandbox that detonates them. They are read, disassembled and matched against rules. Each kind of content is handled by the part with the least access that can do the job:

Container Handles Network Can read
analyzer (rizin) disassembly and decompilation of samples internal only, no route outside the sample store, read-only
capa capabilities of samples internal only the sample store, read-only
docview (LibreOffice, pdfium) previews of documents: macros disabled, links never updated internal only only the document it is sent
pcap (tshark, sharkd) packet captures internal only the sample store, read-only
browser (Chromium) HTML attachments and addresses its own network to the backend, and a route to the internet through a filtering proxy; no network shared with the other workers only the page it is sent
api everything else: e-mails, event logs, static analysis of samples, the report the database, the workers, the internet for threat-intelligence lookups the sample store, read-write

Every one of them runs as an unprivileged user on a read-only filesystem, with all capabilities dropped, no-new-privileges, and memory, CPU and process limits. A worker is reached with a token of its own, compared in constant time; none of them can reach the database. The database is on a network the workers are not on.

The isolated browser is the one part that runs attacker code on purpose. Without network (the default) only the attachment loads and every request is refused. With network, Chromium's only route is a proxy inside the worker that resolves each name itself, refuses unless every address is public, and connects to the address it checked: a redirect to 10.0.0.1, a name that changes its answer between the check and the connection, a cloud metadata address, all go nowhere. What a page submits is held until the analyst releases it. Downloads are refused, dialogs dismissed, permissions denied.

Limits on what a file can make the server do

  • Size: every upload has a limit, enforced while the file is read (SAMPLE_MAX_MB, ARTIFACT_MAX_MB, PCAP_MAX_MB).
  • Time: an analysis has a time limit that ends the work for real: a tool that stalls is killed with everything it started, and a preview is made in a process of its own.
  • SQLite files (browser databases) are opened read-only, with their schema untrusted, a time budget and a row limit: a view over an endless query in place of a table costs twenty seconds, not the server.
  • Names from evidence never become paths or commands: files are stored under their SHA-256 or an identifier, tools are given neutral names, and a download is offered under a name with separators, control characters and text-direction marks replaced.
  • E-mail: the HTML is sanitised on the server; only the first five DKIM signatures are verified; an image that declares a huge size is refused before it is decoded.
  • Reports: every value is escaped, and the PDF renderer fetches nothing, so a logo or a value that points at a URL or a local file is not followed.

What reaches the analyst's browser

  • A picture, not the page: the isolated browser sends screenshots, documents are shown as page images.
  • Hostile HTML (an e-mail body, a captured page, the report preview) is drawn in a frame that runs no script and loads nothing, with its links, forms and redirects disarmed and remote references removed from its styles. Remote images of an e-mail load only when the analyst asks, and tracking pixels never.
  • Addresses from evidence are not links: opening one asks first, shows it defanged, and only http(s) can be opened.
  • Samples are downloaded only inside a password-protected zip (infected by default), so nothing on the way, nor the workstation's antivirus, runs or deletes them by accident.
  • The app's pages carry a Content-Security-Policy that lets only its own scripts run and lets it talk to its own origin only, with X-Content-Type-Options, X-Frame-Options, Referrer-Policy and HSTS. The session cookie is HttpOnly, Secure and SameSite=Lax; nothing sensitive is kept in the browser's storage.

What leaves the server

Nothing, unless one of these is turned on or asked for:

What When What is sent
Threat-intelligence lookups when an admin has entered a provider's key; automatic lookups only for the indicator types an admin switched on the indicator (a hash, a domain, an address), to that provider. Never a private or internal value, one on the allowlist, or one of an incident marked TLP:RED
The isolated browser, with network when an analyst opens a session with network, or scans an address ordinary web requests from the server's address; what the page submits only if released
Mail authentication checks when an e-mail is uploaded or re-analysed DNS queries for the sender's SPF, DKIM and DMARC records (the sender's DNS sees them)
Webhooks when an admin subscribed a URL through the API the event (an incident created, an upload finished), signed

The app's own pages load nothing from outside: no CDN, no fonts, no telemetry.

Accounts, sessions and the audit log

  • Passwords are hashed with bcrypt; sessions are random tokens kept on the server, 12 hours by default.
  • Sign-in is limited per client address, and an account is locked for five minutes after ten wrong passwords in a row. A password change or disabling an account ends its sessions.
  • There is always one admin that can sign in. API keys are stored as digests, carry a role, scopes and an optional expiry, and are shown once.
  • The audit log is written by the server for every change, whoever makes it and however: the app, a script with a key, a request sent by hand. It cannot be written from the browser, and clearing it leaves an entry naming who did.
  • Changes by two people to the same incident are merged or refused, never silently overwritten.

Secrets and backups

  • The stack does not start without DB_PASSWORD, SECRET_KEY and a token per worker, and refuses the example values. deploy/init-env.sh generates them.
  • SECRET_KEY encrypts the threat-intelligence API keys and the TLS key logs stored in the database. It lives in .env, which deploy/backup.sh copies with each backup: a backup directory holds the data, the samples and the key that decrypts the secrets.
  • Treat a backup as you treat the server: it contains live malware and password hashes. Keep a copy off the host, encrypted.

Hardening checklist

  1. Create the first account yourself, at once: whoever reaches a new install first becomes its admin.
  2. Publish the HTTPS port only where analysts are (a management network, a VPN), and replace the self-signed certificate with one your browsers trust; set TLS_HOSTNAME.
  3. Decide whether the server may reach the internet at all. Without it, threat-intelligence lookups, sessions with network and address scans do not work; everything else does.
  4. On the host firewall, keep the browser-egress network away from your internal ranges and the cloud metadata address. The worker already refuses them; a second lock costs nothing.
  5. Exclude the sample store volume from the host's antivirus, or it will quarantine the evidence; do not exclude anything else.
  6. Install the nightly backup (deploy/install-systemd.sh), copy the backups off the host, encrypted, and try a restore once.
  7. Give each person an account; disable, do not delete, the account of someone who leaves.
  8. Give an API key the narrowest role and scopes that work, and an expiry.
  9. Update: git pull and compose up -d --build rebuild the images with the current fixes of LibreOffice, Wireshark and Chromium, which is where the next vulnerability will be.

Known limits

  • Chromium runs with --no-sandbox: its own sandbox needs privileges the container does not give, so the container is the sandbox. A browser exploit gets an unprivileged process in a container with no capabilities, a read-only filesystem and no network but the backend's and the filtered way out.
  • The backend parses some formats itself (e-mails, event logs, PE headers, YARA, QR codes), in a hardened but not disposable container that holds the database password.
  • In a session without network every request is refused by the interception, not by the proxy; the proxy would still keep anything that slipped through away from private addresses.
  • The in-app full backup does not contain samples, e-mails, captures or rule sets: deploy/backup.sh is the backup. Backups are not encrypted by Nik.
  • Analysts can read every incident: there is no per-incident access control.

Reporting a vulnerability

Please report it privately, through a GitHub security advisory, not in a public issue. Say what you did, what happened and what you expected; a sample that triggers it helps, shared the way you would share any malware. SECURITY.md in the repository has the details.
