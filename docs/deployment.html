Quick start with Docker / Podman

The fastest way to run the whole stack — nginx (static SPA + /api reverse proxy), the FastAPI backend and PostgreSQL — is the bundled Compose file: 

deploy/init-env.sh            # writes .env, and the secrets as files in ./secrets
docker compose up -d --build  # build the images and start the whole stack

Open https://localhost:8443 and create the first user — that account becomes the admin, so do it before anyone else can reach the port. The database schema is created and migrated by the api container at every start.

The stack does not start without its secrets (DB_PASSWORD, SECRET_KEY, STORE_KEY and one token per analysis worker) and refuses the values printed in .env.example, which are public. deploy/init-env.sh generates them, each into a file of ./secrets (Keys of the server); it is safe to run again. Keep a copy of that directory away from the server.

On first start the web container self-signs a TLS certificate, so the browser shows a one-time "connection not private" warning — accept it to proceed (or mount a real certificate, see Docker / Podman in production). Nothing is served over plain HTTP: http://localhost:8080 redirects to the HTTPS address. 

docker compose logs -f api    # follow backend logs
docker compose ps             # container status
docker compose down           # stop (keeps the database volume)
docker compose down -v        # stop AND delete every volume: database, samples, certificate

Podman is a drop-in replacement (rootless is fine for ports 8080/8443):

deploy/init-env.sh
podman-compose up -d --build  # or: podman compose up -d --build

Every image in the Dockerfiles and the Compose file names its registry (docker.io/...), so Podman never has to guess one from /etc/containers/registries.conf (on RHEL it would try registry.redhat.io first and ask for Red Hat credentials). Keep it that way when you add an image: deploy/check-images.sh (run by CI) fails on a short name.

Production deployment

Upgrading from a "CSAP"-era deployment? The database role and name are now nik (was csap). A pre-existing Postgres volume still holds the old csap role/database, so either start on a fresh volume (docker volume rm nik_db-data-18 / your project's *_db-data-18), or keep the old names by setting DB_USER, DB_NAME and the compose POSTGRES_* back to csap, or rename in place with ALTER ROLE csap RENAME TO nik; and ALTER DATABASE csap RENAME TO nik;. The session cookie also changed name, so everyone re-logs in once.

Docker / Podman in production

The Compose stack serves the app over HTTPS on :8443; :8080 only redirects there. On first start the web container self-signs a certificate (for TLS_HOSTNAME, default localhost) into the web-certs volume, so HTTPS works out of the box — browsers show the usual warning until the certificate is trusted or replaced. Set TLS_HOSTNAME to the name users type, and for a real deployment pick one of:

  • Option A (recommended): provide your own certificate — internal CA or Let's Encrypt — as nik.crt / nik.key in /etc/nginx/certs; the startup script never overwrites an existing pair. Easiest wiring: swap the named volume for a bind mount in docker-compose.yml (- ./certs:/etc/nginx/certs).
  • Option B: front the stack with a host reverse proxy that terminates TLS (nginx, Caddy, Traefik) proxying to https://127.0.0.1:8443 (the upstream certificate is the self-signed one: tell the proxy to accept it), and bind the two port mappings to 127.0.0.1.

To regenerate the self-signed certificate (e.g. after changing TLS_HOSTNAME): docker compose down && docker volume rm nik_web-certs, then start the stack again.

Notes for Podman on RHEL:

  • Rootless works out of the box — only host ports below 1024 require rootful Podman (or lowering net.ipv4.ip_unprivileged_port_start).
  • Start on boot: restart: unless-stopped does not bring the stack back after a reboot with podman-compose. Install the systemd units (next paragraph): nik.service runs podman compose up -d at boot.
  • SELinux: named volumes (as used here) are relabeled automatically. If you switch to a bind mount, add :Z to that mount.

Start on boot (systemd). From the repository root, as root:

sudo deploy/install-systemd.sh

It installs and enables nik.service, with the repository path and the compose command (podman compose, or docker compose where Podman is absent) filled in: compose up -d at boot, compose down at shutdown. Options: --dir, --compose, --uninstall. Before 6.7 it also installed a nightly nik-backup.timer; the server takes its backups itself now, and the script removes that timer where an earlier run left it.

Keys of the server

The stack has two keys that encrypt, a database password and a token for each worker. The security guide says what each protects and which container holds it; Settings → System → Keys shows where each one comes from on this server and when it last changed. This is the operator's side.

Where they are kept

A new install keeps them in files. deploy/init-env.sh makes ./secrets beside docker-compose.yml, a directory only you can enter, with one file for each secret, and writes NIK_SECRETS_DIR=./secrets in .env, which then holds no secret (the lines SECRET_KEY=, DB_PASSWORD=… stay, empty: Compose asks for them by name). Each container is given the files it uses and no other, read-only, under /run/secrets. Nothing else is needed: podman compose up -d --build as before.

  • The directory is mode 700 and the files in it 644: what protects them is the directory. The containers run as users that are nobody on the host, and neither Docker nor rootless Podman changes who owns a mounted file, so a file only its owner could read would be unreadable to the server. Create the directory as the user that runs the stack.
  • To keep it elsewhere, set NIK_SECRETS_DIR to an absolute path: another disk than the data, a volume that is unlocked at boot, a mount of another machine. A store key that sits on the disk it protects does not protect a host that is stolen whole.
  • Keep a copy of the directory away from the server. SECRET_KEY with the backups (the secrets inside a backup are under it), STORE_KEY apart from them. If the store key is lost with the host nothing is lost with it: a backup holds the files themselves, under its passphrase.
  • The files are mounted with the option z, which gives them the SELinux label a container needs to read them. A directory outside the folder of Nik may need it once by hand: chcon -Rt container_file_t /srv/nik-secrets.
  • podman secret / docker secret work too, with a Compose override that mounts each secret at the same /run/secrets/<name>: the server reads whatever file <NAME>_FILE names. The Compose file does not use secrets: itself because external secrets exist only under Podman, and file secrets are mounted without the SELinux label there.

A server from before 6.8 keeps them in .env, and goes on working that way: the Compose file mounts the empty files of deploy/no-secrets in the place of each secret, an empty file counts as none, and the values come from the environment as before. The administrators are told once, in Nik, that the keys are in the environment. To take them out: 

deploy/secrets.sh status      # where each secret is; never a value
deploy/secrets.sh move        # from .env into ./secrets

move writes each secret into a file, keeps the .env as it was in .env.before-secrets, writes an .env that names the directory and holds no secret, makes the containers again on it (about a minute) and checks that the server answers and reads its keys from the files. If it does not, it puts the .env back and starts the stack on it again: nothing was moved. It can be run twice. At the end .env.before-secrets still holds every secret in clear: destroy it (shred -u) or lock it away once you have seen the server work. A secret must never be in both places: the server refuses to start and says which one is given twice.

Changing a key

Ask for it in Settings → System → Keys → Rotate… (a signed-in administrator, with the password again and a code when the account has a second factor): the dialog counts what will be put under the new key and shows the command. Then, on the server, within a day: 

deploy/secrets.sh rotate secret-key     # or: rotate store-key
  1. The running server makes the new key; the script writes it straight where the keys are kept (it is never on a screen) and keeps the key in use beside it as the earlier key.
  2. It restarts the containers that hold the key: api and automation for SECRET_KEY, api alone for STORE_KEY. Nik does not answer for the time of that restart, about a minute.
  3. The server puts everything under the new key and reads it back with the new key alone. The script waits and shows how far it is; the Keys page shows the same. For SECRET_KEY this takes seconds. For STORE_KEY only the head of each file is rewritten and written to the disk, then each file is opened once with the new key: the time goes with the number of files, not with their size.
  4. Once the server says the change is verified, the script moves the earlier key into secrets/retired/, which nothing reads, restarts the same containers once more so that they forget it, and says what to do with that file: keep the earlier SECRET_KEY with the backups taken before the change (their secrets are under it) and destroy it when they are gone; destroy the earlier STORE_KEY unless you keep copies of the store volume made before.

Stopped at any step, it is run again and goes on: until the change is verified the server holds both keys and everything is readable. If the server says it could not put something under the new key, the script stops, shows what, and leaves the earlier key in place. Run when nobody asked in Nik, it says so and asks before going on (--yes answers for it). On a server that keeps its keys in .env it edits .env instead and makes the containers again. deploy/secrets.sh rotate tokens writes new tokens for the workers and restarts the stack; the database password is changed in PostgreSQL first (ALTER ROLE nik PASSWORD '…'), then where the keys are kept.

"Nik did not start": a key is missing or is not the right one

When a key is missing, is still an example value, is given both as a file and in .env, sits in a file the server cannot read, or when STORE_KEY is not the key the store is sealed under, the api container does not exit and does not start either: it answers every request with the sentence that says what is wrong, the page shows it, and the same lines are in podman compose logs api. Nothing is written meanwhile. Set it right and start again:

  • is not set: deploy/init-env.sh writes what is missing and changes nothing else;
  • is given twice: remove the value from .env (or run deploy/secrets.sh move, which does it for all of them);
  • cannot be read: the file must exist and be readable by everybody inside a directory only you can enter (chmod 700 secrets; chmod 644 secrets/*);
  • is not the key the store is sealed under: the message gives the fingerprint of the key the store expects and of the one given. Put back the store key this server had. A server restored from a backup never meets this: its files were sealed under its own key as they were written.

The store of a server from before 6.8

Its files are in clear. At the first start with a store key the server begins to seal them in the background, one at a time (each is read, sealed beside itself, read back, compared, and only then put in the place of the clear one), while it is used as before: both forms are read, and new files are sealed as they arrive. Settings → System → Storage shows how many files and bytes are done, how long is left, and a Pause; the administrators are told when it has ended, or when a file is stuck. It needs the room of the largest file, never a second copy of the store, and goes on where it was after a restart.

  • It reads at most STORE_SEAL_MBPS megabytes a second (40 unless set in .env; 0 is as fast as the disk goes): about half a minute for each gigabyte at 40.
  • Until it has ended, the files it has not reached are in clear on the disk, as they were before the upgrade.
  • A file there is no room for, or that cannot be read, is listed on the Storage page and tried again every ten minutes. Once the store is sealed, a file put back by hand from a copy made before 6.8 is refused until Check again on that page has sealed it.

The work volumes

No worker mounts the store any more. The packet capture worker has a volume of its own, pcap-work, as the document worker has pst-work: a capture larger than PCAP_MEMORY_FILE_MB (64) is kept there, in clear, while it is open, and both volumes are emptied when their worker starts. They hold nothing to back up. To keep even a large capture off the disk, replace the volume with a tmpfs in a Compose override and give the worker the memory for it.

Backups

A backup can only be read with its passphrase. Whoever restores types it; if it is lost, every backup made under it is lost, and nobody can recover it. Write it down when you set it, and keep it away from the server.

Nik takes its own backups. Nothing has to be installed for it: the API container writes them, on a schedule, into the backup directory; it tests each one by restoring it; the automation container sends a copy to another machine; and every administrator is told when any of this goes wrong. It is set and watched in Settings → System → Backup (the screen).

What a backup holds, and what it does not

One file, nik-YYYYMMDD-HHMMSS.nikbak, encrypted from its first byte of content to its last:

  • the database, as it was at one moment: incidents, accounts, settings, the audit log, the analyses, playbooks, connectors and their instances (whose secrets are in it as they are in the database: encrypted under SECRET_KEY);
  • the store of files, whole: samples (live malware), e-mails, captures, mailboxes, screenshots, added rule files. On the disk they are sealed under the store key; in the backup they are the files themselves, under the backup passphrase like everything else, so a backup is read with its passphrase alone;
  • a manifest: the version of Nik, the revision of the database, when it was taken, the number of rows of every table, the number and size of the files, and the size and SHA-256 of every part.

Beside it, nik-….json says in clear what the file is and how its restore test went. No secret.

Not in a backup, to keep somewhere else:

  • .env and the secrets directory, and in them SECRET_KEY. Without the SECRET_KEY the backup was made under, a restored server works, but the stored secrets (keys of instances, credentials, TLS key logs) cannot be read and have to be entered again. The store key is not needed to restore: the server that restores seals the files under its own. The screen can put the key inside the encrypted backup (Include SECRET_KEY, off by default): then a backup and its passphrase are enough to bring everything back, and are also enough, for whoever holds both, to read every stored secret. It is never written anywhere in clear;
  • the TLS certificate and its key (the web-certs volume, or the files you mounted);
  • your Compose overrides and anything else you added to the deployment.

Where backups go

By default into the volume backups of the stack. A backup on the disk it protects is of little use when that disk fails: point the stack at another disk, or at a mount of another machine, in .env: 

NIK_BACKUP_DIR=/srv/nik-backups     # a directory of the host, in place of the volume

The API container hands the directory to its unprivileged user (uid 10001 inside the container) at its first start; with rootless Podman create it as the user that runs the stack. Where SELinux is enforcing, label a directory of the host for the containers once: chcon -Rt container_file_t /srv/nik-backups (the volume needs nothing). The automation container mounts the same place read-only. The room a backup needs is about the size of the database plus the size of the store (rows compress, samples mostly do not), and Nik refuses to start one the directory has no room for.

When, how many, and the restore test

The schedule is set on the screen: every few hours, every day at a time, or every week, in the time zone you name. Until you change it a backup is taken every six hours, counted through the day from 02:30 UTC: at 02:30, 08:30, 14:30 and 20:30. What is written between two backups is what a lost server loses: at most six hours with this schedule. It runs once a passphrase is set. Back up now and deploy/backup.sh ask for one more, the same way. Never two at once, and none while a release is migrating the database.

A file is written under ….nikbak.partial and renamed when its last byte is on the disk: a file with the name of a backup is always a whole one, and what a run that died left is removed by the next.

Each backup is tested at once. The file is read back from the directory; every chunk is decrypted; the size and checksum of every part are compared; the database is restored into a scratch database (nik_scratch_…, owned by a role made for it that owns nothing else, dropped whatever happens), where its schema, its revision and the number of rows of every table are compared with what was written, and a few questions are asked of it; every file of the store is compared with its checksum. The test reads the whole backup whatever its size. A backup that fails it is marked, is not counted by the retention, and the administrators are told.

What is kept: the latest N good backups (8: two days of them), and the latest good one of each of the last M weeks (4). The last good backup is never removed, however many newer ones failed. Snapshots taken before upgrades have a count of their own (3). A backup holds the whole store each time, whatever changed since the one before: twelve kept backups take about twelve times the size of one. The screen says how much the kept backups take now, and how much the chosen numbers lead to at the size of the last one; the directory is called nearly full when less than a tenth of it is free, or less than twice the size of the last backup (the next one is written before an older one is removed).

How long it takes. A backup reads the database and the store once, and its test reads the file once: both grow with the amount of data, and with little else. On the machine the release was tested on (a laptop with an NVMe disk), a store of 800 MB was written in 4 seconds and tested in 2; a database of 1.3 GB (three million rows) was written in 9 seconds, into a file of 118 MB, and tested in 16. Tens of gigabytes are a matter of minutes there, and of the speed of the disks on a server. Each backup says how long it and its test took (summary.seconds and verify.seconds in GET /api/backups).

What the administrators are told

One notice inside Nik when a problem appears, one when it is solved, nothing in between: a backup failed; a backup failed its restore test; the schedule passed and none started; the last good backup is older than the age set on the screen (13 hours: two runs missed, and an hour); the backup directory is nearly full; the copy off the server failed or has waited six hours; no passphrase is set a day after the server was installed. The API container and the automation container both watch, so the notice comes even when one of the two is the thing that stopped. Every run, test, copy, download, deletion and change of settings is in the audit log (backup.*).

The copy off the server: SFTP to a second host

The backend has no route outside its networks, and backups do not give it one: the copy is sent by the automation container, the one that already has a way out, straight to the host you name (SFTP does not go through an HTTP proxy: the second host must be reachable from the first). On the second host:

  1. Create an account that can do nothing else, and the directory: 
    sudo useradd --system --create-home --shell /usr/sbin/nologin nikbackup
sudo mkdir -p /srv/nik-backups/incoming
sudo chown root:root /srv/nik-backups && sudo chmod 755 /srv/nik-backups
sudo chown nikbackup: /srv/nik-backups/incoming && sudo chmod 700 /srv/nik-backups/incoming
  2. On any machine, make a key for this alone, with no passphrase of its own (Nik keeps it encrypted): 
    ssh-keygen -t ed25519 -N "" -C nik-backups -f nik-backups-key
    Put nik-backups-key.pub in /home/nikbackup/.ssh/authorized_keys on the second host.
  3. Limit the account to SFTP inside that directory, in /etc/ssh/sshd_config, then reload sshd: 
    Match User nikbackup
    ChrootDirectory /srv/nik-backups
    ForceCommand internal-sftp
    AllowTcpForwarding no
    X11Forwarding no
    PasswordAuthentication no
  4. Read the host key of the second host on the second host: cat /etc/ssh/ssh_host_ed25519_key.pub (the two first words), or its fingerprint with ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub.
  5. In Settings → Backup, turn on the copy: host, port, account nikbackup, directory /incoming (the path as the account sees it inside its chroot), the private key pasted (or the name of a stored credential), and the host key from step 4. Save, then Test the destination: it signs in, writes a small file, reads it back and removes it, and shows the key the server presented.

Nik never trusts a host key on first sight: a destination with no pinned key receives nothing, and one that presents another key receives nothing and the administrators are told. A backup is sent once it has passed its restore test, as <name>.nikbak.partial renamed at the end; a transfer that is cut is resumed where it stopped (three times in a pass, then again an hour later); what arrived is read back and its size and SHA-256 are compared with the local file before the copy is counted. The .json of the backup goes beside it. What the retention removes on the first host is removed on the second. The snapshots taken before upgrades are copied too, once the upgraded server is up (the upgrade never waits for the copy, and a copy that fails is told like any other), and the latest three are kept there as here.

The directory of the second host then holds, flat: nik-YYYYMMDD-HHMMSS.nikbak and nik-YYYYMMDD-HHMMSS.json for each backup kept.

Restoring

Restoring is done on the server, from the command line, with the stack stopped: never by a button on a running server. deploy/restore.sh does all of it, with Docker and with Podman, rootless too: 

deploy/restore.sh nik-20261120-023000                      # a backup of this stack's backup directory
deploy/restore.sh /mnt/copy/nik-20261120-023000.nikbak     # a file brought from elsewhere
deploy/restore.sh --inspect nik-20261120-023000            # only read it and say what it holds

It asks for the passphrase (or reads it from NIK_BACKUP_PASSPHRASE or the file named by NIK_BACKUP_PASSPHRASE_FILE, for a restore nobody attends; never from the command line), stops the stack and starts the database alone, then reads the whole file and compares every checksum. Nothing is changed before that has passed. It refuses a database or a store that is not empty unless you add --replace, which replaces both with what the backup holds. The database arrives in one transaction. Then it starts the stack, checks that the server answers, and says what to look at. --database-only leaves the files alone; --no-start leaves the stack stopped; --secret-key first writes the SECRET_KEY a backup holds where the keys of the stack are kept: into the secrets directory (keeping the key as it was beside it, as secret_key.before-restore), or into .env on a server that keeps them there (keeping the file as it was in .env.before-restore). Every file of the store is sealed under the store key of this server as it is written.

Versions. A backup made by the version that is installed, or by an earlier one, is restored as it was; an older one is migrated by the server at its next start, after a snapshot and a rehearsal, like any upgrade. A backup made by a later version is refused with the version to check out: this code does not know what it holds.

The first host is gone: bring Nik up on the second

What you need: the second host with Docker or Podman and git, the backups it received (/srv/nik-backups/incoming), the backup passphrase, and the SECRET_KEY of the first host (from wherever you keep the copy of its secrets; or inside the backups, if you chose to include it). The store key of the first host is not needed: the second host makes its own.

  1. Get the code, at the version that took the backup or a later one (the .json beside each backup names it, in clear): 
    git clone https://github.com/n36l3c7/Nik.git /opt/Nik && cd /opt/Nik
grep '"nik"' /srv/nik-backups/incoming/nik-20261120-023000.json
git checkout v6.7.0
  2. Make the settings and the secrets of this host (a store key of its own among them), then put the old SECRET_KEY in its file (skip that if the backup holds the key: step 3 writes it): 
    deploy/init-env.sh
$EDITOR secrets/secret_key     # the SECRET_KEY of the first host, on one line
$EDITOR .env                   # TLS_HOSTNAME, ports
  3. Restore the latest backup that is marked verified ("passed": true in its .json): 
    sudo install -d -m 755 /srv/nik-restore
sudo ln /srv/nik-backups/incoming/nik-20261120-023000.nikbak /srv/nik-restore/    # a link, not a copy
sudo chmod 644 /srv/nik-restore/nik-20261120-023000.nikbak
deploy/restore.sh /srv/nik-restore/nik-20261120-023000.nikbak
# with the key inside the backup:  deploy/restore.sh --secret-key /srv/nik-restore/nik-….nikbak
    The directory of the backup account is closed to every other user, and the restore runs in a container as a user that is nobody on the host: so the file is first given a second name in a folder that is open (it is encrypted). The script says so if it cannot read the file. It builds the images at its first run, asks for the passphrase, restores and starts the stack.
  4. Sign in with an account of the first host: its password, its second factor and its recovery codes are as they were. Nobody is signed in on a restored server: the sessions that were open when the backup was taken are ended, with the sign-ins that were half-way and the count of failed ones; the accounts, their second factors and the sign-in policy are kept (if the policy lists administrators' networks that do not exist around this host, python -m app.account in the api container clears them: Sign-in and sessions). Check the list of incidents, open a file of the store, look at Settings → System → Workers and at an instance of a connector (its key is readable only with the right SECRET_KEY).
  5. Put the TLS certificate in place, point the name of the service at this host, and set up Settings → Backup again for where this host should now send its own copies: the destination that was restored is this very machine. Set the passphrase again if SECRET_KEY changed.

How long. A restore reads the file twice, once to verify it and once to write. On the machine the release was tested on, the backup of an 800 MB store was restored in 14 seconds and a database of 1.3 GB in 12; the stack then starts in under a minute once its images are built. Building all the images on a host that never ran Nik took two minutes there and depends on the network: that, with installing the engine and getting the code, is where the time of a recovery goes, so do it once on the second host before it is needed. What is lost is what was written after the last backup that reached the second host: with a backup every N hours, at most N hours and the time of a backup.

The file format, and reading a backup without Nik

The format is versioned (format 1) and described in full at the top of backend/app/backups/container.py, which is also a program that needs only Python and the cryptography package, and can be copied out and run alone: 

python container.py list nik-20261120-023000.nikbak            # the parts, their sizes and checksums
python container.py extract nik-20261120-023000.nikbak out/    # every part as a file, and manifest.json

In short: a clear header (format, cipher, how the key is derived, nothing secret), then the content in chunks of one megabyte, each encrypted and authenticated with AES-256-GCM under a key derived from the passphrase with scrypt and a salt of the file. The number of a chunk and whether it is the last are part of what is authenticated, so a file that was changed, reordered or cut short is refused. Inside: the description of the database schema (db/schema.json), one part for each table in the text format of PostgreSQL's COPY (db/<table>.copy, loadable with \copy), the store as a tar (store.tar) and its index. A later Nik reads the backups of an earlier one.

The database part is not a pg_dump: the image holds no PostgreSQL client. It carries tables, columns, defaults, constraints, indexes, sequences, enumerated types and extensions, which is all Nik makes, and a backup stops with a sentence if the database holds anything else (a view, a trigger, a function of your own, a table in another schema) instead of leaving it out. Owners and privileges are not carried: everything belongs to the role that restores.

A backup taken before 6.7

The directories deploy/backup.sh wrote before 6.7 (db.dump, samples.tar, env, SHA256SUMS) stay where they are, unencrypted, and are restored as before, with the version that wrote them (B = the backup directory): 

cd "$B" && sha256sum -c SHA256SUMS
podman exec -i nik_db_1 pg_restore -U nik -d nik --clean --if-exists < "$B/db.dump"
podman exec -i nik_api_1 tar -C /app/samples -xf - < "$B/samples.tar"
podman restart nik_api_1

Once the server has taken and verified backups of its own, remove them: they hold the samples and the .env in clear.

Updates, and the snapshot before each

git pull
podman compose up -d --build    # rebuild images, recreate containers, keep data

Release notes say when an update needs more than this. When a release changes the database, the API container does this before it serves, and says each step in its log (compose logs api):

  1. it takes a lock, so that a second instance waits and no backup starts; it checks that the database is at a revision it knows, that the server is a PostgreSQL it runs on, and that the backup directory has room;
  2. it takes a snapshot of the database into the backup directory (nik-upgrade-….nikbak, marked Before the upgrade from X to Y), in the format of every backup, encrypted with the backup passphrase, or with a key derived from SECRET_KEY while no passphrase is set (the first upgrade from 6.6): never in clear. The files are not in it: no migration touches them;
  3. it rehearses: the snapshot is restored into a scratch database (nik_rehearsal_…) and the migrations are run there;
  4. only then it migrates the database itself.

The snapshot and the rehearsal add to that start the time of a backup of the database alone and of its restore, and the migrations run twice: about two seconds in all for a small database on the machine the release was tested on; for a database of 1.3 GB, 9 seconds for the snapshot and, measured as the restore test of a backup of that database, about 16 for the restore of the rehearsal. On a database too large to copy at every upgrade, NIK_UPGRADE_REHEARSAL=false in .env skips step 3, never the snapshot. If the role Nik uses may not create a database (an external PostgreSQL), the rehearsal is skipped with a warning in the log; ALTER ROLE nik CREATEDB gives it back.

While a long upgrade runs the API container does not answer its health check yet, and Compose may call it unhealthy after a few minutes: it is not restarted, and its log says where it is. The automation container waits until the database is at the revision of its code before it runs anything.

An upgrade went wrong

When the rehearsal or the migrations fail, the API container does not exit and restart for ever: it stays up, says what happened in its log under NIK DID NOT START: THE UPGRADE WAS STOPPED, and answers every request with a sentence, which the web page shows in place of the sign-in.

  1. Read the reason: podman compose logs api. It says which of the two cases this is.
  2. The rehearsal failed (the migrations fail on a copy of this database): the database was never touched and there is nothing to put back. Go back to the version that worked and start it: 
    git checkout v6.6.0 && podman compose up -d --build
    Then report the lines of the log.
  3. The migrations failed on the database itself, or the new version started and you want the old one back: list the snapshots, and put back the one taken before the upgrade: 
    deploy/rollback.sh                                   # lists them, with the version each goes with
deploy/rollback.sh nik-upgrade-20261120-101500
    It stops the stack, verifies the snapshot and replaces the database with it (one transaction), checks out the tag the snapshot names when the folder is a git clone with nothing uncommitted (otherwise it tells you exactly which version to put there, and leaves the stack stopped), starts the stack and checks that the server answers. --no-checkout never touches the code. Running it twice does no harm. Back to a version before 6.8, which reads its store in clear and its secrets in .env, it does two things more, with the code that is still there: it unseals every file of the store (one at a time, each compared before it takes the place of the sealed one; if one cannot be opened it stops before the database is touched and says which), and it puts the secrets back into .env if they had been moved to files.
  4. Sign in and look at the latest incidents. What was written after the upgrade is not in the snapshot: it is lost. Everybody signs in again: a database that is put back keeps no session. What the files of the store hold is untouched: no release so far changes it, and a rollback refuses a snapshot whose upgrade did. (6.8 seals them, and a rollback to an earlier version unseals them: the same bytes either way.)
  5. A snapshot taken while no passphrase was set is read with the SECRET_KEY of the server; otherwise the rollback asks for the backup passphrase.

When a worker is down

The backend checks the workers it is configured with every 30 seconds: each analysis worker whose *_URL is set (analyzer, capa, document viewer, isolated browser, packet capture, script sandbox) by its GET /health, and the automation container by its heartbeat. A worker that has not answered for two minutes without a break is down: every account with the Admin role gets one notification that names it, says since when and what waits meanwhile. One more follows when it answers again, with how long it was down. Nothing is sent in between, and a container that restarts for an update is back well within the two minutes, so it tells nobody.

  • The check runs in the backend, not in the automation worker, so that it still runs when that worker is the one that is down. With several backend processes one of them checks at a time, and what was found is kept in the database: a restart of the backend, or a second process, does not send a notice twice.
  • A worker that is not configured is not watched: an install without the analysis workers, or with AUTOMATION_WORKER=off (or inline, where the loop is a thread of the backend itself), gets no notice about them.
  • Settings → System → Workers shows every worker and its state at any time; the notifications lead there. Then look at the container: podman compose ps, podman compose logs -f <service>.

Sign-in: the client's address, and getting back in

The rules of signing in are an admin's, under Settings → Sign-in and sessions (the guide has them, Security how they hold). Two things about them are the operator's.

The client's address. The waits after failed sign-ins are counted per address, and administrators can be held to listed networks: both need the backend to know where a request comes from. The browser talks to the web container, which passes the request on and writes the address it saw in X-Forwarded-For. The backend believes that header only from the proxies named in TRUSTED_PROXIES (host names, addresses or networks; web in the Compose file, looked up again every half minute), and ignores it from anybody else. FORWARDED_ALLOW_IPS stays empty, as the Compose file has it: with * gunicorn would rewrite the address from the header for whoever sends it. If you keep a Compose override or an .env that sets it, remove it.

What the web container itself sees depends on the container runtime:

Set-up The address the backend gets Per-address waits, administrators' networks
Docker Engine on Linux, as root (the default) The client's own, for clients on other machines. A browser on the server itself arrives from the gateway of the container network. Work.
Podman as root The client's own, as with Docker Engine. Work.
Rootless podman (and rootless Docker) One address for everybody, an address of the container network: published ports are forwarded by a process of the user (rootlessport), which opens a new connection to the container. Do not work. The policy page says so and refuses a list of networks; failures are counted per account only.
Docker Desktop (Windows, macOS) One address for everybody, the gateway of the container network. Do not work, as above.

The policy page shows the address the server sees you at, and says when that address is one of the server's own container network rather than yours: look at it from another machine before listing networks. Under rootless podman the way to give the backend real addresses is to run the stack with podman as root. A reverse proxy on the host in front of the published port does not help as the stack is: the web container replaces X-Forwarded-For with the address it saw itself, on purpose, so what that proxy wrote is lost. Where the addresses cannot be known, leave the administrators' networks empty and rely on the second factor.

In a manual deployment, where nginx and the backend share the host, there is nothing to set: with FORWARDED_ALLOW_IPS unset, gunicorn believes the header from 127.0.0.1, which is that nginx and nobody else. Do not set it to *.

Getting back in. Somebody who lost the phone uses a recovery code; without the codes, an admin resets their second factor under Accounts. For the last administrator who lost everything, and for a list of networks that leaves no administrator in, there are two commands, run on the server in the backend's container. Whoever can run them already holds the database and the secret key, so nothing is asked; each writes what it did in the audit log, under the name server console. 

# Take the second factor of an account away: it signs in with its password and sets one up again.
podman compose exec api python -m app.account reset-second-factor <username>

# Empty the list of the administrators' networks: administrators sign in from anywhere again.
podman compose exec api python -m app.account clear-admin-networks

The first one ends the sessions of the account and removes its recovery codes; the password is not touched and still has to be right. Changing SECRET_KEY without SECRET_KEY_PREVIOUS makes every second factor unreadable, like the other stored secrets: the accounts are then reset with the same command.

Releases up to 2.12.1 run PostgreSQL 16 on the db-data volume. From 2.12.2 the Compose file runs PostgreSQL 18 on a new db-data-18 volume. PostgreSQL 18 cannot open the data files of 16, so the data moves once, with a dump and a restore, by deploy/upgrade-postgres.sh. Plan a short maintenance window: the app is down for the dump, the restore and the restart, a few minutes for a typical database.

  1. Pull the new release, but do not run compose up yet; the running stack is still the old one:

cd /opt/Nik && git pull

  1. Run the upgrade as root:

sudo deploy/upgrade-postgres.sh

It dumps the database with pg_dump (under /var/backups/nik, or BACKUP_DIR), counts the rows of every table, stops the stack, starts PostgreSQL 18 on the new volume, restores the dump, compares the row counts and starts the whole stack again. It stops at the first error and deletes nothing. Running it again is always safe: it carries on from where a previous run stopped, or says there is nothing to do.

  1. Check the app (sign in, open an incident), then the database version:

podman exec nik_db_1 psql -U nik -d nik -Atc 'SHOW server_version'

If compose up already ran on 2.12.2 before the script, the db container restarts in a loop and its log says run deploy/upgrade-postgres.sh: it refuses to create an empty database while the old data has not been moved (deploy/db-entrypoint.sh). Run the script anyway: it dumps the old volume with a temporary PostgreSQL 16 container instead.

The old data stays. The db-data volume is not modified; the new db container mounts it read-only. Keep it 14 days, then remove it (the script prints the exact name): 

podman volume rm nik_db-data

Rollback (within those 14 days): go back to the previous release and start it; it runs PostgreSQL 16 on the untouched db-data volume. Anything recorded after the upgrade is not in it: export the incidents you need first (incident JSON export, or the export of content as one file, which loads across database versions). 

podman compose down
git checkout v2.12.1
podman compose up -d --build

Manual deployment on RHEL

Tested on RHEL 8 and 9 (same steps on Rocky/AlmaLinux). nginx serves the static bundle and reverse-proxies /api/ to the backend, so the browser talks to a single origin — no CORS, and the session cookie just works. All commands assume a sudo-capable user.

This install has no analysis workers. The Code and Capabilities views, document previews, the isolated browser, Network Analysis and URL scans are containers (workers/) and report not configured here; samples and e-mails are still analysed statically, and every other tab works. Unless you have a reason to avoid containers on the host, use the Compose stack: it is the supported way and the one that isolates hostile files (see Security). The workers can also be run with the Compose file next to a manual backend, with their *_URL and *_TOKEN in nik.env.

Because incidents, users and the audit log live in PostgreSQL on the server, back up the database and the sample store with the backups Nik takes by itself (Settings → System → Backup, with BACKUP_DIR set) — the per-incident JSON export (incident export format) is an exchange/archival format, not the primary backup.

Step 1 — Build the static bundle

Build on the RHEL host or on any machine with Node 22+ and copy frontend/dist/ over. To install Node on RHEL (NodeSource, works on 8 and 9): 

curl -fsSL https://rpm.nodesource.com/setup_22.x | sudo bash -
sudo dnf install -y nodejs

Then, from the project's frontend/ directory:

npm ci            # clean, reproducible install from package-lock.json
npm run build     # outputs the static site into dist/

Step 2 — Install and configure PostgreSQL

Any PostgreSQL from 14 on works (CI tests 18); use the version your RHEL release ships.

sudo dnf install -y postgresql-server postgresql-contrib
sudo postgresql-setup --initdb
sudo systemctl enable --now postgresql

# Application role and database:
sudo -u postgres createuser --pwprompt nik
sudo -u postgres createdb -O nik nik

Enable password authentication. A fresh RHEL cluster uses ident/peer auth for local TCP connections, which rejects the app's nik login. Edit /var/lib/pgsql/data/pg_hba.conf so the local lines use scram-sha-256: 

# TYPE  DATABASE  USER  ADDRESS         METHOD
host    nik      nik  127.0.0.1/32    scram-sha-256
host    nik      nik  ::1/128         scram-sha-256

Then sudo systemctl reload postgresql. The connection string for the backend is:

postgresql+psycopg://nik:STRONG_PASSWORD@localhost/nik

The tables are created, and upgraded at every update, by the service itself when it starts (Step 3): there is nothing to create by hand.

Step 3 — Deploy the FastAPI backend (systemd)

The backend needs Python 3.11 or later. The default python3 of RHEL 8 and 9 is older: install python3.11 and call it by that name. Copy backend/ to /opt/nik/backend and build a virtualenv: 

sudo dnf install -y python3.11 python3.11-pip pango
sudo useradd --system --home /opt/nik --shell /sbin/nologin nik

sudo mkdir -p /opt/nik
sudo cp -r backend /opt/nik/backend
cd /opt/nik/backend

sudo python3.11 -m venv .venv
sudo .venv/bin/pip install --upgrade pip
sudo .venv/bin/pip install -r requirements.txt
sudo mkdir -p /var/lib/nik/samples      # the sample store: exclude it from the antivirus
sudo chown -R nik:nik /opt/nik /var/lib/nik

Keep the secrets in /etc/nik/nik.env (readable only by root and the service account). One setting per line, with no comment after a value: systemd would take it as part of the value. 

sudo mkdir -p /etc/nik
sudo tee /etc/nik/nik.env >/dev/null <<EOF
DATABASE_URL=postgresql+psycopg://nik:STRONG_PASSWORD@localhost/nik
SECRET_KEY=$(openssl rand -hex 32)
COOKIE_SECURE=true
SAMPLE_STORE=/var/lib/nik/samples
RUN_CREATE_ALL=false
EOF
sudo chmod 640 /etc/nik/nik.env
sudo chown root:nik /etc/nik/nik.env

Create /etc/systemd/system/nik-api.service — the API binds to loopback only; nginx is the sole public entry point: 

[Unit]
Description=Nik FastAPI backend (gunicorn/uvicorn)
After=network.target postgresql.service
Wants=postgresql.service

[Service]
Type=simple
User=nik
Group=nik
WorkingDirectory=/opt/nik/backend
EnvironmentFile=/etc/nik/nik.env
# Creates the schema on the first start and upgrades it after every update.
ExecStartPre=/opt/nik/backend/.venv/bin/alembic upgrade head
ExecStart=/opt/nik/backend/.venv/bin/gunicorn \
    -k uvicorn.workers.UvicornWorker \
    app.main:app \
    --bind 127.0.0.1:8000 \
    --workers 3
Restart=on-failure
RestartSec=2

[Install]
WantedBy=multi-user.target

sudo systemctl daemon-reload
sudo systemctl enable --now nik-api.service
curl -s http://127.0.0.1:8000/api/health      # → {"status":"ok"}

Step 4 — Install nginx and place the static files

sudo dnf install -y nginx
sudo systemctl enable --now nginx

sudo mkdir -p /var/www/nik
sudo cp -r dist/* /var/www/nik/

Step 5 — SELinux (enforced by default on RHEL)

# a) Let nginx connect to the backend — without this, /api/ returns
#    502 Bad Gateway with an "AVC denied … name_connect" in the audit log:
sudo setsebool -P httpd_can_network_connect 1

# b) Label the static-file directory — or nginx returns 403 Forbidden:
sudo dnf install -y policycoreutils-python-utils
sudo semanage fcontext -a -t httpd_sys_content_t "/var/www/nik(/.*)?"
sudo restorecon -Rv /var/www/nik

Step 6 — TLS certificate

For an internal host a self-signed certificate is enough (clients must trust it or accept the browser warning). Replace the CN/SANs with your host: 

sudo mkdir -p /etc/pki/nginx/private
sudo openssl req -x509 -nodes -days 825 -newkey rsa:2048 \
  -keyout /etc/pki/nginx/private/nik.key \
  -out    /etc/pki/nginx/nik.crt \
  -subj "/CN=nik.example.internal" \
  -addext "subjectAltName=DNS:nik.example.internal,IP:10.0.0.10"

For an internet-facing host use a real certificate instead (e.g. Let's Encrypt: sudo dnf install -y certbot python3-certbot-nginx).

Step 7 — Ensure the .wasm MIME type

sql.js loads a WebAssembly module. RHEL 9's nginx already maps it; RHEL 8's does not. Add the line to the types { … } block of /etc/nginx/mime.types if missing: 

application/wasm  wasm;

Step 8 — nginx server block

Create /etc/nginx/conf.d/nik.conf:

# Redirect plain HTTP to HTTPS (the app requires a secure context)
server {
    listen 80;
    server_name nik.example.internal;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    http2 on;
    server_name nik.example.internal;

    ssl_certificate     /etc/pki/nginx/nik.crt;
    ssl_certificate_key /etc/pki/nginx/private/nik.key;

    # Large uploads (packet captures up to PCAP_MAX_MB, backup restore,
    # incidents with parsed artifacts) blow past nginx's 1m default and get
    # rejected with 413.
    client_max_body_size 600m;

    root  /var/www/nik;
    index index.html;
    include /etc/nginx/snippets/nik-headers.conf;

    # A mailbox (mbox, Maildir archive) can be as large as MAILBOX_MAX_MB:
    # only its upload is allowed that much, and it is not buffered to disk.
    location = /api/artifacts/mailboxes {
        client_max_body_size 2100m;
        proxy_request_buffering off;
        proxy_read_timeout 900s;
        proxy_send_timeout 900s;
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # Reverse-proxy the REST API to the gunicorn/uvicorn backend.
    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        # Opening a large packet capture in Wireshark's engine takes minutes.
        proxy_read_timeout 330s;
        proxy_send_timeout 330s;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        # The client's address as nginx saw it: the API limits sign-ins by it.
        proxy_set_header X-Forwarded-For   $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # Fingerprinted assets can be cached forever…
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
        include /etc/nginx/snippets/nik-headers.conf;
    }

    # …but never cache the HTML entry point, so updates are picked up.
    location = /index.html {
        add_header Cache-Control "no-cache";
        include /etc/nginx/snippets/nik-headers.conf;
    }

    # Serve static files; fall back to index.html
    location / {
        try_files $uri /index.html;
    }
}

If /api/ returns 502 Bad Gateway, the usual culprit is SELinux — confirm httpd_can_network_connect is on (Step 5a) and that nik-api.service is running (curl http://127.0.0.1:8000/api/health).

Put the security headers in a file of their own, /etc/nginx/snippets/nik-headers.conf, so the server block and the two locations that set a header of their own can include it (nginx drops the inherited ones there): 

add_header X-Content-Type-Options "nosniff" always;
add_header Referrer-Policy "no-referrer" always;
add_header X-Frame-Options "DENY" always;
add_header Strict-Transport-Security "max-age=31536000" always;
add_header Content-Security-Policy "default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob: https: http:; font-src 'self' data:; connect-src 'self'; worker-src 'self' blob:; frame-src 'self' blob:; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'" always;

That policy is the one the Compose image sends (frontend/security-headers.js): copy it again from there after an update.

Step 9 — Open the firewall and reload

Only 80/443 are exposed; the backend stays on 127.0.0.1:8000:

sudo firewall-cmd --permanent --add-service=http --add-service=https
sudo firewall-cmd --reload

sudo nginx -t
sudo systemctl reload nginx

Browse to https://nik.example.internal, create the first (admin) user and sign in.

Updating to a new version

# Frontend — rebuild and replace the static files:
(cd frontend && npm ci && npm run build)
sudo rm -rf /var/www/nik/*
sudo cp -r frontend/dist/* /var/www/nik/
sudo restorecon -Rv /var/www/nik

# Backend — refresh code and dependencies, restart the service:
sudo cp -r backend/* /opt/nik/backend/
sudo /opt/nik/backend/.venv/bin/pip install -r /opt/nik/backend/requirements.txt
sudo chown -R nik:nik /opt/nik
sudo systemctl restart nik-api.service

Upgrades do not wipe data: everything persists in PostgreSQL and in the sample store, and the service upgrades the database schema when it starts (alembic upgrade head, in the unit). Put python -m app.backups.upgrade in its place in the unit, with BACKUP_DIR set to a directory the nik user can write, to get what the container does: a snapshot of the database and a rehearsal of the migrations before each upgrade. The backups of Settings → Backup work the same without containers (the copy off the server then leaves from the API process, with AUTOMATION_WORKER=inline); deploy/restore.sh and deploy/rollback.sh are written for the Compose stack: here, run python -m app.backups.restore restore <file> from /opt/nik/backend as the nik user, with the service stopped.

The export of content as one file

At the foot of Settings → System → Backup, under Export as one file, admins can write every incident (imported artifacts, flags and notes included), every user account, the audit log and the shared detection settings to one JSON file, and add the content of such a file to another server. It was called Full backup before 6.7 and works as it did. Its use is moving content to another Nik (including SQLite dev → PostgreSQL production, since the file is database-agnostic).

It is not a backup of the server. The backups Nik takes by itself hold the whole database and every file, are encrypted, and are tested. This file is neither.

What it does not contain. The envelope holds the incident documents, the users, the audit log and the settings. It does not hold the files of the sample store (samples, e-mails, captures), their analyses, the registry of artifacts, the rule sets, the API keys, the webhooks or the threat-intelligence keys. An incident restored from it on another server shows its evidence tabs, flags and notes, and references to samples, e-mails and captures that are not there.

Export

GET /api/backup/export (admin only, logged as backup.export) downloads nik-backup-<timestamp>.json: 

{
  "app": "Nik",
  "type": "backup",
  "version": 1,
  "exportedAt": "2026-07-08T09:00:00.000Z",
  "users":     [ { "id": "…", "username": "…", "passwordHash": "…",
                   "roles": ["admin"], "createdAt": "…", "createdBy": null } ],
  "incidents": [ { "…full incident documents, artifacts included…": "" } ],
  "audit":     [ { "id": "…", "at": "…", "actor": "…", "action": "…" } ],
  "settings":  { "keywords": [ ], "businessHours": { } }
}

⚠️ The file contains bcrypt password hashes: treat it like a database dump (store it encrypted / access-controlled).

Import

POST /api/backup/import (admin only, logged as backup.import) adds what the file holds to the server, in a single all-or-nothing transaction. The screen shows what the file contains and asks before sending anything.

  • An incident whose id is not on the server is added, with its number when that number is free.
  • An account whose name is not on the server is added, with the roles and the password hash of the file: it signs in with the password it had on the other server.
  • An audit entry that is not on the server is added.
  • The detection settings of the file are taken only by a server that has none.
  • Nothing that is on the server is changed or deleted: an incident or an account that exists stays as it is, and so do sessions, second factors, settings, credentials and everything else the file knows nothing of. The answer says how many of each were added and how many were skipped.

Before 6.7 this import replaced the server: it deleted every account, every incident and every row of settings and made them again from the file, so whatever the file did not carry was lost. It no longer does. To put a server back as it was, restore a backup.
