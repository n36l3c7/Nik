Quick start with Docker / Podman

The fastest way to run the whole stack — nginx (static SPA + /api reverse proxy), the FastAPI backend and PostgreSQL — is the bundled Compose file: 

deploy/init-env.sh            # writes .env, and the secrets as files in ./secrets
docker compose up -d --build  # build the images and start the whole stack

Open https://localhost:8443 and create the first user — that account becomes the admin, so do it before anyone else can reach the port. The database schema is created and migrated by the api container at every start.

The stack does not start without its secrets (DB_PASSWORD, SECRET_KEY, STORE_KEY and one token per analysis worker) and refuses the values printed in .env.example, which are public. deploy/init-env.sh generates them, each into a file of ./secrets (Keys of the server); it is safe to run again. Keep a copy of that directory away from the server.

On first start the web container self-signs a TLS certificate, so the browser shows a one-time "connection not private" warning — accept it to proceed (or mount a real certificate, see Docker / Podman in production). Nothing is served over plain HTTP: http://localhost:8080 redirects to the HTTPS address. 

docker compose logs -f api    # follow backend logs
docker compose ps             # container status
docker compose down           # stop (keeps the database volume)
docker compose down -v        # stop AND delete every volume: database, samples, certificate

Podman is a drop-in replacement (rootless is fine for ports 8080/8443):

deploy/init-env.sh
podman-compose up -d --build  # or: podman compose up -d --build

Every image in the Dockerfiles and the Compose file names its registry (docker.io/...), so Podman never has to guess one from /etc/containers/registries.conf (on RHEL it would try registry.redhat.io first and ask for Red Hat credentials). Keep it that way when you add an image: deploy/check-images.sh (run by CI) fails on a short name.

Production deployment

Upgrading from a "CSAP"-era deployment? The database role and name are now nik (was csap). A pre-existing Postgres volume still holds the old csap role/database, so either start on a fresh volume (docker volume rm nik_db-data-18 / your project's *_db-data-18), or keep the old names by setting DB_USER, DB_NAME and the compose POSTGRES_* back to csap, or rename in place with ALTER ROLE csap RENAME TO nik; and ALTER DATABASE csap RENAME TO nik;. The session cookie also changed name, so everyone re-logs in once.

Docker / Podman in production

The Compose stack serves the app over HTTPS on :8443; :8080 only redirects there. On first start the web container self-signs a certificate (for TLS_HOSTNAME, default localhost) into the web-certs volume, so HTTPS works out of the box — browsers show the usual warning until the certificate is trusted or replaced. Set TLS_HOSTNAME to the name users type, and for a real deployment pick one of:

  • Option A (recommended): provide your own certificate — internal CA or Let's Encrypt — as nik.crt / nik.key in /etc/nginx/certs; the startup script never overwrites an existing pair. Easiest wiring: swap the named volume for a bind mount in docker-compose.yml (- ./certs:/etc/nginx/certs).
  • Option B: front the stack with a host reverse proxy that terminates TLS (nginx, Caddy, Traefik) proxying to https://127.0.0.1:8443 (the upstream certificate is the self-signed one: tell the proxy to accept it), and bind the two port mappings to 127.0.0.1.

To regenerate the self-signed certificate (e.g. after changing TLS_HOSTNAME): docker compose down && docker volume rm nik_web-certs, then start the stack again.

Notes for Podman on RHEL:

  • Rootless works out of the box — only host ports below 1024 require rootful Podman (or lowering net.ipv4.ip_unprivileged_port_start).
  • Start on boot: restart: unless-stopped does not bring the stack back after a reboot with podman-compose. Install the systemd units (next paragraph): nik.service runs podman compose up -d at boot.
  • SELinux: named volumes (as used here) are relabeled automatically. If you switch to a bind mount, add :Z to that mount.

Start on boot (systemd). From the repository root, as root:

sudo deploy/install-systemd.sh

It installs and enables nik.service, with the repository path and the compose command (podman compose, or docker compose where Podman is absent) filled in: compose up -d at boot, compose down at shutdown. Options: --dir, --compose, --uninstall. Before 6.7 it also installed a nightly nik-backup.timer; the server takes its backups itself now, and the script removes that timer where an earlier run left it.

Keys of the server

The stack has two keys that encrypt, one that signs the audit log, a database password and a token for each worker. The security guide says what each protects and which container holds it; Settings → System → Keys shows where each one comes from on this server and when it last changed. This is the operator's side.

Where they are kept

A new install keeps them in files. deploy/init-env.sh makes ./secrets beside docker-compose.yml, a directory only you can enter, with one file for each secret, and writes NIK_SECRETS_DIR=./secrets in .env, which then holds no secret (the lines SECRET_KEY=, DB_PASSWORD=… stay, empty: Compose asks for them by name). Each container is given the files it uses and no other, read-only, under /run/secrets. Nothing else is needed: podman compose up -d --build as before.

  • The directory is mode 700 and the files in it 644: what protects them is the directory. The containers run as users that are nobody on the host, and neither Docker nor rootless Podman changes who owns a mounted file, so a file only its owner could read would be unreadable to the server. Create the directory as the user that runs the stack.
  • To keep it elsewhere, set NIK_SECRETS_DIR to an absolute path: another disk than the data, a volume that is unlocked at boot, a mount of another machine. A store key that sits on the disk it protects does not protect a host that is stolen whole.
  • Keep a copy of the directory away from the server. SECRET_KEY with the backups (the secrets inside a backup are under it), AUDIT_KEY and AUDIT_KEY_PREVIOUS where that copy of SECRET_KEY is (a restored server checks its audit log with them), STORE_KEY apart from them. If the store key is lost with the host nothing is lost with it: a backup holds the files themselves, under its passphrase.
  • The files are mounted with the option z, which gives them the SELinux label a container needs to read them. A directory outside the folder of Nik may need it once by hand: chcon -Rt container_file_t /srv/nik-secrets.
  • podman secret / docker secret work too, with a Compose override that mounts each secret at the same /run/secrets/<name>: the server reads whatever file <NAME>_FILE names. The Compose file does not use secrets: itself because external secrets exist only under Podman, and file secrets are mounted without the SELinux label there.

A server from before 6.8 keeps them in .env, and goes on working that way: the Compose file mounts the empty files of deploy/no-secrets in the place of each secret, an empty file counts as none, and the values come from the environment as before. The administrators are told once, in Nik, that the keys are in the environment. To take them out: 

deploy/secrets.sh status      # where each secret is; never a value
deploy/secrets.sh move        # from .env into ./secrets

move writes each secret into a file, keeps the .env as it was in .env.before-secrets, writes an .env that names the directory and holds no secret, makes the containers again on it (about a minute) and checks that the server answers and reads its keys from the files. If it does not, it puts the .env back and starts the stack on it again: nothing was moved. It can be run twice. At the end .env.before-secrets still holds every secret in clear: destroy it (shred -u) or lock it away once you have seen the server work. A secret must never be in both places: the server refuses to start and says which one is given twice.

Changing a key

Ask for it in Settings → System → Keys → Rotate… (a signed-in administrator, with the password again and a code when the account has a second factor): the dialog counts what will be put under the new key and shows the command. Then, on the server, within a day: 

deploy/secrets.sh rotate secret-key     # or: rotate store-key, rotate audit-key

For the two keys that encrypt:

  1. The running server makes the new key; the script writes it straight where the keys are kept (it is never on a screen) and keeps the key in use beside it as the earlier key.
  2. It restarts the containers that hold the key: api and automation for SECRET_KEY, api alone for STORE_KEY. Nik does not answer for the time of that restart, about a minute.
  3. The server puts everything under the new key and reads it back with the new key alone. The script waits and shows how far it is; the Keys page shows the same. For SECRET_KEY this takes seconds. For STORE_KEY only the head of each file is rewritten and written to the disk, then each file is opened once with the new key: the time goes with the number of files, not with their size.
  4. Once the server says the change is verified, the script moves the earlier key into secrets/retired/, which nothing reads, restarts the same containers once more so that they forget it, and says what to do with that file: keep the earlier SECRET_KEY with the backups taken before the change (their secrets are under it) and destroy it when they are gone; destroy the earlier STORE_KEY unless you keep copies of the store volume made before.

The audit key (rotate audit-key) signs the entries of the audit log; nothing is stored under it, so nothing is moved and nothing is waited for. The script adds the key in use to AUDIT_KEY_PREVIOUS, writes the new one, and restarts api and automation once (both write entries, and both must sign with the same key). The new key signs from the next entry on; the entries before it are checked with the earlier keys, which stay in AUDIT_KEY_PREVIOUS for as long as the log holds what they signed. The script ends by saying which key signs and whether any entry lost its key. This is also how a server from before 6.8 is given an audit key of its own: until then it signs with a key derived from SECRET_KEY, which it can always make again, so nothing is lost by the change.

Changing SECRET_KEY on a server that signs with the derived key. The entries written so far were signed with a key made from the SECRET_KEY that is leaving. Before the script takes that earlier key away (step 4) it asks the server for the key derived from it and writes it into AUDIT_KEY_PREVIOUS, without showing it; if the server cannot be asked, the earlier key stays where it is and the script stops. Nothing has to be done by hand, and the Keys page and deploy/secrets.sh status say how many entries, if any, cannot be checked for want of their key. A key that is retired by hand instead (the line removed from .env) is not carried: python -m app.auditlog key --derived, run while the old SECRET_KEY is still the one in use, writes what belongs in AUDIT_KEY_PREVIOUS. It is a key: the command refuses to write it to a terminal, so send it to a file only you can read (compose exec -T api … > file).

Stopped at any step, it is run again and goes on: until the change is verified the server holds both keys and everything is readable. If the server says it could not put something under the new key, the script stops, shows what, and leaves the earlier key in place. Run when nobody asked in Nik, it says so and asks before going on (--yes answers for it). On a server that keeps its keys in .env it edits .env instead and makes the containers again. deploy/secrets.sh rotate tokens writes new tokens for the workers and restarts the stack; the database password is changed in PostgreSQL first (ALTER ROLE nik PASSWORD '…'), then where the keys are kept.

"Nik did not start": a key is missing or is not the right one

When a key is missing, is still an example value, is given both as a file and in .env, sits in a file the server cannot read, or when STORE_KEY is not the key the store is sealed under, the api container does not exit and does not start either: it answers every request with the sentence that says what is wrong, the page shows it, and the same lines are in podman compose logs api. Nothing is written meanwhile. Set it right and start again:

  • is not set: deploy/init-env.sh writes what is missing and changes nothing else;
  • is given twice: remove the value from .env (or run deploy/secrets.sh move, which does it for all of them);
  • cannot be read: the file must exist and be readable by everybody inside a directory only you can enter (chmod 700 secrets; chmod 644 secrets/*);
  • is not the key the store is sealed under: the message gives the fingerprint of the key the store expects and of the one given. Put back the store key this server had. A server restored from a backup never meets this: its files were sealed under its own key as they were written.

The store of a server from before 6.8

Its files are in clear. At the first start with a store key the server begins to seal them in the background, one at a time (each is read, sealed beside itself, read back, compared, and only then put in the place of the clear one), while it is used as before: both forms are read, and new files are sealed as they arrive. Settings → System → Storage shows how many files and bytes are done, how long is left, and a Pause; the administrators are told when it has ended, or when a file is stuck. It needs the room of the largest file, never a second copy of the store, and goes on where it was after a restart.

  • It reads at most STORE_SEAL_MBPS megabytes a second (40 unless set in .env; 0 is as fast as the disk goes): about half a minute for each gigabyte at 40.
  • Until it has ended, the files it has not reached are in clear on the disk, as they were before the upgrade.
  • A file there is no room for, or that cannot be read, is listed on the Storage page and tried again every ten minutes. Once the store is sealed, a file put back by hand from a copy made before 6.8 is refused until Check again on that page has sealed it.

The work volumes

No worker mounts the store any more. The packet capture worker has a volume of its own, pcap-work, as the document worker has pst-work: a capture larger than PCAP_MEMORY_FILE_MB (64) is kept there, in clear, while it is open, and both volumes are emptied when their worker starts. They hold nothing to back up. To keep even a large capture off the disk, replace the volume with a tmpfs in a Compose override and give the worker the memory for it.

Backups

A backup can only be read with its passphrase. Whoever restores types it; if it is lost, every backup made under it is lost, and nobody can recover it. Write it down when you set it, and keep it away from the server.

Nik takes its own backups. Nothing has to be installed for it: the API container writes them, on a schedule, into the backup directory; it tests each one by restoring it; the automation container sends a copy to another machine; and every administrator is told when any of this goes wrong. It is set and watched in Settings → System → Backup (the screen).

What a backup holds, and what it does not

One file, nik-YYYYMMDD-HHMMSS.nikbak, encrypted from its first byte of content to its last:

  • the database, as it was at one moment: incidents, accounts, settings, the audit log, the analyses, playbooks, connectors and their instances (whose secrets are in it as they are in the database: encrypted under SECRET_KEY);
  • the store of files, whole: samples (live malware), e-mails, captures, mailboxes, screenshots, added rule files. On the disk they are sealed under the store key; in the backup they are the files themselves, under the backup passphrase like everything else, so a backup is read with its passphrase alone;
  • a manifest: the version of Nik, the revision of the database, when it was taken, the number of rows of every table, the number and size of the files, and the size and SHA-256 of every part.

Beside it, nik-….json says in clear what the file is and how its restore test went. No secret.

Not in a backup, to keep somewhere else:

  • .env and the secrets directory, and in them SECRET_KEY. Without the SECRET_KEY the backup was made under, a restored server works, but the stored secrets (keys of instances, credentials, TLS key logs) cannot be read and have to be entered again. The store key is not needed to restore: the server that restores seals the files under its own. The screen can put the key inside the encrypted backup (Include SECRET_KEY, off by default): then a backup and its passphrase are enough to bring everything back, and are also enough, for whoever holds both, to read every stored secret. It is never written anywhere in clear;
  • the TLS certificate and its key (the web-certs volume, or the files you mounted);
  • your Compose overrides and anything else you added to the deployment.

Where backups go

By default into the volume backups of the stack. A backup on the disk it protects is of little use when that disk fails: point the stack at another disk, or at a mount of another machine, in .env: 

NIK_BACKUP_DIR=/srv/nik-backups     # a directory of the host, in place of the volume

The API container hands the directory to its unprivileged user (uid 10001 inside the container) at its first start; with rootless Podman create it as the user that runs the stack. Where SELinux is enforcing, label a directory of the host for the containers once: chcon -Rt container_file_t /srv/nik-backups (the volume needs nothing). The automation container mounts the same place read-only. The room a backup needs is about the size of the database plus the size of the store (rows compress, samples mostly do not), and Nik refuses to start one the directory has no room for.

When, how many, and the restore test

The schedule is set on the screen: every few hours, every day at a time, or every week, in the time zone you name. Until you change it a backup is taken every six hours, counted through the day from 02:30 UTC: at 02:30, 08:30, 14:30 and 20:30. What is written between two backups is what a lost server loses: at most six hours with this schedule, when the backups are all there is. The archive of the database log closes most of that gap (Recovery to a moment). The schedule runs once a passphrase is set. Back up now and deploy/backup.sh ask for one more, the same way. Never two at once, and none while a release is migrating the database.

A file is written under ….nikbak.partial and renamed when its last byte is on the disk: a file with the name of a backup is always a whole one, and what a run that died left is removed by the next.

Each backup is tested at once. The file is read back from the directory; every chunk is decrypted; the size and checksum of every part are compared; the database is restored into a scratch database (nik_scratch_…, owned by a role made for it that owns nothing else, dropped whatever happens), where its schema, its revision and the number of rows of every table are compared with what was written, and a few questions are asked of it; every file of the store is compared with its checksum. The test reads the whole backup whatever its size. A backup that fails it is marked, is not counted by the retention, and the administrators are told.

What is kept: the latest N good backups (8: two days of them), and the latest good one of each of the last M weeks (4). The last good backup is never removed, however many newer ones failed. Snapshots taken before upgrades have a count of their own (3). A backup holds the whole store each time, whatever changed since the one before: twelve kept backups take about twelve times the size of one. The screen says how much the kept backups take now, and how much the chosen numbers lead to at the size of the last one; the directory is called nearly full when less than a tenth of it is free, or less than twice the size of the last backup (the next one is written before an older one is removed).

How long it takes. A backup reads the database and the store once, and its test reads the file once: both grow with the amount of data, and with little else. On the machine the release was tested on (a laptop with an NVMe disk), a store of 800 MB was written in 4 seconds and tested in 2; a database of 1.3 GB (three million rows) was written in 9 seconds, into a file of 118 MB, and tested in 16. Tens of gigabytes are a matter of minutes there, and of the speed of the disks on a server. Each backup says how long it and its test took (summary.seconds and verify.seconds in GET /api/backups).

What the administrators are told

One notice inside Nik when a problem appears, one when it is solved, nothing in between: a backup failed; a backup failed its restore test; the schedule passed and none started; the last good backup is older than the age set on the screen (13 hours: two runs missed, and an hour); the backup directory is nearly full; the copy off the server failed or has waited six hours; no passphrase is set a day after the server was installed. The API container and the automation container both watch, so the notice comes even when one of the two is the thing that stopped. Every run, test, copy, download, deletion and change of settings is in the audit log (backup.*).

The copy off the server: SFTP to a second host

The backend has no route outside its networks, and backups do not give it one: the copy is sent by the automation container, the one that already has a way out, straight to the host you name (SFTP does not go through an HTTP proxy: the second host must be reachable from the first). On the second host:

  1. Create an account that can do nothing else, and the directory: 
    sudo useradd --system --create-home --shell /usr/sbin/nologin nikbackup
sudo mkdir -p /srv/nik-backups/incoming
sudo chown root:root /srv/nik-backups && sudo chmod 755 /srv/nik-backups
sudo chown nikbackup: /srv/nik-backups/incoming && sudo chmod 700 /srv/nik-backups/incoming
  2. On any machine, make a key for this alone, with no passphrase of its own (Nik keeps it encrypted): 
    ssh-keygen -t ed25519 -N "" -C nik-backups -f nik-backups-key
    Put nik-backups-key.pub in /home/nikbackup/.ssh/authorized_keys on the second host.
  3. Limit the account to SFTP inside that directory, in /etc/ssh/sshd_config, then reload sshd: 
    Match User nikbackup
    ChrootDirectory /srv/nik-backups
    ForceCommand internal-sftp
    AllowTcpForwarding no
    X11Forwarding no
    PasswordAuthentication no
  4. Read the host key of the second host on the second host: cat /etc/ssh/ssh_host_ed25519_key.pub (the two first words), or its fingerprint with ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub.
  5. In Settings → Backup, turn on the copy: host, port, account nikbackup, directory /incoming (the path as the account sees it inside its chroot), the private key pasted (or the name of a stored credential), and the host key from step 4. Save, then Test the destination: it signs in, writes a small file, reads it back and removes it, and shows the key the server presented.

Nik never trusts a host key on first sight: a destination with no pinned key receives nothing, and one that presents another key receives nothing and the administrators are told. A backup is sent once it has passed its restore test, as <name>.nikbak.partial renamed at the end; a transfer that is cut is resumed where it stopped (three times in a pass, then again an hour later); what arrived is read back and its size and SHA-256 are compared with the local file before the copy is counted. The .json of the backup goes beside it. What the retention removes on the first host is removed on the second. The snapshots taken before upgrades are copied too, once the upgraded server is up (the upgrade never waits for the copy, and a copy that fails is told like any other), and the latest three are kept there as here.

The directory of the second host then holds, flat: nik-YYYYMMDD-HHMMSS.nikbak and nik-YYYYMMDD-HHMMSS.json for each backup kept.

Restoring

Restoring is done on the server, from the command line, with the stack stopped: never by a button on a running server. deploy/restore.sh does all of it, with Docker and with Podman, rootless too: 

deploy/restore.sh nik-20261120-023000                      # a backup of this stack's backup directory
deploy/restore.sh /mnt/copy/nik-20261120-023000.nikbak     # a file brought from elsewhere
deploy/restore.sh --inspect nik-20261120-023000            # only read it and say what it holds

It asks for the passphrase (or reads it from NIK_BACKUP_PASSPHRASE or the file named by NIK_BACKUP_PASSPHRASE_FILE, for a restore nobody attends; never from the command line), stops the stack and starts the database alone, then reads the whole file and compares every checksum. Nothing is changed before that has passed. It refuses a database or a store that is not empty unless you add --replace, which replaces both with what the backup holds. The database arrives in one transaction. Then it starts the stack, checks that the server answers, and says what to look at. --database-only leaves the files alone; --no-start leaves the stack stopped; --secret-key first writes the SECRET_KEY a backup holds where the keys of the stack are kept: into the secrets directory (keeping the key as it was beside it, as secret_key.before-restore), or into .env on a server that keeps them there (keeping the file as it was in .env.before-restore), and adds the keys the audit log of the backup was signed with to AUDIT_KEY_PREVIOUS of this server. Every file of the store is sealed under the store key of this server as it is written.

The audit log after a restore. The log on the server is then the log of the backup. Its first new entry, audit.restore, says which backup was put back; it was written by the restore and not by a session of the server, and is marked so (written outside). What the old server wrote after that backup is in the copy of the syslog receiver, if the log was forwarded. --inspect and the .json beside each backup give the end of the log the backup holds (auditHead: the number of its last entry, its hash, the id of the key that signed it): python -m app.auditlog verify-audit --head SEQ:HASH holds a log against it. The entries that come back keep the signatures of the server that wrote them: this server checks them with the keys in its AUDIT_KEY_PREVIOUS, and shows those whose key it lacks as entries that cannot be checked, never as tampered with.

Versions. A backup made by the version that is installed, or by an earlier one, is restored as it was; an older one is migrated by the server at its next start, after a snapshot and a rehearsal, like any upgrade. A backup made by a later version is refused with the version to check out: this code does not know what it holds.

Recovery to a moment

A backup is the server as it was when the backup was taken. From 6.9 the Compose stack also keeps the log of its database as it is written, and a physical copy of the database taken every day (a base backup). With the two, the database can be brought back to any moment since the oldest base backup kept: a minute before a mistake, or the last thing the server wrote before its host died. The backups of 6.7 are unchanged and stay beside it: the encrypted file every six hours, readable with its passphrase alone on any PostgreSQL, and the snapshot and the rehearsal before an upgrade. What is described here is physical: it goes back into the same major version of PostgreSQL.

What turns on by itself, at the first compose up -d --build on 6.9:

  • the archive of the log. PostgreSQL hands every finished segment of its write-ahead log to the volume wal-archive, compressed, and never writes over one that is there. While something is written it closes a segment at least every NIK_ARCHIVE_TIMEOUT seconds (300): that is the most a host that dies can lose, once its segments leave it. The settings are given to PostgreSQL on its command line by the entrypoint of the db container, so they hold on a database made by any earlier release and nothing is written into its configuration;
  • the recovery service, a new container: the image of the database with another command. It takes the base backups (pg_basebackup, each checked against its manifest with pg_verifybackup), proves the archive, and removes what is no longer kept, each when the backend asks. It has no network: it reaches PostgreSQL through its socket, on the volume db-socket the two share, and talks with the backend only through small files in the archive volume;
  • a base backup every day at 03:30 UTC, and one at once when there is none, and after each recovery or promotion;
  • two days to go back in: the base backups of the last two days are kept, with the one before them (a recovery to the first of those days starts from it), and all the log since the oldest one kept;
  • a recovery test every 24 hours and after each new base backup: the latest base backup and the archive are replayed into a scratch server inside the recovery container, to a moment a minute before the last segment archived, and the audit log found there is held against the one of the server. The server itself is not touched;
  • deleted files are kept. The files of the store are not in the log of the database. On a server with an archive, a file that is deleted is moved to .kept/ inside the store and really removed when no recovery can reach back to before its deletion (two days, with the defaults). Previews and what an interrupted transfer left are not kept.

What does not turn on by itself: the copies off the host. They start when a backup passphrase and a destination with its pinned host key are set in Settings → System → Backup: there is one passphrase and one destination for the backups and for the recovery. Until then the archive is on the server only, and is lost with its disk. All of it is set and watched at the foot of that page, under Recovery to a moment; every administrator is told when the archive stops, when the recovery service does not answer, when a base backup or a recovery test fails, when the second host is not reached or falls behind.

What it takes on the disk. In the archive volume: as many base backups as are kept (one more than the days to go back in, so three with the defaults), each about the size of the database compressed, and the log of those days. In the store: the files deleted in those days. The screen gives the figures of the server it is on, and what they lead to once the archive has run for the days it keeps. Measured on the test pair of the release:

  • a base backup of a nearly empty database: 5.4 MB;
  • a segment closed by the timer: 16 to 20 KB compressed (6 to 100 KB when a checkpoint falls in it). A segment is 16 MB before it is compressed, whatever it holds;
  • with the default of 300 seconds, a server nobody works on archives roughly 10 to 30 MB of log a day. A server in use archives what it writes, on top of that.

So the room is about (days + 1) × (the database compressed + the log of one day). Raising the days one can go back, or taking base backups more often, multiplies the first term; a lower NIK_ARCHIVE_TIMEOUT adds small files to the second. The archive and the base backups on the server are in clear, like the data directory of PostgreSQL beside them: what protects them is what protects the host. What leaves the host is sealed.

When the archive cannot be written (its disk is full, the volume is gone), nothing is lost: PostgreSQL keeps every segment it could not hand over and tries again. But it keeps them in its own log directory, on the disk of the database, which then fills. The administrators are told after five minutes, with how much waits; the reason is in docker compose logs db.

The variables, in .env:

NIK_ARCHIVE_TIMEOUT=300                # seconds: lower loses less when the host dies, and writes more small files
NIK_WAL_ARCHIVE_DIR=/srv/nik-archive   # a directory of the host, in place of the volume wal-archive
NIK_WAL_ARCHIVE=off                    # no archive at all
  • NIK_WAL_ARCHIVE_DIR puts the archive on another disk than the data, as NIK_BACKUP_DIR does for the backups. The db container gives its folders the owners they need each time it starts. Where SELinux is enforcing, label the directory once: chcon -Rt container_file_t /srv/nik-archive.
  • NIK_WAL_ARCHIVE=off starts PostgreSQL without the archive. The server then cannot be brought back to a moment and cannot have a standby; the screen says the archive is off and the administrators are told so.
  • A change of any of the three is read when the containers are made again (compose up -d). RECOVERY_MEMORY (1g) and RECOVERY_CPUS (2) are the limits of the recovery container.

An installation without containers (manual deployment) has no archive: it is part of the Compose stack. The screen says so and shows nothing else.

Go back to a moment

Like a restore, this is done on the server, from the command line, by somebody who can see the host: no button does it. deploy/restore.sh --to is the command. It never writes over a database: the one that is there is kept aside by a rename, under a name that says when.

On the server itself, from its own archive. No passphrase is asked.

  1. Find the moment. Settings → System → Backup, under Recovery to a moment, says from when to when one can go back, and gives the command for the latest moment, to copy. Write the moment with its offset (+00, +01); without one it is read as UTC.
  2. Run it on the server, as the user that runs the stack: 
    deploy/restore.sh --to "2026-11-21 14:03:00+00" --replace   # a minute before the mistake
deploy/restore.sh --to latest --replace                     # everything the archive holds
    It says which base backup it starts from, how many segments follow it and what will be left out, then asks for the word replace. If the archive does not reach the moment (it is before the first base backup, after the last segment, or a segment is missing) it says up to when it can go, and changes nothing. Without --replace it refuses a stack that holds a database.
  3. It stops the stack, keeps the database aside, puts the base backup in its place, has PostgreSQL replay the log to the moment, and checks what came back: the revision of the database, the audit log against its own chain from the first entry to the last of that moment, and every file the database names. A file deleted since the moment is put back from where deletions are kept; one that is named and is nowhere is listed by name. Then it starts the stack and waits until the server answers.
  4. Read what it ends with: What was lost (everything written after the moment: that is what going back means), and what to check before anybody works on the server: sign in, open the incident you came back for and one file of the store; Settings → System → Audit log, where the chain verifies and the first new entry, audit.restore, says to which moment the database was brought back; Settings → Backup, where a new base backup is being taken (the database writes a new timeline from here).
  5. Turn the automation on again when you have looked (below): going back to a moment you named turns its general switch off.
  6. Once all is well, remove the database kept aside (step 2 of the list below). It takes the room of a whole database until then.

Run twice, it does the same thing twice: the second run keeps the database of the first aside and recovers again. So a moment that turns out to be too early or too late is corrected by running the command with another one. --no-start leaves the stack stopped at the end; --yes does not ask. NIK_RECOVERY_WAIT (3600) is how many seconds the script waits for a replay before it gives up.

The work that was in progress, and the other systems. The database that comes back is the one of that moment, with everything that was in progress then. The server that starts treats it as after a kill (what a restart costs), whatever the clock of the host it ran on said:

  • analyses, scans, captures and mailboxes that were running start again by themselves, within seconds of the start;
  • a step of a playbook that was running is done again, or, when it was calling another system in a way that may not be repeated, waits as interrupted for a person to say what happened; a change that was being sent to a mirrored system is sent again, a comment is not, and fails with a sentence;
  • a schedule whose time passed between the moment and now runs once, however many times it was missed (the run reads how many in trigger.missed); a timer of an SLA that ran out meanwhile fires with the moment it really ran out;
  • a connector that fetches goes on from where it was at that moment: the alerts fetched since come in again, as new incidents, and start their playbooks again.

What the server did in other systems after the moment, it no longer knows. A host a playbook isolated since, a ticket it opened, a mail it sent, a comment it mirrored: none of it is in the database that came back, and a playbook started again by the same alert does it again. So going back to a moment you named turns the general switch of the automation off: no playbook runs, no schedule fires and nothing is fetched until an administrator turns it on (Automations, the switch at the top). The command says so when it ends, and the entry audit.restore too. Look first at what the other systems hold since the moment; then turn it on. --to latest, which is what one runs when the host died, loses the last seconds only and leaves the switch as it was: the server goes on by itself.

The databases kept aside.

  1. List them: deploy/restore.sh --asides gives each with its name (….before-20261121-141002) and its size.
  2. Remove one for good: deploy/restore.sh --drop-aside NAME (it asks for the word remove).
  3. Put one back in the place of the database: deploy/restore.sh --put-back NAME. The stack is stopped, the database that is there is kept aside in its turn, and the stack is started. This is how a recovery is undone.

Keeping a database aside needs free room for it on the disk of the database: the script stops before it changes anything when there is not enough, and says how much is missing. --no-aside, with --replace, removes the database that is there instead of keeping it: only when the disk has no room for both, and only when you are sure of the archive.

On a new host, from the copies. When the first host sent its copies to a second one, any host that can read that directory can bring the server back, with the backup passphrase and the keys of the first host (which ones).

  1. Get the code at the version the first host ran, and make the settings of this host: 
    git clone https://github.com/n36l3c7/Nik.git /opt/Nik && cd /opt/Nik
git checkout v6.9.0
deploy/init-env.sh
$EDITOR .env                   # TLS_HOSTNAME, ports
  2. Put the keys of the first host where this stack keeps its keys. With the file made by deploy/standby.sh secrets export while the first host was alive: 
    deploy/standby.sh secrets import nik-keys.txt    # asks for the passphrase of that transfer
    Without that file, write them by hand from your copy of the secrets of the first host, each on one line: secrets/db_password, secrets/secret_key, secrets/store_key, secrets/audit_key, and the …_previous files if the first host had any.
  3. Make the directory of the copies readable by the other users of the host (the recovery runs in a container, as a user that is nobody on the host; everything in the directory is sealed): 
    sudo chmod -R o+rX /srv/nik-backups/incoming
  4. Recover: 
    deploy/restore.sh --to latest --from /srv/nik-backups/incoming
    It asks for the backup passphrase (or reads NIK_BACKUP_PASSPHRASE or NIK_BACKUP_PASSPHRASE_FILE), opens the base backup and the log that follows it, comparing every checksum, takes the files of the store that were copied, and goes on as on the server itself. A moment can be named in the place of latest.
  5. This server now takes the place of the old one. It is one generation later, and the script leaves recovery/superseded.json beside the copies: an old server that comes back and still sends its copies there reads it and serves nothing more. Point the users at this host, and look at Settings → Backup: the destination that came back is the one the old server sent to. If that is this very host, set another.

Rehearsing it, without replacing the server. To find out how long a recovery takes on your data, do it on a host that is not the second host: copy the directory of the copies to it, keep it off the network of the second host, and run step 4 on the copy. The file it leaves is then in the copy and tells nobody. Do not rehearse on the directory the server sends to: the server would read the file and stop.

A standby host

A standby is a second host that runs the same stack with a database that replays, as it arrives, the log the first host sends. It serves nothing and says so; it becomes the server when an operator runs one command on it.

The link is the one of the backups. The first host writes into a directory of the second over the SFTP account of its backups: every segment of the log and every base backup, sealed under the backup passphrase, and the files of the store as they are on the disk, sealed under the store key. The stack of the second host mounts that directory. No port is opened between the two hosts but the SSH one the backups already use, and the first host is the only one that connects; the second host needs no route to the first. There is no streaming replication, so no PostgreSQL port is published, and the standby is behind by the archive timeout and a few seconds. The first host connects when it has something to send, and at least once a minute to leave a small file that says it is alive.

  1. On the second host, make the SFTP account and the directory as for the copies of the backups (steps 1 to 4 there), then let the other users of the host read the directory: the stack reads it as a user that is not the SFTP account, and everything in it is sealed. 
    sudo chmod 755 /srv/nik-backups/incoming
    Install Docker or Podman, and git.
  2. On the first host, in Settings → Backup: set the passphrase, and the destination (the second host, the account, the directory as the account sees it, the host key pinned). Save, Test the destination, and wait until, under Recovery to a moment, the list of base backups shows one on the second host and The second host names the last segment sent.
  3. On the first host, write the keys the second one needs into a file: 
    deploy/standby.sh secrets export nik-keys.txt
    It asks twice for a passphrase made for this transfer (12 characters or more) and seals the file under it: the database password, SECRET_KEY, STORE_KEY, AUDIT_KEY and their earlier values. Carry the file to the second host by any channel, and the passphrase by another.
  4. On the second host, get the same version and make it the standby: 
    git clone https://github.com/n36l3c7/Nik.git /opt/Nik && cd /opt/Nik
git checkout v6.9.0
deploy/init-env.sh
$EDITOR .env                                           # TLS_HOSTNAME, ports
deploy/standby.sh secrets import nik-keys.txt          # the keys init-env.sh made stay beside them, as *.before-standby
deploy/standby.sh init --inbox /srv/nik-backups/incoming
    init asks for the backup passphrase, once: afterwards the standby reads it from the database it replays, and follows it when it is changed. It asks for the word standby, opens the latest base backup and the log after it, writes NIK_STANDBY_INBOX in .env, and starts four containers: the database, the recovery service, the backend and the web server. Nothing else runs on a standby. On a stack that already holds a database it refuses, unless --replace is added: the database is then kept aside, as in a recovery.
  5. Check, and remove nik-keys.txt from both hosts. The address of the second host shows one sentence in the place of the sign-in: This server is the standby: it follows the first host and serves nothing. The state of a standby is read on its host: 
    deploy/standby.sh status
    It says the role and the generation, the last file received, how old the last change replayed is and how many segments wait, when the first host last spoke, and what a promotion would lose now. On the first host the same command, the Backup page and the row Second host of the health page say how far behind the second host is.

What a standby does and does not do. Its database is read-only. Its backend answers every request with the sentence above (the health check of the container passes, with the word standby), takes in what arrives, and copies the files of the store into its own store. It migrates nothing, fetches nothing, runs no playbook, takes no backup and sends nothing. It holds the keys of the first host: it is the first host, one step behind. Give it the same protection.

When the link is cut the first host goes on working and archiving on its own disk: its archive is local, so the log directory of its database does not grow. The administrators are told when the second host has not been reached for ten minutes, and when what it holds is older than the limit set on the screen (15 minutes). When the link is back the first host sends what waited, in order.

The first host is gone

Three ways back, the best first. Which one is open depends on what was set up before the host was lost; what each needs is in one table, and what each loses in another.

1. Promote the standby. Minutes, and what is lost is at most the archive timeout and a few seconds. Nothing promotes by itself: not a screen, not a timer, not the first host falling silent. Somebody who can see both hosts decides.

  1. Make sure the first host is down, or off the network. Two servers must never work at once: each would take in events, run playbooks and write an audit log of its own.
  2. On the second host: 
    deploy/standby.sh status     # what a promotion would lose now
deploy/standby.sh promote
    promote says first what would be lost (what the first host wrote after the last segment that arrived), and asks for the word promote. It then takes in and replays everything that arrived, has PostgreSQL leave recovery, makes this server the server (one generation later than the first host), leaves recovery/superseded.json in the directory of the copies, starts the whole stack and waits until it answers. It ends with what to do next, which is steps 3 to 5. The file is signed with a key both hosts hold (one derived from SECRET_KEY, which the standby was given): a server obeys no other.
  3. Point the users at this host: the name they type must reach it (DNS, or the address of the proxy in front). Nik cannot move an address. The certificate must carry that name (TLS_HOSTNAME).
  4. Keep the old host off, or off the network, until it is made the standby (The first host is back).
  5. Sign in and check the last incidents: what the old host wrote after the moment the command named is not here. Neither is what it did in other systems after that moment. The work that was in progress in the database this server holds is taken back at once, by the rules of a restart (what a restart costs), and a step the old host finished in its last seconds, after the last segment that arrived, is done again here. For a call that may not be repeated that is one call made twice at the worst, within the time the command said was lost: look at Automations → Runs for what ran around that moment. The audit log has an entry standby.promote that says on which entry the log of this server ends; entries a syslog receiver holds after that one were written on the old host. In Settings → Backup the destination is still this host itself, so nothing is sent (the screen says the copies point at this server itself, and the administrators are told): until another host is set there, there is no standby and no copy off the host.

If not everything that arrived can be replayed (a file that is damaged, a replay that does not end in two minutes), promote stops and changes nothing; --force promotes with what was replayed. A promotion that is interrupted is finished by running the command again: until it has finished, the page of that host says This standby is being promoted and the server does not start. A database promoted by hand, outside the command, waits for the command the same way. If the file for the old server cannot be written, the command prints its one line and where to write it. --name sets what this server calls itself in that file (by default the name set on the screen, then NIK_SERVER_NAME, then the name of the machine).

What runs on a standby: nothing. Its database is read-only, and no process of Nik works on it: the backend answers every request with what it is and takes in what arrives, and the automation worker and the analysis workers are not started by init. Started by hand (compose up -d on the standby), the automation worker waits: no playbook, no schedule, no fetch, no copy of a backup, nothing sent to syslog, and one line in its log that says it waits. The same holds on a server that was replaced. Every loop of the server takes a lease before it does anything, and no lease is given on a server that does not serve. When the standby is promoted the backend starts in the container it was in, and promote starts the others.

2. No standby, but the copies were sent: bring Nik up on a new host from them. The same loss as a promotion, and the time to install a host. On the second host, or on any host that can read the directory: deploy/restore.sh --to latest --from /srv/nik-backups/incoming, as numbered steps under On a new host, from the copies. It needs the backup passphrase and the keys of the first host, the store key among them.

3. Restore the last backup. When there is no archive on the second host (the copies of the recovery never left, or the first host ran a version before 6.9), or when the store key of the first host was lost with it (a backup is read with its passphrase alone): the procedure of 6.7, below. It loses what was written since that backup, up to six hours with the default schedule.

What you need: the second host with Docker or Podman and git, the backups it received (/srv/nik-backups/incoming), the backup passphrase, and the SECRET_KEY of the first host with its AUDIT_KEY and AUDIT_KEY_PREVIOUS (from wherever you keep the copy of its secrets; or inside the backups, if you chose to include the key). The store key of the first host is not needed: the second host makes its own.

  1. Get the code, at the version that took the backup or a later one (the .json beside each backup names it, in clear): 
    git clone https://github.com/n36l3c7/Nik.git /opt/Nik && cd /opt/Nik
grep '"nik"' /srv/nik-backups/incoming/nik-20261120-023000.json
git checkout v6.7.0
  2. Make the settings and the secrets of this host (a store key and an audit key of its own among them), then put the old SECRET_KEY in its file, and the audit keys of the first host among the earlier audit keys of this one (skip both if the backup holds the key: step 3 writes them): 
    deploy/init-env.sh
$EDITOR secrets/secret_key     # the SECRET_KEY of the first host, on one line
$EDITOR secrets/audit_key_previous   # its AUDIT_KEY, then what its AUDIT_KEY_PREVIOUS held: one line, commas between
$EDITOR .env                   # TLS_HOSTNAME, ports
  3. Restore the latest backup that is marked verified ("passed": true in its .json): 
    sudo install -d -m 755 /srv/nik-restore
sudo ln /srv/nik-backups/incoming/nik-20261120-023000.nikbak /srv/nik-restore/    # a link, not a copy
sudo chmod 644 /srv/nik-restore/nik-20261120-023000.nikbak
deploy/restore.sh /srv/nik-restore/nik-20261120-023000.nikbak
# with the key inside the backup:  deploy/restore.sh --secret-key /srv/nik-restore/nik-….nikbak
    The directory of the backup account is closed to every other user, and the restore runs in a container as a user that is nobody on the host: so the file is first given a second name in a folder that is open (it is encrypted). The script says so if it cannot read the file. It builds the images at its first run, asks for the passphrase, restores and starts the stack.
  4. Sign in with an account of the first host: its password, its second factor and its recovery codes are as they were. Nobody is signed in on a restored server: the sessions that were open when the backup was taken are ended, with the sign-ins that were half-way and the count of failed ones; the accounts, their second factors and the sign-in policy are kept (if the policy lists administrators' networks that do not exist around this host, python -m app.account in the api container clears them: Sign-in and sessions). Check the list of incidents, open a file of the store, look at Settings → System → Workers and at an instance of a connector (its key is readable only with the right SECRET_KEY). Settings → System → Keys says, under the audit key, how many entries each key signed and whether any cannot be checked: none should, once the keys of the first host are in place. A first host that never had an audit key of its own (it signed with the key derived from its SECRET_KEY) needs nothing more than that SECRET_KEY.
  5. Put the TLS certificate in place, point the name of the service at this host, and set up Settings → Backup again for where this host should now send its own copies: the destination that was restored is this very machine. Set the passphrase again if SECRET_KEY changed.

How long. A restore reads the file twice, once to verify it and once to write. On the machine the release was tested on, the backup of an 800 MB store was restored in 14 seconds and a database of 1.3 GB in 12; the stack then starts in under a minute once its images are built. Building all the images on a host that never ran Nik took two minutes there and depends on the network: that, with installing the engine and getting the code, is where the time of a recovery goes, so do it once on the second host before it is needed. What is lost is what was written after the last backup that reached the second host: with a backup every N hours, at most N hours and the time of a backup.

The first host is back

After a promotion, or after a recovery on a new host from the copies, the old first host holds a database that is no longer the server's. It must not serve again as it is.

  • Started where it can reach the second host, it does not serve. A server that sends copies asks the second host, before it serves, whether it was replaced: its page says Nik is starting: it asks the second host whether this server was replaced while it was away, then This server was replaced on … by …. It then serves nothing, fetches nothing and runs no playbook, and stays so. A server that is running when its standby is promoted learns it within a minute, the next time it sends, and stops the same way.
  • Started where it cannot reach the second host, it cannot know. It waits 45 seconds for an answer, then serves, and tells its administrators that the second host could not be asked. Nothing inside a host can tell a network that is cut from a peer that is dead, and a server that refused to work whenever the second host was out of reach would stop for the failure of its own standby. This is why the old host stays off, or off the network of its users, until the steps below are done: that part is the operator's.

To make it the standby of the new server:

  1. On the old host, make sure there is an SFTP account and a directory for the copies of the new server, readable by the other users of the host, as on the second host (A standby host, step 1).
  2. On the new server, in Settings → Backup, set the old host as the destination, with its host key pinned, and test it. Everything is sent again to the new destination: a base backup, the log, and the files of the store, except the files named by their content (samples and e-mails) that the old host says it already holds. Wait until the screen says a base backup was sent.
  3. On the old host: 
    deploy/standby.sh rejoin --inbox /srv/nik-backups/incoming
    It asks for the backup passphrase and for the word standby, keeps the old database aside, puts a base backup of the new server in its place and starts the host as a standby. Nothing of the old database is merged or rewound: a fresh base backup is what cannot go wrong. The two hosts already hold the same keys.
  4. deploy/standby.sh status on the old host says it follows the new server. What the old host wrote after the last copy that reached the other host is in the database kept aside and nowhere else: if any of it matters, read it from there before you remove it (The databases kept aside).

How long. The time of a base backup over the link, which grows with the size of the database: 27 to 40 seconds on the test pair, whose database was small. To give the roles back afterwards, do the same the other way: stop the server, promote the standby, rejoin the other host.

Upgrading a pair

The standby first, then the server. Never the other way.

  1. On the standby: 
    git pull
docker compose up -d --build db recovery api web
    It migrates nothing: its database is read-only, and the step of the backend that takes the snapshot, rehearses and migrates is never reached on a standby. No snapshot is taken and no rehearsal is run there.
  2. On the server, as for any update: 
    git pull
docker compose up -d --build
    The snapshot, the rehearsal and the migrations run there as always.
  3. The migration reaches the standby through the log, like every other change, once the segment that holds it has arrived and is replayed. Nothing is run on the standby for it. On the test pair the standby held the new revision 83 seconds after the server (snapshot 0.2 seconds, rehearsal 1.5, migration 0.8, with an archive timeout of 20 seconds).

Why this order. A standby replays the database of the server, at whatever revision the server left it. If the server were upgraded first, the standby would hold a database newer than its own code, and could not start as the server if it had to be promoted then. Upgraded first, the standby holds code that is newer than the database it replays: promoted in that state, it migrates the database as it starts, like any server after an upgrade.

PostgreSQL. A new minor version (18.x) comes with the image of the db and recovery services: pull it and recreate the containers in the same order, the standby first. Both hosts must run the same major version: a base backup and the log go back into the version that wrote them. A change of major version is not done through the pair; the backups of 6.7 do not depend on the version.

What the default of 300 seconds changes. The loss when a host dies is bounded by the archive timeout plus the few seconds a segment takes to leave: about five minutes with the default, where the test pair lost seconds. The delay of the standby and the time for a migration to reach it follow the same number. Lower NIK_ARCHIVE_TIMEOUT for less, at the price of more small files in the archive and on the second host. The durations of the commands do not come from the timeout: they grow with the size of the database (a base backup is unpacked, or sent) and with the amount of log to replay, and were not measured on large data.

Limits, as they are.

  • None of this was run under Podman, on two separate machines, or across a corporate network. The scripts use the same engine settings as the other scripts of deploy/; try them on your hosts before you depend on them.
  • There is no streaming replication: a standby is never closer to the server than the last segment closed.
  • A file of the store that is rewritten in place (the log of a capture that is still open, the file of a mailbox) exists in one version. A recovery to a moment brings back the database of that moment and the latest content of such a file.
  • After a promotion or a change of destination everything is sent again, except the samples and e-mails the other host already holds.
  • A server that cannot reach the second host cannot know it was replaced (The first host is back).

The file format, and reading a backup without Nik

The format is versioned (format 1) and described in full at the top of backend/app/backups/container.py, which is also a program that needs only Python and the cryptography package, and can be copied out and run alone: 

python container.py list nik-20261120-023000.nikbak            # the parts, their sizes and checksums
python container.py extract nik-20261120-023000.nikbak out/    # every part as a file, and manifest.json

In short: a clear header (format, cipher, how the key is derived, nothing secret), then the content in chunks of one megabyte, each encrypted and authenticated with AES-256-GCM under a key derived from the passphrase with scrypt and a salt of the file. The number of a chunk and whether it is the last are part of what is authenticated, so a file that was changed, reordered or cut short is refused. Inside: the description of the database schema (db/schema.json), one part for each table in the text format of PostgreSQL's COPY (db/<table>.copy, loadable with \copy), the store as a tar (store.tar) and its index. A later Nik reads the backups of an earlier one.

The database part is not a pg_dump: the image holds no PostgreSQL client. It carries tables, columns, defaults, constraints, indexes, sequences, enumerated types and extensions, which is all Nik makes, and a backup stops with a sentence if the database holds anything else (a view, a trigger, a function of your own, a table in another schema) instead of leaving it out. Owners and privileges are not carried: everything belongs to the role that restores.

A backup taken before 6.7

The directories deploy/backup.sh wrote before 6.7 (db.dump, samples.tar, env, SHA256SUMS) stay where they are, unencrypted, and are restored as before, with the version that wrote them (B = the backup directory): 

cd "$B" && sha256sum -c SHA256SUMS
podman exec -i nik_db_1 pg_restore -U nik -d nik --clean --if-exists < "$B/db.dump"
podman exec -i nik_api_1 tar -C /app/samples -xf - < "$B/samples.tar"
podman restart nik_api_1

Once the server has taken and verified backups of its own, remove them: they hold the samples and the .env in clear.

Updates, and the snapshot before each

git pull
podman compose up -d --build    # rebuild images, recreate containers, keep data

Release notes say when an update needs more than this. When a release changes the database, the API container does this before it serves, and says each step in its log (compose logs api):

  1. it takes a lock, so that a second instance waits and no backup starts; it checks that the database is at a revision it knows, that the server is a PostgreSQL it runs on, and that the backup directory has room;
  2. it takes a snapshot of the database into the backup directory (nik-upgrade-….nikbak, marked Before the upgrade from X to Y), in the format of every backup, encrypted with the backup passphrase, or with a key derived from SECRET_KEY while no passphrase is set (the first upgrade from 6.6): never in clear. The files are not in it: no migration touches them;
  3. it rehearses: the snapshot is restored into a scratch database (nik_rehearsal_…) and the migrations are run there;
  4. only then it migrates the database itself.

The snapshot and the rehearsal add to that start the time of a backup of the database alone and of its restore, and the migrations run twice: about two seconds in all for a small database on the machine the release was tested on; for a database of 1.3 GB, 9 seconds for the snapshot and, measured as the restore test of a backup of that database, about 16 for the restore of the rehearsal. On a database too large to copy at every upgrade, NIK_UPGRADE_REHEARSAL=false in .env skips step 3, never the snapshot. If the role Nik uses may not create a database (an external PostgreSQL), the rehearsal is skipped with a warning in the log; ALTER ROLE nik CREATEDB gives it back.

While a long upgrade runs the API container does not answer its health check yet, and Compose may call it unhealthy after a few minutes: it is not restarted, and its log says where it is. The automation container waits until the database is at the revision of its code before it runs anything.

An upgrade went wrong

When the rehearsal or the migrations fail, the API container does not exit and restart for ever: it stays up, says what happened in its log under NIK DID NOT START: THE UPGRADE WAS STOPPED, and answers every request with a sentence, which the web page shows in place of the sign-in.

  1. Read the reason: podman compose logs api. It says which of the two cases this is.
  2. The rehearsal failed (the migrations fail on a copy of this database): the database was never touched and there is nothing to put back. Go back to the version that worked and start it: 
    git checkout v6.6.0 && podman compose up -d --build
    Then report the lines of the log.
  3. The migrations failed on the database itself, or the new version started and you want the old one back: list the snapshots, and put back the one taken before the upgrade: 
    deploy/rollback.sh                                   # lists them, with the version each goes with
deploy/rollback.sh nik-upgrade-20261120-101500
    It stops the stack, verifies the snapshot and replaces the database with it (one transaction), checks out the tag the snapshot names when the folder is a git clone with nothing uncommitted (otherwise it tells you exactly which version to put there, and leaves the stack stopped), starts the stack and checks that the server answers. --no-checkout never touches the code. Running it twice does no harm. Back to a version before 6.8, which reads its store in clear and its secrets in .env, it does two things more, with the code that is still there: it unseals every file of the store (one at a time, each compared before it takes the place of the sealed one; if one cannot be opened it stops before the database is touched and says which), and it puts the secrets back into .env if they had been moved to files. Back to a version before 6.9, which has no archive of the log, no recovery service and no standby: the recovery container is removed and PostgreSQL starts without archiving on the older version. The volumes wal-archive and db-socket are left as they are, and nothing reads them any more: the command says how to remove them once you are sure not to need that archive. A standby of this server follows nothing from then on: stop its stack, and make it again after the next upgrade.
  4. Files deleted since the snapshot was taken are named again by the database that comes back. A server that archives its log keeps deleted files for a while (under .kept of the store): the rollback moves every one deleted since the snapshot back to its place and says how many. Nothing of 6.9 is left in the database, which is the one of before the upgrade: a step of a playbook that was running when the snapshot was taken is handled as the older version does.
  5. Sign in and look at the latest incidents. What was written after the upgrade is not in the snapshot: it is lost. Everybody signs in again: a database that is put back keeps no session. What the files of the store hold is untouched: no release so far changes it, and a rollback refuses a snapshot whose upgrade did. (6.8 seals them, and a rollback to an earlier version unseals them: the same bytes either way.)
  6. A snapshot taken while no passphrase was set is read with the SECRET_KEY of the server; otherwise the rollback asks for the backup passphrase.

When a worker is down

The backend checks the workers it is configured with every 30 seconds: each analysis worker whose *_URL is set (analyzer, capa, document viewer, isolated browser, packet capture, script sandbox) by its GET /health, and the automation container by its heartbeat. A worker that has not answered for two minutes without a break is down: every account with the Admin role gets one notification that names it, says since when and what waits meanwhile. One more follows when it answers again, with how long it was down. Nothing is sent in between, and a container that restarts for an update is back well within the two minutes, so it tells nobody.

  • The check runs in the backend, not in the automation worker, so that it still runs when that worker is the one that is down. With several backend processes one of them checks at a time, and what was found is kept in the database: a restart of the backend, or a second process, does not send a notice twice.
  • A worker that is not configured is not watched: an install without the analysis workers, or with AUTOMATION_WORKER=off (or inline, where the loop is a thread of the backend itself), gets no notice about them.
  • Settings → System → Workers shows every worker and its state at any time; the notifications lead there. Then look at the container: podman compose ps, podman compose logs -f <service>.

Stopping and restarting the stack: what a restart costs

From 6.9 nothing that the server was doing is lost by a restart, and nothing is done twice. Everything that outlives a request is written in the database, with who holds it and since when it last said it was alive; the process that starts next, in the same container, in a new one or on the standby host after a promotion, goes on from there. There is nothing to do before stopping the stack, and no moment that is better than another.

What was in progress After the restart Where it is said
A playbook: a step working inside Nik, reading from another system, or changing something there that may be repeated The step is done again; the run goes on. The step of the run, under Restarts.
A playbook: a step changing something in another system that may not be repeated (a ticket, a mail) Not done again. The run waits for a person to say whether it happened (Automation). The run, a notification to who started it, the health page.
A playbook that waits (a time, an approval, a task), a schedule, a timer of an SLA It waits on. A time that passed meanwhile is acted on once when the worker is back: one run for a schedule however many times were missed, a timer past its time with the moment it really ran out. The run reads trigger.due; the War Room says "it was noticed late".

A change of fields is sent again; a comment being sent is not, and fails with a sentence that says so. The queue of mirroring; the Fetch tab of the instance.

The tray; GET /api/jobs/<id>.
  • Stopping politely. podman compose restart, up -d --build on a new version and a shutdown of the host send each container SIGTERM. The backend then takes no new request, gives the ones in flight 20 seconds (API_STOP_GRACE), hands back the work and the leases it holds, and exits; the automation worker claims nothing more and gives its steps 25 seconds; each analysis worker takes no new request and gives its jobs 20 seconds (ANALYZER_STOP_GRACE, CAPA_STOP_GRACE, PCAP_STOP_GRACE, DOCVIEW_STOP_GRACE). The stop_grace_period of each service in the Compose file is a little longer than that (40 s for the backend, 35 s for the automation worker, 30 s for the workers). What was handed back is taken at once by the process that starts next. Until 6.9 the workers ignored SIGTERM and were killed after ten seconds.
  • The database and the recovery service stop politely too. PostgreSQL ends its connections, writes a checkpoint and hands every finished segment of its log to the archive before it exits; it is given 60 seconds. The segment it was writing is not finished and is not archived: it is in the data directory, and goes on when the database starts. The recovery service, asked to stop while it takes a base backup or proves the archive, ends the tool, stops its scratch server, removes what was half written and exits (30 seconds); the request stays, and is done again from the start when the service is back. Killed, it leaves the half-written base backup and the files of the scratch server, and removes them when it starts. A base backup or a test that nobody answers is counted as failed after a while (six hours for a base backup whose request is still there, a minute when the request was lost; fifteen minutes for a test), and the administrators are told: neither stays "being taken" for ever. The copies to the second host stop between two files; a file cut half-way by a kill is a .partial there, which nothing reads, and is resumed or sent again. A standby stops at once. The whole stack, each container using all of its time one after the other, stops in under three minutes: the unit deploy/install-systemd.sh installs waits five (TimeoutStopSec=300).
  • A kill, a crash, the power. Nothing is handed back, and it is as safe, only slower: work whose holder has not said it is alive for 45 seconds is taken back, a lease runs out 30 to 300 seconds after its last renewal (the automation worker's after 30), and the worker that then starts takes back at once the steps that were running under the name of the one that is gone. Allow about a minute after the containers are up.
  • The database that restarts alone (or is killed) cuts what was being written. Nothing is failed for it: the loops of the backend and of the automation worker log the error and go on at their next pass; an event that was being turned into runs waits for the next pass; an analysis whose thread could not write its result is handed back and started again; a step of a playbook that could not keep what its call gave is found half a minute later, and is then done again or waits for a person, by the same rule as after a restart.
  • A worker that restarts alone (the analyzer, capa, the capture worker, the document worker) has lost its memory and the files it was given. The backend asks it every five seconds whether it still has the job it waits for; "unknown job" is answered at once, and the job is handed out again with its file. A worker that is merely slow is waited for as long as it says the job is there.
  • Work that keeps being interrupted (a file that takes its worker down every time, a step that does the same to the automation worker) is tried three times and then set aside as failed, with that reason, where it is shown; a person can ask for it again. The health page counts what was set aside.
  • The health page has three rows for all this, under Work in progress: the steps a restart interrupted that wait for a person, the work set aside after it was interrupted, and the oldest work held without a sign of life (more than two minutes means that what should take it back is not running). The last two tell the administrators once when they stop being fine and once when they are fine again; a step that waits for a person told the people who can answer it when it was interrupted, and the row does not tell them a second time.
  • Proving it on a stack of your own. .github/scripts/restart-chaos.sh starts a small stack under a project name of its own (no port, about 8 GB of memory), starts one of every kind of work against a stub that counts what it is asked, kills the backend, the automation worker, each analysis worker and the database at random moments, restarts everything at once and brings it up again on rebuilt images, and then checks that every job ended, that nothing outside was done twice, that nothing is still claimed and that the chain of the audit log verifies. CHAOS_SEED repeats a run.

The audit log: its chain, and sending it to syslog

From 6.8 the audit log is a chain of hashes (what that protects, and what it cannot). Nothing has to be set for the chain: the server links the entries it writes, walks the chain every five minutes and tells the administrators when it finds a break. What an operator sets is where the log goes.

  • Send it to a receiver. Settings → System → Audit log → Forwarding to syslog: the host and the port of the receiver, the protocol (TLS on 6514 is the one to use), the authority or the certificate the receiver presents, a client certificate if the receiver asks for one. Save, press Test (a marked message is sent over a connection of its own and the page says what the socket said), then turn it on. A new receiver gets the whole log from its first entry, or only what follows, as chosen.
  • The automation worker sends, not the backend: the receiver must be reachable from the automation container (its automation-egress network). It connects straight to the receiver (syslog does not go through an HTTP proxy), on a private address too: that host and that port are an exception of their own, and playbooks gain nothing from it. With AUTOMATION_WORKER=off nothing is sent; with inline the backend process sends, if it can reach the receiver.
  • A receiver that is down loses nothing: the entries wait in the table and leave in order when it is back. The page and the health page show how many wait and since when; the administrators are told when that lasts (five minutes by default, a problem after thirty) and when it drained. Entries that wait are never removed by clearing the log.
  • On the receiver each message is one line: an RFC 5424 header, the structured data [nik@32473 seq="…" hash="…" prev="…" id="…" action="…"] and the entry as JSON (with origin="import" and "origin":"import" for an entry that came in a file of content from another server: its date is that file's word). Keep the raw message (rsyslog: a template with %rawmsg%; syslog-ng: ${MSG} with flags(syslog-protocol) keeps the JSON), in a file the administrators of Nik cannot write to. A message with the id checkpoint arrives every five minutes even when nothing happened: alert on its absence.
  • Checking the log against the receiver's copy, on any machine with Python: 
    # on the server: every entry, one JSON object a line
podman compose exec api python -m app.auditlog export > audit-export.jsonl
# anywhere: the export alone, then held against what the receiver got
python backend/app/auditlog/verifier.py audit-export.jsonl
python backend/app/auditlog/verifier.py audit-export.jsonl --syslog /var/log/nik-audit.log
# or against the last checkpoint only (its seq and hash)
podman compose exec api python -m app.auditlog verify-audit --head 4182:9f2c…
    It exits 0 when everything holds, and names what does not: an entry edited, entries missing, a log cut at its end (the receiver knows entries the server no longer has), a log rewritten (the same number with another content). The signatures are checked only when the verifier is given the key, in a file (--keys FILE, one key a line) or in NIK_AUDIT_KEYS; without it, it says signatures not checked: no key.
  • The key the log is signed with is one of the keys of the server, kept and changed like the others. A new install is given an AUDIT_KEY of its own by deploy/init-env.sh; a server from before 6.8 signs with a key derived from SECRET_KEY until deploy/secrets.sh rotate audit-key gives it one (nothing has to be done for the log to be signed). The api and the automation containers are both given it, and no other: both write entries, and with different keys each could not check what the other signed. A text is taken as it is; hex:… as the bytes it spells. python -m app.auditlog key says which key signs now and which earlier ones the server can still make; Settings → Keys shows the same, with how many entries each key signed. The earlier keys stay in AUDIT_KEY_PREVIOUS (several, separated by commas): an entry whose key is not there is reported as one that cannot be checked, not as a break. Changing a key says what happens to them when SECRET_KEY changes. The key is in no database, so a copy of the database alone does not hold it. A backup carries it only when it was asked to carry SECRET_KEY too (Include the key), inside the encrypted file; otherwise keep a copy of it where the copy of SECRET_KEY is.
  • After a restore the server's log is the backup's, with one new entry that says so. The receiver then sees numbers it already has arrive again with other content, starting with that entry (audit.restore): the verifier reads it as a restore, and reports how many entries exist only on the receiver. Those are the ones written between the backup and the restore.
  • Nothing is trimmed by itself: the audit log is kept without limit. Removing old entries (Remove the entries… on the page, or DELETE /api/audit?olderThanDays=N as a signed-in administrator) leaves an entry that says how many went and up to which hash. Nothing removes entries by itself: there is no retention to set.

Health, warnings and Prometheus

Settings → System → Health says in one place whether the server is well: the disks (the store of files and the backup directory, how fast each fills and when it will be full at that rate), the size of the database, every queue with what waits and for how long, the workers, the backups, the database (connections, long transactions, whether its schema is the one this version expects), the recovery to a moment and the second host (the rows), the certificate of the web container, the chain of the audit log and its forwarding, two warnings about the sign-in, the keys of the server and the encryption of the store, and the clock against the database. Each row is fine, needs attention or is a problem, by thresholds an administrator can change at the foot of the page, and leads to the page that has the whole story.

  • Warnings. The server looks once a minute, from the backend and from the automation worker (whichever is alive), and every administrator gets one notification when a row gets worse and one when it is fine again: a disk past 80% (a problem at 90%) or that will be full within 30 days (7), a queue whose oldest item has waited 10 minutes (60), a schedule or a fetch 5 minutes late (60), the certificate 30 days from its end (7), an audit entry that has waited 5 minutes to be forwarded (30), a broken chain, the database at 80% of its connections (95%) or a pool with none left, a transaction open for 15 minutes (the one a backup reads the database in is not counted), clocks 5 seconds apart (60). A value has to be found twice in a row before anybody is told. Workers, backups and the recovery to a moment keep their own notices; this page does not repeat them.
  • Work in progress. Three rows say what restarts left behind (Stopping and restarting the stack): Steps a restart interrupted that wait for a person needs attention as soon as there is one, and leads to the runs; Work set aside after it was interrupted needs attention while a piece of work that was interrupted three times, or a comment to a mirrored system that was not sent again, is there (a row is kept a week); Oldest work held without a sign of life needs attention after two minutes and is a problem after ten.
  • Keys and encryption. Keys of the server needs attention while the secrets are in the environment of the containers (deploy/secrets.sh move), while a change of key is half-way or stopped on something it could not put under the new key, and when entries of the audit log cannot be checked because the key that signed them is not among the keys of the server. Encryption of the store needs attention while a store from before 6.8 is being sealed (it says how much is left), and is a problem when a file failed its check or when files stay in clear that the server could not seal. The keys and the store keep their own notices; this page does not repeat them.
  • The disk of the database cannot be read from the backend (it belongs to the db container): the page gives the size of the database and how fast it grows. Watch the volume on the host.
  • The certificate is read by the backend from the web container itself (NIK_WEB_TLS, web:443 in the stack; set it empty where there is no web container, or to the host and port of your own proxy on a manual install).
  • Prometheus. The same numbers are at /api/metrics, through the web port like everything else, for whoever presents the scrape token: make it at the foot of the health page (it is shown once), put it in a file only Prometheus reads, and add the job the page gives: 
    scrape_configs:
  - job_name: nik
    scheme: https
    metrics_path: /api/metrics
    authorization:
      type: Bearer
      credentials_file: /etc/prometheus/nik-metrics-token
    tls_config:
      ca_file: /etc/prometheus/nik-ca.crt # the certificate of Nik, or of its authority
    static_configs:
      - targets: ["nik.example:8443"]
    Without the token the route answers 401, to a signed-in administrator too. METRICS_TOKEN in .env, the way of earlier versions, is still accepted beside it; with neither, nobody reads the metrics.

Sign-in: the client's address, and getting back in

The rules of signing in are an admin's, under Settings → Sign-in and sessions (the guide has them, Security how they hold). Two things about them are the operator's.

The client's address. The waits after failed sign-ins are counted per address, and administrators can be held to listed networks: both need the backend to know where a request comes from. The browser talks to the web container, which passes the request on and writes the address it saw in X-Forwarded-For. The backend believes that header only from the proxies named in TRUSTED_PROXIES (host names, addresses or networks; web in the Compose file, looked up again every half minute), and ignores it from anybody else. FORWARDED_ALLOW_IPS stays empty, as the Compose file has it: with * gunicorn would rewrite the address from the header for whoever sends it. If you keep a Compose override or an .env that sets it, remove it.

What the web container itself sees depends on the container runtime:

Set-up The address the backend gets Per-address waits, administrators' networks
Docker Engine on Linux, as root (the default) The client's own, for clients on other machines. A browser on the server itself arrives from the gateway of the container network. Work.
Podman as root The client's own, as with Docker Engine. Work.
Rootless podman (and rootless Docker) One address for everybody, an address of the container network: published ports are forwarded by a process of the user (rootlessport), which opens a new connection to the container. Do not work. The policy page says so and refuses a list of networks; failures are counted per account only.
Docker Desktop (Windows, macOS) One address for everybody, the gateway of the container network. Do not work, as above.

The policy page shows the address the server sees you at, and says when that address is one of the server's own container network rather than yours: look at it from another machine before listing networks. Under rootless podman the way to give the backend real addresses is to run the stack with podman as root. A reverse proxy on the host in front of the published port does not help as the stack is: the web container replaces X-Forwarded-For with the address it saw itself, on purpose, so what that proxy wrote is lost. Where the addresses cannot be known, leave the administrators' networks empty and rely on the second factor.

In a manual deployment, where nginx and the backend share the host, there is nothing to set: with FORWARDED_ALLOW_IPS unset, gunicorn believes the header from 127.0.0.1, which is that nginx and nobody else. Do not set it to *.

Getting back in. Somebody who lost the phone uses a recovery code; without the codes, an admin resets their second factor under Accounts. For the last administrator who lost everything, and for a list of networks that leaves no administrator in, there are two commands, run on the server in the backend's container. Whoever can run them already holds the database and the secret key, so nothing is asked; each writes what it did in the audit log, under the name server console. 

# Take the second factor of an account away: it signs in with its password and sets one up again.
podman compose exec api python -m app.account reset-second-factor <username>

# Empty the list of the administrators' networks: administrators sign in from anywhere again.
podman compose exec api python -m app.account clear-admin-networks

The first one ends the sessions of the account and removes its recovery codes; the password is not touched and still has to be right. Changing SECRET_KEY without SECRET_KEY_PREVIOUS makes every second factor unreadable, like the other stored secrets: the accounts are then reset with the same command.

Upgrading to 3.0

Release 3.0 makes the safe configuration the only one: the stack no longer starts with secrets that are missing or still at their example values, plain HTTP only redirects to HTTPS, and the backend runs unprivileged. Coming from 2.x, on the server: 

cd /opt/Nik && git pull
sudo deploy/backup.sh /var/backups/nik    # as before every upgrade
sudo deploy/init-env.sh                   # completes .env, changes nothing that is already good
sudo podman compose up -d --build
  • deploy/init-env.sh generates what .env lacks. If SECRET_KEY was never set (or is an example value), it writes a new one and keeps the old as SECRET_KEY_PREVIOUS: at the next start the secrets of instances and TLS key logs already stored are re-encrypted with the new key, and the line can then be removed. If DB_PASSWORD was never set, it writes the old default, which is what the existing database uses.
  • A stack that ran with no .env at all is an existing install too: the script recognises it by the database volume of the Compose project and says so. If it cannot see the volume (another user's Podman, a project name of your own), tell it: NIK_EXISTING_INSTALL=1 deploy/init-env.sh. Check the result before starting: DB_PASSWORD must be the password the database was created with (nik if you never set one).
  • Everyone now uses https://<host>:8443; http://<host>:8080 answers with a redirect to it. The session cookie is Secure, so everyone signs in once more. A line COOKIE_SECURE=false left in .env should be removed.
  • The sample store volume is handed to the unprivileged user on the first start (one chown, logged by the api container).
  • /api/metrics is no longer reachable through the web port: scrape http://api:8000/api/metrics on the compose network, optionally with METRICS_TOKEN.

If the stack refuses to start, the api container's log says which secret is missing or public and how to set it. If that log says password authentication failed for user "nik", the DB_PASSWORD of .env is not the one the database was created with: either put the old one back in .env, or give the database the new one, then start again: 

podman exec -it nik_db_1 psql -U nik -d nik -c "ALTER ROLE nik PASSWORD 'the value of DB_PASSWORD'"
podman compose up -d

Nothing is lost in either case: the data is in the volumes, which no step here touches.

Upgrading to PostgreSQL 18 (2.12.2)

Releases up to 2.12.1 run PostgreSQL 16 on the db-data volume. From 2.12.2 the Compose file runs PostgreSQL 18 on a new db-data-18 volume. PostgreSQL 18 cannot open the data files of 16, so the data moves once, with a dump and a restore, by deploy/upgrade-postgres.sh. Plan a short maintenance window: the app is down for the dump, the restore and the restart, a few minutes for a typical database.

  1. Pull the new release, but do not run compose up yet; the running stack is still the old one:

cd /opt/Nik && git pull

  1. Run the upgrade as root:

sudo deploy/upgrade-postgres.sh

It dumps the database with pg_dump (under /var/backups/nik, or BACKUP_DIR), counts the rows of every table, stops the stack, starts PostgreSQL 18 on the new volume, restores the dump, compares the row counts and starts the whole stack again. It stops at the first error and deletes nothing. Running it again is always safe: it carries on from where a previous run stopped, or says there is nothing to do.

  1. Check the app (sign in, open an incident), then the database version:

podman exec nik_db_1 psql -U nik -d nik -Atc 'SHOW server_version'

If compose up already ran on 2.12.2 before the script, the db container restarts in a loop and its log says run deploy/upgrade-postgres.sh: it refuses to create an empty database while the old data has not been moved (deploy/db-entrypoint.sh). Run the script anyway: it dumps the old volume with a temporary PostgreSQL 16 container instead.

The old data stays. The db-data volume is not modified; the new db container mounts it read-only. Keep it 14 days, then remove it (the script prints the exact name): 

podman volume rm nik_db-data

Rollback (within those 14 days): go back to the previous release and start it; it runs PostgreSQL 16 on the untouched db-data volume. Anything recorded after the upgrade is not in it: export the incidents you need first (incident JSON export, or the export of content as one file, which loads across database versions).

Manual deployment on RHEL

Tested on RHEL 8 and 9 (same steps on Rocky/AlmaLinux). nginx serves the static bundle and reverse-proxies /api/ to the backend, so the browser talks to a single origin — no CORS, and the session cookie just works. All commands assume a sudo-capable user.

This install has no analysis workers. The Code and Capabilities views, document previews, the isolated browser, Network Analysis and URL scans are containers (workers/) and report not configured here; samples and e-mails are still analysed statically, and every other tab works. Unless you have a reason to avoid containers on the host, use the Compose stack: it is the supported way and the one that isolates hostile files (see Security). The workers can also be run with the Compose file next to a manual backend, with their *_URL and *_TOKEN in nik.env.

Because incidents, users and the audit log live in PostgreSQL on the server, back up the database and the sample store with the backups Nik takes by itself (Settings → System → Backup, with BACKUP_DIR set) — the per-incident JSON export (incident export format) is an exchange/archival format, not the primary backup.

Step 1 — Build the static bundle

Build on the RHEL host or on any machine with Node 22+ and copy frontend/dist/ over. To install Node on RHEL (NodeSource, works on 8 and 9): 

curl -fsSL https://rpm.nodesource.com/setup_22.x | sudo bash -
sudo dnf install -y nodejs

Then, from the project's frontend/ directory:

npm ci            # clean, reproducible install from package-lock.json
npm run build     # outputs the static site into dist/

Step 2 — Install and configure PostgreSQL

Any PostgreSQL from 14 on works (CI tests 18); use the version your RHEL release ships.

sudo dnf install -y postgresql-server postgresql-contrib
sudo postgresql-setup --initdb
sudo systemctl enable --now postgresql

# Application role and database:
sudo -u postgres createuser --pwprompt nik
sudo -u postgres createdb -O nik nik

Enable password authentication. A fresh RHEL cluster uses ident/peer auth for local TCP connections, which rejects the app's nik login. Edit /var/lib/pgsql/data/pg_hba.conf so the local lines use scram-sha-256: 

# TYPE  DATABASE  USER  ADDRESS         METHOD
host    nik      nik  127.0.0.1/32    scram-sha-256
host    nik      nik  ::1/128         scram-sha-256

Then sudo systemctl reload postgresql. The connection string for the backend is:

postgresql+psycopg://nik:STRONG_PASSWORD@localhost/nik

The tables are created, and upgraded at every update, by the service itself when it starts (Step 3): there is nothing to create by hand.

Step 3 — Deploy the FastAPI backend (systemd)

The backend needs Python 3.11 or later. The default python3 of RHEL 8 and 9 is older: install python3.11 and call it by that name. Copy backend/ to /opt/nik/backend and build a virtualenv: 

sudo dnf install -y python3.11 python3.11-pip pango
sudo useradd --system --home /opt/nik --shell /sbin/nologin nik

sudo mkdir -p /opt/nik
sudo cp -r backend /opt/nik/backend
cd /opt/nik/backend

sudo python3.11 -m venv .venv
sudo .venv/bin/pip install --upgrade pip
sudo .venv/bin/pip install -r requirements.txt
sudo mkdir -p /var/lib/nik/samples      # the sample store: exclude it from the antivirus
sudo chown -R nik:nik /opt/nik /var/lib/nik

Keep the secrets in /etc/nik/nik.env (readable only by root and the service account). One setting per line, with no comment after a value: systemd would take it as part of the value. 

sudo mkdir -p /etc/nik
sudo tee /etc/nik/nik.env >/dev/null <<EOF
DATABASE_URL=postgresql+psycopg://nik:STRONG_PASSWORD@localhost/nik
SECRET_KEY=$(openssl rand -hex 32)
COOKIE_SECURE=true
SAMPLE_STORE=/var/lib/nik/samples
RUN_CREATE_ALL=false
EOF
sudo chmod 640 /etc/nik/nik.env
sudo chown root:nik /etc/nik/nik.env

Create /etc/systemd/system/nik-api.service — the API binds to loopback only; nginx is the sole public entry point: 

[Unit]
Description=Nik FastAPI backend (gunicorn/uvicorn)
After=network.target postgresql.service
Wants=postgresql.service

[Service]
Type=simple
User=nik
Group=nik
WorkingDirectory=/opt/nik/backend
EnvironmentFile=/etc/nik/nik.env
# Creates the schema on the first start and upgrades it after every update.
ExecStartPre=/opt/nik/backend/.venv/bin/alembic upgrade head
ExecStart=/opt/nik/backend/.venv/bin/gunicorn \
    -k app.serving.Worker --graceful-timeout 30 \
    app.main:app \
    --bind 127.0.0.1:8000 \
    --workers 3
Restart=on-failure
RestartSec=2

[Install]
WantedBy=multi-user.target

sudo systemctl daemon-reload
sudo systemctl enable --now nik-api.service
curl -s http://127.0.0.1:8000/api/health      # → {"status":"ok"}

Step 4 — Install nginx and place the static files

sudo dnf install -y nginx
sudo systemctl enable --now nginx

sudo mkdir -p /var/www/nik
sudo cp -r dist/* /var/www/nik/

Step 5 — SELinux (enforced by default on RHEL)

# a) Let nginx connect to the backend — without this, /api/ returns
#    502 Bad Gateway with an "AVC denied … name_connect" in the audit log:
sudo setsebool -P httpd_can_network_connect 1

# b) Label the static-file directory — or nginx returns 403 Forbidden:
sudo dnf install -y policycoreutils-python-utils
sudo semanage fcontext -a -t httpd_sys_content_t "/var/www/nik(/.*)?"
sudo restorecon -Rv /var/www/nik

Step 6 — TLS certificate

For an internal host a self-signed certificate is enough (clients must trust it or accept the browser warning). Replace the CN/SANs with your host: 

sudo mkdir -p /etc/pki/nginx/private
sudo openssl req -x509 -nodes -days 825 -newkey rsa:2048 \
  -keyout /etc/pki/nginx/private/nik.key \
  -out    /etc/pki/nginx/nik.crt \
  -subj "/CN=nik.example.internal" \
  -addext "subjectAltName=DNS:nik.example.internal,IP:10.0.0.10"

For an internet-facing host use a real certificate instead (e.g. Let's Encrypt: sudo dnf install -y certbot python3-certbot-nginx).

Step 7 — Ensure the .wasm MIME type

sql.js loads a WebAssembly module. RHEL 9's nginx already maps it; RHEL 8's does not. Add the line to the types { … } block of /etc/nginx/mime.types if missing: 

application/wasm  wasm;

Step 8 — nginx server block

Create /etc/nginx/conf.d/nik.conf:

# Redirect plain HTTP to HTTPS (the app requires a secure context)
server {
    listen 80;
    server_name nik.example.internal;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    http2 on;
    server_name nik.example.internal;

    ssl_certificate     /etc/pki/nginx/nik.crt;
    ssl_certificate_key /etc/pki/nginx/private/nik.key;

    # Large uploads (packet captures up to PCAP_MAX_MB, backup restore,
    # incidents with parsed artifacts) blow past nginx's 1m default and get
    # rejected with 413.
    client_max_body_size 600m;

    root  /var/www/nik;
    index index.html;
    include /etc/nginx/snippets/nik-headers.conf;

    # A mailbox (mbox, Maildir archive) can be as large as MAILBOX_MAX_MB:
    # only its upload is allowed that much, and it is not buffered to disk.
    location = /api/artifacts/mailboxes {
        client_max_body_size 2100m;
        proxy_request_buffering off;
        proxy_read_timeout 900s;
        proxy_send_timeout 900s;
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # Reverse-proxy the REST API to the gunicorn/uvicorn backend.
    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        # Opening a large packet capture in Wireshark's engine takes minutes.
        proxy_read_timeout 330s;
        proxy_send_timeout 330s;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        # The client's address as nginx saw it: the API limits sign-ins by it.
        proxy_set_header X-Forwarded-For   $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # Fingerprinted assets can be cached forever…
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
        include /etc/nginx/snippets/nik-headers.conf;
    }

    # …but never cache the HTML entry point, so updates are picked up.
    location = /index.html {
        add_header Cache-Control "no-cache";
        include /etc/nginx/snippets/nik-headers.conf;
    }

    # Serve static files; fall back to index.html
    location / {
        try_files $uri /index.html;
    }
}

If /api/ returns 502 Bad Gateway, the usual culprit is SELinux — confirm httpd_can_network_connect is on (Step 5a) and that nik-api.service is running (curl http://127.0.0.1:8000/api/health).

Put the security headers in a file of their own, /etc/nginx/snippets/nik-headers.conf, so the server block and the two locations that set a header of their own can include it (nginx drops the inherited ones there): 

add_header X-Content-Type-Options "nosniff" always;
add_header Referrer-Policy "no-referrer" always;
add_header X-Frame-Options "DENY" always;
add_header Strict-Transport-Security "max-age=31536000" always;
add_header Content-Security-Policy "default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob: https: http:; font-src 'self' data:; connect-src 'self'; worker-src 'self' blob:; frame-src 'self' blob:; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'" always;

That policy is the one the Compose image sends (frontend/security-headers.js): copy it again from there after an update.

Step 9 — Open the firewall and reload

Only 80/443 are exposed; the backend stays on 127.0.0.1:8000:

sudo firewall-cmd --permanent --add-service=http --add-service=https
sudo firewall-cmd --reload

sudo nginx -t
sudo systemctl reload nginx

Browse to https://nik.example.internal, create the first (admin) user and sign in.

Updating to a new version

# Frontend — rebuild and replace the static files:
(cd frontend && npm ci && npm run build)
sudo rm -rf /var/www/nik/*
sudo cp -r frontend/dist/* /var/www/nik/
sudo restorecon -Rv /var/www/nik

# Backend — refresh code and dependencies, restart the service:
sudo cp -r backend/* /opt/nik/backend/
sudo /opt/nik/backend/.venv/bin/pip install -r /opt/nik/backend/requirements.txt
sudo chown -R nik:nik /opt/nik
sudo systemctl restart nik-api.service

Upgrades do not wipe data: everything persists in PostgreSQL and in the sample store, and the service upgrades the database schema when it starts (alembic upgrade head, in the unit). Put python -m app.backups.upgrade in its place in the unit, with BACKUP_DIR set to a directory the nik user can write, to get what the container does: a snapshot of the database and a rehearsal of the migrations before each upgrade. The backups of Settings → Backup work the same without containers (the copy off the server then leaves from the API process, with AUTOMATION_WORKER=inline); deploy/restore.sh and deploy/rollback.sh are written for the Compose stack: here, run python -m app.backups.restore restore <file> from /opt/nik/backend as the nik user, with the service stopped.

The export of content as one file

At the foot of Settings → System → Backup, under Export as one file, admins can write every incident (imported artifacts, flags and notes included), every user account, the audit log and the shared detection settings to one JSON file, and add the content of such a file to another server. It was called Full backup before 6.7 and works as it did. Its use is moving content to another Nik (including SQLite dev → PostgreSQL production, since the file is database-agnostic).

It is not a backup of the server. The backups Nik takes by itself hold the whole database and every file, are encrypted, and are tested. This file is neither.

What it does not contain. The envelope holds the incident documents, the users, the audit log and the settings. It does not hold the files of the sample store (samples, e-mails, captures), their analyses, the registry of artifacts, the rule sets, the API keys, the webhooks or the threat-intelligence keys. An incident restored from it on another server shows its evidence tabs, flags and notes, and references to samples, e-mails and captures that are not there.

Export

GET /api/backup/export (admin only, logged as backup.export) downloads nik-backup-<timestamp>.json: 

{
  "app": "Nik",
  "type": "backup",
  "version": 1,
  "exportedAt": "2026-07-08T09:00:00.000Z",
  "users":     [ { "id": "…", "username": "…", "passwordHash": "…",
                   "roles": ["admin"], "createdAt": "…", "createdBy": null } ],
  "incidents": [ { "…full incident documents, artifacts included…": "" } ],
  "audit":     [ { "id": "…", "at": "…", "actor": "…", "action": "…" } ],
  "settings":  { "keywords": [ ], "businessHours": { } }
}

⚠️ The file contains bcrypt password hashes: treat it like a database dump (store it encrypted / access-controlled).

Import

POST /api/backup/import (admin only, logged as backup.import) adds what the file holds to the server, in a single all-or-nothing transaction. The screen shows what the file contains and asks before sending anything.

  • An incident whose id is not on the server is added, with its number when that number is free.
  • An account whose name is not on the server is added, with the roles and the password hash of the file: it signs in with the password it had on the other server.
  • An audit entry that is not on the server is added.
  • The detection settings of the file are taken only by a server that has none.
  • Nothing that is on the server is changed or deleted: an incident or an account that exists stays as it is, and so do sessions, second factors, settings, credentials and everything else the file knows nothing of. The answer says how many of each were added and how many were skipped.

Before 6.7 this import replaced the server: it deleted every account, every incident and every row of settings and made them again from the file, so whatever the file did not carry was lost. It no longer does. To put a server back as it was, restore a backup.
