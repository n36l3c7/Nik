Deployment

Run Nik with Docker or Podman Compose, harden it for production, install it by hand on RHEL, and back it up.

  1. Quick start with Docker / Podman
  2. Production deployment
  3. Full platform backup

Quick start with Docker / Podman

The fastest way to run the whole stack — nginx (static SPA + /api reverse proxy), the FastAPI backend and PostgreSQL — is the bundled Compose file: 

deploy/init-env.sh            # writes .env with fresh random secrets
docker compose up -d --build  # build the images and start the whole stack

Open https://localhost:8443 and create the first user — that account becomes the admin, so do it before anyone else can reach the port. The database schema is created and migrated by the api container at every start.

The stack does not start without its secrets (DB_PASSWORD, SECRET_KEY and one token per analysis worker) and refuses the values printed in .env.example, which are public. deploy/init-env.sh generates them; it is safe to run again.

On first start the web container self-signs a TLS certificate, so the browser shows a one-time "connection not private" warning — accept it to proceed (or mount a real certificate, see Docker / Podman in production). Nothing is served over plain HTTP: http://localhost:8080 redirects to the HTTPS address. 

docker compose logs -f api    # follow backend logs
docker compose ps             # container status
docker compose down           # stop (keeps the database volume)
docker compose down -v        # stop AND delete every volume: database, samples, certificate

Podman is a drop-in replacement (rootless is fine for ports 8080/8443):

deploy/init-env.sh
podman-compose up -d --build  # or: podman compose up -d --build

Every image in the Dockerfiles and the Compose file names its registry (docker.io/...), so Podman never has to guess one from /etc/containers/registries.conf (on RHEL it would try registry.redhat.io first and ask for Red Hat credentials). Keep it that way when you add an image: deploy/check-images.sh (run by CI) fails on a short name.

Production deployment

Upgrading from a "CSAP"-era deployment? The database role and name are now nik (was csap). A pre-existing Postgres volume still holds the old csap role/database, so either start on a fresh volume (docker volume rm nik_db-data-18 / your project's *_db-data-18), or keep the old names by setting DB_USER, DB_NAME and the compose POSTGRES_* back to csap, or rename in place with ALTER ROLE csap RENAME TO nik; and ALTER DATABASE csap RENAME TO nik;. The session cookie also changed name, so everyone re-logs in once.

Docker / Podman in production

The Compose stack serves the app over HTTPS on :8443; :8080 only redirects there. On first start the web container self-signs a certificate (for TLS_HOSTNAME, default localhost) into the web-certs volume, so HTTPS works out of the box — browsers show the usual warning until the certificate is trusted or replaced. Set TLS_HOSTNAME to the name users type, and for a real deployment pick one of:

  • Option A (recommended): provide your own certificate — internal CA or Let's Encrypt — as nik.crt / nik.key in /etc/nginx/certs; the startup script never overwrites an existing pair. Easiest wiring: swap the named volume for a bind mount in docker-compose.yml (- ./certs:/etc/nginx/certs).
  • Option B: front the stack with a host reverse proxy that terminates TLS (nginx, Caddy, Traefik) proxying to https://127.0.0.1:8443 (the upstream certificate is the self-signed one: tell the proxy to accept it), and bind the two port mappings to 127.0.0.1.

To regenerate the self-signed certificate (e.g. after changing TLS_HOSTNAME): docker compose down && docker volume rm nik_web-certs, then start the stack again.

Notes for Podman on RHEL:

  • Rootless works out of the box — only host ports below 1024 require rootful Podman (or lowering net.ipv4.ip_unprivileged_port_start).
  • Start on boot: restart: unless-stopped does not bring the stack back after a reboot with podman-compose. Install the systemd units (next paragraph): nik.service runs podman compose up -d at boot.
  • SELinux: named volumes (as used here) are relabeled automatically. If you switch to a bind mount, add :Z to that mount.

Start on boot and nightly backups (systemd). From the repository root, as root:

sudo deploy/install-systemd.sh

It installs and enables three units, with the repository path and the compose command (podman compose, or docker compose where Podman is absent) filled in:

  • nik.service — compose up -d at boot, compose down at shutdown;
  • nik-backup.timer + nik-backup.service — deploy/backup.sh every night at 02:30 (a run missed while the server was off happens at the next boot).

Options: --backup-dir /srv/nik-backups (default /var/backups/nik), --keep-days 30 (default 14), --backup-time 03:15, --no-backup, --uninstall. Check with systemctl status nik.service nik-backup.timer and journalctl -u nik-backup; run a backup now with systemctl start nik-backup.service.

Backups & restore. Each backup is a directory nik-YYYYMMDD-HHMMSS/, readable by root only, with:

File Content
db.dump PostgreSQL dump (pg_dump -Fc): incidents, users, settings, audit log, sample analyses
samples.tar the sample store: live malware, keep the backups private
env the .env file (secrets, database password)
SHA256SUMS checksums: sha256sum -c SHA256SUMS before restoring

deploy/backup.sh also runs by hand (ENGINE, BACKUP_DIR, KEEP_DAYS in the environment). It reaches the db and api containers with podman exec / docker exec, found by their Compose labels, never through compose exec: podman-compose prints diagnostics on stdout, which would corrupt the dump. To restore on a running stack (B = the backup directory; container names as in podman ps): 

cd "$B" && sha256sum -c SHA256SUMS
podman exec -i nik_db_1 pg_restore -U nik -d nik --clean --if-exists < "$B/db.dump"
podman exec -i nik_api_1 tar -C /app/samples -xf - < "$B/samples.tar"
podman restart nik_api_1    # also gives the restored samples their permissions

On a new server, put env back as .env before the first compose up, so the database password matches the dump. The in-app Full backup (full platform backup) remains the way to move data across database engines; it does not include the sample files.

Updates:

git pull
podman compose up -d --build    # rebuild images, recreate containers, keep data

Release notes say when an update needs more than this, as 3.0 and the move to PostgreSQL 18 below do.

Upgrading to 3.0

Release 3.0 makes the safe configuration the only one: the stack no longer starts with secrets that are missing or still at their example values, plain HTTP only redirects to HTTPS, and the backend runs unprivileged. Coming from 2.x, on the server: 

cd /opt/Nik && git pull
sudo deploy/backup.sh /var/backups/nik    # as before every upgrade
sudo deploy/init-env.sh                   # completes .env, changes nothing that is already good
sudo podman compose up -d --build
  • deploy/init-env.sh generates what .env lacks. If SECRET_KEY was never set (or is an example value), it writes a new one and keeps the old as SECRET_KEY_PREVIOUS: at the next start the provider API keys and TLS key logs already stored are re-encrypted with the new key, and the line can then be removed. If DB_PASSWORD was never set, it writes the old default, which is what the existing database uses.
  • Everyone now uses https://<host>:8443; http://<host>:8080 answers with a redirect to it. The session cookie is Secure, so everyone signs in once more. A line COOKIE_SECURE=false left in .env should be removed.
  • The sample store volume is handed to the unprivileged user on the first start (one chown, logged by the api container).
  • /api/metrics is no longer reachable through the web port: scrape http://api:8000/api/metrics on the compose network, optionally with METRICS_TOKEN.

If the stack refuses to start, the api container's log says which secret is missing or public and how to set it.

Upgrading to PostgreSQL 18 (2.12.2)

Releases up to 2.12.1 run PostgreSQL 16 on the db-data volume. From 2.12.2 the Compose file runs PostgreSQL 18 on a new db-data-18 volume. PostgreSQL 18 cannot open the data files of 16, so the data moves once, with a dump and a restore, by deploy/upgrade-postgres.sh. Plan a short maintenance window: the app is down for the dump, the restore and the restart, a few minutes for a typical database.

  1. Pull the new release, but do not run compose up yet; the running stack is still the old one:

bash cd /opt/Nik && git pull

  1. Run the upgrade as root:

bash sudo deploy/upgrade-postgres.sh

It takes a full backup with deploy/backup.sh (under /var/backups/nik, or BACKUP_DIR), counts the rows of every table, stops the stack, starts PostgreSQL 18 on the new volume, restores the dump, compares the row counts and starts the whole stack again. It stops at the first error and deletes nothing. Running it again is always safe: it carries on from where a previous run stopped, or says there is nothing to do.

  1. Check the app (sign in, open an incident), then the database version:

bash podman exec nik_db_1 psql -U nik -d nik -Atc 'SHOW server_version'

If compose up already ran on 2.12.2 before the script, the db container restarts in a loop and its log says run deploy/upgrade-postgres.sh: it refuses to create an empty database while the old data has not been moved (deploy/db-entrypoint.sh). Run the script anyway: it dumps the old volume with a temporary PostgreSQL 16 container instead.

The old data stays. The db-data volume is not modified; the new db container mounts it read-only. Keep it 14 days, then remove it (the script prints the exact name): 

podman volume rm nik_db-data

Rollback (within those 14 days): go back to the previous release and start it; it runs PostgreSQL 16 on the untouched db-data volume. Anything recorded after the upgrade is not in it: export the incidents you need first (incident JSON export, or the in-app Full backup, which restores across database versions). 

podman compose down
git checkout v2.12.1
podman compose up -d --build

Manual deployment on RHEL

Tested on RHEL 8 and 9 (same steps on Rocky/AlmaLinux). nginx serves the static bundle and reverse-proxies /api/ to the backend, so the browser talks to a single origin — no CORS, and the session cookie just works. All commands assume a sudo-capable user.

Because incidents, users and the audit log live in PostgreSQL on the server, back up the database (pg_dump) or use the in-app Full backup (full platform backup) — the per-incident JSON export (incident export format) is an exchange/archival format, not the primary backup.

Step 1 — Build the static bundle

Build on the RHEL host or on any machine with Node 22+ and copy frontend/dist/ over. To install Node on RHEL (NodeSource, works on 8 and 9): 

curl -fsSL https://rpm.nodesource.com/setup_20.x | sudo bash -
sudo dnf install -y nodejs

Then, from the project's frontend/ directory:

npm ci            # clean, reproducible install from package-lock.json
npm run build     # outputs the static site into dist/

Step 2 — Install and configure PostgreSQL

Any PostgreSQL from 14 on works (CI tests 16 and 18); use the version your RHEL release ships.

sudo dnf install -y postgresql-server postgresql-contrib
sudo postgresql-setup --initdb
sudo systemctl enable --now postgresql

# Application role and database:
sudo -u postgres createuser --pwprompt nik
sudo -u postgres createdb -O nik nik

Enable password authentication. A fresh RHEL cluster uses ident/peer auth for local TCP connections, which rejects the app's nik login. Edit /var/lib/pgsql/data/pg_hba.conf so the local lines use scram-sha-256: 

# TYPE  DATABASE  USER  ADDRESS         METHOD
host    nik      nik  127.0.0.1/32    scram-sha-256
host    nik      nik  ::1/128         scram-sha-256

Then sudo systemctl reload postgresql. The connection string for the backend is:

postgresql+psycopg://nik:STRONG_PASSWORD@localhost/nik

Tables (users, sessions, incidents, audit_log, settings) are created automatically on the API's first startup — no migration step.

Step 3 — Deploy the FastAPI backend (systemd)

The backend needs Python 3.11+ (RHEL 9 ships it; on RHEL 8 install python3.11). Copy backend/ to /opt/nik/backend and build a virtualenv: 

sudo dnf install -y python3 python3-pip
sudo useradd --system --home /opt/nik --shell /sbin/nologin nik

sudo mkdir -p /opt/nik
sudo cp -r backend /opt/nik/backend
cd /opt/nik/backend

sudo python3 -m venv .venv
sudo .venv/bin/pip install --upgrade pip
sudo .venv/bin/pip install -r requirements.txt
sudo chown -R nik:nik /opt/nik

Keep the secrets in /etc/nik/nik.env (readable only by root and the service account):

sudo mkdir -p /etc/nik
sudo tee /etc/nik/nik.env >/dev/null <<'EOF'
DATABASE_URL=postgresql+psycopg://nik:STRONG_PASSWORD@localhost/nik
SECRET_KEY=replace-with-a-long-random-string   # e.g. `openssl rand -hex 32`
COOKIE_SECURE=true                             # requires HTTPS
EOF
sudo chmod 640 /etc/nik/nik.env
sudo chown root:nik /etc/nik/nik.env

Create /etc/systemd/system/nik-api.service — the API binds to loopback only; nginx is the sole public entry point: 

[Unit]
Description=Nik FastAPI backend (gunicorn/uvicorn)
After=network.target postgresql.service
Wants=postgresql.service

[Service]
Type=simple
User=nik
Group=nik
WorkingDirectory=/opt/nik/backend
EnvironmentFile=/etc/nik/nik.env
ExecStart=/opt/nik/backend/.venv/bin/gunicorn \
    -k uvicorn.workers.UvicornWorker \
    app.main:app \
    --bind 127.0.0.1:8000 \
    --workers 3
Restart=on-failure
RestartSec=2

[Install]
WantedBy=multi-user.target

sudo systemctl daemon-reload
sudo systemctl enable --now nik-api.service
curl -s http://127.0.0.1:8000/api/health      # → {"status":"ok"}

Step 4 — Install nginx and place the static files

sudo dnf install -y nginx
sudo systemctl enable --now nginx

sudo mkdir -p /var/www/nik
sudo cp -r dist/* /var/www/nik/

Step 5 — SELinux (enforced by default on RHEL)

# a) Let nginx connect to the backend — without this, /api/ returns
#    502 Bad Gateway with an "AVC denied … name_connect" in the audit log:
sudo setsebool -P httpd_can_network_connect 1

# b) Label the static-file directory — or nginx returns 403 Forbidden:
sudo dnf install -y policycoreutils-python-utils
sudo semanage fcontext -a -t httpd_sys_content_t "/var/www/nik(/.*)?"
sudo restorecon -Rv /var/www/nik

Step 6 — TLS certificate

For an internal host a self-signed certificate is enough (clients must trust it or accept the browser warning). Replace the CN/SANs with your host: 

sudo mkdir -p /etc/pki/nginx/private
sudo openssl req -x509 -nodes -days 825 -newkey rsa:2048 \
  -keyout /etc/pki/nginx/private/nik.key \
  -out    /etc/pki/nginx/nik.crt \
  -subj "/CN=nik.example.internal" \
  -addext "subjectAltName=DNS:nik.example.internal,IP:10.0.0.10"

For an internet-facing host use a real certificate instead (e.g. Let's Encrypt: sudo dnf install -y certbot python3-certbot-nginx).

Step 7 — Ensure the .wasm MIME type

sql.js loads a WebAssembly module. RHEL 9's nginx already maps it; RHEL 8's does not. Add the line to the types { … } block of /etc/nginx/mime.types if missing: 

application/wasm  wasm;

Step 8 — nginx server block

Create /etc/nginx/conf.d/nik.conf:

# Redirect plain HTTP to HTTPS (the app requires a secure context)
server {
    listen 80;
    server_name nik.example.internal;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    http2 on;
    server_name nik.example.internal;

    ssl_certificate     /etc/pki/nginx/nik.crt;
    ssl_certificate_key /etc/pki/nginx/private/nik.key;

    # Large uploads (packet captures up to PCAP_MAX_MB, backup restore,
    # incidents with parsed artifacts) blow past nginx's 1m default and get
    # rejected with 413.
    client_max_body_size 600m;

    root  /var/www/nik;
    index index.html;

    # Reverse-proxy the REST API to the gunicorn/uvicorn backend.
    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        # Opening a large packet capture in Wireshark's engine takes minutes.
        proxy_read_timeout 330s;
        proxy_send_timeout 330s;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # Fingerprinted assets can be cached forever…
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    # …but never cache the HTML entry point, so updates are picked up.
    location = /index.html {
        add_header Cache-Control "no-cache";
    }

    # Serve static files; fall back to index.html
    location / {
        try_files $uri /index.html;
    }
}

If /api/ returns 502 Bad Gateway, the usual culprit is SELinux — confirm httpd_can_network_connect is on (Step 5a) and that nik-api.service is running (curl http://127.0.0.1:8000/api/health).

Step 9 — Open the firewall and reload

Only 80/443 are exposed; the backend stays on 127.0.0.1:8000:

sudo firewall-cmd --permanent --add-service=http --add-service=https
sudo firewall-cmd --reload

sudo nginx -t
sudo systemctl reload nginx

Browse to https://nik.example.internal, create the first (admin) user and sign in.

Updating to a new version

# Frontend — rebuild and replace the static files:
(cd frontend && npm ci && npm run build)
sudo rm -rf /var/www/nik/*
sudo cp -r frontend/dist/* /var/www/nik/
sudo restorecon -Rv /var/www/nik

# Backend — refresh code and dependencies, restart the service:
sudo cp -r backend/* /opt/nik/backend/
sudo /opt/nik/backend/.venv/bin/pip install -r /opt/nik/backend/requirements.txt
sudo chown -R nik:nik /opt/nik
sudo systemctl restart nik-api.service

Upgrades do not wipe data: everything persists in PostgreSQL, and new tables are created on startup. Take a pg_dump (or an in-app full backup, full platform backup) before upgrading if you want a rollback point.

Full platform backup

Admins can export and restore the entire platform — every incident (imported artifacts, flags and notes included), every user account, the audit log and the shared detection settings — from the sidebar's Full backup button. Typical uses: a safety copy before an upgrade, or moving a deployment to another machine (including SQLite dev → PostgreSQL production, since the backup is database-agnostic).

Routine upgrades do not require this: data persists in PostgreSQL across frontend/backend updates and container rebuilds. The full backup is insurance and a migration vehicle, complementary to pg_dump.

The backup envelope holds the analysis of every malware sample, not the raw files: those live in the sample store (SAMPLE_STORE, the sample-store volume in Compose). Copy that directory alongside the backup if the samples themselves must survive.

Export

GET /api/backup/export (admin only, logged as backup.export) downloads nik-backup-<timestamp>.json: 

{
  "app": "Nik",
  "type": "backup",
  "version": 1,
  "exportedAt": "2026-07-08T09:00:00.000Z",
  "users":     [ { "id": "…", "username": "…", "passwordHash": "…",
                   "role": "admin", "createdAt": "…", "createdBy": null } ],
  "incidents": [ { "…full incident documents, artifacts included…": "" } ],
  "audit":     [ { "id": "…", "at": "…", "actor": "…", "action": "…" } ],
  "settings":  { "keywords": [ ], "businessHours": { } }
}

⚠️ The file contains bcrypt password hashes: treat it like a database dump (store it encrypted / access-controlled).

Restore

POST /api/backup/import (admin only, logged as backup.import) replaces all current data with the file's content, in a single all-or-nothing transaction. The UI asks for explicit confirmation and shows what the file contains before sending anything.

Guarantees:

  • Atomic — on any validation or database error, nothing is changed.
  • No lockout — the importing admin stays signed in: if their username exists in the backup, the session re-attaches to that account (whose password becomes the one from the backup); otherwise their current account is re-inserted unchanged alongside the imported users.
  • Sessions are reset — every other analyst must sign in again (with the credentials from the backup).

After a successful restore the app reloads and every context refetches the restored data.
