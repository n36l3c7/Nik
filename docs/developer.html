Local development setup

Prerequisites: Node.js 22+ (with npm; 20.19 or later also works) and Python 3.11–3.13. No database server is needed: the backend defaults to a local SQLite file. The incident report's PDF needs the Pango libraries WeasyPrint uses (Debian/Ubuntu: apt install libpango-1.0-0 libpangoft2-1.0-0; Fedora/RHEL: dnf install pango; macOS: brew install pango); everything else, the HTML report included, works without them. The container image installs them.

Backend (terminal 1):

cd backend

python -m venv .venv
# Windows (PowerShell):
.venv\Scripts\Activate.ps1
# Linux/macOS:
source .venv/bin/activate

pip install -r requirements.txt

cp .env.example .env
# IMPORTANT for dev over plain HTTP: set COOKIE_SECURE=false in backend/.env,
# otherwise the browser drops the session cookie and login won't stick.

uvicorn app.main:app --reload --port 8000

Health check: curl http://localhost:8000/api/health → {"status":"ok"}.

Frontend (terminal 2):

cd frontend
npm install
npm run dev        # http://localhost:5173

The Vite dev server proxies every /api request to http://127.0.0.1:8000 (see frontend/vite.config.js), so the frontend and backend work together end-to-end with no CORS configuration. On first load, create the first user (it becomes the admin) and sign in.

Other npm scripts (from frontend/):

npm run build      # production build (static site in dist/)
npm run preview    # serve the production build locally
npm test           # frontend unit tests (Node's built-in test runner, no deps)
npm run lint       # ESLint (recommended + React hooks rules), must report no problems
npm run format     # Prettier: rewrite JS/JSX, CSS, JSON, HTML and YAML in place
npm run format:check  # Prettier in check mode (what CI runs)
npm run test:e2e   # Playwright smoke test of the whole stack (build first)

Line endings are LF everywhere, including Windows checkouts: .gitattributes sets * text=auto eol=lf, which overrides core.autocrlf, so Prettier and Ruff see the same files as CI.

The end-to-end test (frontend/e2e/smoke.spec.js, frontend/playwright.config.js) starts the backend on a throw-away SQLite database and the production build behind vite preview (which proxies /api, like the dev server), then drives the app as an analyst would: first-run setup, sign-in, a new incident, the evidence files of frontend/e2e/fixtures/ dropped on the app, the timeline. It needs npm run build, the backend dependencies on PATH (activate the venv) and a Chromium from npx playwright install chromium. With the analyzer worker running and E2E_ANALYZER_URL / E2E_ANALYZER_TOKEN set (CI does both), it also checks the Code view against real rizin output; likewise E2E_CAPA_URL / E2E_CAPA_TOKEN for the Capabilities view and the capa worker. Without them it checks the "not configured" messages.

Analyzer worker in development. The Code view needs the rizin worker (workers/analyzer/). With Docker: 

docker build -t nik-analyzer workers/analyzer
docker run -d --name nik-analyzer -p 127.0.0.1:8700:8700 \
  -v "$PWD/backend/samples:/samples:ro" -e ANALYZER_TOKEN=dev-token nik-analyzer
# backend/.env: ANALYZER_URL=http://127.0.0.1:8700  ANALYZER_TOKEN=dev-token

Its own checks: cd workers/analyzer && ruff check . && python -m pytest tests (the tests use recorded rizin output; the live test runs only where rizin is installed).

capa worker in development. The Capabilities view needs the capa worker (workers/capa/): 

docker build -t nik-capa workers/capa
docker run -d --name nik-capa -p 127.0.0.1:8710:8710 --read-only --tmpfs /tmp \
  -v "$PWD/backend/samples:/samples:ro" -e CAPA_TOKEN=dev-capa-token nik-capa
# backend/.env: CAPA_URL=http://127.0.0.1:8710  CAPA_TOKEN=dev-capa-token

Its own checks: cd workers/capa && ruff check . && python -m pytest tests (on a recorded capa report; capa itself is not needed).

Backend tests run with pytest, the linter with ruff check . and the formatter with ruff format . (--check in CI), all from backend/ after pip install -r requirements-dev.txt; Ruff settings for every Python component live in ruff.toml at the repository root. Formatting is enforced, not reviewed: run the formatters before committing. Prettier also checks docs/, the workflows and the Compose file; Markdown is excluded (see frontend/.prettierignore). The documentation site in docs/ is updated in the same change as the behaviour it describes.

CI (.github/workflows/ci.yml) runs on every pull request, and a change is done only when all of it passes:

  • lint: Ruff on the backend and the workers, with nothing else to install;
  • backend-tests and backend-postgres: the backend suite on SQLite, and on PostgreSQL 18 after alembic upgrade head;
  • frontend-build: ESLint, Prettier, the unit tests and the build;
  • stack: .github/scripts/stack-smoke.sh starts the database, the backend and the web server from the Compose file, as an operator would, and checks what only the running stack shows (the redirect to HTTPS, the security headers, the unprivileged backend, the refusal of the example secrets). Run it locally the same way: it uses its own project name and ports;
  • e2e: builds the five worker images, runs each worker's tests inside its image, then the end-to-end suite against them.

Steps that download from the network go through .github/scripts/retry.sh, so a mirror that does not answer for a moment does not fail the build. Actions are pinned to a commit, with the version in a comment that Dependabot keeps in step.

Dependency audits. The Audit workflow (.github/workflows/audit.yml) runs pip-audit on the backend and on the workers that decode hostile files (their packages are pinned in workers/*/requirements.txt), npm audit --audit-level=high and shellcheck on every pull request and every Monday, so a new CVE in an unchanged dependency fails the build without waiting for a code change. Every Monday it also builds each image from scratch and scans it with Trivy: a critical vulnerability with a fix fails the job, the high ones are listed in its summary. Locally: pip-audit -r backend/requirements.txt and npm audit. Dependabot (.github/dependabot.yml) opens one grouped pull request a month per ecosystem (npm, pip, Docker, Compose, Actions) with the minor and patch releases, and a pull request as soon as a dependency gets a security fix; enable the latter in the repository's Settings → Code security. Major releases are left out (except for Actions): they need migration work and are planned as their own change.

Upgrading an existing database: run alembic upgrade head from backend/ after pulling a release that adds a migration (the Docker image does this on start). A database created by the dev-mode create_all is adopted by the baseline migration. Upgrading to 2.0.0 rewrites every incident once (migration 0003_browser_profiles: browser data moves into a "Default" profile); on large databases the first start takes longer — take a backup first.

Tailwind v4 is wired in through the Vite plugin (@tailwindcss/vite), so there is no tailwind.config.js and no extra setup step.

Documentation and screenshots

The documentation is this site, plain HTML in docs/ with one stylesheet: update it in the same pull request as the behaviour it describes. The screenshots of the user guide (docs/img/) are taken by a Playwright script that drives a fresh install with the evidence of frontend/e2e/fixtures/. Retake them after a change to the interface: 

cd frontend
npm run build
npm run docs:screenshots   # writes docs/img/*.png

It needs the same backend environment as the end-to-end test. Start the packet capture worker and set E2E_PCAP_URL / E2E_PCAP_TOKEN for the Network Analysis screenshots; without it they are skipped and the previous images stay. The URL Analysis screenshot also needs the isolated browser (E2E_BROWSER_URL / E2E_BROWSER_TOKEN) and DOCS_SCAN_URL, an address that worker can reach serving frontend/e2e/fixtures/signin.html (it refuses private addresses).

Add a new analysis tab

The frontend/src/config/tabs.js registry is the only existing file to modify. Example: a "DNS Logs" tab.

Step 1 — Create the tab component. Every tab is a component with a default export that receives the active incident as a prop. Create frontend/src/components/tabs/DnsLogsTab.jsx: 

import { useState } from 'react'
import { Network, Upload, Trash2 } from 'lucide-react'
import { useIncidents } from '../../context/IncidentContext.jsx'
import { generateId } from '../../lib/id.js'
import { Card, Button, DataTable, EmptyState, Badge } from '../ui/index.js'
import { formatDateTime, anyToMs } from '../../lib/time.js'

export default function DnsLogsTab({ incident }) {
  const { updateTabData, clearTabData } = useIncidents()
  const dns = incident.data.dns ?? { queries: [], meta: null }
  const [error, setError] = useState(null)

  async function handleFile(file) {
    setError(null)
    try {
      const rows = JSON.parse(await file.text()) // [{ timestamp, domain, type, client }]
      const queries = rows
        .filter((r) => r.domain)
        .map((r) => ({
          id: generateId(),
          domain: r.domain,
          type: r.type ?? 'A',
          client: r.client ?? null,
          timestamp: anyToMs(r.timestamp),
        }))
      updateTabData(incident.id, 'dns', {
        queries,
        meta: { fileName: file.name, format: 'json',
                rows: queries.length, importedAt: new Date().toISOString() },
      })
    } catch (err) {
      setError(err.message ?? 'Invalid file.')
    }
  }

  if (dns.queries.length === 0) {
    return (
      <EmptyState
        icon={Network}
        title="No DNS logs loaded"
        message="Import a JSON export of DNS queries to start the analysis."
        action={
          <label className="cursor-pointer">
            <Button variant="primary" icon={Upload}>Import DNS logs</Button>
            <input type="file" hidden accept=".json"
                   onChange={(e) => e.target.files[0] && handleFile(e.target.files[0])} />
          </label>
        }
      />
    )
  }

  return (
    <div className="space-y-6">
      {error && <p className="text-sm text-red-500">{error}</p>}
      <Card
        title="DNS queries"
        icon={Network}
        actions={
          <Button variant="ghost" size="sm" icon={Trash2}
                  onClick={() => clearTabData(incident.id, 'dns')}>
            Clear data
          </Button>
        }
      >
        <DataTable
          data={dns.queries}
          searchKeys={['domain', 'client']}
          defaultSort={{ key: 'timestamp', dir: 'desc' }}
          columns={[
            { key: 'timestamp', label: 'Date/Time', sortable: true,
              className: 'font-mono text-xs',
              render: (row) => formatDateTime(row.timestamp) },
            { key: 'domain', label: 'Domain', sortable: true, className: 'font-mono text-xs' },
            { key: 'type', label: 'Type', render: (row) => <Badge color="cyan">{row.type}</Badge> },
            { key: 'client', label: 'Client', className: 'font-mono text-xs' },
          ]}
          emptyMessage="No query matches the filters"
        />
      </Card>
    </div>
  )
}

Step 2 — Register the tab in frontend/src/config/tabs.js:

// at the top of the file, next to the other lazy tabs:
const DnsLogsTab = lazy(() => import('../components/tabs/DnsLogsTab.jsx'))

// inside ANALYSIS_TABS, next to the tabs of its group (array order = order
// in the TabBar):
{
  id: 'dns',                  // unique, used to select the tab
  label: 'DNS Logs',          // label in the TabBar
  group: 'threats',           // 'overview' | 'threats' | 'host': a thin rule separates groups
  icon: Network,              // lucide-react icon (import at the top)
  component: DnsLogsTab,      // lazy component → separate build chunk
  dataKey: 'dns',             // key under incident.data
  defaultData: {              // initial structure for every new incident
    queries: [],
    meta: null,
  },
},

Step 3 — Nothing else is needed. The TabBar maps ANALYSIS_TABS, App.jsx renders the active component inside <Suspense>, and buildDefaultIncidentData() includes the new dataKey in every new incident. Existing incidents are covered by normalizeIncident(), which fills missing dataKeys with the registry defaultData on load — no manual migration. The registry defaultData is also the reset state used by clearTabData.

Extend the SOC detection rules

End users edit rules at runtime from Settings (the ⚙ icon in the header): add/edit/remove suspicious keywords and change the business hours. Changes are stored server-side and apply to all analysts and all incidents. This section is about extending things via code.

The engine has three parts:

  • frontend/src/config/detectionRules.js — the factory defaults (DEFAULT_SUSPICIOUS_KEYWORDS, DEFAULT_BUSINESS_HOURS);
  • frontend/src/context/SettingsContext.jsx — the runtime state (useSettings()) plus useSocEngine(), a memoized engine;
  • frontend/src/domain/soc.js — createSocEngine({ keywords, businessHours }), which compiles the regexes and analyzes events (engine.analyze(entry)).

Add a default keyword rule — add an object to DEFAULT_SUSPICIOUS_KEYWORDS; regexes are compiled case-insensitively and applied to URL + title + file name of each event: 

{
  id: 'rat-tools',                 // unique rule identifier
  label: 'RAT / C2',               // badge text in the UI
  // Regex (string source → escape backslashes twice).
  // Use \\b for short keywords that risk false positives: without it,
  // "rat" would match "administrator" or "strategy".
  pattern: '\\brat\\b|cobalt[-_ ]?strike|meterpreter|\\bc2\\b',
  severity: 'high',                // 'high' (red) | 'medium' (amber)
  description: 'References to a Remote Access Trojan or a C2 framework.',
},

Severity logic in engine.analyze(): at least one high match → red row; only medium matches (or just a time anomaly) → amber row.

Business hours — factory default in detectionRules.js:

export const DEFAULT_BUSINESS_HOURS = {
  startHour: 8,        // start of the window (inclusive)
  endHour: 18,         // end of the window (exclusive)
  flagWeekends: true,  // if true, the whole weekend is "outside hours"
}

isOutsideBusinessHours(ms, businessHours) treats hours < startHour || >= endHour as outside, plus the weekend when flagWeekends is set.

Add a new type of detection (example: URLs pointing at a bare IP address, a classic C2/phishing indicator) — extend frontend/src/domain/soc.js in three places: 

// a) the analysis function:
export function isRawIpUrl(url) {
  try {
    return /^\d{1,3}(\.\d{1,3}){3}$/.test(new URL(url).hostname)
  } catch {
    return false
  }
}

// b) include it in analyze() inside createSocEngine:
const isRawIp = isRawIpUrl(entry.url)
// … and let it contribute to `severity` and the returned object.

// c) render it in EventsSection.jsx, next to the keyword badges:
{event.soc.isRawIp && (
  <Badge color="amber" title="URL with a literal IP address: possible C2/phishing">
    direct IP
  </Badge>
)}

If the new signal should appear in the StatCards, update computeSocStats accordingly; optionally add an option to the detection filter in the events section.

Browsers, parsers and formats

Add a browser. Browsers are a registry in frontend/src/config/browsers.js: adding an entry to the BROWSERS array makes the sub-tab appear and wires up upload, path hints and sections automatically. Each browser declares id, label, icon, engine ('chromium' | 'firefox' | 'safari'), accent, optional platforms (host OSes it exists on — Safari is ['macos']; the path note warns when the incident's OS is not listed), profilePaths, artifacts and sources (the files to load, each with key, produces, paths and hint). A Chromium browser can reuse chromiumSources(bases); a brand-new engine also needs a branch in the parsers, and in backend/app/parsing/ for API uploads. Paths may contain <profile>, explained by the optional profileHint.

Profiles. Every browser holds one or more profiles; the profile helpers (normalization of pre-2.0.0 data, ordering, name validation, labels) live in frontend/src/domain/browserProfiles.js and mirror backend/app/browser_profiles.py. A browser always keeps at least one profile; deleting one keeps the flags placed on its rows, shown as coming from a deleted profile.

The parsing dispatcher. All parsing goes through parseBrowserSource(file, engine, source) in frontend/src/parsers/fileParsers.js: 

parseBrowserSource(file, engine, source)
  → Promise<{ produced, format }>
// produced: { history?, downloads?, bookmarks?, shortcuts? }
// format:   'sqlite' | 'plist' | 'json' | 'csv'

Pipeline: isSqliteBuffer() (magic string in the first 16 bytes) → if SQLite, delegate to parseSqliteSource(buffer, engine, sourceKey) in sqliteParser.js (Chromium parsers over urls/visits/downloads/ omni_box_shortcuts, Firefox parsers over moz_places/moz_historyvisits/ moz_bookmarks/moz_annos, Safari over history_items/history_visits); else, a property list (bplist00 header or an XML <plist>) is decoded by plistParser.js — dependency-free — and mapped by safariParser.js (Safari only); otherwise decode as text → JSON or CSV (papaparse). Field mapping is lenient (multiple aliases per field, English and Italian column names), timestamps are normalized, and every row gets a unique id.

A source owns its produces: re-importing it replaces those artifacts; removing it (removeBrowserSource) zeroes them. Errors are always throw new Error('<message>'), surfaced by FileUploadZone.

Add a field alias or a format. For a tool that names fields differently (e.g. visited_at), extend the relevant *_ALIASES chain in fileParsers.js. For a new format (e.g. NDJSON), add a branch in parseBrowserSource before the CSV fallback and reuse the existing mappers (mapHistoryRows, mapDownloadRows, mapBookmarkRows, mapShortcutRows). A new format value also needs its color in the Badge in FileUploadZone.jsx.

Timestamps: mind the engine.

  • Chromium uses "WebKit time" (µs since 1601) → webkitToMs (ms = µs / 1000 − 11644473600000).
  • Firefox uses "PRTime" (µs since 1970) → firefoxToMs (ms = µs / 1000).
  • Safari uses Mac absolute time (seconds since 2001, fractional) → macToMs (ms = (s + 978307200) × 1000); plist dates are decoded to Date.

Getting the conversion wrong shifts dates by ~369 years: always use the right helper for the engine.

UI kit reference

All components live in frontend/src/components/ui/ with a default export, re-exported from the barrel frontend/src/components/ui/index.js: 

import { Button, Card, Badge, Modal, DataTable, EmptyState, ErrorBoundary,
         SearchInput, Select, StatCard, AsciiSkull, MicroSkull } from '../ui/index.js'

ErrorBoundary — keeps a rendering error inside the view that threw it. App wraps the active analysis tab in one, and the Code view wraps its graph and pseudo-C panels: the broken view shows the error and a Reload this view button while the rest of Nik keeps working. Pass a resetKey (e.g. tab and incident) so that moving elsewhere clears the error. New tabs get it for free.

DataTable — the workhorse for every tabular view (events, bookmarks, shortcuts, the audit log and any future tab). Memoized internal pipeline: filter (search) → sort → paginate. 

<DataTable
  columns={[ /* see below */ ]}
  data={rows}                       // rows (pre-filtered by the parent for custom filters)
  searchKeys={['url', 'title']}     // string keys for the built-in search; [] = no search bar
  searchPlaceholder="Search…"
  defaultPageSize={25}
  pageSizeOptions={[10, 25, 50, 100]}
  defaultSort={{ key: 'time', dir: 'desc' }}  // null = no initial sort
  rowClassName={(row) => ''}        // extra classes per row (highlight anomalies)
  toolbar={<Select … />}            // node rendered next to the search
  emptyMessage="No data available"
  rowKey={(row, i) => row.id ?? i}
/>

Column definition:

{
  key: 'time',                 // data key (also used for sorting)
  label: 'Date/Time',          // header
  sortable: true,              // header click: asc → desc cycle
  render: (row) => node,       // custom cell render (optional)
  sortAccessor: (row) => any,  // alternative value for sorting (optional)
  className: 'font-mono text-xs',
  headerClassName: '',
  align: 'left' | 'right',
}

Guaranteed behaviours: case-insensitive search on searchKeys; sort icons; pagination with a page-size selector and an "X–Y of Z results" count; reset to page 1 when search or data change; overflow-x-auto on the container.

Tip: the parent cannot reset the DataTable's internal search/sort/pagination directly. EventsSection clears them on "Reset filters" by bumping a resetToken used as the DataTable key, forcing a remount.

Main components:

Button({ variant = 'primary' | 'secondary' | 'ghost' | 'danger',
         size = 'md' | 'sm' | 'xs', icon: LucideIcon?, children?, … })

             eyes = 'animated' | 'open' | 'closed' | 'x',

  // decorative (aria-hidden): pair it with a role="status" text

  // inline "(o.o)" for busy buttons and status lines

Loading, error and empty states use the ASCII skull, generated by renderSkull() in frontend/src/lib/asciiSkull.js (any size, always symmetric):

Where Skull
Opening an incident (IncidentLoadingState) block, looking around, with the real download progress
Loading a tab's code (Suspense fallback in App.jsx) medium, looking around
An incident failed to load medium, eyes crossed out, muted
No incident open medium, eyes closed (asleep), muted
Parsing an uploaded file (FileUploadZone) small, looking around
Connecting, loading the list, busy buttons, server unreachable MicroSkull — (o.o), or (x.x) on errors

The large preset is kept for future use. With reduce motion enabled in the operating system the skulls stay still.

Look and tokens. Nik has a single dark, terminal-style theme. Colours are named tokens declared once in frontend/src/index.css (@theme), and components use the names, never raw palette classes:

Token Use
sunken · canvas · panel · raised surfaces, darkest to lightest (sidebar/terminal panes, page, cards and inputs, hover)
line · line-soft borders · table row dividers
fg · fg-muted · fg-subtle text · secondary text · decoration and disabled only
accent (+ -strong, -fg, -soft) the green prompt: primary actions, focus rings, active tab
link (+ -fg) · info (+ -line, -soft) links · informational badges
high (+ -fg, -line, -soft) · med (…) SOC severities HIGH (red) and MED (amber)
violet (+ -line, -soft) commands / anti-forensics

Tailwind turns each token into utilities (bg-panel, text-fg-muted, border-line, ring-accent…). Other conventions:

  • Corners are square; borders are 1 px border-line.
  • Monospace (font-mono, JetBrains Mono) for data, labels, tabs and headings; Inter (font-sans) for prose and buttons. Both fonts are bundled (frontend/src/assets/fonts/), no CDN.

  • Severities differ in lightness as well as hue, so they stay readable for colour-blind analysts.

  • Flagged rows use the accent (bg-accent-soft border-l-accent-strong), SOC rows their severity (bg-high-soft border-l-high-line, med alike), so an analyst's flag never looks like a detection.

Import

importIncidentFromFile(file) (async) accepts the envelope above (version 4, or 3 and older — their single-profile browser data lands in a "Default" profile) or a bare incident object. Minimal validation: data must be an object, otherwise an Error is thrown (surfaced by the sidebar). On import the incident:

  • always receives a new id — importing the same file twice creates two distinct copies, no collisions;
  • passes through normalizeIncident(), so the dataKeys of tabs added after the export are filled in with their defaultData;
  • is inserted at the top of the list, activated automatically, and persisted to the server (POST /api/incidents);
  • is recorded as incident.import in the audit log.

The JSON export is self-contained (it holds all imported data, flags and notes), which makes it a convenient exchange/archival format between Nik installations.
