Analysis internals

How each analysis works, for whoever maintains Nik or needs to know exactly what a result means: what the server and each worker do with a sample, an e-mail, a capture or an address. The overall design is on Architecture; the isolation of the workers on Security.

Malware samples

The Malware Analysis tab is the one place where a raw file reaches the server. The flow:

  1. The analyst drops a file; the frontend posts it as is to POST /api/incidents/{id}/samples (services/api.js → upload(), with progress).
  2. The server (routers/samples.py) computes the SHA-256 and writes the bytes once to the sample store (app/malware/samples.py: SAMPLE_STORE/<sha256>.bin, read-only, no execute bit), runs the static analysis (parsing/malware.py: hashes, magic-byte type, entropy overall and per 64 KB block, ASCII/UTF-16 strings, indicators) and stores the result in the samples table. The incident document gets only a light reference under data.malware.samples (sha256, fileName, type, size, who and when).
  3. The tab fetches GET /api/samples/{sha256} when a sample is selected and runs the SOC engine on the indicators client-side (domain/malware.js), with the built-in malware ruleset (DEFAULT_MALWARE_KEYWORDS) on top of the shared keywords, exactly like the other tabs.
  4. Downloads go through GET /api/samples/{sha256}/download, which wraps the file in an AES-256 zip (pyzipper) protected by infected or a password the analyst types; the plain bytes never leave the server. Uploads, downloads and removals are written to the audit log by the server.

Design points: the same file in two incidents is stored and analysed once and deleted only when the last reference goes; the first 5,000 strings are stored with the analysis and the rest is recomputed from the file on demand (/strings); nothing ever opens the sample with a library that interprets its format. On the host, exclude the sample store from the antivirus (it would quarantine the evidence) and include it in backups (see the full platform backup).

Structure and YARA. For executables the analysis also parses the format (parsing/executables.py): PE through pefile (machine, subsystem, compile time, sections with entropy and flags, imports by library, exports, resources, imphash, Authenticode presence, rich header, PDB path), ELF and Mach-O with Nik's own header parsers (segments, sections, needed libraries or dylibs, interpreter, code signature). Malformed headers, the norm in malware, become warnings instead of failures. Every sample is then scanned with YARA (yara_rules.py): the built-in rule files under app/malware/yara/ (YARA_RULES) plus the rule sets admins add in Settings → YARA rules, which are compiled on their own before being saved and recompiled together on change. A match's meta.severity (high / medium) and meta.description drive the badges; YARA severity counts towards the sample's severity. The analysis records its analysisVersion; Re-analyse (POST /api/samples/{sha256}/reanalyse) runs the current engine on the stored file, so older samples catch up after an upgrade or a rule change.

Code view (disassembly and decompilation). Both run in a separate worker, workers/analyzer/, built on the official rizin/rizin image, which ships rz-ghidra (Ghidra's decompiler, Apache-2.0, as a rizin plugin, LGPL-3.0): no Java and no extra build step. The backend never runs rizin itself:

  1. After an upload (and on Re-analyse, or the Disassemble button) the backend queues a job (sample_code table) and calls the worker's POST /analyze with the sample's SHA-256 and the shared X-Analyzer-Token.
  2. The worker opens <store>/<sha256>.bin from its read-only mount in rizin's pipe mode (rizin -q0, driven by nik_analyzer.py, standard library only), runs aaa and returns functions (aflj), their calls (from the call instructions), and for each function its basic blocks (afbj) with their instructions (pdfj). A timer kills rizin after ANALYZER_TIMEOUT; at most ANALYZER_MAX_JOBS requests run at once. Every function is listed: a 5,000-function Rust binary takes about 75 s; ANALYZER_MAX_FUNCTIONS (20,000) is only a safety cap.
  3. In the same session the worker decompiles functions with pdgj for up to ANALYZER_DECOMPILE_SECONDS (entry point and main first, then the functions the worker does not recognise as library code — no FLIRT match, no Rust crate, not a thunk — then the rest, smallest first within each group). rz-ghidra's annotations are reduced to highlight spans and call targets, about a tenth of their size. A function that takes over 30 s is skipped. Functions left out are decompiled when first opened (POST /decompile on the worker) and kept.
  4. The worker then keeps the analysed rizin session open (ANALYZER_WARM_SESSIONS, default 1, for ANALYZER_WARM_IDLE seconds), so a decompilation on demand takes seconds instead of a new aaa (on the 5,000-function sample: 0.1–3 s instead of 13 s and more). A session is lent to one request at a time; if rizin died in the meantime the request falls back to a fresh analysis. Each kept session holds rizin's memory for that file (about 1 GB on a large binary), hence the 4 GB default limit.
  5. The backend stores the function list with the job (sample_code) and each function's CFG and pseudo-C as a row of sample_functions, which the UI fetches one function at a time (GET /api/samples/{sha256}/code/functions/{addr} and …/decompiled): the graphs of a large binary add up to tens of megabytes, and opening a function reads only its own.

rizin 0.9 can crash (segfault) after thousands of commands in one session, on a function it handles fine in a fresh one. The worker survives it: it reopens the sample and retries that function once; a second crash skips the function (it is listed, marked, without CFG). After three restarts in one request it gives up with an error.

In Compose the worker runs as the image's non-root user, with a read-only filesystem, no capabilities, memory and CPU limits, no published port and no route outside the internal analysis network: the sample is read and disassembled, never executed. Without a worker (ANALYZER_URL unset) the Code view says so and everything else keeps working.

The UI (components/tabs/malware/code/) lists the functions with the severity of the APIs they reach (the SOC malware ruleset applied to callee names, propagated through the call graph by domain/code.js) and draws the call graph around the selected function and its control-flow graph with elkjs: ELK's layered algorithm places the blocks (main path in a column, branches on the sides), routes edges orthogonally in their own lanes and sends loops back along the side, as a disassembler's graph view does. Nik draws the result as SVG with its own tokens, with pan, zoom, a minimap and click to select. elkjs (~1.4 MB) is imported only when the Code view opens; it is licensed EPL-2.0 / GPL-3.0 and used unmodified. The Decompiled panel shows the pseudo-C with the decompiler's own highlighting (font ligatures off, so != reads as written); a call to another function of the sample is a link that opens it, and calls to suspicious APIs are red.

Function triage. A real binary has thousands of functions, most of them library code. The worker reports, per function, what it can tell about its origin, and the UI (domain/triage.js) sorts the list with it:

  • Library: functions matched by a FLIRT signature (rizin's bundled set plus the .sig / .pat files admins upload in Settings → FLIRT signatures, stored under SAMPLE_STORE/_flirt/ and passed to the worker, which applies them with Fs after aaa), and, in Rust binaries, functions whose panic locations point at a crate's sources (…\.cargo\registry\src\…\<crate>-x.y.z\src\…rs, or /rustc/<hash>/library/std/… for the standard library). The worker finds those paths among the strings, follows the Location structs that point at them, and credits each function with the crates its instructions reference. The crates found are listed above the table.
  • Runtime (compiler start-up and C runtime support, by name), thunk (jumps to imports, switch fragments) and import.
  • Not recognised: everything else. Release builds leave much library code without a signature or a path, so this is "not recognised", not "the author's code".

Hide recognised library code (on by default) keeps only the unrecognised functions in the list. Start here ranks those that call suspicious APIs directly, use an indicator of compromise, reach a suspicious API through their callees or are complex. The worker also reports the file offsets of the strings each function references; matched against the analysis strings, they give each function's strings used and, in the IOC table, a Used by column that opens the function in the Code view. Analysts rename and comment functions (function_annotations table): names replace rizin's in the list, the graphs and the pseudo-C for everyone opening the same sample.

Capabilities (capa). Mandiant capa matches a community rule set against the program's code and reports what it can do (send data on a socket, create a process, encrypt with RC4, resolve APIs at runtime…), mapped to MITRE ATT&CK and the Malware Behavior Catalog. It runs in a third worker, workers/capa/, built on python:3.12-slim with flare-capa, its rules and its library signatures at a pinned version (the rules and signatures are checked against their SHA-256 at build time); capa uses its pure-Python vivisect backend, so no Java or IDA is needed. capa, capa-rules and vivisect are Apache-2.0.

  1. After an upload and on Re-analyse (or the Run capa button) the backend queues a job (sample_capa table) for x86 / x64 PE and ELF files; other types are marked unsupported without calling the worker.
  2. The worker (server.py, standard library) runs capa -j on <store>/<sha256>.bin from its read-only mount, kills it after CAPA_TIMEOUT, and reduces the report (megabytes on a large binary) to the capabilities with their namespace, scope, ATT&CK / MBC mappings and up to 200 addresses each, a few kilobytes. Rules capa marks as library helpers are dropped, as capa's own report does.
  3. capa is CPU-bound — seconds on a small file, ten minutes or more on a large one — so the worker runs one analysis at a time and the backend sends its jobs one after the other, waiting while the worker is busy.

The Capabilities view lists them by namespace with ATT&CK and MBC badges. capa and rizin split a binary into functions differently, so each address capa reports is credited to the rizin function containing it (placeCapabilities in domain/triage.js): the view links each capability to those functions, the Code view shows the capabilities of each function, and Start here counts them — only for functions not recognised as library code, since crypto and TLS crates match many rules. Capabilities do not change the sample's severity. The capa service has the same isolation as analyzer (read-only store and filesystem, internal network only, no capabilities, memory / CPU / time limits).

capa rules of your own. Admins add capa rules in Settings → capa rules (capa_rules table, one YAML rule each). Since only the worker has capa, the backend asks it to check a rule (POST /validate: parsed by capa and loaded together with the bundled rules and the other enabled admin rules, so syntax errors, unknown features, duplicate names and missing match: dependencies are caught) before saving it. Saved rules are written to SAMPLE_STORE/_capa_rules/<id>.yml and the enabled ones are passed to the worker with each analysis, as extra -r rule paths next to the bundled set. A rule another enabled rule matches cannot be renamed, disabled or deleted. Their matches carry a custom badge in the Capabilities view; new or changed rules apply from the next analysis (Re-analyse).

Mail analysis

The Mail Analysis tab triages reported messages. Like samples, the file goes to the server once: POST /api/incidents/{id}/mails stores it in the sample store as <sha256>.mail (read-only), analyses it (app/mail/analyze.py) and keeps the result in the mails table; the incident gets a light reference under data.mail.messages and the incidents.has_mail column (mirrored, for the mail icon in the sidebar). Nothing in an attachment is opened by the program it is meant for.

  • Parsing (mail/parse.py): .eml with the standard library; .msg (an OLE compound file of MAPI properties) with olefile: the original Internet headers when Outlook kept them, the bodies (Outlook's compressed RTF is decompressed, MS-OXRTFCP), the attachments and attached messages (parsed in turn, three levels deep).
  • Headers (mail/headers.py): the Received chain in travel order with the delay of each hop and clocks going back; the sending server is the first public IP that is not one of your servers. Authentication-Results (and ARC, Received-SPF) are read as written, but only those of your own servers (Settings → Mail analysis) are believed: anyone can put such a header in a message. A header without an authserv-id (Exchange Online) is credited to the server that received the message last.
  • Authentication (mail/verify.py): DKIM signatures verified with dkimpy, SPF of the sending IP with pyspf, DMARC policy and alignment (relaxed/strict, organisational domain from the bundled Public Suffix List) with dnspython. The server needs DNS; each lookup times out after 3 s and a failure reads temperror, never a pass. These say what the DNS says now (a rotated DKIM key fails), so the servers' verdicts are shown next to them. A .msg keeps no original body: its DKIM cannot be checked.
  • Links (mail/links.py): anchors, forms and URLs in the text, unwrapped from Safe Links, Proofpoint (v1–v3), Google, Facebook and Barracuda redirects; look-alikes of well-known brands (Italian banks and public services included) and of your own domains are found by folding confusable characters and comparing edit distance, so punycode and rn→m tricks show.
  • Body (mail/content.py): the HTML is cleaned with nh3 (no scripts, handlers, frames, objects or forms), inline cid: images become data: URIs, hidden text is revealed. The browser shows it in an <iframe sandbox=""> (no scripts, no same-origin, no navigation of the app) whose Content-Security-Policy refuses every request; links lose their target (shown as a tooltip) and remote images load only after a warning, tracking pixels never. Urgency, payment, credential and secrecy phrases are listed (English and Italian).
  • Attachments (mail/attachments.py): type from the magic bytes against the extension, double extensions and right-to-left tricks, VBA/XLM macros (oletools), zip listings (the password is looked for in the text and tried; the archive is never extracted to disk), PDF actions, QR codes in images (zxing-cpp), calendar invitations.
  • Verdict: each finding weighs a fixed number of points (e.g. a look-alike sender domain 40, DMARC failing 30, a password-protected archive 35, urgency 8); the score is capped at 100. It is an aid to triage, not a proof: a clean score means nothing stood out.

The message's indicators (sender addresses and domain, sending IP, link targets and hosts, attachment hashes, QR and invitation links) go into the IOC index as mail:<file name>; the timeline shows each message at the time it was sent, high when the verdict is phishing; the report has an E-mails section.

Threat intelligence

Indicators get a reputation from external services (app/enrichment/). Each provider is one function in providers.py that turns the service's answer into { verdict, summary, link, data }; verdict is malicious, suspicious, harmless or unknown (not known, or nothing conclusive).

Provider Types Key Free tier (as Nik paces it)
VirusTotal IP, domain, URL, hash required 1 request / 15 s, 500 a day
AbuseIPDB IP required 1,000 a day
abuse.ch: ThreatFox, URLhaus, MalwareBazaar IP, domain, URL, hash required (one Auth-Key) —
AlienVault OTX IP, domain, URL, hash required —
urlscan.io (search of public scans, nothing submitted) domain, URL optional 1,000 a day
GreyNoise Community IP optional 50 a day
Shodan InternetDB IP none —
Google Safe Browsing domain, URL required 10,000 a day

What is never sent (service.blocked), whoever asks: private, loopback and other non-public addresses, internal names (no dot, .local, .lan, .internal, .corp, .home.arpa…) and URLs on them; values on the IOC allowlist; values seen in an incident whose report is classified TLP:RED, or that an analyst or a list of the IoC library classified TLP:RED; e-mail addresses. MD5 and SHA-1 of stored samples and mail attachments are not looked up automatically: their SHA-256 is.

Automatic lookups are off until an analyst turns them on in Settings → Threat intelligence, per type: IP addresses, URLs and domains, file hashes. Every API process starts a worker thread (worker.py); a lease row (leases) lets only one of them work at a time, so several gunicorn workers do not multiply the requests. Every 30 seconds it checks the indexed indicators not in the cache (newest incidents first) with every enabled provider that takes their type, pacing each provider to its free tier. An answer stands for the retention of its type (retentionDays: 30 days for IP addresses, 30 for URLs and domains, 180 for hashes; 1 to 730), an error is retried after an hour.

The IoC library (app/ioc_library.py) is one row per (type, value) merged from three tables: ioc_index (what the incidents hold), iocs (indicators added by hand or from a file, and the tags, note, TLP and expiry an analyst wrote about any indicator) and ioc_list_items (the lists). parse() reads a paste or a file: a JSON document is tried as Nik's export, a STIX 2.1 bundle or a MISP event; a table with a value column as CSV; anything else line by line, after undoing the usual defanging. Nothing is saved until POST /api/iocs.

A bulk check is a row of ioc_checks holding what is left to ask ([type, value, [providers]]). The same worker thread works through the checks before the automatic lookups (service.run_checks), with the same keys, limits and "never sent" rules. A check whose remaining sources have all used their daily quota is left waiting, with a message that says which, and goes on when one resets. The plan shown before a check starts counts the requests against what the answering API process has seen used today: with several API processes it is an estimate, and the worker's own count decides.

Watched lists: when an incident is reindexed, the indicators it did not hold before are compared with the watched lists (ioc_library.watch_hits). Each hit is a row of ioc_alerts, an audit entry (ioc.watch_hit) and one delivery of the ioc.watch_hit webhook. Rebuilding the whole index (a restore) raises no alerts.

Check now on the indicator's page asks every usable provider at once (fresh answers are reused unless "Check again"). When the page opens on answers past their retention, GET /api/enrichment lists those providers in refresh and the page asks them again once; with refreshExpired off the list stays empty and the answer is shown as expired. A provider function returns the verdict, a one-line summary, a link, the details the page shows (data), the whole answer (raw, stored up to 1.5 MB and served by /api/enrichment/raw) and how many requests it made, which are charged to the key. The last ten answers per indicator and provider go to ioc_enrichment_history.

The overall verdict is weighted (overall() in service.py): each provider has a weight (VirusTotal, abuse.ch and Safe Browsing 3; AbuseIPDB, urlscan and GreyNoise 2; OTX and Shodan InternetDB 1), a malicious answer counts in full and a suspicious one half, and the score is the weighted share of the providers that answered, from 0 to 100. It is malicious from 50 with at least one malicious answer, suspicious from 20 or with any malicious answer, harmless when nobody flags and somebody says harmless. The IOCs tab's Reputation column shows that verdict and score. VirusTotal's extra sections (virustotal.relations, virustotal.comments) are separate requests and are off by default; virustotal.engines chooses which vendors are listed.

Keys are entered by admins and stored in integration_keys, encrypted with Fernet under a key derived from SECRET_KEY (HKDF, vault.py): the API returns only whether a key is set and its last four characters. A provider can have up to ten keys: the interval and the daily quota are counted per key, a lookup takes the key that is free and was used longest ago (so requests go round them), a key that answers 429 waits an hour while the others carry on, and a key the provider refuses waits ten minutes; after three refusals in a row it is marked rejected with the answer, shown in Settings and left out until an admin removes or replaces it. Whether several keys may be used to raise a free tier's limits is for each provider's terms to say. Changing SECRET_KEY without SECRET_KEY_PREVIOUS makes the stored keys unreadable (Settings says so): enter them again. Requests use the standard library (urllib), so HTTPS_PROXY / NO_PROXY apply; a transparent proxy needs nothing.

Attachment previews and the isolated browser

Two more workers show what an attachment looks like without opening it on the analyst's machine. Like analyzer and capa they run as unprivileged users with a read-only filesystem, no capabilities, memory and CPU limits, no published port, and answer only the backend's shared token.

Documents (workers/docview/, internal network only). The Mail Analysis tab's Preview sends the attachment to POST /api/mails/{sha256}/attachments/{path}/preview; the backend forwards it to the worker, which converts Word, Excel, PowerPoint, OpenDocument and RTF to PDF with LibreOffice (a fresh profile per conversion: macro security "very high", macros disabled, links to other files or the network never updated, killed after 90 s) and renders the first 20 pages of the PDF with pdfium; images are re-encoded with Pillow. The browser receives PNG images only. The pages are kept under SAMPLE_STORE/_previews/<sha256>.json and removed with the last message that holds the attachment.

Isolated browser (workers/browser/). HTML attachments (Open in isolated browser) and links (Links view) open in Chromium, run by Playwright inside the worker's container. The analyst sees a JPEG of the viewport; clicks, double-clicks, typing, Enter / Tab / arrows and the wheel are sent to POST /api/browser/sessions/{id}/action and replayed there, with back, forward, reload and an address bar. Scripts of the page run in the worker, never in the analyst's browser.

  • Network, chosen for each session. Without network (the default) the page is the attachment itself: every other request (images, scripts, frames, form posts, links) is refused, and a navigation shows a "blocked by Nik" page. With network, http and https go out through the server's connection (the browser-egress network, the only one with a route outside), except to private, loopback or link-local addresses and internal names, so a page cannot reach the organisation's own network. Every session is audited (browser.open), with or without network.
  • The rule is enforced where the connections are made. Chromium is started with one route, the worker's own proxy (egress.py, on loopback): every connection a page causes goes through it, the hops of a redirect and the sub-resources included, which the request interception alone never sees. For each connection the proxy resolves the name itself, refuses unless every address is public, and connects to the address it just checked, so a name that changes its answer between the check and the connection (DNS rebinding) gains nothing. WebRTC and QUIC, which would send UDP around a proxy, are off. The proxy also tells the network log where each request really went.
  • Networks. The backend reaches the worker on browser-control, an internal network the two share with nobody: the one container that runs hostile pages has no route to the other workers or to the database.
  • Tabs and size. A window the page opens (window.open, a target=_blank link) becomes a tab of the session, shown at once, with at most eight open; when a tab closes itself the one that opened it is shown again. The state returned by every action lists the tabs, and the tab / closeTab actions switch and close them. The pages are drawn at the size the analyst's window has for them (resize, between 640×400 and 2560×1600; a pop-up that asks for its own little window gets the session's size). RemoteBrowser.jsx measures that space, asks for it, and offers a full-screen mode.
  • Downloads are refused and reported, alert / confirm / prompt dialogs are dismissed and reported, permission prompts denied. A session belongs to the analyst who opened it, closes after 5 minutes without an action (30 minutes at most) and when the window is closed; at most BROWSER_MAX_SESSIONS are open at once.
  • Chromium's own sandbox needs privileges the container does not give, so it runs with --no-sandbox: the container is the sandbox.

Network analysis

The Network Analysis tab reads packet captures with Wireshark's own engine, in the pcap worker (workers/pcap/): Debian's tshark and sharkd, run as an unprivileged user in a container with a read-only filesystem and the sample store mounted read-only, no capabilities (nothing is ever captured) and the internal network only.

  • Upload (POST /api/incidents/{id}/captures): pcap or pcapng, gzip too, up to PCAP_MAX_MB (500), checked by its magic bytes, written to SAMPLE_STORE/_captures/<id>/ (read-only) and recorded in the network_captures table. The worker then reads it once with tshark for the summary: hosts by bytes, DNS names and answers, HTTP requests, TLS server names, POST / PUT / PATCH requests, beacons (six or more connections to the same address and port, at least 5 s apart, intervals within 15 %), the exported objects with their SHA-256 and the Expert Info counts. These feed the IOC index (network:<file>), the timeline and the report's Network section.
  • Viewing goes through sharkd, Wireshark's daemon for web front ends, one process per open capture (two at most, closed after 15 minutes unused): the packet list with Wireshark's colouring rules, paged; the protocol tree with the byte range of every field; Follow Stream; Export Objects. The backend forwards a fixed set of read-only calls (POST /api/captures/{id}/rpc); columns are never taken from the caller, since some custom column definitions crash sharkd.
  • TLS is decrypted with a key log (SSLKEYLOGFILE, NSS format) added at upload or later. It is stored encrypted like the API keys and written to the worker's /tmp only while a capture is open.
  • Packets can be flagged into the incident timeline (pcap:<capture>:<n>).

Isolated browser sessions. The browser worker records every request of a session (netlog.py): method, URL, type, headers, bodies in clear (the browser sees HTTPS decrypted, 2 MB per body and 50 MB per session, past that size and SHA-256 only), response, server address, certificate, timings and WebSocket messages; refused requests (no network, private address) and held submissions included. In a session with network, POST / PUT / PATCH / DELETE requests are held by default: recorded, not sent, the page shows "Submission held by Nik"; the analyst may send them for the session (audited). Opened from an incident, the session's log is copied after every action (network/service.py) and shown live in the window's Network panel, DevTools-like. When the window closes (or the session expires) the log is rebuilt as pcapng (network/pcapng.py): a DNS answer per host, a TCP handshake and HTTP/1.1 in clear per request, a comment saying it is a reconstruction and marking held and refused requests, so Wireshark's filters, Follow Stream and Export Objects work on it, then analysed like an upload. It also exports as HAR 1.2 (network/har.py).

URL analysis

An address is scanned by the isolated browser worker, the same that opens HTML attachments: urlscan.run_scan (a background task of the API) opens a session with network access (private and internal hosts are refused, submissions are held), calls the worker's inspect action, which returns a screenshot and what the page asks for (its forms, read from the DOM), copies the session's network log and closes the session. Nothing is typed, clicked or submitted.

urlscan.assess weighs the facts into findings with points, as Mail Analysis does: the address itself (lookalike of a brand, punycode, @ in the authority, an IP address as host, a throwaway top-level domain, a shortener, a cloud-hosted page: the link rules of mail/links.py), a page that asks for a password outside the brand's own domains (and over plain http, or under a brand's name in its title), a form that posts to another registrable domain, a chain through three or more domains, a certificate issued less than seven days ago, a download the page started. A score of 70 or more is phishing, 40 to 69 suspicious, less clean.

One row per distinct address (url_scans, id = the first 32 hex characters of the SHA-256 of the normalised URL): scanning it again replaces the result. The screenshot sits in SAMPLE_STORE/_urls/; the visit's network log becomes a capture (an isolated browser session), related to the address as its child. An incident keeps a light reference under data.urls.scans; the address, the hosts it led to and the server's IP join the incident's indicators, the scan its timeline and report.
