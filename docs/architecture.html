High-level design

        Analyst's browser                         Server
┌──────────────────────────────┐     ┌────────────────────────────────┐
│  React SPA (Vite build)      │     │  nginx                         │
│  ├─ artifact parsing (WASM)  │────▶│  ├─ static files (dist/)       │
│  ├─ SOC detection engine     │ TLS │  └─ /api/ ──▶ FastAPI (:8000)  │
│  └─ REST client (/api)       │     │              └─▶ PostgreSQL    │
└──────────────────────────────┘     └────────────────────────────────┘

The split is deliberate:

  • Parsing stays in the browser. Raw artifact files (SQLite databases, JSON, CSV) are read and normalized client-side; only the resulting entries are sent to the API as part of the incident document.
  • State lives on the server. Incidents, users, settings and the audit log are stored in the database and shared by all analysts; nothing is kept in the browser's storage.
  • Single origin. nginx serves the SPA and proxies /api/ to the backend, so no CORS configuration is needed and the httpOnly session cookie flows transparently. In development, the Vite proxy plays nginx's role.

The REST API (/api) exposes: auth (bootstrap/login/logout/me), users, incidents, audit, settings and backup routers, plus GET /api/health as a liveness probe.

Why parsing is client-side

All artifact parsing — including Chromium's History, a binary SQLite database — happens in the browser via sql.js (SQLite compiled to WebAssembly). Rationale:

  1. Privacy / chain of custody — forensic artifacts can hold personal and sensitive data (a subject's browsing history, credentials in URLs…). The raw files never leave the analyst's machine; only normalized entries are stored.
  2. No upload pipeline — no file-size limits, no multipart handling, no temporary storage of evidence on the server.
  3. Works in the field — the parsing layer needs no connectivity beyond the API calls that persist results.

The sql.js WASM module (~1 MB) is loaded lazily on the first SQLite import (see frontend/src/services/sqliteParser.js): analysts who only work with JSON/CSV exports never download it.

File schema per engine. Chromium browsers (Chrome/Edge/Brave/Opera) share Chrome's SQLite schema (History with urls/visits/downloads, a JSON Bookmarks file, a Shortcuts database). Firefox is different: a single places.sqlite database (moz_* schema) holds history, bookmarks and downloads. Safari (macOS only) keeps history in a History.db database (history_items/history_visits) and downloads and bookmarks in two property lists, Downloads.plist and Bookmarks.plist, usually binary. Timestamps differ too — see browsers, parsers and formats.

Heavy binary formats are parsed on the server instead. Windows event logs (.evtx, chunks of binary XML) are the first: the Event Logs tab uploads the file, backend/app/parsing/eventlog.py parses it with the evtx package (a Rust parser) in a background job and merges the curated events into the incident, in the same shape the browser produces from the collection script's JSON. PCAP and disk images would follow the same path.

The one exception: malware samples. The Malware Analysis tab sends the file itself to the server, because the sample is the evidence under study (not a container of entries to normalize) and the later analysis stages (disassembly, decompilation) can only run server-side. See malware samples.

Naming an incident. An incident has a ticket ID (the reference in your tracker), a short title, a host and a user, all optional but at least one. Its name is built from them: the ticket first, in square brackets, then the title when there is one, otherwise host - user: [INC-2041] Invoice phishing, finance, [INC-2039] WKS-042 - m.rossi, SRV-FILE-01. The severity (low, medium, high, critical) is a tag the analysts set, shown next to the name in the sidebar and the header but never part of it. The status (open, in_progress, closed; an incident with none is open) and the assignee (a username) live in the document and are mirrored into columns, like the ticket and the severity, so the panel lists and filters them without reading documents. Everything is editable from the Summary tab; the search palette and GET /api/incidents?q= also find incidents by ticket.

Right-click. One menu for the whole app (frontend/src/context/ContextMenuContext.jsx): on an indicator (anywhere it is shown: the IOCs tab, a sample's indicators, event-log addresses) Where else was this seen?, Search for it, Copy, Copy defanged (hxxps[:]//evil[.]top) and Add to the allowlist…; on an event row (Browser, Commands, Endpoint, Event Logs, Timeline) Flag or Remove the flag, Add a comment…, Copy as text, Copy as JSON and Show in the Timeline; on an incident in the sidebar Open, Incident report…, Export (JSON), Copy link and Delete…. Text fields and selected text keep the browser's menu, and so does Shift + right-click. Add to the allowlist (also the shield button on each IOC row) proposes the value or a wider entry — its domain or a parent domain, its /24 network — and writes it to the shared allowlist with a comment line saying who added it and when; Undo stays available for a few seconds. Any analyst can do it.

Drag-and-drop anywhere. Drop a file on any part of the app (outside the tabs' own drop zones) and a dialog proposes where it goes, from its first bytes and its name (frontend/src/domain/fileRouting.js): PE, ELF and Mach-O executables, PDF, Office documents, scripts and archives → Malware Analysis; .evtx and the event-log script's JSON → Event Logs; Chromium History / Shortcuts / Bookmarks, Firefox places.sqlite, Safari History.db and plists → Browser Forensics; shell histories → Command History; CSV → Endpoint Artifacts. The dialog always asks whether the file goes into the open incident or a new one (with its ticket, title, severity, host, user and OS), lets you change the tab and the source, then opens the tab and imports the file as its own drop zone would.

Each incident is tied to a single host and carries an operating system (windows | macos | linux, see frontend/src/config/os.js), chosen when the incident is created and editable from the Summary tab. The OS drives the host-specific bits of the UI: the artifact paths suggested in Browser Forensics, which shells appear in Command History, and the incident icon shown in the sidebar and header.

The Command History tab mirrors Browser Forensics for terminal activity: one sub-tab per shell (Bash / Zsh / Fish / PowerShell, see frontend/src/config/shells.js), parsing the native history files (.bash_history, .zsh_history, fish_history, PSReadLine ConsoleHost_history.txt) plus JSON/CSV exports. Commands run through the SOC engine — the shared keyword rules plus a built-in command ruleset (DEFAULT_COMMAND_KEYWORDS in frontend/src/config/detectionRules.js: download-and-execute, encoded payloads, reverse shells, credential access, defense evasion, persistence, exfiltration, history tampering…) — can be flagged, searched, filtered by the suspicious window, and appear on the incident timeline exactly like browser events.

The Endpoint Artifacts tab covers host forensic artifacts that neither the browser nor the shell captures, one sub-tab per category built from one or more sources (see frontend/src/config/artifacts.js): Program Execution (BAM, KnowledgeC), Persistence (Run keys, Scheduled Tasks, services, startup, WMI, cron, systemd, SSH keys, rc files, LaunchAgents), File & Folder Access (GTK recently-used) and USB & Devices (USBSTOR, setupapi log, kernel journal). The table shows the union of every source's records, tagged by which source produced them, and runs the shared keywords plus a built-in artifact ruleset (DEFAULT_ARTIFACT_KEYWORDS: execution from temp/user-writable paths, LOLBins, double extensions, suspicious persistence, known offensive tool names).

Crucially, every source is collected without any third-party tool, in one of two ways driven by the incident's host OS:

  • file — the data already lives in a plain text / XML / log / SQLite file, so the analyst uploads that existing file and it is parsed in-browser (custom parsers in frontend/src/services/artifactParsers.js: recently-used.xbel, authorized_keys / cron / rc files, LaunchAgent .plist, setupapi.dev.log, and knowledgeC.db via sql.js).
  • script — the data is live system state (registry, service manager, kernel journal), so the tab shows a native collection script (frontend/src/config/collectionScripts.js, PowerShell / systemctl / journalctl only) with copy/download buttons; it writes a CSV whose headers match the importer 1:1, which the analyst then imports.

Artifacts that can only be recovered with third-party DFIR parsers (Prefetch, Amcache, ShimCache, UserAssist, LNK, JumpLists, ShellBags, RecentDocs) are intentionally left out; a category with no custom source on a given OS shows an explicit note rather than a dead end.

The Event Logs tab (Windows) holds curated events from the host's event logs, per channel (Security, System, PowerShell, PowerShell classic, RDP sessions and authentication, Defender, Task Scheduler, Sysmon; see frontend/src/config/eventLogs.js). They arrive two ways: raw .evtx files copied from C:\Windows\System32\winevt\Logs\ (or a disk image), uploaded and parsed on the server, which also recovers records left in the file's unused space after a clear and keeps the file's SHA-256; or the JSON written by a native Get-WinEvent collection script on a live host, parsed in the browser. Only about 50 curated event IDs are stored (at most 20,000 per channel, the newest); the rest is counted. The tab shows:

  • the log coverage: one bar per channel from its first to its last record, with silences of 6 hours or more hatched, clears marked in red and the incident's suspicious window behind them — a gap or a clear inside the window is where evidence may be missing;
  • the logon sessions: each 4624 paired with its logoff (4634/4647) and admin privileges (4672) by logon id, service logons and machine accounts left out;
  • every event with a readable summary, filters by detection, category, channel and time, and a detail view with all its fields.

Command lines (4688, Sysmon 1) and PowerShell script blocks go through the command-line ruleset; the built-in event-log ruleset (DEFAULT_EVENTLOG_RULES, logic in frontend/src/domain/eventLogs.js) adds log cleared, audit policy changed, service installed (high when the binary sits in a user-writable path or runs a shell), suspicious PowerShell, brute force (10 failed logons for one account or source within 10 minutes), a logon right after 5 failures, RDP outside business hours, account created, member added to a privileged group, Defender alerts and scheduled task created. Machine activity (service logons, boots) is not judged by the clock. Linux (journald, auth.log) and macOS unified logs will follow.

The Timeline tab is the super-timeline: it merges every timestamped event from the Browser, Command History, Endpoint Artifacts and Event Logs tabs into a single chronological, filterable table (by source, detection and time window). Entries without a reliable timestamp (e.g. PSReadLine commands) are intentionally left out. Any row can be flagged straight from the timeline.

The sidebar is resizable: drag its right edge to widen the incident list up to a quarter of the window; the width is remembered per browser.

The IOCs tab lists the incident's indicators of compromise. The server builds them (backend/app/iocs.py) whenever the incident's data is saved — a merge patch that only touches flags or notes leaves them alone — and keeps one ioc_index row per incident, type and value, so "where else have we seen this?" is one indexed query for every analyst, whoever owns the other incident. The sources:

  • browser history: the visited hosts (not every URL); downloads: the URL, its referrer and their hosts;
  • shell commands and endpoint records: URLs, IP addresses, domains (known TLDs), e-mail addresses and MD5/SHA-1/SHA-256 digests in the text;
  • event logs: address and host fields (IpAddress, DestinationIp, QueryName…), Sysmon Hashes, and the indicators in command lines, script blocks and service paths;
  • malware samples: the sample's hashes and the network indicators in its strings;
  • e-mails: sender addresses and domain, sending IP, link targets and hosts, attachment hashes, QR-code and invitation links (mail:<file name>).

Indicators also seen in other incidents come first, in red. Clicking a value here, in a sample's IOC table or in the Event Logs tab opens Where seen: every incident it appears in, with the sources, count and first/last time, and a link to open it. Settings → IOC allowlist (one entry per line: a domain and its subdomains, an IP or CIDR network, or an exact value) starts with private and loopback ranges and common vendor and CDN domains; matching values are hidden by default and never exported. The index keeps them, so editing the list applies at once. Exports: CSV, a STIX 2.1 bundle and a MISP event, for a TIP or a firewall blocklist. Incidents saved before 2.12.0 are indexed on the api's first start.

Incident report. The report button in the header (or > report in the search palette) opens the report dialog: language (English or Italian), TLP classification, the sections to include and an executive summary — all saved with the incident (report key of the document) — a preview, and the download as PDF or HTML. The server builds the report (backend/app/report.py) as one self-contained HTML page styled for print, and renders the PDF with WeasyPrint: A4 pages with the organisation and the TLP label at the top and page numbers at the bottom. Its sections:

  • executive summary and key facts (flagged events, SOC detections, indicators, samples, techniques);
  • flagged events in time order, with the analysts' comments;
  • MITRE ATT&CK techniques from capa's capabilities, the YARA rules' mitre_attack metadata (the built-in rules carry it) and the SOC rules that matched (each built-in rule names its techniques in frontend/src/config/detectionRules.js), each with where it was seen;
  • indicators of compromise outside the allowlist, those seen in other incidents first (up to 500; the rest are in the CSV/STIX/MISP export);
  • malware samples with their hashes, YARA matches and capa capabilities;
  • Windows event logs: each channel's coverage and when it was cleared;
  • analyst notes;
  • an evidence appendix: every imported file with its format, rows, import time and SHA-256. Browser, shell-history, endpoint and event-log JSON files are hashed in the browser when they are imported (the file still never leaves the machine); .evtx files and samples are hashed by the server.

The organisation name and logo come from Settings → Report header. API clients get the same report from POST /api/incidents/{id}/report.

Global search. Ctrl/Cmd+K anywhere, or / outside a text field, or the search… button in the header, opens a nik> prompt. As you type it asks the server (GET /api/search) for incidents, indicators from every incident and samples, and searches the open incident in memory: its timeline events (every tab), notes and samples (by file name too). Enter opens the result: an incident is selected, an indicator or a sample opens Where seen, an event jumps to its tab, a note to the Summary. A query starting with > lists actions instead: go to any tab, new incident, export the incident, settings, the IOC allowlist, sign out. On PostgreSQL the substring matches use the trigram (pg_trgm) indexes of migration 0012; when the extension cannot be created the search works without them.

Platform configuration lives in one sectioned Settings panel (opened from the rail's gear, or deep-linked from the rail's Users and Audit log buttons): detection rules (with the built-in rulesets shown for reference), business hours, account management and the audit log.

State and the data model

IncidentContext

All incident state lives in frontend/src/context/IncidentContext.jsx, exposed through the useIncidents() hook:

Loading is lazy. After authentication only the light list is fetched (GET /api/incidents?view=summary). Opening an incident downloads its full document (GET /api/incidents/{id}) while the main area shows a non-blocking loading state — the sidebar stays usable and opening another incident cancels the pending download. Documents stay cached in memory for the session; reopening one, or coming back to the window, shows it at once and revalidates it with If-None-Match (304 when unchanged, merged when someone else edited it).

The cache is an optimistic model: every mutation updates local state immediately and hands the incident to the save queue (frontend/src/services/saveQueue.js). The queue keeps, per incident, the last version the server is known to hold and its ETag, and persists only the difference, as an RFC 7396 JSON Merge Patch generated by frontend/src/lib/mergePatch.js. Toggling a flag therefore sends the flag, not the incident's artifacts. setActiveBrowser, setActiveProfile and setActiveShell are view preferences, never sent.

  • One save at a time, in order. Edits made while a save travels leave with the next one; two edits of the same tick (a comment on a row that was not flagged) are one request.
  • Nothing is forgotten. Because the patch is the difference from the last acknowledged version, a save that failed is still in the next one. It is retried at growing intervals and reported by App.jsx as a red banner (storageError, unsavedChanges, retrySave) until it goes through.
  • Two writers do not overwrite each other. Each save sends If-Match. The backend bumps the incident's revision (incidents.rev, its ETag) at every write of the document, whoever makes it, and takes the row lock before reading it (backend/app/core/locking.py), so the check and the write are atomic. On 412 the queue reads the server's version and carries the local changes over it with a three-way merge (frontend/src/lib/rebase.js): objects member by member, lists of things with an identity (notes, comments, references) item by item.
  • An expired session loses nothing. A 401 sets sessionExpired in AuthContext; SessionExpiredDialog asks for the password over the app, and the queue resumes after the sign-in.

Shape of an incident

  ticketId:  'INC-2041',                   // identity (NOT unique — the id is the key),
  title:     '',                           //   all optional, at least one set

  username:  'm.rossi',                    //   "
  name:      '[INC-2041] WKS-FINANCE-01 - m.rossi', // derived: "[ticket] title" | "[ticket] host - username"

  status:    'in_progress',                // 'open' | 'in_progress' | 'closed' — where the work stands

      },

    network: {                             // packet captures: light references, the packets

meta is indexed by file source (keys vary per engine: Chromium has history/bookmarks/shortcuts, Firefox has places). Each entry describes the imported file: { fileName, format, rows, importedAt }.

Authentication, sessions and the audit log

Authentication

Passwords are hashed with bcrypt on the server (backend/app/core/security.py). A successful POST /api/auth/login creates a server-side session row and sets the httpOnly nik_session cookie (with the Secure flag when COOKIE_SECURE=true, the default); credentials: 'include' on every fetch keeps it flowing. Sessions expire after SESSION_TTL_HOURS.

User shape: { id, username, role: 'admin' | 'analyst', createdAt, createdBy, disabled } — the password hash never leaves the backend. A sign-in that names an unknown account does the same hashing work as a wrong password, ten wrong passwords in a row lock the account for five minutes (users.failed_logins, users.locked_until), and expired sessions are purged at each sign-in.

The App shell (App.jsx) implements a three-state auth gate, driven by GET /api/auth/bootstrap and GET /api/auth/me:

  • no users at all → FirstRunSetup: the first POST /api/users succeeds without authentication and the created account is forced to the admin role;
  • users exist but not signed in → LoginScreen;
  • signed in → the main app;
  • session ended while working (any request answers 401) → SessionExpiredDialog over the app, which keeps its unsaved changes.

Admins manage accounts in Settings → Accounts (AccountsSection.jsx): add a user, change its name, role or password, disable it, or delete it (PATCH / DELETE /api/users/{id}). The server keeps at least one admin able to sign in and refuses a change to the caller's own role. A rename is carried to the incidents assigned to the account, under their row lock; a new password or disabling ends the account's sessions. Every user changes their own password in My account (PUT /api/users/me/password).

Audit log

The log is written by the server: each handler records what it does through backend/app/core/audit.py, for a session and for an API key alike, so a request sent by hand leaves the same entry as the app. An entry says who (actor), when (at), what (action), the details, and which incident it belonged to. Entries are returned newest-first, capped at 5000.

A merge patch says what changed, not what it means, so describe_patch() compares the document before and after and names the changes: a flag added or removed, a comment, a note, the attributes that changed, the evidence tabs touched and the files imported into them. The browser reports only what happens in it alone: POST /api/audit accepts incident.export and refuses anything else.

Entry shape: { id, at, actor, action, target, details, incidentId, incidentName }.

Action strings include: auth.login / .logout / .locked, user.create / .update / .delete / .password, apikey.create / .revoke, settings.update, incident.create / .update / .delete / .export, evidence.update, flag.add / .remove / .comment, note.add / .update / .remove, the sample, e-mail, capture and URL actions, backup.export / backup.import and audit.clear.

The Audit log section of Settings (AuditLogSection.jsx, also opened from the rail) reads the trail each time it opens and shows it in a searchable table; an admin can clear the whole log behind an inline confirmation step, and the new log starts with an audit.clear entry naming them.

Large data sets

A browser history of a few hundred thousand visits has to stay usable, so the Browser tab keeps its per-row work to a minimum:

  • buildEvents() parses each URL once (analyzeUrl in utils/url.js) and stores domain and searchQuery on the event; the stat cards, the ranking widgets and the table cells read those fields instead of parsing again (entryDomain() / entrySearchQuery() fall back to parsing for raw entries).
  • DataTable sorts text with one shared Intl.Collator: localeCompare with options builds a collator per comparison, which made a 300k-row sort take seconds. The search box uses useDeferredValue, so typing never waits for the filter.
  • buildTimelineEvents() takes incident.data, not the incident: flags and notes do not change the timeline, so toggling a flag does not rebuild the Timeline tab.

Tables stay paginated (25 rows by default), so the DOM never holds more than one page; the cost of a large incident is in these data passes, not in rendering. When you add a per-row computation, do it once in the build* helper, not in a cell renderer.

Malware samples

The Malware Analysis tab is the one place where a raw file reaches the server. The flow:

  1. The analyst drops a file; the frontend posts it as is to POST /api/incidents/{id}/samples (services/api.js → upload(), with progress).
  2. The server (routers/samples.py) computes the SHA-256 and writes the bytes once to the sample store (app/malware/samples.py: SAMPLE_STORE/<sha256>.bin, read-only, no execute bit), runs the static analysis (parsing/malware.py: hashes, magic-byte type, entropy overall and per 64 KB block, ASCII/UTF-16 strings, indicators) and stores the result in the samples table. The incident document gets only a light reference under data.malware.samples (sha256, fileName, type, size, who and when).
  3. The tab fetches GET /api/samples/{sha256} when a sample is selected and runs the SOC engine on the indicators client-side (utils/malware.js), with the built-in malware ruleset (DEFAULT_MALWARE_KEYWORDS) on top of the shared keywords, exactly like the other tabs.
  4. Downloads go through GET /api/samples/{sha256}/download, which wraps the file in an AES-256 zip (pyzipper) protected by infected or a password the analyst types; the plain bytes never leave the server. Uploads, downloads and removals are written to the audit log by the server.

Design points: the same file in two incidents is stored and analysed once and deleted only when the last reference goes; the first 5,000 strings are stored with the analysis and the rest is recomputed from the file on demand (/strings); nothing ever opens the sample with a library that interprets its format. On the host, exclude the sample store from the antivirus (it would quarantine the evidence) and include it in backups (see the full platform backup).

Structure and YARA. For executables the analysis also parses the format (parsing/executables.py): PE through pefile (machine, subsystem, compile time, sections with entropy and flags, imports by library, exports, resources, imphash, Authenticode presence, rich header, PDB path), ELF and Mach-O with Nik's own header parsers (segments, sections, needed libraries or dylibs, interpreter, code signature). Malformed headers, the norm in malware, become warnings instead of failures. Every sample is then scanned with YARA (yara_rules.py): the built-in rule files under app/malware/yara/ (YARA_RULES) plus the rule sets admins add in Settings → YARA rules, which are compiled on their own before being saved and recompiled together on change. A match's meta.severity (high / medium) and meta.description drive the badges; YARA severity counts towards the sample's severity. The analysis records its analysisVersion; Re-analyse (POST /api/samples/{sha256}/reanalyse) runs the current engine on the stored file, so older samples catch up after an upgrade or a rule change.

Code view (disassembly and decompilation). Both run in a separate worker, workers/analyzer/, built on the official rizin/rizin image, which ships rz-ghidra (Ghidra's decompiler, Apache-2.0, as a rizin plugin, LGPL-3.0): no Java and no extra build step. The backend never runs rizin itself:

  1. After an upload (and on Re-analyse, or the Disassemble button) the backend queues a job (sample_code table) and calls the worker's POST /analyze with the sample's SHA-256 and the shared X-Analyzer-Token.
  2. The worker opens <store>/<sha256>.bin from its read-only mount in rizin's pipe mode (rizin -q0, driven by nik_analyzer.py, standard library only), runs aaa and returns functions (aflj), their calls (from the call instructions), and for each function its basic blocks (afbj) with their instructions (pdfj). A timer kills rizin after ANALYZER_TIMEOUT; at most ANALYZER_MAX_JOBS requests run at once. Every function is listed: a 5,000-function Rust binary takes about 75 s; ANALYZER_MAX_FUNCTIONS (20,000) is only a safety cap.
  3. In the same session the worker decompiles functions with pdgj for up to ANALYZER_DECOMPILE_SECONDS (entry point and main first, then the functions the worker does not recognise as library code — no FLIRT match, no Rust crate, not a thunk — then the rest, smallest first within each group). rz-ghidra's annotations are reduced to highlight spans and call targets, about a tenth of their size. A function that takes over 30 s is skipped. Functions left out are decompiled when first opened (POST /decompile on the worker) and kept.
  4. The worker then keeps the analysed rizin session open (ANALYZER_WARM_SESSIONS, default 1, for ANALYZER_WARM_IDLE seconds), so a decompilation on demand takes seconds instead of a new aaa (on the 5,000-function sample: 0.1–3 s instead of 13 s and more). A session is lent to one request at a time; if rizin died in the meantime the request falls back to a fresh analysis. Each kept session holds rizin's memory for that file (about 1 GB on a large binary), hence the 4 GB default limit.
  5. The backend stores the function list with the job (sample_code) and each function's CFG and pseudo-C as a row of sample_functions, which the UI fetches one function at a time (GET /api/samples/{sha256}/code/functions/{addr} and …/decompiled): the graphs of a large binary add up to tens of megabytes, and opening a function reads only its own.

rizin 0.9 can crash (segfault) after thousands of commands in one session, on a function it handles fine in a fresh one. The worker survives it: it reopens the sample and retries that function once; a second crash skips the function (it is listed, marked, without CFG). After three restarts in one request it gives up with an error.

In Compose the worker runs as the image's non-root user, with a read-only filesystem, no capabilities, memory and CPU limits, no published port and no route outside the internal analysis network: the sample is read and disassembled, never executed. Without a worker (ANALYZER_URL unset) the Code view says so and everything else keeps working.

The UI (components/tabs/malware/code/) lists the functions with the severity of the APIs they reach (the SOC malware ruleset applied to callee names, propagated through the call graph by utils/code.js) and draws the call graph around the selected function and its control-flow graph with elkjs: ELK's layered algorithm places the blocks (main path in a column, branches on the sides), routes edges orthogonally in their own lanes and sends loops back along the side, as a disassembler's graph view does. Nik draws the result as SVG with its own tokens, with pan, zoom, a minimap and click to select. elkjs (~1.4 MB) is imported only when the Code view opens; it is licensed EPL-2.0 / GPL-3.0 and used unmodified. The Decompiled panel shows the pseudo-C with the decompiler's own highlighting (font ligatures off, so != reads as written); a call to another function of the sample is a link that opens it, and calls to suspicious APIs are red.

Function triage. A real binary has thousands of functions, most of them library code. The worker reports, per function, what it can tell about its origin, and the UI (utils/triage.js) sorts the list with it:

  • Library: functions matched by a FLIRT signature (rizin's bundled set plus the .sig / .pat files admins upload in Settings → FLIRT signatures, stored under SAMPLE_STORE/_flirt/ and passed to the worker, which applies them with Fs after aaa), and, in Rust binaries, functions whose panic locations point at a crate's sources (…\.cargo\registry\src\…\<crate>-x.y.z\src\…rs, or /rustc/<hash>/library/std/… for the standard library). The worker finds those paths among the strings, follows the Location structs that point at them, and credits each function with the crates its instructions reference. The crates found are listed above the table.
  • Runtime (compiler start-up and C runtime support, by name), thunk (jumps to imports, switch fragments) and import.
  • Not recognised: everything else. Release builds leave much library code without a signature or a path, so this is "not recognised", not "the author's code".

Hide recognised library code (on by default) keeps only the unrecognised functions in the list. Start here ranks those that call suspicious APIs directly, use an indicator of compromise, reach a suspicious API through their callees or are complex. The worker also reports the file offsets of the strings each function references; matched against the analysis strings, they give each function's strings used and, in the IOC table, a Used by column that opens the function in the Code view. Analysts rename and comment functions (function_annotations table): names replace rizin's in the list, the graphs and the pseudo-C for everyone opening the same sample.

Capabilities (capa). Mandiant capa matches a community rule set against the program's code and reports what it can do (send data on a socket, create a process, encrypt with RC4, resolve APIs at runtime…), mapped to MITRE ATT&CK and the Malware Behavior Catalog. It runs in a third worker, workers/capa/, built on python:3.12-slim with flare-capa, its rules and its library signatures at a pinned version (the rules and signatures are checked against their SHA-256 at build time); capa uses its pure-Python vivisect backend, so no Java or IDA is needed. capa, capa-rules and vivisect are Apache-2.0.

  1. After an upload and on Re-analyse (or the Run capa button) the backend queues a job (sample_capa table) for x86 / x64 PE and ELF files; other types are marked unsupported without calling the worker.
  2. The worker (server.py, standard library) runs capa -j on <store>/<sha256>.bin from its read-only mount, kills it after CAPA_TIMEOUT, and reduces the report (megabytes on a large binary) to the capabilities with their namespace, scope, ATT&CK / MBC mappings and up to 200 addresses each, a few kilobytes. Rules capa marks as library helpers are dropped, as capa's own report does.
  3. capa is CPU-bound — seconds on a small file, ten minutes or more on a large one — so the worker runs one analysis at a time and the backend sends its jobs one after the other, waiting while the worker is busy.

The Capabilities view lists them by namespace with ATT&CK and MBC badges. capa and rizin split a binary into functions differently, so each address capa reports is credited to the rizin function containing it (placeCapabilities in utils/triage.js): the view links each capability to those functions, the Code view shows the capabilities of each function, and Start here counts them — only for functions not recognised as library code, since crypto and TLS crates match many rules. Capabilities do not change the sample's severity. The capa service has the same isolation as analyzer (read-only store and filesystem, internal network only, no capabilities, memory / CPU / time limits).

capa rules of your own. Admins add capa rules in Settings → capa rules (capa_rules table, one YAML rule each). Since only the worker has capa, the backend asks it to check a rule (POST /validate: parsed by capa and loaded together with the bundled rules and the other enabled admin rules, so syntax errors, unknown features, duplicate names and missing match: dependencies are caught) before saving it. Saved rules are written to SAMPLE_STORE/_capa_rules/<id>.yml and the enabled ones are passed to the worker with each analysis, as extra -r rule paths next to the bundled set. A rule another enabled rule matches cannot be renamed, disabled or deleted. Their matches carry a custom badge in the Capabilities view; new or changed rules apply from the next analysis (Re-analyse).

Mail analysis

The Mail Analysis tab triages reported messages. Like samples, the file goes to the server once: POST /api/incidents/{id}/mails stores it in the sample store as <sha256>.mail (read-only), analyses it (app/mail/analyze.py) and keeps the result in the mails table; the incident gets a light reference under data.mail.messages and the incidents.has_mail column (mirrored, for the mail icon in the sidebar). Nothing in an attachment is opened by the program it is meant for.

  • Parsing (mail/parse.py): .eml with the standard library; .msg (an OLE compound file of MAPI properties) with olefile: the original Internet headers when Outlook kept them, the bodies (Outlook's compressed RTF is decompressed, MS-OXRTFCP), the attachments and attached messages (parsed in turn, three levels deep).
  • Headers (mail/headers.py): the Received chain in travel order with the delay of each hop and clocks going back; the sending server is the first public IP that is not one of your servers. Authentication-Results (and ARC, Received-SPF) are read as written, but only those of your own servers (Settings → Mail analysis) are believed: anyone can put such a header in a message. A header without an authserv-id (Exchange Online) is credited to the server that received the message last.
  • Authentication (mail/verify.py): DKIM signatures verified with dkimpy, SPF of the sending IP with pyspf, DMARC policy and alignment (relaxed/strict, organisational domain from the bundled Public Suffix List) with dnspython. The server needs DNS; each lookup times out after 3 s and a failure reads temperror, never a pass. These say what the DNS says now (a rotated DKIM key fails), so the servers' verdicts are shown next to them. A .msg keeps no original body: its DKIM cannot be checked.
  • Links (mail/links.py): anchors, forms and URLs in the text, unwrapped from Safe Links, Proofpoint (v1–v3), Google, Facebook and Barracuda redirects; look-alikes of well-known brands (Italian banks and public services included) and of your own domains are found by folding confusable characters and comparing edit distance, so punycode and rn→m tricks show.
  • Body (mail/content.py): the HTML is cleaned with nh3 (no scripts, handlers, frames, objects or forms), inline cid: images become data: URIs, hidden text is revealed. The browser shows it in an <iframe sandbox=""> (no scripts, no same-origin, no navigation of the app) whose Content-Security-Policy refuses every request; links lose their target (shown as a tooltip) and remote images load only after a warning, tracking pixels never. Urgency, payment, credential and secrecy phrases are listed (English and Italian).
  • Attachments (mail/attachments.py): type from the magic bytes against the extension, double extensions and right-to-left tricks, VBA/XLM macros (oletools), zip listings (the password is looked for in the text and tried; the archive is never extracted to disk), PDF actions, QR codes in images (zxing-cpp), calendar invitations.
  • Verdict: each finding weighs a fixed number of points (e.g. a look-alike sender domain 40, DMARC failing 30, a password-protected archive 35, urgency 8); the score is capped at 100. It is an aid to triage, not a proof: a clean score means nothing stood out.

The message's indicators (sender addresses and domain, sending IP, link targets and hosts, attachment hashes, QR and invitation links) go into the IOC index as mail:<file name>; the timeline shows each message at the time it was sent, high when the verdict is phishing; the report has an E-mails section.

Threat intelligence

Indicators get a reputation from external services (app/enrichment/). Each provider is one function in providers.py that turns the service's answer into { verdict, summary, link, data }; verdict is malicious, suspicious, harmless or unknown (not known, or nothing conclusive).

Provider Types Key Free tier (as Nik paces it)
VirusTotal IP, domain, URL, hash required 1 request / 15 s, 500 a day
AbuseIPDB IP required 1,000 a day
abuse.ch: ThreatFox, URLhaus, MalwareBazaar IP, domain, URL, hash required (one Auth-Key) —
AlienVault OTX IP, domain, URL, hash required —
urlscan.io (search of public scans, nothing submitted) domain, URL optional 1,000 a day
GreyNoise Community IP optional 50 a day
Shodan InternetDB IP none —
Google Safe Browsing domain, URL required 10,000 a day

What is never sent (service.blocked), whoever asks: private, loopback and other non-public addresses, internal names (no dot, .local, .lan, .internal, .corp, .home.arpa…) and URLs on them; values on the IOC allowlist; values seen in an incident whose report is classified TLP:RED; e-mail addresses. MD5 and SHA-1 of stored samples and mail attachments are not looked up automatically: their SHA-256 is.

Automatic lookups are off until an analyst turns them on in Settings → Threat intelligence, per type: IP addresses, URLs and domains, file hashes. Every API process starts a worker thread (worker.py); a lease row (leases) lets only one of them work at a time, so several gunicorn workers do not multiply the requests. Every 30 seconds it checks the indexed indicators not in the cache (newest incidents first) with every enabled provider that takes their type, pacing each provider to its free tier. An answer is kept for the cache period (24 h by default, up to 30 days), an error is retried after an hour; a provider that answers 429 waits an hour, one that refuses its key six hours.

Check now in Where seen asks every usable provider at once (fresh answers are reused unless "Check again"). The IOCs tab's Reputation column shows the worst cached verdict and how many providers flag the value.

Keys are entered by admins and stored in integration_keys, encrypted with Fernet under a key derived from SECRET_KEY (HKDF, vault.py): the API returns only whether a key is set and its last four characters. Changing SECRET_KEY without SECRET_KEY_PREVIOUS makes the stored keys unreadable (Settings says so): enter them again. Requests use the standard library (urllib), so HTTPS_PROXY / NO_PROXY apply; a transparent proxy needs nothing.

Attachment previews and the isolated browser

Two more workers show what an attachment looks like without opening it on the analyst's machine. Like analyzer and capa they run as unprivileged users with a read-only filesystem, no capabilities, memory and CPU limits, no published port, and answer only the backend's shared token.

Documents (workers/docview/, internal network only). The Mail Analysis tab's Preview sends the attachment to POST /api/mails/{sha256}/attachments/{path}/preview; the backend forwards it to the worker, which converts Word, Excel, PowerPoint, OpenDocument and RTF to PDF with LibreOffice (a fresh profile per conversion: macro security "very high", macros disabled, links to other files or the network never updated, killed after 90 s) and renders the first 20 pages of the PDF with pdfium; images are re-encoded with Pillow. The browser receives PNG images only. The pages are kept under SAMPLE_STORE/_previews/<sha256>.json and removed with the last message that holds the attachment.

Isolated browser (workers/browser/). HTML attachments (Open in isolated browser) and links (Links view) open in Chromium, run by Playwright inside the worker's container. The analyst sees a JPEG of the viewport; clicks, double-clicks, typing, Enter / Tab / arrows and the wheel are sent to POST /api/browser/sessions/{id}/action and replayed there, with back, forward, reload and an address bar. Scripts of the page run in the worker, never in the analyst's browser.

  • Network, chosen for each session. Without network (the default) the page is the attachment itself: every other request (images, scripts, frames, form posts, links) is refused, and a navigation shows a "blocked by Nik" page. With network, http and https go out through the server's connection (the browser-egress network, the only one with a route outside), except to private, loopback or link-local addresses and internal names, so a page cannot reach the organisation's own network. Every session is audited (browser.open), with or without network.
  • The rule is enforced where the connections are made. Chromium is started with one route, the worker's own proxy (egress.py, on loopback): every connection a page causes goes through it, the hops of a redirect and the sub-resources included, which the request interception alone never sees. For each connection the proxy resolves the name itself, refuses unless every address is public, and connects to the address it just checked, so a name that changes its answer between the check and the connection (DNS rebinding) gains nothing. WebRTC and QUIC, which would send UDP around a proxy, are off. The proxy also tells the network log where each request really went.
  • Networks. The backend reaches the worker on browser-control, an internal network the two share with nobody: the one container that runs hostile pages has no route to the other workers or to the database.
  • Tabs and size. A window the page opens (window.open, a target=_blank link) becomes a tab of the session, shown at once, with at most eight open; when a tab closes itself the one that opened it is shown again. The state returned by every action lists the tabs, and the tab / closeTab actions switch and close them. The pages are drawn at the size the analyst's window has for them (resize, between 640×400 and 2560×1600; a pop-up that asks for its own little window gets the session's size). RemoteBrowser.jsx measures that space, asks for it, and offers a full-screen mode.
  • Downloads are refused and reported, alert / confirm / prompt dialogs are dismissed and reported, permission prompts denied. A session belongs to the analyst who opened it, closes after 5 minutes without an action (30 minutes at most) and when the window is closed; at most BROWSER_MAX_SESSIONS are open at once.
  • Chromium's own sandbox needs privileges the container does not give, so it runs with --no-sandbox: the container is the sandbox.

Network analysis

The Network Analysis tab reads packet captures with Wireshark's own engine, in the pcap worker (workers/pcap/): Debian's tshark and sharkd, run as an unprivileged user in a container with a read-only filesystem and the sample store mounted read-only, no capabilities (nothing is ever captured) and the internal network only.

  • Upload (POST /api/incidents/{id}/captures): pcap or pcapng, gzip too, up to PCAP_MAX_MB (500), checked by its magic bytes, written to SAMPLE_STORE/_captures/<id>/ (read-only) and recorded in the network_captures table. The worker then reads it once with tshark for the summary: hosts by bytes, DNS names and answers, HTTP requests, TLS server names, POST / PUT / PATCH requests, beacons (six or more connections to the same address and port, at least 5 s apart, intervals within 15 %), the exported objects with their SHA-256 and the Expert Info counts. These feed the IOC index (network:<file>), the timeline and the report's Network section.
  • Viewing goes through sharkd, Wireshark's daemon for web front ends, one process per open capture (two at most, closed after 15 minutes unused): the packet list with Wireshark's colouring rules, paged; the protocol tree with the byte range of every field; Follow Stream; Export Objects. The backend forwards a fixed set of read-only calls (POST /api/captures/{id}/rpc); columns are never taken from the caller, since some custom column definitions crash sharkd.
  • TLS is decrypted with a key log (SSLKEYLOGFILE, NSS format) added at upload or later. It is stored encrypted like the API keys and written to the worker's /tmp only while a capture is open.
  • Packets can be flagged into the incident timeline (pcap:<capture>:<n>).

Isolated browser sessions. The browser worker records every request of a session (netlog.py): method, URL, type, headers, bodies in clear (the browser sees HTTPS decrypted, 2 MB per body and 50 MB per session, past that size and SHA-256 only), response, server address, certificate, timings and WebSocket messages; refused requests (no network, private address) and held submissions included. In a session with network, POST / PUT / PATCH / DELETE requests are held by default: recorded, not sent, the page shows "Submission held by Nik"; the analyst may send them for the session (audited). Opened from an incident, the session's log is copied after every action (network/service.py) and shown live in the window's Network panel, DevTools-like. When the window closes (or the session expires) the log is rebuilt as pcapng (network/pcapng.py): a DNS answer per host, a TCP handshake and HTTP/1.1 in clear per request, a comment saying it is a reconstruction and marking held and refused requests, so Wireshark's filters, Follow Stream and Export Objects work on it, then analysed like an upload. It also exports as HAR 1.2 (network/har.py).

URL analysis

An address is scanned by the isolated browser worker, the same that opens HTML attachments: urlscan.run_scan (a background task of the API) opens a session with network access (private and internal hosts are refused, submissions are held), calls the worker's inspect action, which returns a screenshot and what the page asks for (its forms, read from the DOM), copies the session's network log and closes the session. Nothing is typed, clicked or submitted.

urlscan.assess weighs the facts into findings with points, as Mail Analysis does: the address itself (lookalike of a brand, punycode, @ in the authority, an IP address as host, a throwaway top-level domain, a shortener, a cloud-hosted page: the link rules of mail/links.py), a page that asks for a password outside the brand's own domains (and over plain http, or under a brand's name in its title), a form that posts to another registrable domain, a chain through three or more domains, a certificate issued less than seven days ago, a download the page started. A score of 70 or more is phishing, 40 to 69 suspicious, less clean.

One row per distinct address (url_scans, id = the first 32 hex characters of the SHA-256 of the normalised URL): scanning it again replaces the result. The screenshot sits in SAMPLE_STORE/_urls/; the visit's network log becomes a capture (an isolated browser session), related to the address as its child. An incident keeps a light reference under data.urls.scans; the address, the hosts it led to and the server's IP join the incident's indicators, the scan its timeline and report.
