Architecture

How Nik is built: the design choices, the folder structure, the data model and the authentication. How each analysis works is on Analysis internals; how the pieces are kept apart is on Security.

High-level design

   Analyst's browser                      Server (the Compose stack)
┌───────────────────────────┐     ┌─────────────────────────────────────────────┐
│  React SPA (Vite build)   │     │  web: nginx                                 │
│  ├─ parses small evidence │────▶│  ├─ static files, security headers          │
│  │   (text, SQLite: WASM) │ TLS │  └─ /api/ ──▶ api: FastAPI                  │
│  ├─ detection engine      │     │        ├─▶ db: PostgreSQL                   │
│  └─ REST client (/api)    │     │        ├─▶ sample store (a volume)          │
└───────────────────────────┘     │        ├─▶ analyzer, capa, docview, pcap    │
                                  │        │     (workers with no route outside)│
                                  │        └─▶ browser ──▶ internet, filtered   │
                                  └─────────────────────────────────────────────┘

The split is deliberate:

  • Small evidence is parsed in the browser. Browser databases, shell histories and the output of collection scripts and DFIR tools (SQLite, JSON, CSV, property lists) are read and normalized client-side; only the resulting entries are sent to the API as part of the incident document.
  • Evidence that is a file to study goes to the server. Malware samples, e-mails, packet captures and Windows event logs are uploaded: the server stores them (the sample store) and analyses them, itself or through a worker. Addresses are visited by the isolated browser worker.
  • State lives on the server. Incidents, users, settings and the audit log are stored in the database and shared by all analysts; the browser keeps only view preferences (a panel's width, a switch).
  • Single origin. nginx serves the SPA and proxies /api/ to the backend, so no CORS configuration is needed and the httpOnly session cookie flows transparently. In development, the Vite proxy plays nginx's role.
  • Hostile content is handled by the least privileged part. Each worker does one job in a container with no network, a read-only filesystem and resource limits; the backend itself runs unprivileged. See Security.

The REST API is one FastAPI application with a router per area (backend/app/routers/, 23 of them), all under /api. The API page lists the endpoints; Swagger UI at /api/docs has every request and response shape.

What is parsed where

Browser artifacts, shell histories and tool output are parsed in the analyst's browser. That includes Chromium's History, a binary SQLite database, read with sql.js (SQLite compiled to WebAssembly). Rationale:

  1. Privacy / chain of custody — these files hold a subject's whole browsing history, credentials in URLs and more. The raw file of one of these kinds never leaves the analyst's machine: only the normalized entries are stored.
  2. Less to protect on the server — no copy of somebody's browser profile sits in a store that has to be secured, backed up and eventually deleted.
  3. Works in the field — the parsing layer needs no connectivity beyond the API calls that persist results.

The sql.js WASM module (~1 MB) is loaded lazily on the first SQLite import (see frontend/src/parsers/sqliteParser.js): analysts who only work with JSON/CSV exports never download it. The same files can be sent through the API instead (POST /api/incidents/{id}/upload): the server then parses them with a Python port of the same parsers (backend/app/parsing/), within the limits described on Security.

File schema per engine. Chromium browsers (Chrome/Edge/Brave/Opera) share Chrome's SQLite schema (History with urls/visits/downloads, a JSON Bookmarks file, a Shortcuts database). Firefox is different: a single places.sqlite database (moz_* schema) holds history, bookmarks and downloads. Safari (macOS only) keeps history in a History.db database (history_items/history_visits) and downloads and bookmarks in two property lists, Downloads.plist and Bookmarks.plist, usually binary. Timestamps differ too — see browsers, parsers and formats.

What is uploaded, and where it goes:

Evidence Kept on the server as Analysed by
Malware sample the file, in the sample store (named by its SHA-256, never executed) the backend (hashes, strings, YARA, structure), the analyzer and capa workers
E-mail (.eml, .msg) the file, in the sample store the backend; attachments previewed by the document and browser workers
Packet capture the file, in the sample store; an optional TLS key log, encrypted in the database the capture worker (Wireshark's engine)
Windows event log (.evtx) the curated events only, in the incident document; the file is not kept the backend, in a background job
Address to scan a screenshot and the requests of the visit, as a capture the isolated browser worker

These are uploaded because the file is the evidence under study, not a container of entries to normalize, and because their analysis (disassembly, protocol dissection, rendering a hostile document) must not happen on an analyst's workstation. How each analysis works is on Analysis internals.

Naming an incident. An incident has a ticket ID (the reference in your tracker), a short title, a host and a user, all optional but at least one. Its name is built from them: the ticket first, in square brackets, then the title when there is one, otherwise host - user: [INC-2041] Invoice phishing, finance, [INC-2039] WKS-042 - m.rossi, SRV-FILE-01. The severity (low, medium, high, critical) is a tag the analysts set, shown next to the name in the sidebar and the header but never part of it. The status (open, in_progress, closed; an incident with none is open) and the assignee (a username) live in the document and are mirrored into columns, like the ticket and the severity, so the panel lists and filters them without reading documents. Everything is editable from the Summary tab; the search palette and GET /api/incidents?q= also find incidents by ticket.

Right-click. One menu for the whole app (frontend/src/context/ContextMenuContext.jsx): on an indicator (anywhere it is shown: the IOCs tab, a sample's indicators, event-log addresses) Where else was this seen?, Search for it, Copy, Copy defanged (hxxps[:]//evil[.]top) and Add to the allowlist…; on an event row (Browser, Commands, Endpoint, Event Logs, Timeline) Flag or Remove the flag, Add a comment…, Copy as text, Copy as JSON and Show in the Timeline; on an incident in the sidebar Open, Incident report…, Export (JSON), Copy link and Delete…. Text fields and selected text keep the browser's menu, and so does Shift + right-click. Add to the allowlist (also the shield button on each IOC row) proposes the value or a wider entry — its domain or a parent domain, its /24 network — and writes it to the shared allowlist with a comment line saying who added it and when; Undo stays available for a few seconds. Any analyst can do it.

Drag-and-drop anywhere. Drop a file on any part of the app (outside the tabs' own drop zones) and a dialog proposes where it goes, from its first bytes and its name (frontend/src/domain/fileRouting.js): PE, ELF and Mach-O executables, PDF, Office documents, scripts and archives → Malware Analysis; .evtx and the event-log script's JSON → Event Logs; Chromium History / Shortcuts / Bookmarks, Firefox places.sqlite, Safari History.db and plists → Browser Forensics; shell histories → Command History; CSV → Endpoint Artifacts. The dialog always asks whether the file goes into the open incident or a new one (with its ticket, title, severity, host, user and OS), lets you change the tab and the source, then opens the tab and imports the file as its own drop zone would.

Each incident is tied to a single host and carries an operating system (windows | macos | linux, see frontend/src/config/os.js), chosen when the incident is created and editable from the Summary tab. The OS drives the host-specific bits of the UI: the artifact paths suggested in Browser Forensics, which shells appear in Command History, and the incident icon shown in the sidebar and header.

The Command History tab mirrors Browser Forensics for terminal activity: one sub-tab per shell (Bash / Zsh / Fish / PowerShell, see frontend/src/config/shells.js), parsing the native history files (.bash_history, .zsh_history, fish_history, PSReadLine ConsoleHost_history.txt) plus JSON/CSV exports. Commands run through the SOC engine — the shared keyword rules plus a built-in command ruleset (DEFAULT_COMMAND_KEYWORDS in frontend/src/config/detectionRules.js: download-and-execute, encoded payloads, reverse shells, credential access, defense evasion, persistence, exfiltration, history tampering…) — can be flagged, searched, filtered by the suspicious window, and appear on the incident timeline exactly like browser events.

The Endpoint Artifacts tab covers host forensic artifacts that neither the browser nor the shell captures, one sub-tab per category built from one or more sources (see frontend/src/config/artifacts.js): Program Execution (BAM, KnowledgeC), Persistence (Run keys, Scheduled Tasks, services, startup, WMI, cron, systemd, SSH keys, rc files, LaunchAgents), File & Folder Access (GTK recently-used) and USB & Devices (USBSTOR, setupapi log, kernel journal). The table shows the union of every source's records, tagged by which source produced them, and runs the shared keywords plus a built-in artifact ruleset (DEFAULT_ARTIFACT_KEYWORDS: execution from temp/user-writable paths, LOLBins, double extensions, suspicious persistence, known offensive tool names).

Crucially, every source is collected without any third-party tool, in one of two ways driven by the incident's host OS:

  • file — the data already lives in a plain text / XML / log / SQLite file, so the analyst uploads that existing file and it is parsed in-browser (custom parsers in frontend/src/parsers/artifactParsers.js: recently-used.xbel, authorized_keys / cron / rc files, LaunchAgent .plist, setupapi.dev.log, and knowledgeC.db via sql.js).
  • script — the data is live system state (registry, service manager, kernel journal), so the tab shows a native collection script (frontend/src/config/collectionScripts.js, PowerShell / systemctl / journalctl only) with copy/download buttons; it writes a CSV whose headers match the importer 1:1, which the analyst then imports.

Artifacts that can only be recovered with third-party DFIR parsers (Prefetch, Amcache, ShimCache, UserAssist, LNK, JumpLists, ShellBags, RecentDocs) are intentionally left out; a category with no custom source on a given OS shows an explicit note rather than a dead end.

The Event Logs tab (Windows) holds curated events from the host's event logs, per channel (Security, System, PowerShell, PowerShell classic, RDP sessions and authentication, Defender, Task Scheduler, Sysmon; see frontend/src/config/eventLogs.js). They arrive two ways: raw .evtx files copied from C:\Windows\System32\winevt\Logs\ (or a disk image), uploaded and parsed on the server, which also recovers records left in the file's unused space after a clear and keeps the file's SHA-256; or the JSON written by a native Get-WinEvent collection script on a live host, parsed in the browser. Only about 50 curated event IDs are stored (at most 20,000 per channel, the newest); the rest is counted. The tab shows:

  • the log coverage: one bar per channel from its first to its last record, with silences of 6 hours or more hatched, clears marked in red and the incident's suspicious window behind them — a gap or a clear inside the window is where evidence may be missing;
  • the logon sessions: each 4624 paired with its logoff (4634/4647) and admin privileges (4672) by logon id, service logons and machine accounts left out;
  • every event with a readable summary, filters by detection, category, channel and time, and a detail view with all its fields.

Command lines (4688, Sysmon 1) and PowerShell script blocks go through the command-line ruleset; the built-in event-log ruleset (DEFAULT_EVENTLOG_RULES, logic in frontend/src/domain/eventLogs.js) adds log cleared, audit policy changed, service installed (high when the binary sits in a user-writable path or runs a shell), suspicious PowerShell, brute force (10 failed logons for one account or source within 10 minutes), a logon right after 5 failures, RDP outside business hours, account created, member added to a privileged group, Defender alerts and scheduled task created. Machine activity (service logons, boots) is not judged by the clock. Linux (journald, auth.log) and macOS unified logs will follow.

The Timeline tab is the super-timeline: it merges every timestamped event from the Browser, Command History, Endpoint Artifacts and Event Logs tabs, and from the samples, e-mails, captures and scanned addresses of the incident, into a single chronological, filterable table (by source, detection and time window). Entries without a reliable timestamp (e.g. PSReadLine commands) are intentionally left out. Any row can be flagged straight from the timeline.

The sidebar is resizable: drag its right edge to widen the incident list up to a quarter of the window; the width is remembered per browser.

The IOCs tab lists the incident's indicators of compromise. The server builds them (backend/app/iocs.py) whenever the incident's data is saved — a merge patch that only touches flags or notes leaves them alone — and keeps one ioc_index row per incident, type and value, so "where else have we seen this?" is one indexed query for every analyst, whoever owns the other incident. The sources:

  • browser history: the visited hosts (not every URL); downloads: the URL, its referrer and their hosts;
  • shell commands and endpoint records: URLs, IP addresses, domains (known TLDs), e-mail addresses and MD5/SHA-1/SHA-256 digests in the text;
  • event logs: address and host fields (IpAddress, DestinationIp, QueryName…), Sysmon Hashes, and the indicators in command lines, script blocks and service paths;
  • malware samples: the sample's hashes and the network indicators in its strings;
  • e-mails: sender addresses and domain, sending IP, link targets and hosts, attachment hashes, QR-code and invitation links (mail:<file name>).

Indicators also seen in other incidents come first, in red. Clicking a value here, in a sample's IOC table or in the Event Logs tab opens the indicator's window, with Seen in: every incident it appears in, with the sources, count and first/last time, and a link to open it. Settings → IOC allowlist (one entry per line: a domain and its subdomains, an IP or CIDR network, or an exact value) starts with private and loopback ranges and common vendor and CDN domains; matching values are hidden by default and never exported. The index keeps them, so editing the list applies at once. Exports: CSV, a STIX 2.1 bundle and a MISP event, for a TIP or a firewall blocklist. Incidents saved before 2.12.0 are indexed on the api's first start.

Incident report. The report button in the header (or > report in the search palette) opens the report dialog: language (English or Italian), TLP classification, the sections to include and an executive summary — all saved with the incident (report key of the document) — a preview, and the download as PDF or HTML. The server builds the report (backend/app/report.py) as one self-contained HTML page styled for print, and renders the PDF with WeasyPrint: A4 pages with the organisation and the TLP label at the top and page numbers at the bottom. Its sections:

  • executive summary and key facts (flagged events, SOC detections, indicators, samples, techniques);
  • flagged events in time order, with the analysts' comments;
  • MITRE ATT&CK techniques from capa's capabilities, the YARA rules' mitre_attack metadata (the built-in rules carry it) and the SOC rules that matched (each built-in rule names its techniques in frontend/src/config/detectionRules.js), each with where it was seen;
  • indicators of compromise outside the allowlist, those seen in other incidents first (up to 500; the rest are in the CSV/STIX/MISP export);
  • malware samples with their hashes, YARA matches and capa capabilities;
  • Windows event logs: each channel's coverage and when it was cleared;
  • analyst notes;
  • an evidence appendix: every imported file with its format, rows, import time and SHA-256. Browser, shell-history, endpoint and event-log JSON files are hashed in the browser when they are imported (the file still never leaves the machine); .evtx files and samples are hashed by the server.

The organisation name and logo come from Settings → Report header. API clients get the same report from POST /api/incidents/{id}/report.

Global search. Ctrl/Cmd+K anywhere, or / outside a text field, or the search… button in the header, opens a nik> prompt. As you type it asks the server (GET /api/search) for incidents, indicators from every incident and samples, and searches the open incident in memory: its timeline events (every tab), notes and samples (by file name too). Enter opens the result: an incident is selected, an indicator or a sample opens its window, an event jumps to its tab, a note to the Summary. A query starting with > lists actions instead: go to any tab, new incident, export the incident, settings, the IOC allowlist, sign out. On PostgreSQL the substring matches use the trigram (pg_trgm) indexes of migration 0012; when the extension cannot be created the search works without them.

Platform configuration lives in one sectioned Settings panel (opened from the rail's gear, or deep-linked from the rail's Users and Audit log buttons). Everyone has detection rules (with the built-in rulesets shown for reference), business hours, the IOC allowlist, My account and the audit log; admins also have the report header, mail analysis, threat intelligence, accounts, API keys and the YARA, FLIRT and capa rule sets.

State and the data model

IncidentContext

All incident state lives in frontend/src/context/IncidentContext.jsx, exposed through the useIncidents() hook:

  retryActiveIncident,    // () => void — retry after activeLoadError

  clearTabData,           // (id, dataKey) => void — reset to the registry defaultData

  setActiveProfile,       // (id, browserId, profileId) => void — switch profile (local only)

  clearArtifactSource,    // (id, categoryId, sourceKey) => void — clear ONE source
  clearArtifactCategory,  // (id, categoryId) => void — clear ALL sources of a category

  clearEventLogs,         // (id, channel?) => void — one channel, or all of them

Loading is lazy. After authentication only the light list is fetched (GET /api/incidents?view=summary). Opening an incident downloads its full document (GET /api/incidents/{id}) while the main area shows a non-blocking loading state — the sidebar stays usable and opening another incident cancels the pending download. Documents stay cached in memory for the session; reopening one, or coming back to the window, shows it at once and revalidates it with If-None-Match (304 when unchanged, merged when someone else edited it).

The cache is an optimistic model: every mutation updates local state immediately and hands the incident to the save queue (frontend/src/services/saveQueue.js). The queue keeps, per incident, the last version the server is known to hold and its ETag, and persists only the difference, as an RFC 7396 JSON Merge Patch generated by frontend/src/lib/mergePatch.js. Toggling a flag therefore sends the flag, not the incident's artifacts. setActiveBrowser, setActiveProfile and setActiveShell are view preferences, never sent.

  • One save at a time, in order. Edits made while a save travels leave with the next one; two edits of the same tick (a comment on a row that was not flagged) are one request.
  • Nothing is forgotten. Because the patch is the difference from the last acknowledged version, a save that failed is still in the next one. It is retried at growing intervals and reported by App.jsx as a red banner (storageError, unsavedChanges, retrySave) until it goes through.
  • Two writers do not overwrite each other. Each save sends If-Match. The backend bumps the incident's revision (incidents.rev, its ETag) at every write of the document, whoever makes it, and takes the row lock before reading it (backend/app/core/locking.py), so the check and the write are atomic. On 412 the queue reads the server's version and carries the local changes over it with a three-way merge (frontend/src/lib/rebase.js): objects member by member, lists of things with an identity (notes, comments, references) item by item.
  • An expired session loses nothing. A 401 sets sessionExpired in AuthContext; SessionExpiredDialog asks for the password over the app, and the queue resumes after the sign-in.

Shape of an incident

{
  id:        'uuid',
  ticketId:  'INC-2041',                   // identity (NOT unique — the id is the key),
  title:     '',                           //   all optional, at least one set
  host:      'WKS-FINANCE-01',             //   "
  username:  'm.rossi',                    //   "
  name:      '[INC-2041] WKS-FINANCE-01 - m.rossi', // derived: "[ticket] title" | "[ticket] host - username"
  severity:  'high',                       // 'low' | 'medium' | 'high' | 'critical' | null — a tag
  status:    'in_progress',                // 'open' | 'in_progress' | 'closed' — where the work stands
  assignee:  'a.bianchi',                  // username of the analyst who has it, or ''
  suspiciousStart: 1751871120000,          // Unix ms | null — start of suspicious activity
  suspiciousEnd:   1751899999000,          // Unix ms | null — end of suspicious activity
  createdAt: '2026-07-07T09:00:00.000Z',   // ISO 8601
  updatedAt: '2026-07-07T11:30:00.000Z',   // bumped on every change
  createdBy: 'analyst',                    // username of the creator

  data: {
    // one key per tab registered in config/tabs.js:
    summary: {},                           // the Summary tab reads incident.* directly
    browser: {
      activeBrowser: 'chrome',
      browsers: {                          // data PER BROWSER, then PER PROFILE
        chrome: {
          activeProfile: 'default',
          profiles: {                      // keyed by a stable id; shown in createdAt order
            default: { id: 'default', name: 'Default', createdAt: '1970-01-01T00:00:00.000Z',
                       history: [], downloads: [], bookmarks: [], shortcuts: [],
                       meta: { history: null, bookmarks: null, shortcuts: null } },
            '<uuid>': { id: '<uuid>', name: 'Work', createdAt: '2026-07-07T09:10:00.000Z', … },
          },
        },
        firefox: { activeProfile, profiles: { … meta: { places: null } } },
        edge: { … }, brave: { … }, opera: { … },
        safari:  { activeProfile, profiles: { … meta: { history, downloads, bookmarks } } },
      },
    },
    network: {                             // packet captures: light references, the packets
      captures: [ { id, kind: 'pcap' | 'browser', fileName, size, sha256, status, packets,
                    first, last, keylog, label, held: [{ method, url, time }], posts,
                    beacons: [{ destination, port, count, interval }], objects } ],
    },                                     //   come from POST /api/captures/{id}/rpc
    endpoint: {},
    eventlogs: {
      channels: {                          // one key per Windows event-log channel
        Security: {
          events: [ { id: 'evt:Security:9120', time, eventId: 4624, channel: 'Security', provider,
                      computer, recordId: 9120, level, data: { TargetUserName, LogonType, … },
                      recovered /* only when recovered after a clear */ } ],
          meta: { fileName, format: 'evtx' | 'json', importedAt, rows, total, kept,
                  dropped, recovered, first, last, gaps: [[start, end]], sha256 /* evtx */ },
        },
      },
    },
    mail: {                                // analysed e-mails: light references, the analysis
      messages: [ { sha256, fileName, format: 'eml' | 'msg', size, subject, from, date,
                    verdict: 'phishing' | 'suspicious' | 'clean', score, importedAt, importedBy } ],
    },                                     //   is fetched from GET /api/mails/{sha256}
  },

  // Entries the analyst flagged as malicious (keyed by the event id):
  flags: {
    '<eventId>': {
      key, browserId, section, eventType, title, url, time,   // the flagged snapshot
      profileId, profileName,                                  // browser flags only (2.0.0+)
      flaggedAt, flaggedBy,                                    // provenance
      comments: [ { id, text, at, author } ],                  // per-flag comments
    },
  },

  // Free-form notes shown on the Summary timeline:
  notes: [ { id, text, createdAt, updatedAt, author } ],
}

meta is indexed by file source (keys vary per engine: Chromium has history/bookmarks/shortcuts, Firefox has places). Each entry describes the imported file: { fileName, format, rows, importedAt }.

data is built by buildDefaultIncidentData() (frontend/src/config/tabs.js), which iterates the tab registry: each tab contributes structuredClone(defaultData) under its own dataKey. Every incident loaded from the server or imported from a file passes through normalizeIncident(), which merges the registry defaults with the stored data — so adding a tab requires no data migration: existing incidents receive the new tab's defaultData automatically (see add a new analysis tab).

Where things are stored

Store Content
incidents the incident documents (parsed evidence, flags, notes, references to samples, e-mails, captures and scans), with a few fields mirrored into columns for the list and a revision counter
ioc_index the indicators of every incident, rebuilt when its evidence changes
samples, sample_code, sample_functions, sample_capa, function_annotations the analysis of each sample: static analysis, disassembly, capabilities, the analysts' renames
mails, network_captures, url_scans the analysis of each e-mail, capture (and isolated browser session) and scanned address
artifacts, artifact_links, artifact_relations the registry of everything analysed, which incidents reference it, and what came out of what
yara_rules, flirt_signatures, capa_rules the rule sets added by admins
integration_keys, ioc_enrichment, leases threat-intelligence API keys (encrypted), cached answers, and the lock of the lookup worker
users, sessions, api_keys accounts (bcrypt hash), server-side sessions, API keys (SHA-256 digest only)
audit_log the global audit trail
settings, webhooks, jobs, idempotency_keys the shared settings, event subscriptions, background uploads, replay protection
The sample store (a volume) the files themselves: samples and e-mails named by SHA-256, captures (_captures/), screenshots of scanned addresses (_urls/), FLIRT and capa rule files

A backup is therefore two things: a dump of the database and a copy of the sample store (deploy/backup.sh takes both, with .env). The in-app full backup covers the first four tables' worth of work only; see Full platform backup.

Authentication, sessions and the audit log

Authentication

Passwords are hashed with bcrypt on the server (backend/app/core/security.py). A successful POST /api/auth/login creates a server-side session row and sets the httpOnly nik_session cookie (with the Secure flag when COOKIE_SECURE=true, the default); credentials: 'include' on every fetch keeps it flowing. Sessions expire after SESSION_TTL_HOURS.

User shape: { id, username, role: 'admin' | 'analyst', createdAt, createdBy, disabled } — the password hash never leaves the backend. A sign-in that names an unknown account does the same hashing work as a wrong password, ten wrong passwords in a row lock the account for five minutes (users.failed_logins, users.locked_until), and expired sessions are purged at each sign-in.

The App shell (App.jsx) implements a three-state auth gate, driven by GET /api/auth/bootstrap and GET /api/auth/me:

  • no users at all → FirstRunSetup: the first POST /api/users succeeds without authentication and the created account is forced to the admin role;
  • users exist but not signed in → LoginScreen;
  • signed in → the main app;
  • session ended while working (any request answers 401) → SessionExpiredDialog over the app, which keeps its unsaved changes.

Admins manage accounts in Settings → Accounts (AccountsSection.jsx): add a user, change its name, role or password, disable it, or delete it (PATCH / DELETE /api/users/{id}). The server keeps at least one admin able to sign in and refuses a change to the caller's own role. A rename is carried to the incidents assigned to the account, under their row lock; a new password or disabling ends the account's sessions. Every user changes their own password in My account (PUT /api/users/me/password).

Audit log

The log is written by the server: each handler records what it does through backend/app/core/audit.py, for a session and for an API key alike, so a request sent by hand leaves the same entry as the app. An entry says who (actor), when (at), what (action), the details, and which incident it belonged to. Entries are returned newest-first, capped at 5000.

A merge patch says what changed, not what it means, so describe_patch() compares the document before and after and names the changes: a flag added or removed, a comment, a note, the attributes that changed, the evidence tabs touched and the files imported into them. The browser reports only what happens in it alone: POST /api/audit accepts incident.export and refuses anything else.

Entry shape: { id, at, actor, action, target, details, incidentId, incidentName }.

Action strings include: auth.login / .logout / .locked, user.create / .update / .delete / .password, apikey.create / .revoke, settings.update, incident.create / .update / .delete / .export, evidence.update, flag.add / .remove / .comment, note.add / .update / .remove, the sample, e-mail, capture and URL actions, backup.export / backup.import and audit.clear.

The Audit log section of Settings (AuditLogSection.jsx, also opened from the rail) reads the trail each time it opens and shows it in a searchable table; an admin can clear the whole log behind an inline confirmation step, and the new log starts with an audit.clear entry naming them.

Large data sets

A browser history of a few hundred thousand visits has to stay usable, so the Browser tab keeps its per-row work to a minimum:

  • buildEvents() parses each URL once (analyzeUrl in lib/url.js) and stores domain and searchQuery on the event; the stat cards, the ranking widgets and the table cells read those fields instead of parsing again (entryDomain() / entrySearchQuery() fall back to parsing for raw entries).
  • DataTable sorts text with one shared Intl.Collator: localeCompare with options builds a collator per comparison, which made a 300k-row sort take seconds. The search box uses useDeferredValue, so typing never waits for the filter.
  • buildTimelineEvents() takes incident.data, not the incident: flags and notes do not change the timeline, so toggling a flag does not rebuild the Timeline tab.

Tables stay paginated (25 rows by default), so the DOM never holds more than one page; the cost of a large incident is in these data passes, not in rendering. When you add a per-row computation, do it once in the build* helper, not in a cell renderer.
