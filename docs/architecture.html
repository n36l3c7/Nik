The split is deliberate:

  • Small evidence is parsed in the browser. Browser databases, shell histories and the output of collection scripts and DFIR tools (SQLite, JSON, CSV, property lists) are read and normalized client-side; only the resulting entries are sent to the API as part of the incident document.
  • Evidence that is a file to study goes to the server. Malware samples, e-mails, packet captures and Windows event logs are uploaded: the server stores them (the sample store) and analyses them, itself or through a worker. Addresses are visited by the isolated browser worker.
  • State lives on the server. Incidents, users, settings and the audit log are stored in the database and shared by all analysts; the browser keeps only view preferences (a panel's width, a switch).
  • Single origin. nginx serves the SPA and proxies /api/ to the backend, so no CORS configuration is needed and the httpOnly session cookie flows transparently. In development, the Vite proxy plays nginx's role.
  • Hostile content is handled by the least privileged part. Each worker does one job in a container with no network, a read-only filesystem and resource limits; the backend itself runs unprivileged. See Security.

The REST API is one FastAPI application with a router per area (backend/app/routers/, 28 of them), all under /api. The API page lists the endpoints; Swagger UI at /api/docs has every request and response shape.

What is parsed where

Browser artifacts, shell histories and tool output are parsed in the analyst's browser. That includes Chromium's History, a binary SQLite database, read with sql.js (SQLite compiled to WebAssembly). Rationale:

  1. Privacy / chain of custody — these files hold a subject's whole browsing history, credentials in URLs and more. The raw file of one of these kinds never leaves the analyst's machine: only the normalized entries are stored.
  2. Less to protect on the server — no copy of somebody's browser profile sits in a store that has to be secured, backed up and eventually deleted.
  3. Works in the field — the parsing layer needs no connectivity beyond the API calls that persist results.

The sql.js WASM module (~1 MB) is loaded lazily on the first SQLite import (see frontend/src/parsers/sqliteParser.js): analysts who only work with JSON/CSV exports never download it. The same files can be sent through the API instead (POST /api/incidents/{id}/upload): the server then parses them with a Python port of the same parsers (backend/app/parsing/), within the limits described on Security.

File schema per engine. Chromium browsers (Chrome/Edge/Brave/Opera) share Chrome's SQLite schema (History with urls/visits/downloads, a JSON Bookmarks file, a Shortcuts database). Firefox is different: a single places.sqlite database (moz_* schema) holds history, bookmarks and downloads. Safari (macOS only) keeps history in a History.db database (history_items/history_visits) and downloads and bookmarks in two property lists, Downloads.plist and Bookmarks.plist, usually binary. Timestamps differ too — see browsers, parsers and formats.

What is uploaded, and where it goes:

Evidence Kept on the server as Analysed by
Malware sample the file, in the sample store (named by its SHA-256, never executed) the backend (hashes, strings, YARA, structure), the analyzer and capa workers
E-mail (.eml, .msg) the file, in the sample store the backend; attachments previewed by the document and browser workers
Packet capture the file, in the sample store; an optional TLS key log, encrypted in the database the capture worker (Wireshark's engine)
Windows event log (.evtx) the curated events only, in the incident document; the file is not kept the backend, in a background job
Address to scan a screenshot and the requests of the visit, as a capture the isolated browser worker

These are uploaded because the file is the evidence under study, not a container of entries to normalize, and because their analysis (disassembly, protocol dissection, rendering a hostile document) must not happen on an analyst's workstation. How each analysis works is on Analysis internals.

Naming an incident. An incident has a ticket ID (the reference in your tracker), a short title, a host and a user, all optional but at least one. Its name is built from them: the ticket first, in square brackets, then the title when there is one, otherwise host - user: [INC-2041] Invoice phishing, finance, [INC-2039] WKS-042 - m.rossi, SRV-FILE-01. The severity (low, medium, high, critical) is a tag the analysts set, shown next to the name in the sidebar and the header but never part of it. The status (open, in_progress, closed; an incident with none is open) and the assignee (a username) live in the document and are mirrored into columns, like the ticket and the severity, so the panel lists and filters them without reading documents. Everything is editable in Edit the incident; the search palette and GET /api/incidents?q= also find incidents by ticket.

Right-click. One menu for the whole app (frontend/src/context/ContextMenuContext.jsx): on an indicator (anywhere it is shown: the Indicators tab, a sample's indicators, event-log addresses) Where else was this seen?, Search for it, Copy, Copy defanged (hxxps[:]//evil[.]top) and Add to the allowlist…; on an event row (Browser, Commands, Endpoint, Event Logs, Timeline) Flag or Remove the flag, Add a comment…, Copy as text, Copy as JSON and Show in the Timeline; on an incident in the sidebar Open, Incident report…, Export (JSON), Copy link and Delete…. The browser's own menu never opens: the provider stops every contextmenu event at the window, lets the elements it passes through say what they offer (openMenu; a page adds its entries with usePageMenu), reads what else is under the pointer (lib/underPointer.js: selected text, a text field, a link, a cell or a line of text) and joins the sections in the order domain/contextMenu.js gives, the general section last. The menu key and Shift + F10 ask for the same menu on what has the focus; a code editor says how it is cut, pasted and undone with registerEditor (lib/textField.js). Add to the allowlist (also the shield button on each IOC row) proposes the value or a wider entry — its domain or a parent domain, its /24 network — and writes it to the shared allowlist with a comment line saying who added it and when; Undo stays available for a few seconds. Any analyst can do it.

Drag-and-drop anywhere. Drop a file on any part of the app (outside the tabs' own drop zones) and a dialog proposes where it goes, from its first bytes and its name (frontend/src/domain/fileRouting.js): PE, ELF and Mach-O executables, PDF, Office documents, scripts and archives → Malware Analysis; .evtx and the event-log script's JSON → Event Logs; Chromium History / Shortcuts / Bookmarks, Firefox places.sqlite, Safari History.db and plists → Browser Forensics; shell histories → Command History; CSV → Endpoint Artifacts. The dialog always asks whether the file goes into the open incident or a new one (with its ticket, title, severity, host, user and OS), lets you change the tab and the source, then opens the tab and imports the file as its own drop zone would.

Each incident is tied to a single host and may carry an operating system (windows | macos | linux, or none; see frontend/src/config/os.js), chosen when the incident is created or in Edit the incident. With none, what follows is that of Windows. The OS drives the host-specific bits of the UI: the artifact paths suggested in Browser Forensics, which shells appear in Command History, and the incident icon shown in the sidebar and header.

The Command History tab mirrors Browser Forensics for terminal activity: one sub-tab per shell (Bash / Zsh / Fish / PowerShell, see frontend/src/config/shells.js), parsing the native history files (.bash_history, .zsh_history, fish_history, PSReadLine ConsoleHost_history.txt) plus JSON/CSV exports. Commands run through the SOC engine — the shared keyword rules plus a built-in command ruleset (DEFAULT_COMMAND_KEYWORDS in frontend/src/config/detectionRules.js: download-and-execute, encoded payloads, reverse shells, credential access, defense evasion, persistence, exfiltration, history tampering…) — can be flagged, searched, filtered by the suspicious window, and appear on the incident timeline exactly like browser events.

The Endpoint Artifacts tab covers host forensic artifacts that neither the browser nor the shell captures, one sub-tab per category built from one or more sources (see frontend/src/config/artifacts.js): Program Execution (BAM, KnowledgeC), Persistence (Run keys, Scheduled Tasks, services, startup, WMI, cron, systemd, SSH keys, rc files, LaunchAgents), File & Folder Access (GTK recently-used) and USB & Devices (USBSTOR, setupapi log, kernel journal). The table shows the union of every source's records, tagged by which source produced them, and runs the shared keywords plus a built-in artifact ruleset (DEFAULT_ARTIFACT_KEYWORDS: execution from temp/user-writable paths, LOLBins, double extensions, suspicious persistence, known offensive tool names).

Crucially, every source is collected without any third-party tool, in one of two ways driven by the incident's host OS:

  • file — the data already lives in a plain text / XML / log / SQLite file, so the analyst uploads that existing file and it is parsed in-browser (custom parsers in frontend/src/parsers/artifactParsers.js: recently-used.xbel, authorized_keys / cron / rc files, LaunchAgent .plist, setupapi.dev.log, and knowledgeC.db via sql.js).
  • script — the data is live system state (registry, service manager, kernel journal), so the tab shows a native collection script (frontend/src/config/collectionScripts.js, PowerShell / systemctl / journalctl only) with copy/download buttons; it writes a CSV whose headers match the importer 1:1, which the analyst then imports.

Artifacts that can only be recovered with third-party DFIR parsers (Prefetch, Amcache, ShimCache, UserAssist, LNK, JumpLists, ShellBags, RecentDocs) are intentionally left out; a category with no custom source on a given OS shows an explicit note rather than a dead end.

The Event Logs tab (Windows) holds curated events from the host's event logs, per channel (Security, System, PowerShell, PowerShell classic, RDP sessions and authentication, Defender, Task Scheduler, Sysmon; see frontend/src/config/eventLogs.js). They arrive two ways: raw .evtx files copied from C:\Windows\System32\winevt\Logs\ (or a disk image), uploaded and parsed on the server, which also recovers records left in the file's unused space after a clear and keeps the file's SHA-256; or the JSON written by a native Get-WinEvent collection script on a live host, parsed in the browser. Only about 50 curated event IDs are stored (at most 20,000 per channel, the newest); the rest is counted. The tab shows:

  • the log coverage: one bar per channel from its first to its last record, with silences of 6 hours or more hatched, clears marked in red and the incident's suspicious window behind them — a gap or a clear inside the window is where evidence may be missing;
  • the logon sessions: each 4624 paired with its logoff (4634/4647) and admin privileges (4672) by logon id, service logons and machine accounts left out;
  • every event with a readable summary, filters by detection, category, channel and time, and a detail view with all its fields.

Command lines (4688, Sysmon 1) and PowerShell script blocks go through the command-line ruleset; the built-in event-log ruleset (DEFAULT_EVENTLOG_RULES, logic in frontend/src/domain/eventLogs.js) adds log cleared, audit policy changed, service installed (high when the binary sits in a user-writable path or runs a shell), suspicious PowerShell, brute force (10 failed logons for one account or source within 10 minutes), a logon right after 5 failures, RDP outside business hours, account created, member added to a privileged group, Defender alerts and scheduled task created. Machine activity (service logons, boots) is not judged by the clock. Linux (journald, auth.log) and macOS unified logs will follow.

The Timeline tab is the super-timeline: it merges every timestamped event from the Browser, Command History, Endpoint Artifacts and Event Logs tabs, and from the samples, e-mails, captures and scanned addresses of the incident, into a single chronological, filterable table (by source, detection and time window). Entries without a reliable timestamp (e.g. PSReadLine commands) are intentionally left out. Any row can be flagged straight from the timeline.

The list of incidents is a page (/incidents): what is shown while no incident, artifact or page of the indicators is open. Its rows are the light list; its quick view reads GET /api/incidents/{id}/quick, never a document. Every side panel is resizable, and its width is remembered per browser.

The IOCs tab lists the incident's indicators of compromise. The server builds them (backend/app/iocs.py) whenever the incident's data is saved — a merge patch that only touches flags or notes leaves them alone — and keeps one ioc_index row per incident, type and value, so "where else have we seen this?" is one indexed query for every analyst, whoever owns the other incident. The sources:

  • browser history: the visited hosts (not every URL); downloads: the URL, its referrer and their hosts;
  • shell commands and endpoint records: URLs, IP addresses, domains (known TLDs), e-mail addresses and MD5/SHA-1/SHA-256 digests in the text;
  • event logs: address and host fields (IpAddress, DestinationIp, QueryName…), Sysmon Hashes, and the indicators in command lines, script blocks and service paths;
  • malware samples: the sample's hashes and the network indicators in its strings;
  • e-mails: sender addresses and domain, sending IP, link targets and hosts, attachment hashes, QR-code and invitation links (mail:<file name>).

Indicators also seen in other incidents come first, in red. Clicking a value here, in a sample's IOC table or in the Event Logs tab opens the indicator's window, with Seen in: every incident it appears in, with the sources, count and first/last time, and a link to open it. Settings → IOC allowlist (one entry per line: a domain and its subdomains, an IP or CIDR network, or an exact value) starts with private and loopback ranges and common vendor and CDN domains; matching values are hidden by default and never exported. The index keeps them, so editing the list applies at once. Exports: CSV, a STIX 2.1 bundle and a MISP event, for a TIP or a firewall blocklist. Incidents saved before 2.12.0 are indexed on the api's first start.

Incident report. The report button in the header (or > report in the search palette) opens the report dialog: language (English or Italian), TLP classification, the sections to include and an executive summary — all saved with the incident (report key of the document) — a preview, and the download as PDF or HTML. The server builds the report (backend/app/report.py) as one self-contained HTML page styled for print, and renders the PDF with WeasyPrint: A4 pages with the organisation and the TLP label at the top and page numbers at the bottom. Its sections:

  • executive summary and key facts (flagged events, SOC detections, indicators, samples, techniques);
  • flagged events in time order, with the analysts' comments;
  • MITRE ATT&CK techniques from capa's capabilities, the YARA rules' mitre_attack metadata (the built-in rules carry it) and the SOC rules that matched (each built-in rule names its techniques in frontend/src/config/detectionRules.js), each with where it was seen;
  • indicators of compromise outside the allowlist, those seen in other incidents first (up to 500; the rest are in the CSV/STIX/MISP export);
  • malware samples with their hashes, YARA matches and capa capabilities;
  • Windows event logs: each channel's coverage and when it was cleared;
  • analyst notes;
  • an evidence appendix: every imported file with its format, rows, import time and SHA-256. Browser, shell-history, endpoint and event-log JSON files are hashed in the browser when they are imported (the file still never leaves the machine); .evtx files and samples are hashed by the server.

The organisation name and logo come from Settings → Report header. API clients get the same report from POST /api/incidents/{id}/report.

Global search. Ctrl/Cmd+K anywhere, or / outside a text field, or the search… button in the header, opens a nik> prompt. As you type it asks the server (GET /api/search) for incidents, indicators from every incident and samples, and searches the open incident in memory: its timeline events (every tab), notes and samples (by file name too). Enter opens the result: an incident is selected, an indicator or a sample opens its window, an event jumps to its tab, a note to the Summary. A query starting with > lists actions instead: go to any tab, new incident, export the incident, settings, the IOC allowlist, sign out. On PostgreSQL the substring matches use the trigram (pg_trgm) indexes of migration 0012; when the extension cannot be created the search works without them.

Platform configuration lives in one sectioned Settings panel (opened from the rail's gear, or deep-linked from the rail's Users and Audit log buttons). Everyone has detection rules (with the built-in rulesets shown for reference), business hours, the IOC allowlist, My account and the audit log; admins also have the report header, mail analysis, threat intelligence, accounts, API keys and the YARA, FLIRT and capa rule sets.

Loading is lazy. After authentication only the light list is fetched (GET /api/incidents?view=summary). Opening an incident downloads its full document (GET /api/incidents/{id}) while the main area shows a non-blocking loading state — the sidebar stays usable and opening another incident cancels the pending download. Documents stay cached in memory for the session; reopening one, or coming back to the window, shows it at once and revalidates it with If-None-Match (304 when unchanged, merged when someone else edited it).

The cache is an optimistic model: every mutation updates local state immediately and hands the incident to the save queue (frontend/src/services/saveQueue.js). The queue keeps, per incident, the last version the server is known to hold and its ETag, and persists only the difference, as an RFC 7396 JSON Merge Patch generated by frontend/src/lib/mergePatch.js. Toggling a flag therefore sends the flag, not the incident's artifacts. setActiveBrowser, setActiveProfile and setActiveShell are view preferences, never sent.

  • One save at a time, in order. Edits made while a save travels leave with the next one; two edits of the same tick (a comment on a row that was not flagged) are one request.
  • Nothing is forgotten. Because the patch is the difference from the last acknowledged version, a save that failed is still in the next one. It is retried at growing intervals and reported by App.jsx as a red banner (storageError, unsavedChanges, retrySave) until it goes through.
  • Two writers do not overwrite each other. Each save sends If-Match. The backend bumps the incident's revision (incidents.rev, its ETag) at every write of the document, whoever makes it, and takes the row lock before reading it (backend/app/core/locking.py), so the check and the write are atomic. On 412 the queue reads the server's version and carries the local changes over it with a three-way merge (frontend/src/lib/rebase.js): objects member by member, lists of things with an identity (notes, comments, references) item by item.
  • An expired session loses nothing. A 401 sets sessionExpired in AuthContext; SessionExpiredDialog asks for the password over the app, and the queue resumes after the sign-in.

The sample store (a volume) the files themselves: samples and e-mails named by SHA-256, captures (_captures/), screenshots of scanned addresses (_urls/), FLIRT and capa rule files

A backup is therefore two things: a dump of the database and a copy of the sample store (deploy/backup.sh takes both, with .env). The in-app full backup covers the first four tables' worth of work only; see Full platform backup.

Authentication, sessions and the audit log

Authentication

Passwords are hashed with bcrypt on the server (backend/app/core/security.py). A successful POST /api/auth/login creates a server-side session row and sets the httpOnly nik_session cookie (with the Secure flag when COOKIE_SECURE=true, the default); credentials: 'include' on every fetch keeps it flowing. An account with a second factor (user_factors, recovery_codes) gets a ticket instead (signin_tickets, a cookie of its own) and its session from POST /api/auth/login/code (backend/app/signin.py, core/totp.py). A session ends when it was not used for the idle time of the sign-in policy (sessions.last_used_at; requests the page sends by itself carry X-Nik-Background and do not count, frontend/src/lib/activity.js) and at most lifetimeHours after the sign-in (SESSION_TTL_HOURS until an admin sets it). The policy is one row of settings (core/signin_policy.py).

User shape: { id, username, roles, permissions, createdAt, createdBy, disabled, secondFactor, secondFactorRequired } — the password hash never leaves the backend. A sign-in that names an unknown account does the same hashing work as a wrong password and is counted the same way; failures in a row make the next attempt wait, per account and per address (signin_attempts; users.failed_logins and users.locked_until are no longer read), and expired sessions are purged at each sign-in. The client's address is the connection's, or the one X-Forwarded-For names when the connection comes from a proxy of TRUSTED_PROXIES (core/client_address.py).

The App shell (App.jsx) implements a three-state auth gate, driven by GET /api/auth/bootstrap and GET /api/auth/me:

  • no users at all → FirstRunSetup: the first POST /api/users succeeds without authentication and the created account is forced to the admin role;
  • users exist but not signed in → LoginScreen;
  • signed in → the main app;
  • session ended while working (any request answers 401) → SessionExpiredDialog over the app, which keeps its unsaved changes.

Admins manage accounts in Settings → Accounts (AccountsSection.jsx): add a user, change its name, role or password, disable it, or delete it (PATCH / DELETE /api/users/{id}). The server keeps at least one admin able to sign in and refuses a change to the caller's own role. A rename is carried to the incidents assigned to the account, under their row lock; a new password or disabling ends the account's sessions. Every user changes their own password in My account (PUT /api/users/me/password).

Audit log

The log is written by the server: each handler records what it does through backend/app/core/audit.py, for a session and for an API key alike, so a request sent by hand leaves the same entry as the app. An entry says who (actor), when (at), what (action), the details, and which incident it belonged to. Entries are returned newest-first, capped at 5000.

A merge patch says what changed, not what it means, so describe_patch() compares the document before and after and names the changes: a flag added or removed, a comment, a note, the attributes that changed, the evidence tabs touched and the files imported into them. The browser reports only what happens in it alone: POST /api/audit accepts incident.export and refuses anything else.

Entry shape: { id, at, actor, action, target, details, incidentId, incidentName }.

Action strings include: auth.login / .logout / .failed / .refused / .code.failed / .factor.on / .factor.off / .factor.reset / .recovery.new / .recovery.used / .session.end / .policy, user.create / .update / .delete / .password, apikey.create / .revoke, settings.update, incident.create / .update / .delete / .export, evidence.update, flag.add / .remove / .comment, note.add / .update / .remove, the sample, e-mail, capture and URL actions, backup.export / backup.import and audit.clear.

The Audit log section of Settings (AuditLogSection.jsx) reads the trail each time it opens and shows it in a searchable table; an admin can clear the whole log behind an inline confirmation step, and the new log starts with an audit.clear entry naming them.

Roles and permissions

An account or an API key holds a list of roles; a role grants permissions; what a caller may do is the union (backend/app/core/permissions.py: ROLE_PERMISSIONS, permissions_of(roles)). The roles are read from the row on every request, so there is nothing cached to refresh when they change.

  • A route asks for a permission, never for a role. It depends on require("<permission>"), or on one of the gates built from it in core/security.py: reader_principal (read), writer_principal (write), admin_principal, audit_principal, rules_principal. require with several permissions lets through a caller that holds one of them; principal alone is any signed-in caller.
  • Adding a route: give it its gate and add a line to EXPECTED in backend/tests/test_permissions_matrix.py. The test fails for a route that is not in the table, checks that the gate the route declares is the one the table says, and calls every route with one API key per role.
  • Adding a role or a permission: a line in permissions.py and its mirror frontend/src/domain/permissions.js (what the role picker shows). No migration: roles are a JSON list on users and api_keys.
  • In the interface, can('<permission>') of AuthContext reads the permissions that GET /api/auth/me returns. A section of Settings names the permission it needs in domain/settingsNav.js.

The query language

backend/app/query/ reads a query into a tree (parser.py, hand-written, with limits on length, depth and number of conditions) and gives it a meaning for an entity (entities.py): a model or a set of rows, the fields it exposes with their kind (text, keyword, ordered, number, date, bool, tags) and the fields a plain word is looked for in.

  • query.sql(entity, text, caller) returns SQLAlchemy conditions with bound parameters for an entity that is a table; query.rows(entity, text, caller) a predicate for one assembled in Python (the indicator library). Both meanings are written side by side in fields.py, and tests/test_query.py runs the same queries through both, on SQLite and on PostgreSQL.
  • The permission of the entity is checked by the compiler, so a new caller of the module cannot forget it.
  • Adding a field is a FieldSpec in entities.py; GET /api/query/schema and with it the autocomplete and the builder follow by themselves.
  • The browser has the same parser (frontend/src/domain/query/parse.js) for colours, completion and the builder; both read backend/tests/data/query_vectors.json in their tests. The server alone decides what a query matches.

The automation engine

Playbooks are run by Nik itself (backend/app/automation/), not by another product. The design follows from one rule: a run is rows in the database, never something a process holds in memory.

  • Tables: playbooks (with the draft, the limits, the hosts and the classes of data opened), playbook_versions, scripts, script_versions, automation_events (the outbox), runs, run_steps, approvals, automation_schedules. Migration 0026_automation creates those that are missing; 0027_connectors adds connectors (each with its file as text) and connections (plain values, and the secrets encrypted), and to playbooks the hash of the token a playbook is started at from outside.
  • The outbox. A change to an incident writes an event in the same transaction as the change; the worker reads the events and starts the playbooks whose trigger matches. An event is never lost to a crash between the change and the start, and a playbook's own changes carry the depth of what started them.
  • Steps. A run is advanced one step at a time: the worker claims the steps that are due (FOR UPDATE SKIP LOCKED on PostgreSQL), takes each in a transaction of its own, and writes what comes next. Where branches meet, a node waits for every branch that can still reach it; a branch not taken is marked dead and does not hold it. A step claimed by a worker that died is taken back after a grace time.
  • Waiting costs nothing. A wait, a retry and an approval are a step with a time on it (or none); no thread sleeps.
  • One worker at a time holds a lease in the database and renews it; the container can be restarted, or a second one started, without a run being taken twice. The API container takes no step unless AUTOMATION_WORKER=inline (development and tests).
  • Classes of data travel beside values: each step stores, with its output, a map from the paths of that output to the classes they hold, and an expression that reads a path carries them on. guard.py decides on them when something is about to leave.
  • Scripts are sent to the sandbox worker over the internal network and run there in a child process (workers/sandbox/).
  • In the browser the graph is plain data edited by pure functions (frontend/src/domain/automation/graph.js), which is what undo and redo are; the canvas (@xyflow/react) draws it and reports edits. The expression parser exists twice, in Python and in JavaScript, and both are tested on the same vectors.

Connectors. A connector is a row of connectors that holds its YAML file as text; a connection is a row of connections with its plain values and, encrypted with the vault key, its secrets. connectors.py turns the text into typed models (pydantic, unknown keys refused) and checks every template for the names it may read; it remembers the line of every key, so a problem is reported where it is. connector_runtime.py runs one command: it renders the request, adds the credentials, sends it through egress to the connection's host and no other, reads pages, and for a command that polls gives the step back to the engine with the time to call it again (the run waits; no worker does). connector_actions.py registers a provider with the registry of actions, so that servicenow.create-incident is found like an action written in code, as long as the connector is installed.

Events. Beside incidents, the analysis of an e-mail, a file and an address, a change of an indicator's overall verdict, a watched indicator found in an incident and a disk nearly full each write a row of the outbox in the transaction of what they tell of. A request to POST /api/automation/hooks/<token> starts a run directly: the token is looked up by its SHA-256, which is all that is stored of it.

Fields, types, context and the War Room (4.3)

An incident is still one JSON document (incidents.doc) with a few of its values mirrored to columns for the lists. Release 4.3 adds four things beside the document, so that nothing that reads it had to change:

  • The field registry (fields, fields.py). Every field has one name. The system fields Nik always had are only named there: SYSTEM_FIELDS says where each lives (a key of the document, a column, or incidents.fields). Custom fields live in incidents.fields (JSONB with a GIN index on PostgreSQL). fields.update is the only writer: the routes, the playbooks' actions and the context all go through it.
  • Types (incident_types). incidents.type_id is null for Unclassified. A type holds the list of its custom fields with their flags and its layout: sections of field names, one of which is the side panel, and the order of the tabs. The page is drawn from it (frontend/src/domain/fields.js).
  • The context (incident_context, one document per incident, and incident_context_meta, who set each item). It is replaced with a compare-and-swap on its version. The engine gives it to expressions as context and writes what a step declared after the step (engine._to_context).
  • The War Room (war_room_entries). The engine adds a line for each step that did something on an incident, pointing at the step. Notes stay in the document: the War Room reads them through an adapter, and writes a new one to both. A command typed there is a run of one node of a hidden playbook (commands.py).

The incident as the API gives it carries type and fields, added on the way out (routers/incidents.py) and taken out on the way in, where they go through the registry. Migrations 0028_fields_types and 0029_context_war_room add the tables and columns where they are missing.

Tasks, timers and lists (4.4)

  • Tasks (tasks, tasks.py). A task or an ask node of a playbook makes a row and its step waits (step.waiting = {kind: "task", id}); completing the task calls engine.resume(step, port, output), which is what lets a run go on by the port of an answer. The ports of a question are its choices (graph.ports_of, mirrored in domain/automation/graph.js). A task past its due time is left by overdue as well and stays open: engine.follow takes that one edge and _resolve leaves an edge already taken alone when the step ends. tasks.tick, called by the worker every minute, sends reminders, marks what is overdue and gives up the questions nobody answered. A run that waits for a person is waiting, and its deadline moves by the time it waited.
  • The work plan (work_plan.py) is read, never stored: for each run on the incident, the nodes of its version in topological order, grouped by the phase of their settings, each with the state of its step. It gives a node's name, kind and phase and none of its other settings, so whoever reads the incident may read it.
  • SLA timers (timers.py). A timer is the value of a field of type timer in incidents.fields: {state, started_at, accumulated_s, due_s, breached_at, business}. It is never written through fields.update: timers.sync applies the sla of the incident's type whenever an incident is saved and at every tick of the worker, and timers.tick marks what is past its time once and publishes sla.breached. Business time is counted by business_seconds from the hours of the list business_hours, in UTC.
  • Notifications (notifications): one row for each thing an account is told, read through /api/notifications. tasks.notify is the only writer.
  • Lists (lists, list_items, lists.py). What the settings document kept as arrays lives in lists Nik ships; the document holds {"list": "<name>"} in their place, which is also how a feature is pointed at another list. read_settings fills the old keys from the lists and PUT /api/settings writes to them, so nothing that reads the settings changed. Reads go through a cache of a few seconds, dropped when this process writes a list. A watch list of the Indicators page is read through the same functions, by its name as a slug. In expressions, in_list is answered by the scope (Scope.in_list), which the engine builds with the database at hand.

Migrations 0030_tasks_sla (tables tasks and notifications, and a wider run_steps.port on PostgreSQL) and 0031_lists (the two tables, then the move of the settings, once).

Fetching, mappers and mirroring (4.5)

  • The connector file gained four keys, read and checked by automation/connectors.py: fetch, schema, ext_fields and mirror. Runtime.fetch sends the request of a fetch with the loop of pages a paged command uses; mirroring runs commands of the same connector, nothing else.
  • Classifiers and mappers (classifiers, mappers, mapping.py) are rows, not parts of the file: a classifier belongs to a connection, a mapper to a connector, a direction and a type of incident (or every type). apply_incoming returns the fields and the context writes an item gives and writes nothing; apply_outgoing returns what the other side is sent. The mappers in automation/seed/mappers/ are added at startup as builtin rows and follow a release until someone saves one.
  • Fetching (fetch.py, fetched_items, the columns fetch_enabled, fetch_state, fetch_status and fetch_settings of a connection). The automation worker runs the cycles that are due in its pool, one at a time for a connection. An item is told apart by item_id and kept in fetched_items with what became of it; the state of the next cycle is saved only when the whole cycle was read. 200 items a cycle; 500 incidents an hour, then the connection is paused; a failure is tried again after longer and longer, an hour at most. How often an instance fetches, how far back the first time and its look-back are in fetch_settings where they differ from its connector (fetch.settings_of). The moment a fetch by time asks from, since, is worked out by the engine (fetch.since_of): it keeps how far the cycles reached in fetch_state under _since, beside what the connector keeps there, and fetch.reset empties both while fetched_items stays.
  • Pre-processing rules (preprocess_rules, preprocess.py) are tried in order on what an item was mapped to, before an incident is made: the first that matches decides.
  • Mirroring (mirror.py, mirror_queue). What is read from the other side goes through the incoming mapper and fields.update, which records who set each field last (registry.note_source): a field a person set is kept unless the rule is authoritative. What is sent is put in a queue in the transaction of the change and sent by the worker through the data guard.

Migration 0032_fetch_mappers: the five tables and the three columns of connections.

Dashboards, content packs and the debugger (4.6)

  • Counting (query/aggregate.py, POST /api/query/aggregate). A query is compiled as for a list, then what it finds is grouped and measured. A plain count is one GROUP BY (a date is grouped by a prefix of its ISO text, which is how Nik stores times); anything else (a median, a percentile, the time between two dates, a week, a field of tags) is worked out in Python from the columns that are needed, 100 000 rows at most. An entity can carry conditions of its own (Entity.base): the runs of the debugger are never part of runs. Runs, approvals and tasks became entities for this.
  • Dashboards (dashboards, dashboards.py). A row with its widgets in layout. The server checks each widget as the aggregate API would and moves widgets so that none covers another (compact; the page does the same while one is dragged, domain/dashboards.js). It never runs a widget: the page asks for each one as the person looking, six requests in flight at most, answers kept a minute (services/widgetData.js). Charts are plain SVG (components/charts/). The report (dashboard_report.py) asks the same questions on the server, as the caller, and writes them with the style sheet of the incident report.
  • Content packs (packs, pack_items, pack_uploads, packs.py). read turns the bytes of a zip into items, refusing what is not a safe pack; current gives any item of this Nik in the shape a pack writes it, which is what plan compares to say add, update, same or conflict; apply does the plan in the caller's transaction, each kind through the function that saves it everywhere else. Items are known by kind and name. An inspected file waits in pack_uploads for an hour. What Nik ships is installed by each kind's own seeding as before, and register_builtin writes it down as one pack, Nik built-in (four until 5.4). What is about a product of a vendor is not seeded: it is a pack of the catalogue (pack_catalogue.py), and adopt_legacy writes down as packs the vendors' connectors a Nik older than 6.0 holds.
  • The debugger (automation/debugger.py, the column runs.debug). A debug run is a run the engine asks one more question of: before performing a node, debugger.park may leave the step waiting with {"kind": "debug"}. Releasing it (debugger.act) puts it back to pending with what was asked for that step in step.waiting (override, real), which the engine reads when it performs the node. A run of a draft carries its graph in run.state["graph"]. Everything else is the engine as it is.

Migration 0033_dashboards_packs: the tables dashboards, packs, pack_items and pack_uploads, and the column runs.debug.

Signatures, list history, expiry and large mailboxes (4.7)

  • Script signatures (script_signatures, jsanalysis.py). The signatures are rows, written from the ones in the code when the table is empty and followed by each release for as long as nobody changed them (updated_by is nik). A scan reads them once (load_signatures). Patterns are compiled with the regex module, which can stop a match: half a second for a signature on a script, and a pattern that takes longer on Nik's own hostile texts is refused when it is saved (pattern_problem).
  • The history of a list (ioc_list_history, ioc_verdict_changes, ioc_history.py). A check started for a whole list carries the list and the verdicts as they were (ioc_checks.list_id, baseline); when it ends, finish writes one line and a row for each verdict that is not what it was. A check of a selection writes nothing.
  • Expiry (artifacts.expires_at, artifact_expiry.py). A date, in UTC, that only a person sets. The automation worker calls tick with its other periodic work: it emits artifact.expiring once, a week before, and on the day deletes through the function the delete button uses, or puts the date off by a week when an incident that is not closed references the artifact.
  • Mailboxes in an export (artifact_transfer.py). The index goes out a message a line (records/<id>.messages.jsonl), the file only with the files. An archive is put together and taken apart on the disk of the store (_transfer), never in memory; an imported index is accepted only if every message lies inside the file that came with it.
  • PST on disk, and progress (workers/docview/server.py, workers/previews.py). The worker writes the PST and its mbox under /work, the volume pst-work, after checking the room (pst_refusal), and clears the folder when it starts and after each conversion. The API sends and receives in pieces and counts them; indexing counts the bytes it has read. Both write meta.preparing every two seconds at most, which the page polls.

Migration 0034_misc: the tables script_signatures, ioc_list_history and ioc_verdict_changes, and the columns ioc_checks.list_id, ioc_checks.baseline, artifacts.expires_at, artifacts.expiry_note and artifacts.expiry_noticed.

Instances, packages and mail (5.1)

  • Instances. A connection is an instance of its connector; the table keeps its name. connections.enabled is read wherever an instance is chosen: by a node (find_connection), the War Room, the fetch (fetch.due) and mirroring. The catalogue of the editor says of each command which connector it belongs to and whether one of its instances is on.
  • A connector as a package. connectors.logo, logo_type and readme hold what comes beside the file. A content pack reads and writes a connector as a folder when it has either (packs.read, write); a shipped connector may be a folder too (connector_actions.package_of). connector_logo.clean is the one place a logo is checked. An incident says what brought it in (source, from incidents.source_connection_id).
  • Native connectors. A file with native: mail has no requests: runtime_for gives a MailRuntime, which has the methods of the HTTP runtime (run, would_send, test, fetch, close), so the engine, the test of an instance and the fetch cycle do not know the difference. The connections are opened by egress.imap_client and egress.smtp_client.
  • The e-mail node of 4.x (email.send) is an alias: it sends through an instance of the Mail connector, and through the SMTP server of the settings while there is none. adopt_smtp makes that server an instance, once, when the server starts.

Migration 0036_instances: the columns connections.enabled, connectors.logo, connectors.logo_type and connectors.readme.

The page of an incident (5.3)

  • The tab registry (frontend/src/config/tabs.js) lists the seven tabs and, marked evidence: true, the eight kinds of evidence. domain/evidence.js says what the page shows for the tab that was asked (resolveTab: the id of a kind is the Evidence tab on that kind) and builds the side list (evidenceGroups). A kind's component is the analysis tab of 4.x, given focus (the file to show alone) and evidence.
  • The Summary is the grid of the dashboards (components/dashboards/Grid.jsx) fed by domain/layoutGrid.js: gridOf(type) gives the grid the type keeps (incident_types.layout.grid, checked by incident_types.clean_grid) or the one made from its sections. components/tabs/summary/LayoutWidgets.jsx draws each kind. The playbook editor (5.2)

  • Branches are rows of playbook_branches (migration 0037_branches): the graph, the version the branch started from, who made it. The engine never reads them: a run uses a row of playbook_versions, and a push writes one. behind is computed, the base against the current version; nothing is merged.
  • Tidy up (domain/automation/layout.js) gives ELK the playbook as the canvas draws it: each node with its size and its ports at fixed places (the input in the middle of the top, each output along the bottom, on error on the right side: handlePlaces, which the canvas draws its handles from as well), each line with the size of its words, layered, top to bottom, with orthogonal routing. It keeps the place of each node and, on each line, the route ELK gave (edges[].route: {points, label?}, checked by graph.validate, never read by the engine, ignored by the comparison of two graphs). moveNodes drops the route of the lines of a node that moves and copyOf does not copy routes, so a route is only ever the layout's, for the positions the layout gave. crossings is the check that no line passes over the box of a node it does not join and no words sit on a node; the unit tests hold the layout to it on a loop, branches that join, far errors, several answers and the shipped playbooks, and the E2E suite on the page itself.
  • A connection is drawn by CanvasEdge.jsx: along its route when it has one, else as a stepped line the canvas routes; and its ×. From 5.2 to 6.3 a line could hold corners, edges[].points in the graph; graph.validate still accepts them (a list of at most twenty {x, y}) so that the versions that have them stay valid, the engine never read them, and the client leaves them behind when it reads a graph (normalise in domain/automation/graph.js): they are gone from a draft or a branch the next time it is saved.
  • The right-click menu of the editor is the menu of the rest of the product (ContextMenuContext). domain/automation/editorMenu.js decides the entries of a node, a selection, a line and the canvas, their keys and why one cannot be done; useEditorMenu.js gives each what it runs, which are the functions the keys call.
  • Sub-fields: the catalog gives each command its outputs and, for a command of a connector, the sample of its file; domain/automation/catalog.js (subFields) turns them into the paths suggested in {{ }}. An output of an action written in code says what is inside it with shape: a list of {name, type, description}, or the name of a shape the catalog carries once in shapes (incident, what payloads.incident_data builds for a trigger and for a node alike; fields, the registry's fields of incidents, read from the database; context, the keys of the common schema). tests/test_automation_shapes.py reads every such path in a run, real and dry. The library (libraryOf) is the same catalog split in tabs.
  • The address of a branch is read by domain/automationNav.js; the editor is mounted again for each branch, so what was not saved is sent on the way out to where it belongs.

Numbers, the query language and the shell (5.0)

  • The number of an incident (incidents.number, sequences). The key of an incident is its uuid, as before; the number is given by a before_insert listener of the model, so every way of creating an incident gets one. The counter is a row that is updated first, which makes two creations wait for each other, and it only goes up.
  • The query language. !field:value gives the same node field:!value gave (one condition, empty fields included); ! before anything else is a negation. A list is read as the conditions it shortens, so nothing after the parser knows of it. The two parsers (query/parser.py, domain/query/parse.js) share their test vectors, and each has modern, which rewrites the old writing.
  • Indicators added by hand (data.iocs.manual in the document, iocs.add_manual): what a reputation command looked up. extract reads them with the rest of the evidence.
  • Side panels share one handle (ui/ResizeHandle.jsx, domain/panes.js); menus of what is not evidence share menu/useObjectMenu.js and domain/menus.js.

Large data sets

A browser history of a few hundred thousand visits has to stay usable, so the Browser tab keeps its per-row work to a minimum:

  • buildEvents() parses each URL once (analyzeUrl in lib/url.js) and stores domain and searchQuery on the event; the stat cards, the ranking widgets and the table cells read those fields instead of parsing again (entryDomain() / entrySearchQuery() fall back to parsing for raw entries).
  • DataTable sorts text with one shared Intl.Collator: localeCompare with options builds a collator per comparison, which made a 300k-row sort take seconds. The search box uses useDeferredValue, so typing never waits for the filter.
  • buildTimelineEvents() takes incident.data, not the incident: flags and notes do not change the timeline, so toggling a flag does not rebuild the Timeline tab.

Tables stay paginated (25 rows by default), so the DOM never holds more than one page; the cost of a large incident is in these data passes, not in rendering. When you add a per-row computation, do it once in the build* helper, not in a cell renderer.
